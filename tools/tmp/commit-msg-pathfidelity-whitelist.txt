feat(model): pathFidelity 白名单可编辑 + 写入单实例缺陷与 external 缺口

## 一、白名单改为可编辑集合

    private val PATH_FIDELITY_WHITELIST: Set<String> = setOf(
        CM_PACKAGE,          // 原始定向对抗目标
        "mark.via",          // via：验证 file:// 与 WebView MIME
    )
    fun isPathFidelityGuest(packageName: String) = packageName in PATH_FIDELITY_WHITELIST

原来写死 `packageName == CM_PACKAGE`。加包名到集合即可启用，不用改函数。

## 二、写入代码的已知缺陷（用户要求）

### 缺陷 1：只支持单实例

`syntheticDataDir(pkg) = /data/user/0/<pkg>` **不含 instanceId**。
同一 app 装两份 -> 两个实例合成路径相同 -> 规则表是
`ConcurrentHashMap<from, to>`，后注册覆盖前者 -> 先注册的实例所有 I/O
跑到另一个实例的沙箱（**数据损坏级**）。

多实例需要改成 `/data/user/<10+slot>/<pkg>` 之类的按槽位映射
（Android 原生多用户就是 user 10+，形态合法）。

### 缺陷 2：external 目录不合成

`getExternalFilesDir` / `getExternalCacheDir` / `getObbDir` / `getExternalMediaDirs`
**没有 pathFidelity 分支**，仍返回 `<sandbox>/sdcard/Android/data/<pkg>/...`。

所以**即使加进白名单，外部存储仍然暴露沙箱**。要彻底不暴露，需要：
  1. 新增 syntheticExternalDir(pkg)
  2. VirtualContext 的 external 方法加 pathFidelity 分支
  3. 规则已就绪（本轮刚修好 /storage/emulated/0/Android/data/<pkg>/ -> 沙箱）

## 三、性能代价（实测代码路径，不是估算）

### 3.1 pathFidelity 本身的开销：可忽略

| 项 | 代价 |
| --- | --- |
| `isPathFidelityGuest()` | 一次 `Set.contains`（白名单 2 个元素） |
| `get*Dir()` 的 if 分支 | 一次 boolean 判断 |
| 合成路径构造 | 一次 `File(String)`，不 touch 文件系统 |
| 规则条数 | +3 条（apk/lib/data 已有）-> 最长前缀匹配多 3 次 `startsWith` |

### 3.2 真正的开销不来自 pathFidelity，而来自 ensureDir

`VirtualContext.getFilesDir()` 在**返回假路径之前**会调
`sandboxManager.getFilesDir(instanceId)`，它走 `ensureDir()`：

    private fun ensureDir(file: File): File {
        val path = file.absolutePath
        if (ensuredDirs.contains(path) && file.isDirectory) {   // <- 每次一次 stat
            return file
        }
        val created = file.mkdirs()
        ...
    }

**关键：这行 `file.isDirectory` 每次 getFilesDir() 都会触发一次 stat。**
但这条开销**本来就存在**（非 pathFidelity 分支也调同一个 sandboxManager 方法），
**不是 pathFidelity 引入的**。

### 3.3 结论

**pathFidelity 的增量开销 ≈ 0**。若将来要优化，目标应是
`ensureDir` 的 `isDirectory`（可加短 TTL 缓存），而不是 pathFidelity。

## 四、AOSP 横向调研：Environment / MediaStore 要不要一起合成

### 4.1 Environment：不需要合成

`Environment.java` 的所有路径都来自进程级静态 `sCurrentUser`（UserEnvironment）：

    public static File getExternalStorageDirectory() {
        throwIfUserRequired();
        return sCurrentUser.getExternalDirs()[0];
    }
    public static File getExternalStoragePublicDirectory(String type) {
        return sCurrentUser.buildExternalStoragePublicDirs(type)[0];
    }
    public static String getExternalStorageState() {
        final File externalDir = sCurrentUser.getExternalDirs()[0];
        return getExternalStorageState(externalDir);
    }

**关键**：`Environment` 返回的是**「共享存储根」`/storage/emulated/0`** ——
真机上就是这个值，**它本身不包含任何包名，不暴露沙箱**。

需要合成的是 **「每 app 私有目录」**（`/data/user/0/<pkg>`），因为那里才含包名。

**所以**：
  * `Environment.getExternalStorageDirectory()` 保持返回 `/storage/emulated/0` 是正确的
  * guest 拿这个根再拼 `Android/data/<pkg>/...`，由规则映射到沙箱 —— **已经工作**
  * **不需要**反射改 `sCurrentUser`

### 4.2 MediaStore：不需要合成

  * `MediaStore` 走 `ContentResolver` + `content://` URI，**不返回文件绝对路径**
  * `MediaStore.MediaColumns.DATA`（`_data` 列）在 Android 10+ 的 scoped storage 下
    对第三方 app 已不可用（查询返回 null / 抛异常），现代 app 不再依赖它
  * `MediaStore.getExternalVolumeNames()` 返回卷名（`external_primary`），不是路径

**所以 MediaStore 一侧无需合成。**

### 4.3 需要一起合成的是这三个（而它们和 Environment 无关）

| 方法 | 现状 | 是否暴露 |
| --- | --- | --- |
| `Context.getExternalFilesDir()` | `<sandbox>/sdcard/Android/data/<pkg>/files` | **是** |
| `Context.getExternalCacheDir()` | 同上 `/cache` | **是** |
| `Context.getObbDir()` | `<sandbox>/sdcard/Android/obb/<pkg>` | **是** |

这三个是 **Context 方法**，不是 `Environment` / `MediaStore`。
