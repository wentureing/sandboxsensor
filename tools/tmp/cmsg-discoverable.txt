docs(设计): 讨论假路径换真路径的可发现性 —— 与 WebView 可读性互斥

## 结论

在当前架构下，「via 不能直接发现」与「WebView 能读到文件」是互斥的。

原因链：
  WebView isolated 进程只认「真实存在」的路径
    -> 交给它的路径必须真实
    -> 而那是 via 从 getFilesDir() 拿的
    -> via 拿到的必然也是真实路径
    -> 必然可被发现

唯一解是 hook WebView.loadUrl（让真路径只在交给 WebView 那一刻出现），
需改 ArtMethod entry，代价大。

## 可发现面按严重程度分三级

### 严重（逻辑自相矛盾，任何自洽性检查都会命中）

  1  getFilesDir().getParentFile() != getDataDir()
     真机永远相等；我们这里：getFilesDir 的父是 <sandbox>，
     getDataDir 是 /data/user/0/mark.via -> 不相等
  2  getDataDir() 拼上 files 段 != getFilesDir()

为什么最致命：这不是「路径长得奇怪」，而是框架不变量被破坏。
任何检查「我的目录结构是否自洽」的代码都会命中，而 Android 自己就有这类检查
（ContextImpl.makeFilename、StorageManager.fixupAppDir、各种 ensureDirExists）。

### 中等（路径内容异常，一眼可见）

  3  路径含 com.nextvm.app + virtual/data + 实例 ID
  4  段数 9 段（正常 5 段）
  5  路径里出现 mark.via_<数字> 这种正常 app 不会有的后缀
  6  StatFs(getFilesDir()) 的挂载点是容器 data 分区

### 轻微（真机也可能出现，不足以单独定罪）

  7  getOpPackageName() = com.nextvm.app（真机共享 uid 的应用也会返回别的包名）
  8  getPackageName() / proc self cmdline 都正确
  9  proc self maps 里的 APK 路径是合成的
 10  ApplicationInfo.dataDir / sourceDir / nativeLibraryDir 都是合成的

## 三条理论解法

  A  hook WebView.loadUrl         完整解决，需 ArtMethod 偏移表
  B  让假路径真的存在（mount）     需 root，本项目前提不成立
  C  全部用真路径（当前状态）      牺牲伪装，零成本

关键判断：内置 WebView 是唯一能同时满足两者的路 —— 那时渲染进程由容器 fork，
能装 hook，可以用假路径。所以 contentPathsUseReal=false 是过渡态，
内置 WebView 后应改回 true 并验证主页。

## 附：现状下最可能被踩到的两个具体检测

  // 检测 1：父子关系不成立
  if (!getFilesDir().getParentFile().equals(getDataDir())) { /* 容器 */ }

  // 检测 2：路径含 virtual 字样
  if (getFilesDir().getAbsolutePath().contains("/virtual/")) { /* 容器 */ }

这两条都比「含宿主包名」更容易写、更常见，因为它们不依赖猜包名，只检查框架不变量。
