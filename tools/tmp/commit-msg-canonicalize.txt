fix(hook): canonicalize0 对合成路径改为「返回规范化原始路径」—— 既不暴露沙箱也不抛异常

## 一、实测暴露的两个问题

装 synth.apk（4b3b7fa，含 external 合成）后，via 主页错误类型改变（好消息），
但 logcat 出现：

    E StorageManager: Failed to get canonical path for
        /storage/emulated/0/Android/data/com.nextvm.app/files/logs
    E StorageManager: java.io.IOException:
        /data/user/0/com.nextvm.app/files/virtual/data/<inst>/sdcard/Android/data/mark.via/files/logs:
        No such file or directory
        at java.io.UnixFileSystem.canonicalize0(Native Method)
        at android.os.storage.StorageManager.fixupAppDir(StorageManager.java:2675)

对照 hooked_ufs_canonicalize0 的实现，问题有两条：

  1 失败时抛 IOException     -> 调用方（StorageManager.fixupAppDir）报错
  2 成功时 return realpath 结果 -> 那是 <sandbox>/... **直接暴露沙箱，比不 hook 更糟**

第 2 条尤其严重：注释里写着「不 hook 会暴露真实沙箱绝对路径」，
但当前实现在成功路径上**正好返回了那个路径**。

## 二、根因：合成路径在真机上必然不存在

合成路径（/storage/emulated/0/Android/data/<pkg>/files）是「假路径」，
realpath 必然失败。而调用方只用结果做「路径去重 / 归属判断」，并不要求文件存在。

所以对合成路径，「抛异常」和「返回沙箱路径」都是错的。

## 三、修法

新增 canonicalize_logically(const std::string&)：
纯字符串规范化，消除 "//"、"/./"、"/../"，**不 touch 文件系统**。
对不存在的路径也能成功。

hooked_ufs_canonicalize0 分两个分支：

  translated == true（合成路径）
      return canonicalize_logically(原始未翻译输入)
      行为：与 realpath 结果同形、实际不存在、绝不泄露沙箱、不抛异常
      日志：LOGI("ufs-alias canonicalize0 [synth]: %s -> %s", raw, canonical)

  translated == false（普通路径）
      保持 AOSP 语义：realpath 成功返回结果，失败抛 IOException

## 四、这条改动直接对应「只误导、不危害读写」原则

| 做法 | 是否误导 | 是否危害 | 是否暴露 |
| --- | --- | --- | --- |
| 抛 IOException（原） | — | **是**（调用方失败） | 否 |
| 返回 realpath 结果（原） | 是 | 否 | **是**（泄露沙箱） |
| 返回规范化原始路径（新） | **是** | **否** | **否** |
