fix(hook): list0 改用 readdir64 + readdir 出错了要上报 errno

## 一、现场事实（1edb6a2 装包实测）

离线文件确实在沙箱的正确位置：

  <inst>/sdcard/Android/data/mark.via/files/offline/probe1.mht
  <inst>/sdcard/Android/data/mark.via/files/offline/probe2.mht

mark.via 的整套 external 目录也都建好了（files/{logs,proxy,filters,tabs,gm,font,
offline,favicons} + cache + obb + media）—— pathFidelity 的 external 合成生效。

但 hooked_ufs_list0 对同一个路径报：

  ufs list0 [xlat]: <sandbox>/sdcard/Android/data/mark.via/files/offline -> 0 entries (EMPTY)

=> 路径翻译对了、目录也对了，卡在「读目录项」这一步。

## 二、两个可疑点，本次都修

### 1) struct dirent vs struct dirent64（主怀疑）

AOSP 的 UnixFileSystem_md.c 用的是 readdir64：

  while ((ptr = readdir64(dir)) != NULL) {

我们用 readdir + struct dirent。两者在 64 位 bionic 上是不同的符号/结构体
（d_ino / d_off 宽度不同）。混用会导致 d_name 读到的位置不对 —— 表现正是
「opendir 成功但一个条目都读不到」。

改为 struct dirent64* + readdir64(d)。

### 2) readdir 返回 null 时把 errno 吞掉

旧实现：

  struct dirent* e = readdir(d);
  if (e == nullptr) break;                 <- 出错也当遍历结束

readdir 返回 null 有两种情况：遍历正常结束（errno 不动），或出错。
旧实现把后一种也当成「目录为空」，这正是「文件在但列表空」最难查的地方。

改为：

  if (e == nullptr) {
      if (errno != 0) { 记录 + LOGE("ufs list0: readdir err=...") }
      break;
  }

## 三、顺带记录的一个隐患（本次不改）

hooked_opendir 在 real_opendir == nullptr 时直接 return nullptr：

  if (real_opendir == nullptr) return nullptr;

而 real_opendir 由 install_plt_hooks（Phase 2）赋值，install_java_io_hooks 在
Phase 1 执行。若将来有代码在 Phase 1 里调 opendir，会拿到 nullptr 而不是真实现。
当前 hooked_ufs_list0 用的是 eal_opendir != nullptr ? real_opendir(x) : ::opendir(x)，
所以不受影响，但这是脆弱点。
