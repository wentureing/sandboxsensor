# 调查：能否自建一套"我们定义的路径访问系统"

- 日期：2026-11-23
- 起因：用户提出 —— 能否自行移植一套接近原生但由我们定义的路径访问系统？
  提前替代系统关键函数 / 提前匹配上调用 / 用某种机制实现更强的代理 / 深度参与 guest 运行、取代相关函数
- 结论先给：**能做到，机制是 inline hook `libc.so` 本身**；
  **但代价是"同时改到了 ART"，因此必须按调用方过滤**

---

## 一、三种 hook 方式的本质区别（这是全部答案的基础）

来源：[Gracker/android-internals-wiki · Native Hook 技术选型](https://github.com/Gracker/android-internals-wiki/blob/master/src/part5-app/ch20-stability/12-native-hook-technology-selection-implementation.md)

### 原文的两句关键论断

> **PLT/GOT Hook** 改写的是：某个 ELF **调用方的导入重定位槽**
> 覆盖：该调用方经动态链接发出的外部函数调用
> **不覆盖：内部直接调用、内联、直接系统调用、已保存的函数指针**

> **同样是拦 `malloc`，两者覆盖面也不同：**
> **修改 `libfoo.so` 中 `malloc` 的导入槽，只影响 `libfoo.so` 经该槽发出的调用；**
> **修改 `libc.so` 中 `malloc`，影响所有调用者。**

**这就是我们 P28 遭遇的根因**：
- 我们做的是**前者**（改调用方的 GOT）
- 所以 `libprobe.so` 这个**新加载的库**没被改 → 它的 `fopen` 是原版

### 三者的覆盖面对比

| 方式 | 改什么 | 覆盖 | **不覆盖** |
| --- | --- | --- | --- |
| **PLT/GOT hook**（我们现在的） | 某个 ELF 的**导入槽** | 该 ELF 经槽发出的外部调用 | 内部直接调用、内联、**直接 syscall**、**已保存的函数指针**、**新加载的库（除非另行扫描）** |
| **Inline hook** | **目标函数的指令体** | **所有调用者**（包括运行期新加载的库） | 内联（编译期展开）、直接 syscall、已保存的函数指针 |
| **Trap hook** | 断点指令 | 同上，但性能差 | 同上 |

## 二、"自建路径访问系统"= inline hook `libc.so`

### 2.1 为什么这样就能"取代系统函数"

```
libc.so 在 /apex/com.android.runtime/lib64/bionic/libc.so
  → 每个进程 mmap 同一份物理页
    → 函数体（.text）只有一份
      → inline hook 改了它
        → 所有调用者都受影响（包括运行期加载的 libprobe.so）
```

**这正是"提前替代系统关键函数"的字面含义** —— 不是每个调用方各改一次（那样永远漏），
而是**改那个唯一被所有人调用的实体**。

### 2.2 这样能解决什么问题

| 现有问题（L6） | inline hook `libc` 后 |
| --- | --- |
| `System.loadLibrary` 加载的库 GOT 未 patch | ✅ 它调用 `libc` 的 `open`，直接进我们的实现 |
| 需要 patch `libnativeloader.so` | ✅ **不需要了**（不再依赖 GOT 链） |
| 需要 `hooked_dlopen` 补 patch | ✅ 不需要了 |
| 库被卸载/重加载 | ✅ 不用管（改的是 libc，不是库） |

**对比方向 A（patch `libnativeloader`）**：
- 方向 A：修**一条具体的链**（正确但脆弱，链上任何一环变了就失效）
- **inline hook libc：修"根"**（不依赖任何加载顺序）

### 2.3 但代价很大：**你同时改到了 ART**

`libc.so` 的 `open`/`openat`/`read`/`stat` 被 ART 自己大量使用：

```
ART 启动时要 open：
  /apex/com.android.art/lib64/libart.so
  /system/etc/...（各种配置）
  /data/dalvik-cache/...（oat/vdex）
  /proc/self/maps（自己也要读）
```

**如果无差别拦截，ART 会被改到** → 崩溃或性能崩。

### 2.4 所以必须"按调用方过滤"

```cpp
static int hooked_open(const char* path, int flags, ...) {
    void* caller = __builtin_return_address(0);
    if (!is_guest_library(caller)) {
        return real_open(path, flags, ...);        // ART / linker / 系统库 → 直通
    }
    // 只有 guest 的库才重定向
    std::string redirected = redirect_path(path);
    return real_open(redirected.empty() ? path : redirected.c_str(), flags, ...);
}
```

**`is_guest_library(caller)` 怎么判断**：
- 用 `dladdr(caller, &info)` 拿到调用方所在的库
- 判断路径是否在 `/data/app/`、`/data/user/`、guest 的 sandbox 内
- **这正是现有 `is_app_lib` 的逆运算**

**成本**：每次 `open` 多一次 `dladdr`（几十纳秒）→ 可接受。

### 2.5 风险清单

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **`mprotect` 被 SELinux 拦** | `libc.so` 是 `r-xp`，改成可写需要 `PROT_WRITE` | 需实测（`untrusted_app` 域的 `execmod` 权限） |
| **ART 崩** | 改到 ART 用的函数 | 按调用方过滤 + 先只 hook `fopen`（ART 用得少） |
| **CFI / MTE 干扰** | Android 14+ 的 CFI 会校验函数指针 | 需要处理（shadowhook 声称兼容 CFI unwind） |
| **并发** | 多个线程同时 `open` | 无状态（只读 g_path_redirects），现有设计已满足 |
| **性能** | 每次 `open` 多一次过滤 | 可接受；必要时加 per-thread 缓存 |

## 三、现成的库：shadowhook 已经做了我们要做的事

来源：[bytedance/android-inline-hook · shadowhook 手册](https://github.com/bytedance/android-inline-hook/blob/main/doc/manual.zh-CN.md)

### 3.1 它提供的关键能力（正好对应我们的三个缺口）

| shadowhook 的能力（原文） | 对应的我们的缺口 |
| --- | --- |
| "**自动完成对'新加载 ELF'的 hook 和 intercept**，执行完成后调用可选的回调函数" | **L6：运行期加载的库** |
| "支持**绕过 linker namespace 的限制**，查询进程中所有 ELF 的 `.dynsym` 和 `.symtab` 中的符号地址" | 取 `android_dlopen_ext` 等符号地址 |
| "支持注册 linker 调用新加载 ELF 的 `.init` + `.init_array` 和 `.fini` 前后的回调函数" | **拿到"库刚加载完"的确切时机** |
| "支持通过'地址'或'库名 + 函数名'指定 hook 和 intercept 的目标位置" | 精确 hook 指定函数 |
| "在 hook 代理函数和 intercept 拦截器函数中，兼容 CFI unwind 和 FP unwind" | Android 14+ CFI |

### 3.2 与 bhook（PLT hook）的分工

shadowhook 手册自己说了：
> "如果你需要的是 Android PLT hook 库，建议试试 ByteHook"（bhook）

**所以字节的两件套正好分工**：
- **bhook** = PLT/GOT hook（我们已自研）
- **shadowhook** = inline hook（我们缺的）

### 3.3 引入它的代价

| 项 | 说明 |
| --- | --- |
| **体积** | 两个 `.so`（`libshadowhook.so` + `libshadowhook_nothing.so`），约 200–400 KB |
| **依赖** | Maven Central / prefab v2（AGP 7.1+，我们是 8.7.3 ✅） |
| **风险** | 它是**字节在线上验证过**的，比自研 inline hook 稳 |
| **可控性** | 黑盒（但开源，可读源码） |

## 四、AOSP 侧需要验证的三件事

### 4.1 `libc.so` 的段权限（能否 mprotect）

**待验证**（设备掉线了，下次补）：

```bash
# 取一个运行中的应用进程，看 libc 的映射权限
adb shell "cat /proc/<pid>/maps | grep 'libc.so'"
# 期望看到类似：7xxx-7xxx r-xp ... /apex/com.android.runtime/lib64/bionic/libc.so
# r-xp = 只读+可执行 → 需要 mprotect(PROT_READ|PROT_WRITE|PROT_EXEC)
```

**AOSP 依据**：
- bionic 的 linker 在 `soinfo::protect_relro()` 里把 `.data.rel.ro` 设成只读
- **`.text` 从来就是 `r-xp`**
- `mprotect` 需要内核允许 → **`untrusted_app` 域通常允许对自己的映射做 `mprotect`**（这是 `selinux_check_access` 的 `process:execmem`）

### 4.2 SELinux 对 `execmem` 的限制

**关键问题**：`mprotect(PROT_EXEC)` 在 `untrusted_app` 域受 `execmem` 限制。

- **Android 10+ 引入了 `execmem` 检查**（`neverallow` 规则）
- **但**：`mprotect` 现有 `r-xp` 段改成 `rwx` 是**新增 W**，不是新增 X → **可能允许**
- **需实测**

**如果被拦**：备选方案是 **`memfd` + `dlopen`**（把 hook 后的代码放到自己的 memfd 里执行）—— 这就是 shadowhook 内部可能做的事。

### 4.3 ART 用到哪些 `open` 族函数

需要确认哪些 libc 函数**绝对不能无差别拦截**：

| 函数 | ART 是否大量使用 | 建议 |
| --- | --- | --- |
| `open` / `openat` | ✅ 大量（加载 oat/vdex/配置） | **必须按调用方过滤** |
| `fopen` | ⚠️ 中等（读配置） | 可以试，但也要过滤 |
| `stat` / `lstat` | ✅ 大量 | 按调用方过滤 |
| `read` / `pread` | ✅ 极大量 | **不建议 inline hook**（性能 + 风险） |
| `mmap` | ✅ 大量（映射 oat） | **不建议** |

**所以"取代相关函数"要分级**：
- **可 inline hook**：`open`、`openat`、`fopen`（有明确的"路径"参数，过滤后风险可控）
- **不建议**：`read`/`pread`/`mmap`（数据流，ART 重度使用）

## 五、四条技术路线的对比（含新方案）

| 路线 | 机制 | 覆盖运行期加载库 | 改动量 | 风险 | 建议 |
| --- | --- | --- | --- | --- | --- |
| **现有：GOT hook** | 改各库导入槽 | ❌ | 已做 | 低 | 保留 |
| **方向 A：patch `libnativeloader`** | GOT hook 系统库 | ✅ | ~20 行 | 中 | **可做，但脆** |
| **路线 B：inline hook `libc`** | 改函数体 | ✅ | 中（自研） | **中高** | **技术最优** |
| **路线 C：引入 shadowhook** | inline hook + 自动处理新库 | ✅ | 加依赖 | 中（字节已验证） | **最省事** |

### 三条路线的"深度参与 guest 运行"程度

| 路线 | 深度 | 说明 |
| --- | --- | --- |
| GOT hook | 浅 | 只覆盖"经 GOT 的外部调用" |
| patch `libnativeloader` | 中 | 覆盖新加载库，但仍依赖 GOT |
| **inline hook libc** | **最深** | **所有调用者，包括内部调用**（因为改的是函数体） |

**"深度参与 guest 运行、取代相关函数" = 路线 B/C。**

## 六、一个更本质的问题：**要不要走到这一步**

### 6.1 inline hook libc 能带来的**新能力**（GOT hook 做不到的）

| 能力 | 为什么 GOT hook 做不到 |
| --- | --- |
| **拦 `dlsym("open")` 后的直接调用** | `dlsym` 返回的是 `libc` 里的真实地址，不经过 GOT |
| **拦库内部的直接调用**（如 `libc` 自己调 `open`） | 没有 GOT 槽 |
| **拦运行期加载的库** | 没有 patch 过它 |
| **拦 `__open_2` / `__openat_2` 这类 fortify 变体** | 不同符号名 |

**这些正是"应用加固"会用的手段** —— 所以如果要对付加固壳，**路线 B/C 是必需的**。

### 6.2 但代价

| 代价 | 量级 |
| --- | --- |
| **稳定性** | inline hook 一旦出错是**整个进程崩**（不像 GOT hook 只影响一个库） |
| **兼容性** | 每个 Android 版本的 `libc` 指令序列不同 → 需要维护多套 |
| **CFI/MTE** | Android 14+ 的新机制会干扰 |
| **调试难度** | 崩在 libc 里，栈不可信 |

### 6.3 折中建议

> **先用 shadowhook 做"最小侵入"的验证**：
> 1. 只 inline hook **`android_dlopen_ext`**（一个函数，风险最小）
> 2. 用它拿到"库加载完成"的回调
> 3. 在回调里用**现有的 GOT patch** 改那个新库
> 4. **不直接 hook `open`**
>
> **这样既解决了 L6，又不承担"改 libc 函数体"的风险。**

**这就是路线 C 的保守用法** —— 用 inline hook 补 GOT hook 的"时机缺口"，而不是替代它。

## 七、结论

| 问题 | 答案 |
| --- | --- |
| **能否自建一套我们定义的路径访问系统？** | **能**，机制是 inline hook `libc.so`（改函数体，所有调用者生效） |
| **能否"提前替代系统关键函数"？** | **能**，但 `libc` 被 ART 重度使用 → **必须按调用方过滤** |
| **能否"提前匹配上调用"？** | **能**，shadowhook 提供 `.init_array` 前后的回调，能拿到"库刚加载完"的确切时机 |
| **能否实现"更强的代理"？** | **能**，inline hook 能拦到 GOT hook 拦不到的：`dlsym` 后的调用、库内部调用、fortify 变体 |
| **推荐路径** | **引入 shadowhook，但只 inline hook `android_dlopen_ext` + 在回调里补 GOT patch**（不直接改 `open`） |
| **不推荐** | 自研完整 inline hook 引擎（工作量大、稳定性风险高，字节已经做了） |

### 待验证（设备回来时补）

1. `libc.so` 的 `.text` 段权限与 `mprotect` 可行性
2. `untrusted_app` 域的 `execmem` 限制是否影响 inline hook
3. ART 对 `open`/`fopen`/`stat` 的实际调用频率（决定过滤开销）
