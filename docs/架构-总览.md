# 架构-总览（开发参考）

> 目的：**减少"因不熟悉架构而做的错误假设"**。
> 本轮已经因此踩了 3 次坑（WebView 三层弯路、`/sdcard/Download` 查错层、`LIST count=0` 误判）。
> 本文只写**代码事实 + 为什么这样设计 + 哪里容易踩坑**，不写推测。

---

## 一、进程模型（最容易误判的一层）

```
┌─────────────────────────────────────────────────────────────┐
│ com.nextvm.app                    ← 容器主进程（唯一）        │
│   · MainActivity / Compose UI                                │
│   · CmdReceiver（INSTALL/LAUNCH/.../COLLECT_OUT/CAT_OUT）    │
│   · VirtualEngine.initialize() → initNativeHooks()           │
│   · 所有"管理"动作都在这里：装包、删包、列表                    │
│   · 进程名 = "com.nextvm.app"                                │
└─────────────────────────────────────────────────────────────┘
                              │ fork + 改名
                              ▼
┌─────────────────────────────────────────────────────────────┐
│ com.nextvm.app:p0 → 改名为 "com.sandbox.probe"（guest 包名）   │
│   · 同一个 APK、同一份 native 库                              │
│   · Application.onCreate 会再跑一遍                           │
│   · 进程名 = guest 包名（Process.setArgV0 / nativeSetProcessName）│
│   · 真正的文件重定向、/proc 伪装都在这里生效                    │
└─────────────────────────────────────────────────────────────┘
```

### 判断当前进程的可靠方法

```kotlin
val procName = android.app.Application.getProcessName()
val pkg = context.packageName            // "com.nextvm.app"
val isContainerMain = (procName == pkg)  // 主进程
val isGuest = procName.startsWith("$pkg:") || procName == guestPkg
```

`ActivityManagerProxy.kt:629-635` 已有类似实现。

### ⚠️ 陷阱 1：`pidof com.nextvm.app` 为空的含义

**不等于** guest 没了。**只表示容器主进程被系统回收**。

实测：容器主进程被杀后，沙箱数据完好，`LIST` 会返回 `count=0`（因为没人能响应广播或 engine 未初始化），
但 `run-as ls files/virtual/data` 里实例还在。

**排查时永远先看三样**：
```powershell
adb shell pidof com.nextvm.app                                    # 主进程活着吗
adb shell dumpsys activity activities | grep topResumedActivity   # 前台是谁
adb shell run-as com.nextvm.app ls files/virtual/data             # 沙箱里有什么
```

## 二、两层 hook 的真实边界

`NativeHookBridge.initNativeHooks()` 有两相，但**只有一相真正生效**：

| 相 | 实现 | 实际状态 |
| --- | --- | --- |
| **Phase 1: Java IO hooks** | `installJavaIoHooks()` | **空的** —— `hookFileClass()` / `hookRuntimeExec()` 只打日志返回 true |
| **Phase 2: native GOT patch** | `nativeInit()` + `hooked_*` 系列 | **这层才是真正起作用的** |

### Phase 2 的作用范围（`native-hook.cpp` 过滤链）

```cpp
1) 容器自身库（含 "com.nextvm.app" / "libnextvm"）→ 永不 patch
2) 图形栈（libGLES/libEGL/eglSubDriver/libvulkan/vulkan.adreno/libllvm-glnext）→ 永不 patch
3) 应用/沙箱库（/data/app、/data/user、/virtual）→ patch
4) 其余系统库 → NS_HOOK_SYSTEM_LIBS=0（默认）→ 不 patch
```

### ⚠️ 陷阱 2："容器自己的文件访问被重定向了"

**基本不成立**。因为：
- 容器代码的 `open` 走 `libc.so` → 属第 4 类 → **不 patch** → 不重定向
- 证据：`run-as com.nextvm.app cat /data/local/tmp/x.apk`（独立进程，不装 hook）能读

**如果容器读不到文件，先怀疑 DAC 权限，不是重定向。**

### ⚠️ 陷阱 3：`initNativeHooks` 在主进程也会执行

`VirtualEngine.initialize()`（`L280`）和 `getOrCreateClassLoader`（`L880`）都会调它，
而这两处在**主进程和 guest 进程都会跑**。

→ 所以**主进程也装了 hook**，只是 hook 对它自己的 `open` 无效（见陷阱 2）。
→ 这也是"要不要给主进程装 hook"这个改造点的由来（见计划文档）。

### ⚠️ 陷阱 4：沙箱有两个根

| 路径 | 谁在用 | 实测内容 |
| --- | --- | --- |
| **`/data/user/0/com.nextvm.app/files/virtual/`** | `VirtualEngine`（3 处）、`PackageManagerProxy`（2 处） | `<instance>/` 下 **12 项**（files/cache/databases/lib/…）**← 真实数据** |
| `/data/user/0/com.nextvm.app/app_virtual/` | `SandboxManager`（构造注入的 `virtualRoot`） | `<instance>/` 下**只有 sdcard**（空壳） |

**原因**：`AppModule.provideSandboxManager` 用了 `context.getDir("virtual")`（→ `app_virtual`），
而 `VirtualEngine` 用 `File(context.filesDir, "virtual")`（→ `files/virtual`）。
**上游 bug，fork 点 `63346e6` 就存在。**

**结论**：任何"遍历沙箱"的代码，必须用 `files/virtual/data`，**不能用 `SandboxManager.virtualRoot`**。

## 四、关键数据流

### 4.1 安装（`CmdReceiver.INSTALL`）

```
adb broadcast → CmdReceiver（主进程）
  → engine.installApp(apkPath)
     1. File(apkPath) + frameworkApkParser.parseFullPackage(apkFile)   ← 需要能读到源 APK
     2. 生成 instanceId = "<pkg>_<timestamp>"
     3. 复制到 files/virtual/apks/<instanceId>.apk
     4. NativeLibManager.extractNativeLibs → files/virtual/data/<instanceId>/lib
     5. sandboxManager.createAppDataDir(...)     ← 建在 app_virtual（空壳，见陷阱 4）
     6. 分配 processSlot
```

**源 APK 能读到的条件**（三个都要满足）：
1. 路径不被重定向（主进程本来就不重定向）
2. **DAC 允许**（`/data/local/tmp` 644 ✓；`/sdcard/Download` 660 且非本人 ✗）
3. SELinux 允许

### 4.2 启动（`CmdReceiver.LAUNCH`）

```
→ engine.launchAppByPackage(pkg)
  → ActivityManagerProxy 起 stub Activity（P0..P9$Standard00..）
    → fork guest 进程（:p0 → 改名）
      → ActivityThreadHook → Application.onCreate
        → initNativeHooks（guest 进程这次真的生效）
          → 路径重定向 + /proc 伪装
```

**容器只解析 LAUNCHER** —— 要起非 LAUNCHER 页面必须用 `LAUNCH_ACTIVITY`。

### 4.3 路径重定向（native）

```
guest 进程 libc.open("/sdcard/xxx")
  → hooked_open
    → is_path_hidden? → ENOENT
    → 导入豁免? (is_import_read_exempt)  ← p18/p28
    → redirect_path(path)  ← 前缀匹配 g_path_redirects
      → real_open(实际路径)
```

**注意**：`redirect_path` 是**进程级**的，不区分调用方。这是"豁免"存在的原因，也是它难以精确的原因。

## 五、本轮踩过的坑（每条都花了时间）

| # | 错误假设 | 实际 | 代价 |
| --- | --- | --- | --- |
| 1 | 长按 ANR 是容器 `WindowManager`/`PopupWindow` 问题 | 只在 WebView 里出现 | 数轮排查 |
| 2 | patch `libwebviewchromium` 能修 Via 主页源码 | WebView 渲染在 isolated 进程，容器 hook 覆盖不到 | 一次构建 + 回退 |
| 3 | Gaia 沙箱在 `/sdcard`（外部存储） | 实测在 `/data/user/0/<容器>/gaia/`（内部） | 方案作废 |
| 4 | `/sdcard/Download` 失败是路径重定向 | **DAC 权限**（660，非本人）+ MANAGE_EXTERNAL_STORAGE 未授权 | **前几轮全部查错层** |
| 5 | `LIST count=0` = guest 丢了 | 容器主进程被系统回收 | 误判一次 |
| 6 | Robolectric 冒烟过了就说明环境 OK | p21 那次是碰巧下载到了 100MB 的 `android-all` jar | 一次 CI 全红 |
| 7 | KDoc 里写 `.../**` 没问题 | Kotlin 块注释可嵌套 → `Unclosed comment` | 一次编译失败 |

**共同点**：**都是从现象直接跳到结论，没有先确认"这一层到底生效没有"**。
→ 所以下一份文档是《调试指南》里的**分层排查顺序**。

## 六、给开发者的三条硬规则

1. **任何"读不到/看不到"类问题，先按层排查**（存在性 → DAC → appops → SELinux → 重定向），不要跳到第 5 层。
2. **任何"容器状态"判断，先打印三样**（`pidof` / `topResumedActivity` / `run-as ls files/virtual/data`），不要假定。
3. **任何"沙箱路径"代码，用 `files/virtual/data`**，不要用 `SandboxManager.virtualRoot`（陷阱 4）。
