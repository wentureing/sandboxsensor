## 一、现行结论

| # | 结论 | 等级 | 证据/来源 |
| --- | --- | --- | --- |
| **P-a** | 路径有三层手段：① `VirtualContext` 直接返回沙箱/合成路径 ② 原生 GOT patch ③ Java `RegisterNatives`（默认关） | A | 代码 + `现状-hook摸底` |
| **P-b** | `File` 是**纯 Java 且分叉**：`list0/createDirectory0/...` 走 `UnixFileSystem`，`length/delete/renameTo` 绕去 `Linux.*` → 必须两层都 hook | A | 反编译 + 实测 |
| **P-c** | 默认配置下"双层不一致"：app .so 落沙箱，Java `File` 落宿主真实路径 | A | via 的 mkdir 落宿主实测 |
| **P-d** | 翻译**幂等**（沙箱路径不命中任何规则）⇒ 多层并存不会双重翻译；**新增规则必须重验幂等** | A | `verify-idempotent-translate` |
| **P-e** | 合成路径族（`syntheticDataDir`/`pathFidelity`）只为"报告类" API 服务；实测**对 WebView MIME 无效** | A | W37 |
| **P-f** | 内容目录用真路径是有效的（WebView `file://` 的 `content://`/真路径场景） | A | `架构-WebView假路径换真路径.md` |
| **P-g** | 豁免名单（via 零欺骗、仍隔离）是设计理念第三条的落地：**只误导不危害读写** | A | golden C9 + 实测 |
| **P-h** | **`file://` 的 MIME 由"路径是否含应用包名"决定**（详见「册-WebView与file-MIME」） | A | W-ext 四组 |
| **P-i** | 容器存储权限：只有 `MANAGE_EXTERNAL_STORAGE`（appops allow）生效；`READ/WRITE_EXTERNAL_STORAGE` 声明但 targetSdk 35 下**不授予** | A | `dumpsys`/`appops` |

## 二、已证伪 / 不要再试

| 路线 | 为什么 |
| --- | --- |
| 假 `dataDir`（让 `getDataDir()` 返回 guest 路径） | 变了 dataDir，WebView MIME 仍错（W37） |
| 靠"给合成路径"修 WebView `file://` | MIME 判定在 Chromium，合成路径只会更糟（含包名 ⇒ 嗅探） |
| 只 hook 一层（只 Java 或只 native） | `File` 分叉 + libjavacore 是系统库 ⇒ 必漏一半 |
| 把沙箱整体迁到外部存储（笼统） | 外部 `Android/data/<pkg>` 实测仍 `text/plain`（W-ext-private） |
| 改 `getOpPackageName()` 返回值 | 破坏 appops 归因（`checkPackage` 抛 SecurityException） |

## 三、待确认 / 可能错

| # | 事项 | 说明 |
| --- | --- | --- |
| 1 | NIO2（`UnixNativeDispatcher` 0/38）的真实危害 | 用户决定"暂不实现"，但未量化有多少 app 用 NIO 写宿主 |
| 2 | `readlink` 在 Java 层缺失的泄露面 | A 族未 hook ⇒ 可把沙箱路径换算回真实路径（`疑似缺陷`） |
| 3 | 路径经 Binder 传出（`FileProvider`/Intent 里的 `file://`）是否被系统侧解析成真实路径 | 未单独评估（所有 pathFidelity 方案共同风险） |
| 4 | `hiddenPaths` 无 native 精确匹配 | Java 隐藏、native 不知道（低优先） |

| 场景 | 用什么路径 | 备注 |

## 四之二、模块级摸底（哪些启用 / 哪些没有 / 各管哪一层）

| # | 模块 | 层面 | 负责什么翻译 | 默认 | 困难 / 证据 |
| --- | --- | --- | --- | --- | --- |
| **M1** | `VirtualContext`（`core/sandbox`） | Java `Context` | **14 个路径 getter**：`getFilesDir/CacheDir/CodeCacheDir/DatabasePath/Dir/ExternalFilesDir(s)/ExternalCacheDir(s)/ExternalMediaDirs/ObbDir(s)/NoBackupFilesDir/DataDir` | ✅ 开 | 只覆盖"经 Context 拿路径"；guest 自己拼路径绕过 |
| **M2** | `PathRuleStore` / `PathRedirectRegistry` | Java + 规则表 | 规则注册（前缀映射）、族根形态、`ROOT_FORM` | ✅ 开 | 只支持前缀/族根，无通配 |
| **M3** | `VirtualApplicationManager`（datadir patch） | Java（LoadedApk） | 改 `ApplicationInfo.dataDir` 等 | ✅（白名单） | `v143-datadir skip (whitelist)`（via 豁免） |
| **M4** | `PackageManagerProxy` / `VirtualPackageManagerService` | Java PM | 改 `PackageInfo`/`ApplicationInfo` 的**报告值** | ✅ 开 | 只影响"报告"，不改变 I/O |
| **M5** | **`JavaIoHooks`（RegisterNatives）** | **JNI native 方法** | 替换 `libcore.io.Linux` 8 个 + `java.io.UnixFileSystem` 8 个 = **16 个方法** | ❌ **默认关**（`javaIo=0`） | 见 §四之三 的两次翻车 |
| **M6** | `hooked_*`（GOT patch） | native libc PLT | **27 符号**，其中 **14 条**走 `redirect_path` 翻译 | ✅ 开 | 只覆盖"被 patch 的库的 PLT"；`dlsym`/raw syscall/**Chromium 内部**都绕过 |
| **M7** | `core/path_rules` + `core/path_pattern` | C++ 纯函数 | 前缀匹配、模式匹配、族根 | ✅ 开 | 与 Java 共用 golden TSV（防语义分叉） |
| **M8** | `core/path_spoof`（N1a） | C++ 纯函数 | 合成路径形状、maps 行改写 | ✅ 开 | 只负责"看起来"，不负责 I/O |
| **M9** | `ProcSpoofing` | Java + native | `/proc/self/*` **内容**（不是路径） | ✅ 开 | cmdline/comm/status/maps |
| **M10** | seccomp SIGSYS（`sc_rewrite_fd_target`） | **内核边界** | fd 目标路径改写 | ⚠️ 诊断模式 | handler 内无分配/无 libc；性能未评估 |
| **M11** | **NIO2 `UnixNativeDispatcher`** | JNI native 方法 | `java.nio.file.Files/Path` 的 38 个方法 | ❌ **未实现（0/38）** | 用户决定"暂不实现"；**真实危害未量化** |
| **M12** | A 族 **`readlink`** | JNI native 方法 | `File.getCanonicalPath` 等 | ❌ **未实现** | 泄露面：可把沙箱路径换算回真实路径 |
| **M13** | B 族 **`setPermission0`** | JNI native 方法 | `setWritable/setExecutable` | ❌ **未实现** | 静默 false（可用性） |

**一句话分层**：M1–M4 改"报告值"（Java 层能看到的字符串）；M5–M8 改"实际 I/O"；M9 改"内容"；M10 兜"内核边界"；M11–M13 是**缺口**。

## 四之三、被禁用模块当年遇到什么困难

| 模块 | 困难（有证据） | 现状 |
| --- | --- | --- |
| **M5 javaIo** | ① v141 只对齐**成功路径**：`Linux.*` 失败应抛 `ErrnoException`、`UnixFileSystem.*0` 应返回 `null/false/0`；写错 → **Via 完全不可交互**（`记录-JavaIoHook导致Via不可交互.md`）<br>② v147 把 `ErrnoException` 类名写成 **`libcore/io`**，实际在 **`android/system`** ⇒ `UnixFileSystem.checkAccess`（只 catch 前者）捕获不到 ⇒ **FATAL**（代码注释 `native-hook.cpp:6708-6715` 记为"开了 javaIo 就崩的最终根因"） | **两处都已修**，但仍默认关 = **历史创伤后的保守**，不是技术不可行 |
| **M11 NIO** | 从未实现。当时的判断是"NIO 用得少，除严重危害权限外不做"（用户决定），**没有量化**有多少 app 用 NIO 写宿主 | 缺口保留 |
| **M12 `readlink` / M13 `setPermission0`** | 从未实现；归"疑似缺陷（泄露）/ 待评估（可用性）" | 缺口保留 |

## 四之四、要不要考虑 inline hook / 专门的 so 加载 hook

### inline hook：现在不做，但它是"像真机"路线的**唯一**可行技术

| 维度 | 结论 |
| --- | --- |
| **能解决什么** | GOT patch 改的是"被 patch 库的 PLT 槽"；**Chromium 的 `open` 在 `libwebviewchromium.so` 里直连 libc**（该 so 属"永不 patch"），所以第②段失效。**inline hook 改的是 libc 函数入口**，任何调用者（含 Chromium）都会被拦到 ⇒ 这才是"合成路径也能读到文件"的唯一办法 |
| **代价** | ① 改机器码（ARM64 4 字节对齐、需邻接空间；bionic 的 CFI/BTI 会校验）② **被测特征明显**（指令被改 + 页可写）③ Chromium 热路径稳定性 ④ 项目文档明确"不换 hook 库"（xHook/ShadowHook/Dobby 都只借鉴） |
| **建议** | **暂不引入**。若将来必须"像真机 + 全拦截"，它才是入口，需单独立项 + 大量回归（渲染/popup/稳定性/检测面） |

### so 加载路径的通知：**不需要 hook，用 linker 自己的计数器**（推荐）

| 方案 | 做法 | 覆盖 | 成本 | 风险 | 评价 |
| --- | --- | --- | --- | --- | --- |
| A. `dlopen` GOT patch（现状） | 只有"被 patch 的库"里调用 `dlopen` 才触发 | 部分 | 已实现 | — | 调用方是 `libnativeloader`（系统库，不 patch）⇒ 漏 |
| B. 白名单 patch `libnativeloader.so` | 只 patch 它的 `dlopen`/`android_dlopen_ext` | 全 | 中 | **动系统库**（历史两次崩溃） | 备选 |
| **C. `dlpi_adds` / `dlpi_subs` 轮询** | `dl_iterate_phdr` 的 `dlpi_adds`（API 30+）是**库加载计数**；在已有 I/O hook 里顺带比较一个 int，变化即触发 `patch_newly_loaded_libraries()` | **全**（任何来源的加载） | **极低**（一次 int 比较，纳秒级） | 无（只读计数） | ✅ **推荐**：实时、零定时器、零 hook、零系统库改动 |
| D. linker `r_debug.r_brk` 通知 | 改 linker 全局 `_r_debug.r_brk` 指向自己的函数 | 全、实时 | 中 | 中（改 linker 全局状态，需定位 `_r_debug`） | 备选（C 不够实时时才考虑） |

**推荐落地**（最小改动）：在 `hooked_open/openat/stat/access` 等热路径入口加一句

```cpp
// 每 N 次调用或每次（一个 int 比较）检查库加载计数
if (g_last_dlpi_adds != dlpi_adds_snapshot()) {  // 用 dl_iterate_phdr 第 0 项的 dlpi_adds
    patch_newly_loaded_libraries();
}
```

**收益**：把现在"bind 后 +5s/+20s 定时补丁"（滞后、且 20s 后漏）换成**加载即补**，且不碰系统库、不引入 inline hook。
**前提**：`dlpi_adds` 在目标 API 级别可用（API 30+；本机 Android 15 ✅），旧版本回退到定时触发。
