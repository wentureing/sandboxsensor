## 一、三条通道（谁写、谁读）

| 通道 | 写入 API | 落到 | 消费者 | 频率约束 |
| --- | --- | --- | --- | --- |
| **结构化自检** | `DiagnosticsHolder.check(CheckResult)` / `.stage(tag,msg)` / `.error(tag,msg,cause)` | `files/checks.log`（`C/S/E` 行） | 自检、探针、人读 | 低频；`check()` 是**结构化结果**，不要塞任意文本 |
| **自由文本/细节** | `DebugTrace.event/detail/fail`、`Timber.*`（`DebugTrace` 是全局 Tree，仅 debug 包 plant） | `files/debug-trace.log` | 人读 | 可高频，但 release 自动空转 |
| **guest 生命周期** | `GuestBreadcrumb.log(...)`（全链路 199 处埋点） | `<沙箱>/files/breadcrumb-<pid>.log` | `BreadcrumbGoldenContractTest`、排查 | 只在签名变化时写 |

**硬规则**：
1. **只打 `Timber` 不算"可判定"**（ROM 会吞）—— 重要过程必须能 `run-as cat` 到文件里；
2. **不要用 `GuestBreadcrumb` 写主进程事件**（它绑当前进程 filesDir，污染 golden C1–C12）；
3. **新增日志文件必须走 TSV 三件套**：改 `core/common/src/main/resources/diag_channels.tsv` → `gen-diag-channels.mjs` → `check-diag-channels.mjs`；否则 C++ 侧 `is_container_diag_path` 不认，Java IO 配额会被写满。

## 二、现行结论

| # | 结论 | 等级 |
| --- | --- | --- |
| **G-a** | 干净安装后 `logcat --pid=<容器>` 可能完全无输出，而 `checks.log`/`debug-trace.log` 一直在写 | A（多次实测） |
| **G-b** | `release` 包诊断自动空转（`DebugFlags.isDebugBuild()`），业务代码不需要自己判断 | B |
| **G-c** | 诊断文件被 `is_container_diag_path()` 排除在路径重定向之外（否则日志会写进沙箱/被规则改写） | B |
| **G-d** | 26 个诊断文件通道由 TSV 单一来源生成（改一处、生成两处） | B |
| **G-e** | 探针体系与容器自检是两套：自检测"容器动作是否可行"，探针测"guest 视角是否一致" | A |
