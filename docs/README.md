## 三、时效与可信度规范（**硬性**）

任何"现状/架构/设计/册子"类文档，**头部三行必须有**：

```markdown
- 时效：<复核日期>。触发复核：<条件1> / <条件2>
- 可信度：A=实测（探针/日志/CI）/ B=代码级推理 / C=推测
- 替代：本文取代 <旧文档列表>（原文保留作证据）
```

正文里**逐条结论**尽量带等级列（`A`/`B`/`C`）+ 证据（探针编号 / 日志片段 / 提交）。

**"可错性"要求**：每篇必须有 **「待确认 / 可能错」** 一节，写出：
- 哪些结论只是归纳（未读源码确认）；
- 哪些只在**单机单版本**验证过（设备 `10AFA8169Z0039G` / Android 15）；
- 哪些已被推翻过（并在 `archive/` 有登记）。

**为什么**：本项目的错误多来自"把一次实测当普适规律"（例如"沙箱迁外部存储"曾被否证两次）。
把"证据等级 + 复核条件 + 可能错"写进文档头，比事后考古便宜得多。

## 四、五类目录怎么分工

| 目录 | 回答的问题 | 什么时候读 |
| --- | --- | --- |
| **主题/** | 「这个主题现在到底是什么结论」 | **首选**，日常只读这 6 篇 |
| **计划/** | 「接下来做什么」 | 定任务、看优先级 |
| **架构/** | 「它怎么运作」 | 改代码前（册子指向具体篇） |
| **设计/** | 「为什么这么选」 | 要推翻/延续设计决策时 |
| **现状/** | 「现在什么生效」 | 判断某能力是否真生效（含基线判据） |
| **输出/** | 「做过什么、证据在哪」 | 复盘、查证据（`变更/` 有 diff，`记录/` 有实测） |
| **代码镜像/** | 每个代码文件的职责/函数/偏差/坑 | 改那个文件前（规则 7 强制，一文件一篇） |
| **archive/** | 「哪些结论是错的」 | 引用任何结论前 |

## 五、写作约定

| 类型 | 放哪 | 命名 |
| --- | --- | --- |
| 主题册（现行结论） | `主题/` | `册-<主题>.md` |
| 计划 | `计划/` | `计划-<主题>.md` |
| 架构 | `架构/` | `架构-<主题>.md` |
| 设计 | `设计/` | `设计-<主题>.md` |
| 现状快照 | `现状/` | `现状-<主题>.md` |
| 实验记录 | `输出/记录/` | `记录-<主题>.md` |
| 变更计划与实际 diff | `输出/变更/` | `<YYYYMMDD>-<任务>.md` + `.actual.diff` |
| 调研 | `输出/调研/` | `调查-*.md` / `调研-*.md` |

**硬性要求**：
1. 结论必须带**实测证据**（探针编号 / 日志片段 / 反编译结果），不能只有推理；
2. 被推翻的结论**不删**，移到 `archive/错误结论-<年月>/` 并在其 README 登记；
3. 引用别的文档用**相对路径**；
4. 一份文档只回答一个问题；
5. **同一主题的新文档，结论要回写进对应册子**（册子是唯一现行入口，避免又散开）。
