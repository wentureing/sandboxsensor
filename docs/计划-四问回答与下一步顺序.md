## 一、WebView 的路径：`is_path_hidden` **不该藏**

### 1.1 关键区分：WebView 的文件读取有**两个完全不同的执行者**

```
Via 的 Java 层（guest 进程，装 hook）
  FileInputStream → 容器 hook → 重定向到沙箱 → ✅ 读到沙箱文件
  loadDataWithBaseURL(html 字符串)
    → renderer 收到字符串，不需要读文件 → ✅ 正常渲染

或者

Via 的 Java 层
  loadUrl("file://" + getFilesDir() + "/homepage2.html")
    → WebView 把 URL 交给 renderer
      → renderer（isolated uid 99499）按**自己的 uid** 读那个路径
        → 而那个路径是 guest 视角的 /data/user/0/mark.via/...（VirtualContext 伪造的）
          → 真实磁盘上不存在（真实数据在 <沙箱>/data/mark.via_xxx/files/）
            → ❌ renderer 读不到 → WebView 退化
```

### 1.2 标准环境 vs 容器内，路径的真实差异

| 环节 | 标准（直接安装） | 容器内 |
| --- | --- | --- |
| Via 认为的 `getFilesDir()` | `/data/user/0/mark.via/files` | **同一个字符串**（`VirtualContext` 伪造） |
| **Via 的 Java 层实际读到** | 就是那个路径 | `<沙箱>/data/mark.via_xxx/files`（被 hook 重定向） |
| **renderer 拿到的 URL** | `file:///data/user/0/mark.via/files/homepage2.html` | **同一个 URL** |
| **renderer 实际读** | 那个路径（真实存在）| **那个路径（真实磁盘上不存在）→ 失败** |

**核心矛盾**：
> **`VirtualContext` 让 guest 看到"标准路径"，但 renderer 不受容器 hook 影响，
> 它按标准路径去读真实磁盘 —— 而真实数据在沙箱里。**
>
> **这就是"路径保真"（`pathFidelity`）在 WebView 场景下的必然失败。**

### 1.3 所以 `is_path_hidden` 该不该藏？

| 藏什么 | 该不该 | 理由 |
| --- | --- | --- |
| **容器自己的路径**（`/data/data/com.nextvm.app`） | ✅ **该藏** | 检测面（OWASP package structure） |
| **guest 的沙箱路径**（`<沙箱>/data/mark.via_xxx`） | ❌ **不该藏** | 它是真实的、guest 有权访问的 |
| **guest 视角的"标准路径"**（`/data/user/0/mark.via`） | ❌ **不能藏** | 藏了 renderer 会更快失败；而且它本来就不存在，藏不藏都不影响 |

**关键**：**`is_path_hidden` 只影响 `open`/`stat`/`access` 的返回值**，**影响不到 renderer**（它在另一个进程）。

### 1.4 那 WebView 该怎么办（三种）

| # | 方案 | 可行性 | 代价 |
| --- | --- | --- | --- |
| **A** | 不修，接受"`loadUrl("file://")` 类失败" | ✅ 现状 | 少数应用（本地 HTML 阅读器）不可用 |
| **B** | 让 `pathFidelity = true`，租客真的用标准路径 | ⚠️ 需要真实目录可写 | 要在 `/data/user/0/<guest>` 建真目录 → 需要 root 或恶意利用 |
| **C** | hook `WebView.loadUrl`，把 `file://` 改写成 `loadDataWithBaseURL` | 中 | 要 hook framework 类（`WebView`），难；且改写了应用行为 |

**建议**：**A（接受）**，并把"本地 HTML 打不开"写进已知边界。
**理由**：`file:///android_asset/` 正常（走 `AssetManager`），`https://` 正常，**只有"应用自写文件 + file:// 打开"这一种失败**。

### 1.5 顺带：16:19 那次实测发现，Via 的 `Shell` 只活了 1188ms

```
17:19:45.654  instr callActivityOnCreate enter mark.via.Shell
17:19:45.793  cb onActivityResumed                          ← 前台
17:19:46.781  cb onActivityPaused                           ← 1188ms 后
17:19:46.810  wm_destroy_activity: [.stub.P0$Standard00, finish-imm:idle]
17:19:46.825  cb onActivityDestroyed
17:19:46.838  E chromium: Renderer process (13639) crash detected (code -1)   ← renderer 随宿主被回收
```

**`finish-imm:idle` 说明有代码调了 `finish()`**（不是崩溃）。
`am_kill: [..., isolated not needed, ...]` → renderer 是"不再需要"被正常回收，**`code -1` 是噪音**。

**这条链条意味着**：Via 主页显示的"源码"可能是**Activity 被销毁前已经渲染出的结果**，
或者**用户看到的是容器 UI 里的截图残留**。**需要单独一次"不被打断的 Via 启动"才能定论。**

## 二、SelfCheckRunner 改用非主进程

### 2.1 为什么必须改

**P0-3 后主进程不装 hook** → 主进程的行为**等于真机** →
在主进程跑自检**测不出"容器环境"**（因为 hook 没装）。

**而 SelfCheckRunner 的目的恰恰是"测容器环境"** → **必须在 guest 进程跑**。

### 2.2 三种实现方式

| # | 方式 | 机制 | 评价 |
| --- | --- | --- | --- |
| **A** | `CmdReceiver` 转发到一个**容器自己的 stub Service**（`:p0`） | `startService(Intent().setClassName(pkg, "com.nextvm.app.stub.P0\$S00"))` | ⚠️ `:p0` 的 ClassLoader 可能已被换成 guest 的，跑容器代码有风险 |
| **B** | **借用一个已安装的探针/guest，通过 `ContentProvider` 或广播触发** | 探针已经在 guest 进程跑，直接扩展它 | ✅ **最简单**，但依赖探针 |
| **C** | **新增 `:selfcheck` 进程**（manifest 加 `android:process=":selfcheck"`） | 独立进程，装 hook，跑容器自己的代码 | ✅ **最干净**，但要加一个进程 |

**推荐 C**，理由：
- **不依赖 guest 的 ClassLoader**（`:selfcheck` 是容器的独立进程）
- **装 hook**（`initNativeHooks` 会跑，因为进程名 ≠ 包名）
- **结果导出**：写 `files/probe-out/selfcheck.json`（**真实路径**，主进程能读）

### 2.3 实现要点

```kotlin
// 1) manifest 加一个 Service（不导出）
<service android:name=".selfcheck.SelfCheckService"
         android:process=":selfcheck"
         android:exported="false" />

// 2) CmdReceiver 转发
ACTION_SELFCHECK -> {
    val i = Intent().apply {
        setClassName(context.packageName, "${context.packageName}.selfcheck.SelfCheckService")
    }
    context.startService(i)
    Log.i(TAG, "SELFCHECK dispatched to :selfcheck")
}

// 3) Service 里跑检查，写文件（真实路径）
override fun onStartCommand(...): Int {
    Thread {
        val report = SelfCheckRunner(this).run()
        val out = File(filesDir.parentFile, "probe-out/selfcheck.json")  // <dataDir>/files/probe-out
        out.parentFile?.mkdirs()
        out.writeText(report.toString())
        Log.i(TAG, "SELFCHECK done -> ${out.absolutePath} (${out.length()} B)")
        stopSelf()
    }.start()
    return START_NOT_STICKY
}
```

**验证**：
- `logcat -s SelfCheck` 出现 `:selfcheck` 进程的 pid
- `run-as com.nextvm.app cat files/probe-out/selfcheck.json` 有内容
- **主进程的 `logcat` 里不应出现 SelfCheck 的 hook 日志**（它是独立进程）

## 三、P0-4/P0-5：分支开发 + 过滤注意事项 + 主进程不 hook 的帮助

### 3.1 分支开发

```bash
git -C _ref/ShitJumpingVM checkout -b feat/p0-4-p0-5-hide-container
```

**理由**：
- P0-5 风险高，需要能随时 `checkout main` 回退
- `main` 保持"可用状态"（当前 `1631541` 已验证通过）

### 3.2 **主进程不 hook 带来一个决定性的简化**

**这是本轮最重要的发现**：

```
is_path_hidden 读的是 g_hidden_paths（进程内的全局 unordered_set）
  ↓
P0-3 后：主进程不装 hook
  → 主进程的 g_hidden_paths 即使有值，也没有 hook 去用它
    → 主进程完全不受 hidePath 影响
      → 不需要任何"按进程判断"的逻辑
```

**对比**：

| 项 | P0-3 之前 | **P0-3 之后** |
| --- | --- | --- |
| 加 `hidePath("/data/data/com.nextvm.app")` 对容器自己的影响 | ⚠️ **容器自己读不到自己的 dataDir**（灾难） | ✅ **零影响**（主进程没 hook） |
| 需要"只对 guest 生效"的判断吗 | **必须**（否则把容器搞坏） | **完全不需要** |
| `readdir` 过滤的安全性 | ⚠️ 要小心不要过滤掉容器自己要用的目录 | ✅ **无脑过滤**（主进程看不到） |

**所以 P0-5 的风险从"高"降到"中"** —— **主进程不装 hook 是前置条件，已经完成了**。

### 3.3 P0-5 过滤要注意的四件事

| # | 注意点 | 为什么 | 怎么做 |
| --- | --- | --- | --- |
| **1** | **`is_path_hidden` 改前缀匹配** | 现在是 `g_hidden_paths.count(path)`（精确），`/data/data/com.nextvm.app/files` 不匹配 | 改成 `for (p : g_hidden_paths) if (strncmp(path, p.c_str(), p.size()) == 0) return true;` |
| **2** | **路径归一化** | guest 可能传 `/data/data/com.nextvm.app`、`/data/data/com.nextvm.app/`、`/data//data/...`（多个斜杠） | 匹配前先 `realpath` 或手动折叠 `//`；尾斜杠统一去掉 |
| **3** | **`readdir` 过滤要包装 `DIR*`** | glibc 的 `DIR*` 是私有结构，无法直接在 `readdir` 里改返回值 | 维护 `map<DIR*, filter_fn>`：`hooked_opendir` 打开后记录该 DIR* 对应的过滤规则，`hooked_readdir` 时跳过匹配项 |
| **4** | **不能藏 `/proc` 自己的东西** | `/proc/self/*` 有单独的 spoof 机制（`make_proc_spoof_fd`），不要和 `hidePath` 混 | `is_path_hidden` 里加 `if (strncmp(path, "/proc", 5) == 0) return false;` |

### 3.4 需要隐藏的路径清单（建议）

```
/data/data/com.nextvm.app
/data/user/0/com.nextvm.app
/data/app/~~*/com.nextvm.app-*
/sdcard/Android/data/com.nextvm.app
/storage/emulated/0/Android/data/com.nextvm.app
```

**注意**：`/data/local/tmp` **不能藏**（探针和导入都要用）

## 四、探针 + SelfCheckRunner 的测试内容更新

### 4.1 探针需要更新的项

| # | 现状 | 需要更新 | 原因 |
| --- | --- | --- | --- |
| 1 | `P16` 查 `/data/data/com.nextvm.app` 的 `stat` | **加了前缀匹配后，`/data/data/com.nextvm.app/files` 也应返回 ENOENT** | 新增对照项 |
| 2 | **无** `readdir` 检查 | **新增 `P31`**：`listFiles("/data/data")` 里有没有 `com.nextvm.app` | P0-5 的 `readdir` 过滤是否生效 |
| 3 | **无** 主进程检查 | **新增 `P32`**：`getApplication()` 的类名 | 验证 guest Application 绑定（`mark.via.BrowserApp` vs `NextVmApplication`） |
| 4 | `J01` 查 `getDataDir()` | 已够用 | — |
| 5 | **无** WebView renderer 检查 | **新增 `P33`**：`WebView` 能否创建 + 加载 `loadDataWithBaseURL("", "<h1>x</h1>")` 并检查 `onPageFinished` | **验证 renderer 是否可用**（不依赖 file://） |

### 4.2 SelfCheckRunner 需要检查的项（都是"容器自己"的，不依赖 guest）

| # | 检查 | 判据 |
| --- | --- | --- |
| 1 | **当前进程名** | 应为 `com.nextvm.app:selfcheck` |
| 2 | **`initNativeHooks` 是否装了** | `nativeHooksAvailable == true` |
| 3 | **`g_hidden_paths` 是否包含容器路径** | 需要 native 侧暴露一个查询 API |
| 4 | **双轨沙箱是否收敛** | `SandboxManager.virtualRoot == File(filesDir, "virtual")` |
| 5 | **`is_import_read_exempt` 是否已删** | 源码检查（或 native 侧暴露"有没有这个符号"） |
| 6 | **`app_virtual` 是否不存在** | `File(context.dataDir, "app_virtual").exists() == false` |
| 7 | **`files/virtual` 的 4 个子目录** | `apks`/`apps`/`data`/`snapshots` 都存在 |
| 8 | **签名版本** | `PackageManager.getPackageInfo(...).signatures` 的 SHA256（与 Secret 里的对比） |

**导出**：`<dataDir>/files/probe-out/selfcheck.json`（主进程能读，`COLLECT_OUT` 能收）

## 五、结论与建议顺序

| 顺 | 任务 | 原因 |
| --- | --- | --- |
| **1** | **SelfCheckRunner 用 `:selfcheck` 进程 + 8 项检查 + 导出** | **P0-5 的前置**（没有自检就不知道过滤是否生效） |
| **2** | **探针加 `P31`/`P32`/`P33`** | 为 P0-5 和 Via 提供判据 |
| **3** | **P0-4/P0-5 在分支开发** | 主线保持可用 |
| 4 | `mAudioService` 版本兼容 | 独立 |
| 5 | 查 Via 主页真因（需"不被打断的启动"） | 依赖探针 `P33` |

**核心判断**：
> **主进程不 hook 已经把 P0-5 最大的风险（把容器自己搞坏）消掉了。**
> **现在缺的是"怎么知道过滤生效了" —— 所以 SelfCheckRunner 要先行。**
