# Guest 的路径请求分级，与宿主的处理策略矩阵

- 调查日期：2026-11-21
- 回答的问题：**guest 会以哪些"等级"发起路径读取请求？宿主分别怎么处理？**
- 配套：`03-标准路径与沙箱文件系统.md`（为什么需要标准路径 / 路径视图层设计）、`05-从Espresso与测试框架借鉴的设计模式.md`（root+相对路径模型）

---

## 1. 分级模型：按"宿主还能不能看见"分级

| 等级 | 请求来源 | 宿主可见性 | 可控性 |
| --- | --- | --- | --- |
| **L0** | Java 公开 API（`Context` / `ApplicationInfo` / `PackageManager`） | 完全可见（我们就是返回值） | **完全可控** |
| **L1** | Java 层字面量路径（`new File("/data/data/x")`、`FileInputStream`） | 可见（最终落到 JNI） | **高**（靠 native 层兜住） |
| **L2** | libc 导入符号（`open/openat/stat/fopen/access`…） | 可见（GOT/PLT 可 patch） | **高**（目标模块内） |
| **L3** | 直接 syscall（`syscall(SYS_openat)`）、内联 `svc` | 部分可见 | **部分**（`syscall` 是 libc 导出符号可 patch；内联 `svc` 不可） |
| **L4** | `/proc` 与内核视图（`maps` / `fd` / `status` / `mountinfo`） | 部分可见 | **低**（只能合成，无法改内核） |
| **L5** | 系统服务（`StorageManager` / `MediaStore` / `DocumentsProvider` / `Settings`） | 可见（Binder 代理） | **中**（能改返回值，但要处理 attribution） |
| **L6** | 跨进程与外部观察者（其他 App、adb、`system_server`、`/data` 目录遍历） | 不可见 | **无** |

**关键结论：L0–L2 是"必须做且能做到"的战场；L3–L5 是"尽力而为"；L6 是"永远做不到"。**

---

## 2. 五种处理动作（宿主的全部选择）

| 动作 | 含义 | 典型用途 |
| --- | --- | --- |
| **PASS** | 放行原路径，不做任何改写 | 系统库 `/system`、`/apex`；已映射过的真实沙箱路径 |
| **MAP** | 前缀映射到沙箱真实路径后执行 | 虚拟路径的读写、SQLite、`dlopen` |
| **EMULATE** | 返回合成结果（不落到真实文件） | `getFilesDir()` 返回值、`/proc/self/fd/N`、虚拟 sdcard 根 |
| **DENY** | 返回错误码，保持"不存在/无权限"语义 | 访问其他包私有目录、越界路径 |
| **DIAG** | 记录后放行（保守兜底） | 未识别路径——**这是泄露真实路径的主要通道，必须记录** |

> **原则：任何一层如果无法处理，都必须显式记成 `unverified`，绝不"看起来放行"。** 静默放行 = 真实路径泄露 = 被检测。

---

## 3. 逐级处理策略表

### L0 Java 公开 API（必须 100% 覆盖）

| 调用 | 动作 | 处理 |
| --- | --- | --- |
| `getDataDir()` | EMULATE | 返回虚拟根（方案 B1 = `/data/user/0/<guest>`；方案 A = 沙箱真实目录） |
| `getFilesDir()/getCacheDir()/getCodeCacheDir()/getNoBackupFilesDir()` | EMULATE | 由 `root + "/files"` 等相对段生成（**统一 resolver，不要每处硬编码**） |
| `getDatabasePath(name)` | EMULATE | `root + "/databases/" + name` |
| `getDir(name, mode)` | EMULATE | `root + "/app_" + name` |
| `getExternalFilesDir(type)/getExternalCacheDir()/getObbDir()/getExternalMediaDirs()` | EMULATE | 虚拟 sdcard 根下的对应子目录 |
| `getSharedPreferences(name, mode)` | PASS(经 resolver) | 走 `getDataDir()` 推导，无需单独处理 |
| `ApplicationInfo.dataDir/sourceDir/publicSourceDir/splitSourceDirs/nativeLibraryDir` | EMULATE | 与上面同一套值；APK 与 lib 指向沙箱真实文件（必须真实可读、只读） |
| `PackageManager.getApplicationInfo()/getPackageInfo()/getInstalledPackages()` | EMULATE | 返回虚拟化后的 `ApplicationInfo` |

`getExternalStorageDirectory()` / `getExternalStoragePublicDirectory()` 属**必须处理**项：它返回真实 `/storage/emulated/0`，若不虚拟化，guest 会直接写真实外部存储（既污染设备又暴露）。

### L1 Java 字面量路径（必须靠 L2 兜住）

典型写法：

```java
new File("/data/data/" + pkg + "/files/cache")
new FileInputStream("/data/user/0/" + pkg + "/shared_prefs/x.xml")
```

- **L0 对它无效**（它没经过 Context）；
- 它会落到 `java.io` → JNI → **L2 的 `open/stat`**，所以在 L2 做前缀映射即可救；
- 但 `File.exists()` / `canRead()` / `length()` / `listFiles()` 分别落到 `stat` / `access` / `stat` / `opendir+readdir` ⇒ **这四个符号必须一起覆盖**，只做 `open` 会出现"能读写但 `exists()` 为 false"的诡异现象。

### L2 libc 导入符号（主战场）

**P0 符号集（12 个，覆盖 95% 常规访问）**：

```
open  open64  openat  fopen  stat  lstat  fstatat
access  faccessat  readlink  readlinkat  opendir
```

**P1 补充（写与目录操作，缺了会出现"能读不能写"）**：

```
mkdir  mkdirat  rmdir  unlink  unlinkat  rename  renameat  truncate  ftruncate
```

**三个必踩坑（复述自 `03` 文档 4.3）**：

1. **`dirfd` 相对路径**：`openat(dirfd, "sub/x")` 不含前缀 ⇒ 必须维护 `fd → 虚拟路径` 表，并随 `dup/dup2/dup3/fcntl(F_DUPFD)/close` 同步；
2. **`/proc/self/fd/N` 的 `readlink`**：只要打开过虚拟文件就会泄露真实路径 ⇒ 必须查表返回虚拟路径；
3. **只拦读不拦写**：`mkdir/rename/unlink` 不映射会导致"建目录失败"或"删到真实目录"。

### L3 直接 syscall

| 形态 | 能否处理 | 处理策略 |
| --- | --- | --- |
| `libc` 导出的 `syscall(SYS_openat, ...)` | ✅ 可 patch（`syscall` 本身是导出符号） | 解析 `SYS_*` 号，对 `openat/statx/readlinkat` 走同一映射 |
| 内联 `svc` 汇编（加固壳、反调试 SDK 常见） | ❌ 不可 | **DIAG + 如实标 `unverified`**，不假装能处理 |

### L4 `/proc` 与内核视图

| 请求 | 动作 | 说明 | 优先级 |
| --- | --- | --- | --- |
| `readlink /proc/self/fd/N` | EMULATE | 查 fd 表；**不做就前功尽弃** | **P0** |
| `read /proc/self/cmdline` | EMULATE | 让进程名是 guest | P1 |
| `read /proc/self/status`（Name/Uid） | EMULATE | 与 L0 的 UID 策略保持一致 | P1 |
| `read /proc/self/maps` | EMULATE | 过滤宿主 `base.apk`、hook 库名 | **P2（先不做）** |
| `read /proc/self/mountinfo` | EMULATE | 同上 | P2 |
| 其他 `/proc/*` | PASS + DIAG | 内核态无法改 | — |

### L5 系统服务

| 服务 | 动作 | 备注 |
| --- | --- | --- |
| `Context.getExternalFilesDirs()` 等已由 L0 处理 | — | — |
| `StorageManager.getStorageVolumes()` | PASS | 返回真实卷，通常无害 |
| `MediaStore` 查询/插入 | PASS（必要时 DENY 写入） | 写入真实媒体库会污染设备，建议 DENY + 诊断 |
| `DocumentsProvider` / `SAF` | PASS | 用户显式选择文件，不应拦截 |
| `Settings.Secure/Global` | PASS + 局部 EMULATE | `android_id` 等身份类需虚拟化 |
| `DownloadManager` / `JobScheduler` 的路径参数 | EMULATE | 路径需映射到沙箱，否则下载落真实外部存储 |

### L6 永不可控（写进 PRD 边界）

- 其他 App / `adb` / `system_server` 观察到的仍是宿主；
- `/data/user/0/<guest>` 在真实文件系统中**不存在**；
- 任何"外部设备/服务端"对路径的校验都无法欺骗。

## 4. 三条硬规则（比符号集合更重要）

### 4.1 先规范化，再映射，还要做边界检查

guest 可以构造逃逸路径：

```
/data/user/0/<guest>/../../../../<host>/files/...
```

**必须在映射前做词法规范化（折叠 `.` `..`），映射后再检查结果是否仍位于沙箱根之内**，否则就是一个沙箱逃逸漏洞。

### 4.2 映射必须幂等

```
虚拟前缀 → 沙箱真实前缀 → （不得再次进入映射）
```

实现方式：映射前先判断"是否已以沙箱根开头"，是则直接 PASS。**否则会出现无限递归或路径越长越离谱。**

### 4.3 错误码决定"像不像正常设备"

| 场景 | 应返回 | 原因 |
| --- | --- | --- |
| 虚拟路径的父目录不存在（首次运行） | **ENOENT** | 应用会当"首次运行"自动建目录，行为自然 |
| 访问其他包私有目录 | **ENOENT** | 保持"该包不存在"语义；返回 EACCES 反而暴露"这里有东西但你没权限" |
| 越界逃逸路径 | **ENOENT** | 同上 |
| 系统路径 | 正常返回 | — |

> 这是一个容易被忽略但影响很大的细节：**EACCES 会让开发者/风控意识到"沙箱存在"，ENOENT 只是"没有"。**

## 5. 处理决策树（实现时照抄即可）

```
收到路径请求 p
├─ 规范化 p → p'（折叠 . / ..）
├─ p' 以沙箱根开头？           → PASS（幂等出口）
├─ p' 命中虚拟前缀表？
│    ├─ 规范化后仍落在沙箱根内  → MAP → 执行
│    └─ 越界                    → DENY(ENOENT) + DIAG
├─ p' 是 /proc/self/fd/<n>     → EMULATE（查 fd 表；miss → PASS + DIAG）
├─ p' 是 /proc/self/{cmdline,status,maps,mountinfo} → EMULATE 或 PASS（按能力集）
├─ p' 是 /data/{data,user/N}/<other_pkg> → DENY(ENOENT)
├─ p' 是 /sdcard 或 /storage/emulated/0/Android/data/<guest> → MAP（虚拟 sdcard）
├─ p' 是 /system /apex /vendor /data/dalvik-cache → PASS
└─ 其他                        → DIAG + PASS（记录为"未识别路径"）
```

## 6. 三种方案下的策略差异（只有一列会变）

| 级别 | **A 真路径** | **B2 半虚** | **B1 全虚（推荐默认）** |
| --- | --- | --- | --- |
| L0 | EMULATE（沙箱路径） | EMULATE（半虚路径） | EMULATE（`/data/user/0/<guest>`） |
| L1 字面量 | ❌ 必然失败 | ❌ 必然失败 | ✅ 由 L2 救 |
| L2 符号集 | 仅虚拟 sdcard | 仅虚拟 sdcard | **全套 P0/P1** |
| L3 syscall | 不需要 | 不需要 | 能拦 libc.syscall |
| L4 `/proc` | P1（fd 表） | P1（fd 表） | **P0（fd 表）** |

> 关键：**L0 的实现是三套方案共享的**（都用 root+相对路径生成），切换成本只在"root 字符串 + 是否启用 L2 表"。这就是 `05` 文档第 6 节的建议为什么重要。

---

## 7. 明确建议（本次调查的结论）

1. **默认走 B1（虚拟标准路径 `/data/user/0/<guest>`），并把方案 A 保留为可切开关。**
   理由：硬编码 `/data/data/<pkg>` 的 SDK 存量太大，A/B2 无法救；而 B1 的增量只有"12 个 libc 符号 + 一张 fd 表"，且只 patch 目标模块，风险可控。
2. **Context 层必须用「root + 相对路径」resolver 实现**，禁止散落硬编码沙箱路径——这样 A/B1 切换只改一个字符串。
3. **符号覆盖面按 P0（12 个）→ P1（写操作）→ L4 的 fd 表**，三项缺一不可；`/proc/self/maps` 合成放 P2，先不做。
4. **未知请求一律 DIAG + PASS**，并把"未识别路径"做成可观测指标——它是检测与兼容问题的第一手线索。
5. **其他包与越界路径返回 ENOENT，不返回 EACCES。**
6. **不做内联 `svc` 的处理**，如实标 `unverified`；这属于立项时就写进 PRD 的能力边界。

## 8. 验收矩阵（每个等级至少一个探针用例）

| 级别 | 探针用例 | 期望 |
| --- | --- | --- |
| L0 | `getFilesDir()/getDataDir()/getDatabasePath()` 前缀 + `exists()` | 前缀 = 虚拟根，`exists()` = true |
| L0 | `getExternalFilesDir(null)` 写入后 `getExternalStorageDirectory()` 下不可见 | 无污染 |
| L1 | `new File("/data/data/"+pkg+"/files/x").mkdirs()` + 写入读回 | 成功 |
| L1 | `File("/data/data/"+pkg).listFiles()` | 返回沙箱内容 |
| L2 | native `fopen("/data/data/"+pkg+"/n.tmp","w")` | 成功 |
| L2 | `openat(dirfd, "sub/x", O_CREAT)` 相对路径 | 成功（验证 fd 表） |
| L2 | `rename` / `unlink` / `mkdir` / `rmdir` | 全部成功且不越界 |
| L3 | `syscall(SYS_openat, ...)` | 期望 `verified`（libc 导出）；内联 `svc` 期望 `unverified` |
| L4 | `readlink("/proc/self/fd/N")` | 返回虚拟路径，**不含沙箱真实前缀** |
| L4 | `read("/proc/self/maps")` | 当前允许含真实路径（P2 前如实记录） |
| L6 | 宿主进程读取 `/data/user/0/<guest>` | 不存在（预期，不算失败） |

---

## 9. 一句话结论

> **guest 的路径请求分六级，宿主真正能赢的是前两级半（L0/L1/L2），第四级只能"合成"（L4 的 fd 表），第六级永远赢不了。**
> 处理策略归为五个动作：**PASS / MAP / EMULATE / DENY / DIAG**；其中**映射必须幂等、必须先规范化并做越界检查、错误码优先用 ENOENT**。
> 默认策略选择 **B1 + P0 符号集 + fd 表**，把"未识别路径"当作最重要的诊断信号，而不是当作放行。
