## 零点五、技术路线与工具对比（2026-11-23 调研结论）

> 这一节是后面所有任务的**选型依据**。当有人说"改成 inline hook 就好了"时，先看这张表。

### 0.5.1 四条技术路线的本质区别

来源：[Gracker/android-internals-wiki](https://github.com/Gracker/android-internals-wiki/blob/master/src/part5-app/ch20-stability/12-native-hook-technology-selection-implementation.md) 的原文论断：

> **PLT/GOT Hook** 改写的是：某个 ELF **调用方的导入重定位槽**
> 覆盖：该调用方经动态链接发出的外部调用
> **不覆盖：内部直接调用、内联、直接系统调用、已保存的函数指针**
>
> **同样是拦 `malloc`：**
> **修改 `libfoo.so` 中 `malloc` 的导入槽 → 只影响 `libfoo.so`**
> **修改 `libc.so` 中 `malloc` → 影响所有调用者**

| # | 路线 | 改什么 | 覆盖范围 | 不覆盖 | 波及范围 | 过滤难度 | 风险 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| **R0** | **现有 GOT hook** | 各库的导入槽 | 已被 patch 的库 | **运行期新加载的库**、`dlsym` 后调用、内部调用、直接 syscall | **小**（只改目标库的 GOT） | 🟢 **无**（`is_app_lib` 已过滤） | 低 |
| **R1** | **patch `libnativeloader`**（方向 A） | 系统库的 `android_dlopen_ext` GOT | 所有 `System.loadLibrary` 加载的库 | 同上（仍依赖 GOT） | **中**（影响所有 so 加载路径） | 🟢 低（库级过滤） | 中（ART 核心组件） |
| **R2** | **自研 inline hook `libc`** | `libc` 的**函数体** | **所有调用者**（含新加载库、`dlsym` 后调用、内部调用） | 内联展开、直接 syscall、已保存的函数指针 | **大**（`libc` 被 ART 重度使用） | 🔴 **高**（每次调用要 `dladdr(caller)` 判断） | **中高**（崩是整个进程） |
| **R3** | **引入 shadowhook，只 inline hook `android_dlopen_ext`** | 一个函数的指令体 | 所有 so 加载（**只加回调，不改行为**） | — | **小**（1 个函数） | 🟢 无 | 中（依赖第三方） |

**读法**：
- **R0 是现状**，P28 暴露的 L6 就是 R0 的天花板
- **R1 是"修一条链"** —— 正确但脆，链上任一环变了就失效
- **R2 是"修根"** —— 技术最优，但波及 ART
- **R3 是"用最小代价补时机缺口"** —— 不替代 GOT hook，只补"库刚加载完"这个时机

### 0.5.2 检测面 × 路线覆盖矩阵

OWASP MASWE-0052 点名的四类检测面，各路线能覆盖哪些：

| 检测面 | 现有 R0 | R1 | R2 | R3 | 备注 |
| --- | --- | --- | --- | --- | --- |
| **data directory**（`getDataDir`） | ✅ Java 层已覆盖 | — | — | — | 与路线无关 |
| **package structure**（`getPackageInfo(容器)`） | ✅ Java 层可覆盖 | — | — | — | **`P13` 待做** |
| **process path**（`/proc/self/cmdline`，native） | ❌ | ✅ | ✅ | ✅ | 探针的 native 层现在读真实值 |
| **known frameworks**（`/proc/self/maps`） | ❌ | ✅（路径重定向） | ✅ | ✅ | **内容伪造是另一件事**（需 memfd） |

**关键区分**：
> **路线解决的是"路径能不能被重定向"，不解决"内容要不要伪造"。**
> `/proc/self/maps` 里的容器痕迹，即使路径重定向生效，**内容仍是真实的 maps**（除非用 memfd 伪造）。

### 0.5.3 波及范围：三条路线的"爆炸半径"

| 路线 | 改动点 | 影响谁 | 出错的后果 |
| --- | --- | --- | --- |
| **R1** | `libnativeloader.so` 的 1 个 GOT 项 | 所有 `System.loadLibrary` 调用 | 库加载失败 → guest 起不来 |
| **R2** | `libc.so` 的 `open`/`openat`/`fopen`/`stat` 函数体 | **整个进程**（含 ART 加载 oat/vdex） | **进程崩溃**（不是单个功能坏） |
| **R3** | `android_dlopen_ext` 的指令体 | 所有 so 加载 | 库加载失败（但只影响我们自己加的回调） |

**这就是为什么推荐 R3 而不是 R2**：
**R2 的爆炸半径是整个进程，R3 只是"我们自己的回调出问题"。**

### 0.5.4 过滤难度：为什么 R2 最贵

**R0/R1 的过滤**（库级）：
```cpp
if (!is_app_lib(lib_name)) return;   // 加载时判断一次，之后零开销
```

**R2 的过滤**（调用级）：
```cpp
// 每次 open 都要判断调用方是谁
static int hooked_open(const char* path, int flags, ...) {
    void* caller = __builtin_return_address(0);
    Dl_info info;
    if (!dladdr(caller, &info) || !is_guest_library(info.dli_fname)) {
        return real_open(path, flags, ...);   // ART/linker → 直通
    }
    // 只有 guest 的库才重定向
}
```

| 项 | R0/R1 | R2 |
| --- | --- | --- |
| 过滤时机 | **加载时一次** | **每次调用** |
| 过滤依据 | 库名（字符串匹配） | `dladdr(caller)` + 库名匹配 |
| 单次开销 | 0 | 数十纳秒（`dladdr` 要查 `link_map`） |
| 漏判后果 | 该库不 patch | **误重定向 ART 的调用 → 崩** |
| 误杀后果 | — | **同上，更严重** |

**R2 必须做到**：ART 的每一次 `open` 都走直通路径。漏一次就可能崩。

### 0.5.5 hook 流程对比

#### R0（现状）：两阶段，但第二阶段断链

```
VirtualEngine.initialize()   [容器主进程]
  └─ nativeInit()
       ├─ dl_iterate_phdr → 遍历已加载库
       │    └─ patch_library_got(每个 app 库)     ← 阶段 1：有效
       └─ 之后靠 hooked_dlopen 补 patch
            └─ 但 System.loadLibrary 的 dlopen 调用方是 libnativeloader.so
                 └─ 它没被 patch → patch_newly_loaded_libraries 不执行  ← 阶段 2：断链
```

**结果**：`libprobe.so`（`System.loadLibrary("probe")`）的 GOT 完全没被改 → `P28` 能写真实文件。

#### R1：补上断链的那一环

```
nativeInit()
  └─ dl_iterate_phdr → 遍历已加载库
       ├─ patch_library_got(app 库)
       └─ **patch_library_got(libnativeloader.so)**        ← 新增
            └─ 它的 android_dlopen_ext GOT 指向 hooked_android_dlopen_ext
                 └─ 之后所有 System.loadLibrary → hooked_android_dlopen_ext
                      └─ patch_newly_loaded_libraries()     ← 链通了
```

**风险点**：`libnativeloader` 必须在 `nativeInit` 时**已加载**。若不在，需额外处理（`dlopen` 自己加载它？）。

#### R3：用 inline hook 抢"加载完成"的时机

```
shadowhook 初始化时
  └─ inline hook android_dlopen_ext（一个函数）
       └─ 注册 .init_array 前后的回调
            └─ 库加载完成 → 回调里调现有的 patch_library_got(那个库)
```

**与 R1 的区别**：
- **R1 依赖 GOT 链**（如果 `libnativeloader` 之后又被重新加载，链就断）
- **R3 改的是函数体**（不管谁调用、什么时候加载，都拦得到）

#### R2：改 `libc` 函数体

```
nativeInit()
  └─ mprotect(libc.text, PROT_WRITE|PROT_EXEC)
       └─ inline hook open/openat/fopen/stat 的函数体
            └─ 每次调用：
                 ├─ dladdr(caller) 判断是不是 guest 的库
                 ├─ 是 → redirect_path() → real_open(重定向后的路径)
                 └─ 否 → real_open(原路径)          ← ART/linker 走这里
```

**流程更简单，但每一步都更危险。**

### 0.5.6 选型结论

| 场景 | 选哪条 |
| --- | --- |
| **只修 L6（新加载库拿不到 patch）** | **R3**（shadowhook 只 hook `android_dlopen_ext`）—— 爆炸半径最小 |
| **不想引入第三方** | **R1**（patch `libnativeloader`，~20 行）—— 但要知道它脆 |
| **要对付加固壳（`dlsym` 后调用、内部调用）** | **R2**（inline hook `libc`）—— 唯一选择，但要接受"崩是整个进程" |
| **现在就该做的** | **都不是** —— 先做 `P13`/`P16`（Java 层 + 路径隐藏），见 §零点六 |

### 0.5.7 为什么"现在不该做 R1/R2/R3"

| 理由 | 说明 |
| --- | --- |
| **收益暂时配不上风险** | 修好 L6 能让探针的 native 项准确，但**对"能不能跑起来 guest"没有帮助** |
| **有更便宜的收益** | `P13`（容器包不可见）、`P16`（容器 dataDir 不可 stat）**各半天**，直接消灭 OWASP 点名的检测面 |
| **R2 有前置未知** | `mprotect` 是否被 `execmem` 拦，**还没验证**（需探针加一项） |
| **R3 需要评估依赖** | shadowhook 引入 200–400 KB + 第三方维护风险 |

**所以顺序是**：`P13`/`P16` → 探针加 `mprotect` 验证项 → 再决定 R1/R2/R3。

| **验证** | 探针 `P13` 从 `visible` 变 `hidden`；容器自身功能不坏（能装 guest、能启动） |

### 0.6.3 P0-5：容器 dataDir 不可访问（1 天，与 P0-4 同批做）

| 项 | 内容 |
| --- | --- |
| **目标** | guest 对 `/data/user/0/com.nextvm.app`、`/data/data/com.nextvm.app` 的 `stat`/`access`/`open` 返回 `ENOENT`，且 `opendir("/data/data")` 列表里没有它 |
| **改哪里** | `native-hook.cpp` 的 `g_hidden_paths` + `hooked_opendir` |
| **必须改三处** | ①`is_path_hidden` 改成**前缀匹配**（现在是精确匹配，连子路径都不隐藏）②加容器两个前缀 ③**`readdir` 过滤** |
| **代码量** | ~80 行（前缀匹配 10 行 + `DIR*` 包装 60 行 + 调用 10 行） |
| **难点** | ①**不能藏掉容器自己需要的**（容器主进程要读自己的 dataDir）→ 按进程判断 ②`readdir` 过滤要维护 `fd → 过滤器` 的映射 |
| **验证** | 探针 `P16` 从 `exists=true` 变 `exists=false`；再 `opendir("/data/data")` 确认列表里没有容器 |

> **只做 `stat` 不做 `readdir`，等于主动暴露矛盾** —— guest 用目录遍历就能发现容器。

### 0.6.4 探针 P29：验证 `mprotect` 可行性（0.5 天，前置调查）

| 项 | 内容 |
| --- | --- |
| **目标** | 在 guest 进程里对 `libc.so` 的 `.text` 做 `mprotect(PROT_READ\|PROT_WRITE)`，看返回值 |

| **判据** | 成功 → R2 可行；`EPERM` → R2 只能靠 memfd 方案 |
| **风险** | 低（只改一页，立刻恢复） |

## 一、P0-1：`DiagnosticsSink` 接口 + NoOp

### 1.0 它到底是什么（一句话）

> **一个"测试挂钩"，不是日志系统。**
>
> 只有一个接口 + 一个 NoOp 实现。作用是让 **debug 模块能把实现插进来**，
> 让"容器认为自己做了什么"变成**可被程序读取的结构化数据**，而 release 里保持零开销。

**它不做的事**：不采集数据（采集仍由 `GuestBreadcrumb`/`StateProbe` 做）、
不格式化、不落盘、不轮转、不判断对错。

**类比**：像 JUnit 的 `TestWatcher` ——不产生日志，只提供"开始/结束/失败"的回调点。

### 1.0.1 为什么现有调试设施不够用

| 现有设施 | 输出到 | 谁能读 |
| --- | --- | --- |
| `GuestBreadcrumb`（199 处埋点） | logcat + `breadcrumb-<pid>.log` | **人**（或 grep） |
| `StateProbe` | 自己的 log 文件 | 人 |
| `WebViewWatch` | `webviewwatch-<pid>.log` | 人 |
| `WebViewWarmup` | `webviewwarm-<pid>.log` | 人 |

**全是"写给人看的文本"，没有"给程序读的结构"。**

后果：`SelfCheckRunner` 想把 6 项自检结果输出成 JSON 时**没有正当出口**——
要么写死文件路径（耦合），要么写 logcat（回到"看日志反推"，正是要避免的）。

### 1.0.2 与后续任务的依赖关系

```
P0-1 DiagnosticsSink（60 行）
  │
  ├──→ P1-1 SelfCheckRunner
  │      SelfCheckRunner 在 :core:diagnostics 里，
  │      通过 Diagnostics.sink 把 6 项结果送回来，
  │      主流程再写进 probe-out/selfcheck.json（P0-2 的目录）
  │
  ├──→ P2-1 收敛双轨路径：重构前加断言 sandbox.pathShape，重构后必须仍绿
  ├──→ P2-2 拆超大文件：每拆一个文件跑一次自检
  └──→ P2-3 打破双向耦合：用自检兜底，确认重构没破坏运行

P1-2 HostReadPolicy ── 不依赖本桩（纯函数单测，直接 JUnit）
P1-3 WebView ───────── 间接依赖（需要一处报告"file:// 拦截是否生效"）
```

**关系一句话**：**P0-1 是"插槽"，P0-2 是"管道"**，两者一起才让 P1-1 的 `SelfCheckRunner` 能存在；
P2 的所有重构都靠它做回归判据。

### 1.1 目标

让「容器认为自己做了什么」可以被**断言**，而不是靠外部 logcat 反推。

### 1.2 为什么需要这一层（而不是直接用 `GuestBreadcrumb`）

| 现状 | 问题 |
| --- | --- |
| `GuestBreadcrumb` 199 处埋点 | 只**采集**，而且只在故障时被读 |
| `StateProbe` | 同上 |
| 无统一出口 | 测试无从"问容器：沙箱建好了吗" |

### 1.3 设计

**新增文件**：`core/virtualization/src/main/java/com/nextvm/core/virtualization/diag/DiagnosticsSink.kt`（约 60 行）

```kotlin
interface DiagnosticsSink {
    fun onEvent(phase: String, detail: String)
    fun onSnapshot(name: String, value: String)
}

object Diagnostics {
    @Volatile
    var sink: DiagnosticsSink = NoOp
        private set

    fun install(s: DiagnosticsSink) { sink = s }
    fun reset() { sink = NoOp }

    inline fun event(phase: String, detail: () -> String) {
        val s = sink
        if (s !== NoOp) s.onEvent(phase, detail())
    }

    inline fun snapshot(name: String, value: () -> String) {
        val s = sink
        if (s !== NoOp) s.onSnapshot(name, value())
    }

    val isInstalled: Boolean get() = sink !== NoOp

    private object NoOp : DiagnosticsSink {
        override fun onEvent(phase: String, detail: String) = Unit
        override fun onSnapshot(name: String, value: String) = Unit
    }
}
```

### 1.4 关键约束

| 约束 | 理由 |
| --- | --- |
| **`inline` + `s !== NoOp` 早退** | release 构建里 lambda 不会被执行，**零开销** |
| **`@Volatile` 但无锁** | 只在启动时写一次，之后全是读 |
| **不改现有 199 处 `GuestBreadcrumb` 调用** | 桥接由 P1-1 的 `:core:diagnostics` 做 |
| **`NoOp` 是 `private object`** | 外部无法构造第二个，`!==` 判断可靠 |

### 1.5 验证

```bash
# 编译通过
# 运行时确认默认是 NoOp
adb logcat -d -s Diagnostics | Select-String "installed=false"
```

## 二、P0-2：`probe-out` + CmdReceiver 三命令

### 2.1 目标

让容器把 guest 沙箱里的探针输出**收集到自己的私有目录**，并能**通过命令导出**，不依赖 `run-as` 猜路径。

### 2.2 目录结构

```
/data/user/0/com.nextvm.app/files/probe-out/
├── <instanceId>/
│   ├── probe-report.json
│   ├── probe-early.json
│   ├── meta.txt            ← 收集时间 / 源路径 / 大小 / sha256
│   └── selfcheck.json      ← P1-1 之后由 SelfCheckRunner 写
└── index.json
```

**为什么放 `files/probe-out/` 而不是 `files/virtual/` 内**：

- `files/virtual/` 是沙箱根，参与 guest 路径翻译
- `probe-out/` 与它平级 → **guest 看不到，不增加暴露面**

### 2.3 三条命令

| 命令 | 参数 | 行为 | 日志前缀 |
| --- | --- | --- | --- |
| `COLLECT_OUT` | 无 / `--es pkg` | 遍历 `files/virtual/data/<instance>/files/`，白名单文件复制到 `probe-out/<instance>/` | `COLLECT instance=... file=... bytes=...` |
| `LIST_OUT` | 无 | 列 `probe-out/` 全部文件 | `OUT <instance> <name> <bytes> sha=<前8位>` |
| `CAT_OUT` | `--es instance X --es name Y` | 分块 base64 打到 logcat | `OUTCHUNK v1 part i/n <b64>` |

### 2.4 `CAT_OUT` 的分块协议

```
CmdReceiver: OUTCHUNK v1 part 1/10 <base64>
CmdReceiver: OUTCHUNK v1 part 2/10 <base64>
...
CmdReceiver: OUTCHUNK v1 end instance=<id> name=<name> parts=10 bytes=12722 sha=<sha256>
```

**与探针的 `REPORT v1 part` 同构**，`extract-report.py` 的分块逻辑可以直接复用。

**分块大小**：每块原始 6KB → base64 后 8KB（logcat 单行上限约 4KB，需要再切；实际按 **3KB 原始 / 4KB base64** 取，留余量）。

### 2.5 为什么两段参数而不是一段路径

| 一段路径 `--es name <instance>/<file>` | 两段 `--es instance X --es name Y` |
| --- | --- |
| 要解析 `/` | 不解析 |
| 校验复杂（两段都要防 `..`） | 各自独立校验 |
| shell 转义易错 | 无斜杠，无转义问题 |

**校验规则**：

```kotlin
private val INSTANCE_RE = Regex("[A-Za-z0-9._-]{1,128}")
private val NAME_WHITELIST = setOf("probe-report.json", "probe-early.json", "meta.txt", "selfcheck.json")

fun validInstance(s: String?) = s != null && INSTANCE_RE.matches(s) && !s.contains("..")
fun validName(s: String?) = s != null && NS_NAME_WHITELIST.contains(s)
```

### 2.6 实现位置

| 文件 | 改动 |
| --- | --- |
| `core/sandbox/.../SandboxManager.kt` | 新增 `collectProbeOutput(): List<CollectedFile>` + 私有 `writeMeta` / `writeIndex` |
| `app/.../CmdReceiver.kt` | 新增 3 个 action 分支 + `catOut()` 分块函数 |

**`collectProbeOutput` 的遍历根**：`File(context.filesDir, "virtual/data")`（即 `files/virtual/data`），**不是** `SandboxManager.virtualRoot`（那是 `app_virtual`，见 `记录-双轨沙箱路径.md`）。

### 2.7 安全边界

| 约束 | 说明 |
| --- | --- |
| 只读 guest 沙箱的 `files/` | 不碰 `databases`/`shared_prefs` |
| 只复制白名单文件名 | 不做通配 |
| `CAT_OUT` 的 instance/name 校验 | 见 2.5 |

## 二点五、P0-3：进程分割 + 删除路径豁免（**新增，优先于 P1-1**）

### 2.5.1 为什么插进来

实测（`records/记录-导入通道真实约束.md`）：

| 检查 | 结果 |
| --- | --- |
| `run-as com.nextvm.app cat /sdcard/Download/x.apk` | **Permission denied**（DAC 660，非本人） |
| `run-as com.nextvm.app cat /data/local/tmp/x.apk` | **成功** |
| `appops get com.nextvm.app MANAGE_EXTERNAL_STORAGE` | **default**（未授权） |

**结论**：p18 的 `/sdcard/Download` 豁免**从根上无效** —— 它只作用于 `redirect_path`，
而 DAC 在它之前就拒了。**继续加豁免是在错误的层做修补。**

### 2.5.2 设计：让主进程不装 hook

```kotlin
// NativeHookBridge.initNativeHooks 开头
val procName = android.app.Application.getProcessName()
val pkg = (context ?: appContext)?.packageName
if (pkg != null && procName == pkg) {
    Timber.tag(TAG).i("initNativeHooks skipped: container main process")
    initialized = true
    return false
}
```

**依据**：
- `CmdReceiver` 在主进程（manifest 无 `android:process`）
- guest 在 `com.nextvm.app:p0`（改名为 guest 包名）
- `libc.so` 属系统库，`NS_HOOK_SYSTEM_LIBS=0` → 主进程的 `open` 本来就不被重定向
- `run-as` 子进程（不装 hook）能读 `/data/local/tmp` 就是证明

### 2.5.3 收益

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 装包路径 | 依赖 `is_import_read_exempt`（6 个函数） | 主进程直接读真实路径，**不需要豁免** |
| `/sdcard/Download` | 豁免无效（DAC 拒） | 仍读不到（DAC），但**不再假装能读** |
| `/data/local/tmp` | 需要豁免 | **不需要**（644） |
| 攻击面 | guest 可读三个前缀 | **只剩 DAC 允许的** |

### 2.5.4 四阶段

| 阶段 | 内容 | 风险 |
| --- | --- | --- |
| 1 | 验证 `CmdReceiver` 只在主进程；`AntiDetectionEngine.hidePath` 等调用方是否跨进程 | 低（只读） |
| 2 | `initNativeHooks` 加进程判断，主进程 return | 中（主进程少了 hook，若有功能依赖会暴露） |
| 3 | **删除 `is_import_read_exempt` 及 6 处调用** | 中（先确认阶段 2 生效） |
| 4 | 导入通道固定 `/data/local/tmp`，文档移除 `/sdcard/Download` | 低 |

### 2.5.5 验收

```powershell

# 2) 装包走 /data/local/tmp 成功，且日志里没有 "import exempt"
```

## 三、P1-2：`HostReadPolicy` + Robolectric 单测

### 3.1 目标

把「宿主代读到底允不允许某条路径」变成**可自动验证的断言**。

**为什么先做这个**：纯函数、零依赖、是安全边界——在没有测试基础设施时最容易落地。

### 3.2 白名单

```
✅ guest 自己的沙箱
   /data/user/0/com.nextvm.app/files/virtual/data/<instanceId>/**
   /data/user/0/com.nextvm.app/files/virtual/apks/<instanceId>.apk

✅ NEXTVM 被授权读取的外部区域
   /storage/emulated/0/Android/data/com.nextvm.app/**
   /sdcard/Android/data/com.nextvm.app/**     （规范化后同上）

❌ 其他一律拒绝
   /data/data/<其他应用>
   /data/user/0/<其他应用>
   /system/**  /vendor/**  /apex/**
   其他 guest 的沙箱
```

### 3.3 四条硬约束

```kotlin
fun resolve(instanceId: String, requested: String): String? {
    // ① canonicalPath 规范化：防 ../ 逃逸、解析软链
    val real = runCatching { File(requested).canonicalPath }.getOrNull() ?: return null

    // ② 前缀后必须加分隔符：防 /x/data/abc 匹配 /x/data/abcd
    val own = File(sandboxDataDir(instanceId)).canonicalPath + File.separator
    if (real.startsWith(own)) return real

    // ③ 容器外部区域（同一份常量，与 p18 导入豁免共享）
    for (allowed in HOST_ALLOWED) {
        val p = allowed.canonicalPath + File.separator
        if (real.startsWith(p)) return real
    }

    // ④ 其他一律 null
    return null
}
```

| JUnit | 4.13.2 | Robolectric 4.x 的标准搭配 |

## 六、P2（长期，不阻塞 P0/P1）

### P2-1：收敛双轨沙箱路径（2 天，高风险）

**问题**：`SandboxManager` 用 `app_virtual/`，`VirtualEngine`/`PackageManagerProxy` 用 `files/virtual/`。

**为什么高风险**：`VirtualContext.getExternalFilesDir()` 现在走 `app_virtual/.../sdcard`，
直接改根会让 guest 的"外部存储"内容全部消失。

**步骤**：
1. 先做 P1-1 的 `sandbox.pathShape` 自检，把当前状态固化成断言
2. 写迁移：`app_virtual/data/<id>/sdcard/**` → `files/virtual/data/<id>/sdcard/**`
3. 改 `provideSandboxManager` 的根
4. 用自检验证
5. 保留一个版本的回退开关

### P2-2：拆超大文件（3 天，中风险）

| 文件 | 现状 | 拆分方案 |
| --- | --- | --- |
| `native-hook.cpp` | 6,458 行 / 1 文件 | `path_redirect.cpp` / `hook_impl.cpp` / `proc_spoof.cpp` / `maps_snapshot.cpp` / `jni_bridge.cpp` |
| `SystemServiceProxyManager.kt` | 3,242 行 / 143 函数 | 按服务类型拆（Package/Activity/Window/Content…） |

**拆分原则**：纯机械移动，不改逻辑；每拆一个文件跑一次 P1-1 自检。

### P2-3：打破 `VirtualEngine` 双向耦合（2 天，中高风险）

**问题**：5 条虚线回指（`VirtualApplicationManager` / `ActivityThreadHook` / `NativeHookBridge` / `PackageManagerProxy` / `ActivityManagerProxy` 都反向依赖引擎）。

**方案**：抽 `EngineHost` 接口，管理器依赖接口而非 `VirtualEngine` 具体类。

**风险**：改动面广，必须有 P1-1 自检兜底。
