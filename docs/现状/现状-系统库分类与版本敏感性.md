- 数据来源：guest 进程（`mark.via`，pid 25078）的 `/proc/<pid>/maps`，去重后 **385 个 `.so`**。
- 用途：G3 库级白名单**不该"单库"也不该"全量"**，而应按"**稳定性 / 版本敏感性**"分类选取。

## 二、分类（按"能否安全 patch"）

### A. 基础 / 稳定 —— **G3 白名单首选**

| 族 | 代表 | 为什么稳 |
| --- | --- | --- |
| libc 家族 | `libc.so`、`libm.so`、`libdl.so`、`libdl_android.so` | ABI 十年稳定；`open/openat/stat` 的**实现者**（不是调用者） |
| 日志 | `liblog.so` | 接口稳定 |
| 工具 | `libbase.so`、`libutils.so`、`libcutils.so`、`libutilscallstack.so` | 接口稳定，跨版本变化小 |

**注意**：这些库多是"被调用方"，它们的 **PLT 里通常没有 `open`**（自己就是实现），
所以"patch 它们"往往等于无效操作 —— 需要先确认 PLT 里有目标符号。

### B. 中等稳定 —— **可用，但要逐库验证**

| 族 | 代表 | 风险 |
| --- | --- | --- |
| Framework 核心 | `libandroid_runtime.so` / `_lazy`、`libandroidfw.so` | 跨版本 API 有增删；`_lazy` 变体是 Android 12+ 新增 |
| Binder | `libbinder.so`、`libbinder_ndk.so`、`libbinderdebug.so` | 接口稳定但内部实现随版本变 |
| 加载器 | `libnativeloader.so` / `_lazy`、`libnativehelper.so` | **`_lazy` 变体是版本信号**（见 §四） |

### C. **版本敏感 —— 单独列表，默认不 patch**

| 族 | 数量 | 代表 | 为什么不稳 |
| --- | --- | --- | --- |
| **ART 运行时** | **21** | `libart.so`、`libjavacore.so`、`libopenjdk.so`、`libopenjdkjvm.so`、`libdexfile.so`、`libnativebridge.so`、`libprofile.so`、`libsigchain.so`、`libunwindstack.so`、`libperfetto_hprof.so` | 每个 Android 大版本都重写内部；`libjavacore` 的 PLT 只有 `open`（实测），但调用时机与语义随版本变 |
| **图形/渲染** | **16** | `libEGL.so`、`libGLESv2.so`、`libhwui.so`、`libminikin.so`、`libharfbuzz_ng.so`、`libvulkan.so`、`*_adreno.so`、`libllvm-glnext.so` | **已在 `lib_deny` 里硬排除**（历史两次崩溃）；且 Adreno 驱动随机型变 |
| **ICU/加密** | 9 | `/apex/com.android.i18n/*`（5）、`/apex/com.android.conscrypt/*`（4） | APEX 模块化，版本独立升级 |
| **Vendor/ROM 私有** | **49** | `/vendor/lib64/*`（含 `libadreno_utils.so` 等） | **跨机型完全不可移植**；内容随厂商 OTA 变 |

### D. 已排除（不进任何名单）

- 容器自身：`libnextvm-native.so`、`libprobe.so`（`/data/...`）
- `libart.so` / `libhwbinder` / `linker` / `vdso`（callback 层早期过滤）

### 结论：`lib_deny` 需要从 6 条扩到覆盖 40 个

**建议关键词（前缀/子串，覆盖全部 40 个）**：

```
libEGL, libGLES, eglSubDriver, libvulkan, vulkan., libllvm-glnext,
libhwui, libminikin, libharfbuzz, libgui.so, libui.so, libgui_,
libdrm, libgralloc, libgsl, libq3dtools, libOpenCL, libadreno,
libskia, librenderengine, libSurfaceFlinger, libpanglearmor,
libgpurenderengine, libgps_lightgbm
```

**为什么扩 deny 是纯收益**：这些库**不参与文件路径翻译**（图形栈不走 `open` 读路径），
patch 它们只会引入"GOT 被改写"的风险（历史两次崩溃就在这类库），**没有任何功能收益**。

**使用规则（建议）**：

| 场景 | 规则 |
| --- | --- |
| 生产白名单 | **只从 A/B 类里选**；C 类默认不 patch |
| 诊断/取证 | 允许 C 类（如 `openDiag` 全量），但必须登记"仅诊断" |
| 升级适配 | Android 大版本变更后，**重跑本摸底**，对比 385 个库的增删 |
| 打包分发 | `/vendor/*` 永不上白名单（机型相关） |

## 四、从这次摸底得到的两个**版本信号**（可用于自动检测）

| 信号 | 含义 |
| --- | --- |
| **`_lazy` 变体**（`libandroid_runtime_lazy.so`、`libnativeloader_lazy.so`） | Android 12+ 的"延迟加载"机制。若白名单按名字精确匹配 `libandroid_runtime.so`，在 12+ 上**会漏掉 `_lazy`** ⇒ 必须用**子串匹配**（我们的 `list_matches` 正是如此 ✅） |
| **`/apex/com.android.*` 路径** | 模块化组件，**版本与系统不同步**。白名单若按路径匹配，需同时接受 `/system/lib64` 与 `/apex/...` 两种前缀 |

## 五、对 G3 的直接结论

1. **"全量"（`applied=81`）里，A/B 类只占少数，其余多是 ART/图形/vendor** —— 这解释了"全量能跑但风险高"：
   它把 21 个 ART 库 + 16 个图形库（已排除）+ 49 个 vendor 库里的"有 open 的"都 patch 了；
2. **`libjavacore` 单库崩、全量不崩**的现象，指向"**一致性集合**"而非"单个库"：
   `libjavacore`（读）与 `libandroid_runtime`（读字体配置）、`libminikin`/`libhwui`（用字体）在**同一条逻辑链**上，
   只 patch 前者会让"读到的路径/内容"与后者的假设不一致；
3. **下一步**：把白名单从"单库"升级为"**一致性集合**"——例如
   `{libjavacore, libandroid_runtime, libandroidfw}`（读侧 + 配置侧 + 资源侧），逐个集合 A/B 验证，
   而不是继续在"单库 vs 全量"之间二选一。
