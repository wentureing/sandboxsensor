## 二、依赖关系（无环）

```
        model   common   designsystem          ← 叶子（不依赖任何项目模块）
            ↑      ↑
   framework  hook  sandbox  apk
            ↑      ↑      ↑
            services  ← framework, sandbox, hook
                ↑
             binder  ← hook, sandbox, services
                ↑
         virtualization  ← binder, hook, sandbox, services, apk, framework
                ↑
   feature:{appmanager, launcher, settings}   （feature 之间互不依赖）
```

| 模块 | 直接依赖 |
| --- | --- |
| `:core:hook` `:core:sandbox` `:core:framework` `:core:apk` | model, common（apk 另加 model） |
| `:core:services` | model, common, framework, sandbox, hook |
| `:core:binder` | model, common, hook, sandbox, services |
| `:core:virtualization` | model, common, hook, binder, apk, sandbox, framework, services |

**结论**：分层清晰、无循环依赖。`hook`/`sandbox` 在底层（被 binder/services/virtualization 依赖），改它们的破坏面最大；`virtualization` 在顶层（只被 feature 依赖），是**最安全的重构入口**。

`seccomp`，host 编不了。**再拆只能按 TU 拆分（需要环境桩），用户已暂停**。

## 五、结论与建议

1. **重构入口应选 `virtualization`**：它是顶层（只被 feature 依赖），且已有一套现成护栏（SELF_CHECK 8 项 ×2 进程、探针 96 项、单测 matrix）。
2. **`binder`/`services` 改动风险高**：被 `virtualization` 依赖，且 `SystemServiceProxyManager` 稳定（churn 2），没有故障驱动就不动。
3. **native 侧不再做"抽纯逻辑"**：2% 的可测比例说明这条路走完了；剩余价值在"依赖收敛"（已做到 3 条 include、3 个编译单元）与"白名单下发"（可选）。
4. 四个模块占 72% 代码量 → 后续任何"职责梳理"都应优先覆盖 `virtualization`、`binder`、`services`、`hook`。
