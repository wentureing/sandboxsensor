## 一、现有自测手段（6 种，能力不同）

| 代号 | 手段 | 在哪里跑 | 规模 | 触发方式 |
| --- | --- | --- | --- | --- |
| **A** | `SELF_CHECK`（`ContainerSelfCheck`） | 容器主进程 | **6 项**（S1–S6） | `am broadcast … com.nextvm.cmd.SELF_CHECK` |
| **B** | 探针 APK（`ProbeRunner`） | guest 进程 | **96 项**：J36 / P24 / F14 / N15 / D5（+P24–P27 窗口项） | `setprop debug.probe.suite` + `LAUNCH_ACTIVITY` |
| **C** | `CmdReceiver` 命令通道 | 容器主进程 | **12 条**：INSTALL / LAUNCH / LAUNCH_ACTIVITY / UNINSTALL / LIST / COLLECT_OUT / LIST_OUT / CAT_OUT / SPOOF_EXEMPT_ADD / REMOVE / LIST / SELF_CHECK | broadcast |
| **D** | 真机脚本 | PC | `auto-test.ps1`（T1/T2a/T2b）、`collect-probe.ps1`、`install-and-wait.ps1`、`diag-boot-loop.ps1` | powershell |
| **E** | 单测 | CI | `module-test` matrix（common / hook / virtualization / sandbox）+ `cpp-core-test` | CI dispatch |
| **F** | 人工观感 | 人 | Via 主页、长按、登录页 | 截图 |

**A 的 6 项内容**（`ContainerSelfCheck.kt`）：S1 规则命中 / S2 规则移除后不命中 / S3 规则翻译后可写（写 app 私有 cacheDir）/ S4 未知路径不误改 / S5 诊断通道可写 / S6 `path_spoof.conf` 含 `[豁免名单]`。

**B 的套件语义**（`ProbeSuite`）：`round`（默认）= J + F + D；`path` = J + F；`diag` = D；`all` = 全部；`none` = 空。**P 与 N 系列在 round 下全部 skipped（39 项）**——这是设计，不是缺失。

## 二、覆盖矩阵（21 个功能面）

| # | 功能 | 自测手段 | 覆盖度 | 缺口 / 说明 |
| --- | --- | --- | --- | --- |
| 1 | 容器启动 | C（`am start -W`）+ D | ✅ | `Status: ok` + `TotalTime` 可判 |
| 2 | **guest 启动链**（bind → Provider → onCreate → 首 Activity） | 无自动断言，靠人读 breadcrumb | ⚠️ **最大缺口** | 顺序只能人工比对；B4-4 的前置「8–10 条 breadcrumb 契约测试」就是补这里 |
| 3 | 沙箱隔离（写入） | F01/F04/F08/F09/F14 + D04 | ⚠️ 边界需人判 | F08 是**故意的写穿检测**（`made=true`），宿主 external 出现文件属已知边界，没有自动判据区分"边界"与"回归" |
| 4 | 路径欺骗（豁免名单） | J08/J11 + C(`SPOOF_EXEMPT_LIST`) + A(S6) | ✅ | S6 只验"配置含 `[豁免名单]` 段"，**不验内容正确** |
| 5 | 族根翻译（ROOT_FORM） | J01/J02/J14 | ✅ | value 明确（`/data/user/0/com.sandbox.probe`） |
| 6 | Java 层 hook（可开关） | J26/J27（`javaIo=0` 时 fail）+ `stats` | ⚠️ **只覆盖"关"侧** | 开 `javaIo=1` 的路径无自动化；历史教训（Via 不可交互）导致**刻意不测**，应显式登记而非隐瞒 |
| — | **`J26/J27` fail = 设计故意，不是回归** | 探针故意用字面量宿主路径检测写穿；`debug.nextvm.javaIo` 默认 `0`（开启会破坏真实应用）→ Java 层字面量不翻译 → `ENOENT` | 判读时**跳过**；对照项 `J02`(ok) / `J28`(`exists=false`) | 见 `容器能力清单与回归方法.md` 第三节 |
| 7 | native hook 安装 | breadcrumb `v142 registered rules=N` + `fs.stats` | ⚠️ 只读日志 | 探针 N 系列是 syscall 直调，**不回答"hook 是否装上了"** |
| 8 | 诊断通道 | D01–D05 + A(S5) | ✅ 强 | 存在 / 行数 / 尾部 / 总量 / 可写，五维 |
| 9 | watchdog 栈转储 | D03 | ⚠️ 时序依赖 | 报告时刻常 `exists=false`，容易被误读为"能力缺失" |
| 10 | 内存 dex 转储（壳 guest） | 无 | ❌ | 仅 AW/SecNeo 壳触发，普通 guest 跳过 → 事实上不可自测 |
| 11 | 豁免生效（via 零欺骗） | C(`SPOOF_EXEMPT_LIST`) + 人工 | ⚠️ | 只验"名单里有 mark.via"，不验"实际未翻译" |
| 12 | 规则注册/删除对称 | A(S1/S2) + 单测 R5/R8 | ⚠️ | **自检用临时规则 `/selfcheck/*`**，真实规则表是否注册成功它抓不到 |
| 13 | 探针套件本身 | 自身 + skipped 记账 | ✅ | 39 项 skipped 是显式契约 |
| 14 | 探针输出收集 | C(`COLLECT_OUT`/`LIST_OUT`/`CAT_OUT`) | ⚠️ | 三条命令**没有脚本断言**，能力清单标 ✅ 但无自动判据 |
| 15 | WebView MIME | 无 | ❌ | 只能人眼看"主页显示源码" |
| 16 | 跨进程文件选择器 | 无 | ❌ | 未接管 |
| 17 | NIO 翻译 | 无 | ❌ | 不实现（用户决定） |
| 18 | 多实例 | 无 | ❌ | 开发暂停 |
| 19 | 反检测（AntiDetection / IdentitySpoofing） | 无 | ❌ | 零调用；接线后需扩 N 系列 |
| 20 | 自检工具自身 | `ContainerSelfCheckTest` 8 条 | ✅ | 有单测 |
| 21 | 诊断写入不占 Java IO 配额（`diag=`） | 只有字段，无断言 | ⚠️ | 需要"写日志 → `diag` 增、`total` 不增"的用例 |

**统计**：✅ 6 项、⚠️ 9 项、❌ 6 项（合计 21）。

## 三、结构性缺口（比单项更重要）

| # | 缺口 | 为什么是结构性的 |
| --- | --- | --- |
| 1 | **SELF_CHECK 只测机制，不测真实规则** | S1–S4 用自造的 `/selfcheck/*` 规则；真实违规（如 v142「规则注册点与生效进程不一致」）它全绿也能漏 |
| 2 | **主进程自检与 guest 探针没有合并视图** | SELF_CHECK 只打一行 logcat，探针写 JSON；判读要人对着两个来源比 |
| 3 | **启动链顺序无断言** | bind / Provider / onCreate / 首 Activity 的顺序只存在于 breadcrumb 文本里，没有 golden |
| 4 | **"能力缺失"与"时序未到"不可区分** | D03 stackdump、F08 写穿、P25/P26 窗口 token 都属于这类，容易被误判成回归 |
| 5 | **自测结果不可机读** | 已有 `DiagnosticsHolder` / `CheckResult` 结构化设施，但 SELF_CHECK 没用它，探针又是另一套 JSON |
| 6 | **刻意不测的项没有被登记** | `javaIo=1` 的开侧、多实例、反检测都是"故意不测"，但在能力清单里只写 ❌，看不出是"没做"还是"不敢测" |
| 7 | **探针存在"静默缺项"**（2026-11-26 实测发现） | `ProbeRunner.probeUiEntries()` 在 `UiProbe.takeEntries()` 返回 null 时直接 `return`（`probe/src/main/java/com/sandbox/probe/ProbeRunner.java:889-891`）→ P24–P27 既不进报告、也不进 `skipped`。实测同一个 `suite=round`、同一个探针 APK：10:05 那轮 `entries=98`（含 P24–P27），10:12 那轮 `entries=94`（缺 4 项），**两轮都判绿** |

### 已知早期窗口：容器刚启动时 `J19/J20` 会 NameNotFound（2026-11-26 实测）

| 轮次 | 前置 | `J19 getApplicationInfo.dataDir` / `J20 getPackageInfo` | 其它 fail |
| --- | --- | --- | --- |
| 1 | 实例刚 INSTALL，立刻 LAUNCH 探针 | **fail**：`NameNotFoundException: com.sandbox.probe` | J26/J27/P25/P26 |
| 2 | `STOP` 后立刻 LAUNCH（容器未重启） | **fail**（同上，稳定复现） | 同上 |
| 3 | **重启容器 + 等 10s** 再 LAUNCH | **ok**：`dataDir=…/com.sandbox.probe_1795662349075 uid=0`、`versionName=1.22 versionCode=23` | **只剩 J26/J27** |

**归因（按 18.4 分类：时序未就绪，不是行为偏移）**：
容器进程刚启动或实例刚 `INSTALL` 时，虚拟 PM 的包列表还没就绪，guest 侧 `getPackageManager().getApplicationInfo(自己)` 会 `NameNotFound`；
容器重启并等 10s 后自然恢复，且 `J21 getInstalledPackages.count` 从 2 变为 3（自己+Via+bin.mt），说明是注册时机而非代理缺失。

**处置（不改生产代码，改测试口径）**：
1. 采集/回归脚本在 `LAUNCH` 探针前，先确认容器就绪（`MainActivity` 起来后**等 ≥10s**，或轮询 `LIST` 直到目标实例出现）；
2. 报告判读时把「容器启动 10s 内」的 `J19/J20` 视为**未就绪**，不算能力缺失——与 D03 的 `not-yet` 同一性质；
3. 若要彻底消除，需在 `VirtualPackageManagerService` 的实例注册上加"INSTALL 后立即入表"的保证，属独立改动（不在 STOP 批次内）。

**S7/S8 首跑 fail 的归因（18.4 分类：编码错误）**：

| 项 | 现象 | 根因 | 修法 |
| --- | --- | --- | --- |
| S7 | 主进程规则表为空 → fail | 规则在 **guest 进程**注册（v142 教训），主进程冷启动必然为空 | 空表记 `skipped`；有规则才做往返断言 |
| S8 | 写 3 次诊断后 `diagDelta=0` → fail | 未装 javaIo hook 时 `stats()` 返回**全 0 而不是 null**，`parseIoStats` 误判为"可观察" | `PathProbe` 加 `javaIoInstalled()`，未装则 `skipped` |
| 共同 | fail 后无法诊断 | `checks.log` 只有一行汇总，detail 不落盘 | 每项写 `S selfcheck.<id> ok/FAIL <detail>` |

## 五、结论

- **容器机制层（路径翻译、写入隔离、诊断通道、配置）自测是够的**：A 6 项 + B 的 J/F/D 55 项 + 单测，且本轮真机复跑与基线逐项一致。
- **行为层（启动链顺序、真实规则、窗口、WebView）基本靠人**：这是当前最大风险，也正是 B4-4 契约测试要补的。
- **"刻意不测"的项（javaIo 开侧、多实例、反检测、壳 guest dex dump）必须显式登记原因**，否则以后会被误当成"已验证"。
