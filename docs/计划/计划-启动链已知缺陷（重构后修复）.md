## 一、缺陷清单

### L1 session 级（阻塞重复验证）——**修序第 1**

| 项 | 内容 |
| --- | --- |
| 现象 | 同一 slot 启动 5 次后 `LAUNCH_ACTIVITY` 报 `No available stub for process slot N`（`VirtualEngine.kt:634`），必须重启容器 |
| 证据 | 2026-11-26 实测：via 在 slot 1 连续启动 5 次后 probe 第六次直接失败；`StubRegistry.resolveStub` 把 stub 放进 `inUseStubs`，但**生产代码无任何 `releaseStub` / `releaseAllStubsForSlot` 调用点**（只有定义与测试） |
| 归属 | 两条路径共有（与 bind 路径无关） |
| 影响 | 采集/回归最多 5 次/进程，之后必须重启容器 → 所有真机验证成本被放大 |
| 建议修法 | `VirtualEngine.stopApp()` 里 `stubRegistry.releaseAllStubsForSlot(slot)`；补一条单测「stop 后同 slot 仍可解析」 |
| 验证 | 连续 6 次 STOP+LAUNCH 不报 stub 错误；`StubRegistryTest` 新增用例 |

### L2 两实例共用同一 `processSlot`

| 项 | 内容 |
| --- | --- |
| 现象 | `LIST` 显示 `mark.via` 与 `com.sandbox.probe` **都是 `slot=1`** |
| 根因 | `processSlot` 是**安装时持久化**进 `VirtualApp` 的值；容器重启后内存 `slots` 表为空，与持久化值不一致 |
| 归属 | 共有 |
| 建议修法 | 启动时用持久化的 `processSlot` 重建 `VirtualProcessManager` 的占用表；或安装时不再持久化 slot，改为运行时分配 |
| 验证 | `LIST` 两实例 slot 不同；`VirtualProcessManagerTest` 增加"按持久化值重建"用例 |

### L3 **legacy 回退路径上加固 guest 崩溃**

| 项 | 内容 |
| --- | --- |
| 现象 | `bin.mt.plus.canary` 启动即崩：`NoClassDefFoundError: l.۠᩹ܽ` |
| 证据（logcat 原文） | `11-26 10:43:23.059 E/AndroidRuntime(10318): Process: bin.mt.plus.canary` → `at VirtualApplicationManager.createApplication(VirtualApplicationManager.kt:1140)` → `at VirtualApplicationManager.bindApplication(VirtualApplicationManager.kt:265)`。`VAM:265` 是 **legacy Step 2** → 该次 bind 走了 legacy |
| 归属 | **legacy 特有**（framework 分支在 `VAM:215-256`，265 属 legacy） |
| 未取到的证据 | 该次 framework 为何失败（logcat 已滚动，`breadcrumb-<pid>.log` 未保留）→ 复现时先取 breadcrumb |
| 影响 | 加固/混淆 guest 在 framework 失败后回退 legacy，legacy 的反射构造直接炸 → **回退路径反而更脆** |
| 建议修法 | 先复现并采集 `framework bind FAILED` 的完整栈（判断是 LoadedApk 还是 ApplicationInfo）；legacy 的 `createApplication` 失败时应给出**可诊断的错误**（当前只 `Timber.e` + 返回 null → 上层 NPE/崩溃） |
| 验证 | bin.mt.plus 能启动；或至少崩溃处有 breadcrumb `bind FAILED` + 明确原因 |

### L4 framework 下 via 的 `InitializationProvider` 失败（legacy 却成功）

| 项 | 内容 |
| --- | --- |
| 现象 | `provider FAILED (bind continues): androidx.startup.InitializationProvider <StartupException: ClassNotFoundException: androidx.emoji2.text.EmojiCompatInitializer>` |
| 证据 | `via-1/via-2` golden（framework）23–64 行有该异常 + 完整栈；`via-legacy-1/2` 中同一 provider 是 `provider ok` |
| 归属 | **两条路径不一致**（framework 失败 / legacy 成功）|
| 影响 | ① via 的 AndroidX Startup 初始化被跳过（emoji2 通常可选，但其它 initializer 可能连带）；② 两条路径行为不同 → 回退不等于"同样的环境" |
| 候选根因（**未定论**） | framework 传给 `initContentProviders` 的 `classLoader` 是 `loadedApk.getClassLoader()`（`v53 probe` 显示其 DexPathList 只有 mark.via.apk）；legacy 用的是另一套 CL，链上可能能看到更多 dex |
| 建议修法 | 先加**一次性**观测（provider 的 CL 身份 + DexPathList 长度、metaData 是否为空）定位，再决定是"修 framework"还是"接受差异并写进契约" |
| 验证 | 两条路径下该 provider 结果一致；或差异被显式登记为契约 |

### L5 `mInitialApplication` 身份不一致

| 项 | 内容 |
| --- | --- |
| 现象 | `v138-appctx mInitialApplication com.nextvm.app -> com.nextvm.app`（framework）vs `-> mark.via`（legacy） |
| 归属 | 两条路径不一致 |
| 影响 | `ActivityThread.mInitialApplication` 是全局 Context，包名不同会影响"谁在问系统"（身份面）与部分 SDK 的包名判断 |
| 建议修法 | 明确"哪条正确"（framework 更接近真实：ActivityThread 的 mInitialApplication 是进程的 Application，guest 进程里它就是 guest）→ 若判定 legacy 正确则应让 framework 也对齐（**属行为变更，走变更流程**） |
| 验证 | 两条路径该字段一致，且探针 J 系列 + via 可用性不回退 |

### L6 legacy 专属的三段 patch 在 framework 路径缺失

| 项 | 内容 |

## 二、重构完成后的修复顺序

| 序 | 项 | 理由 |
| --- | --- | --- |
| 1 | **L1**（stub 释放） | 不修则后面每次真机验证都要重启容器，回归成本高、容易漏测 |
| 2 | **L2**（slot 持久化） | 与 L1 同域（同一次 `stopApp`/`allocateSlot` 改动），一起做最省 |
| 3 | **L3**（legacy 崩溃可诊断） | 加固 guest 是最需要的场景；先让它"能报出原因"再谈修 |
| 4 | **L4 / L6** | 先加一次性观测定根因，再决定修哪一侧（可能同源） |
| 5 | **L5** | 涉及身份语义，需变更流程 + 探针回归 |
| 6 | **L7** | R1 型，独立小改动 |
| 7 | **L8** | 探针侧，与容器无关 |
| — | L9 / L10 | L9 不修；L10 单独排期 |

## 四、与重构的关系（为什么不能现在顺手改）

- B4-4c 要拆的正是 `bindApplication`（212 行）与 `bindViaFrameworkLoadedApk`（169 行）——**L3/L4/L5/L6 全在其中**；
- 规则 10 要求重构提交"只允许等价搬迁 + 明确登记的偏差"；一旦顺手修 L4，拆分的等价检查会立刻失效
  （`check-refactor-equivalence` 报不等价，且无法用"结构性改造"解释）；
- 所以：**先把结构拆干净、契约稳定，再在这个结构上一条一条修** —— 每修一条都有 golden 兜底。
