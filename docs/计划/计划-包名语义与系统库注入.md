# 计划：包名语义的承载体 —— 从 `g_spoofed_package_name` 换成「规则表 + 库级白名单」（2026-11-28）

- 用户要求：**包名语义很重要**；允许更换维护包名语义的模块，**用容器本身的能力**，而不是等 `g_spoofed_package_name` 产生。
- 本文给出调研结论、三条路径与实施计划。

---

## 一、先纠正一个前提：容器是**单进程模型**（实测）

```
ps -A | grep nextvm           →  600  1583  com.nextvm.app        （只有 1 个进程）
/proc/600/cmdline             →  com.nextvm.app                   （无 :pN 后缀）
dumpsys activity activities   →  topResumedActivity = com.nextvm.app/.stub.P1$Standard00
```

| 结论 | 证据 |
| --- | --- |
| 所有 guest 的 Activity 都跑在**同一个容器进程**（stub Activity 承载） | `pidof` 只有 1 个 pid；stub 组件在 `com.nextvm.app` 进程 |
| **没有"某个 guest 的进程"** | 容器代码里也没有 `Process.start`/`niceName`（grep 0 命中） |
| guest 的 native 库也加载在同一进程 | `hook stats` 里 `libs=415` 是这一个进程的库数 |

**因此**："只为这个 guest 注入系统库"**在进程层面不可实现** —— 系统库（`libjavacore.so`）在**容器进程启动时**就加载了，
那时**任何 guest 都还没被选择**。这不是代码缺陷，是单进程架构的必然。

---

## 二、关键论证：包名语义其实**不需要"进程级专属注入"**就能保持

包名语义在运行时由**两层**承载：

| 层 | 承载者 | 作用 |
| --- | --- | --- |
| **规则表**（真正决定"翻译成什么"） | `nativeSetPathRedirections` / `nativeAddPathRedirection` 按 `g_spoofed_package_name` 注册 | 未 bind 时为空 ⇒ `redirect_path` 返回空 ⇒ **不翻译**；bind 后只有当前 guest 的规则 ⇒ **只翻译该 guest 的路径** |
| **库级 hook**（决定"是否拦"） | `libAllow`（G3） | 只决定"这些库的 open/stat 要不要进 `redirect_path`" |

也就是说：**patch `libjavacore.so` 本身不构成"给其他 guest 注入"** ——
因为翻译与否取决于**规则表**，而规则表是**当前 bind 的 guest** 的。

> 这就是"用容器本身的能力"：容器在 bind 时注册规则（已经在做），native 侧只负责"让读取路径进入翻译函数"。

## 三、三条路径

| 方案 | 做法 | 包名语义 | 复杂度 | 结论 |
| --- | --- | --- | --- | --- |
| **A（推荐）** | 白名单改为 **库级命中即 patch**（不看 pkg）；语义由**规则表**保证；`pkgDeny` 仅作排除 | ✅ **等价保持**（未 bind 不翻译） | 低（~10 行） | **采用** |
| B | 容器在 `nativeInit` 时传入"当前活跃 guest" | 🟡 部分（进程启动瞬间无 guest） | 中 | 不必要 |
| C | 等做多实例（每 guest 独立进程）后，pkg 白名单自然成立 | ✅ 真正的进程级 | 高（依赖 M1–M8） | 留作将来 |
| **D（已实现 `c201658`）** | 延后重评：`g_skipped_bases` + `repatch_skipped_libs()`（pkg 注入后补 patch） | ✅ 保持，但 bind 前的 I/O 不翻译 | 已实现 | **保留作兜底**（覆盖 bind 后才 dlopen 的库，如 `libmonochrome_64.so`） |

**结论：A + D 组合。**

## 四、实施计划（A）

### 4.1 代码改动（native，约 10 行）

```
ns_lib_allow_hit(lib)      拆成：
  ns_lib_in_allow(lib)      ← 只看 libAllow（新增）
  ns_pkg_in_deny(pkg)       ← 只看 pkgDeny（排除用）
放行条件（patch_library_got 内）：
  if (!verdict patch) {
      if (ns_open_diag_enabled()) 放行            // 诊断全量（保留）
      else if (ns_lib_in_allow(lib)) 放行          // ★ A：不看 pkg
      else return;
      if (reason != kSystemLib) return;            // graphics/self 仍跳过
  }
符号限制：
  if (ns_lib_in_allow(lib) || ns_open_diag_enabled()) 只 patch symAllow
```

### 4.2 保留 D 作为兜底

`repatch_skipped_libs()` 仍用于"bind 之后才 dlopen 的库"（`libmonochrome_64.so` 在 WebView 初始化时才加载，那时 pkg 已有值，直接命中）。

### 4.3 判据

| 项 | 期望 |
| --- | --- |
| `hook stats`（probe 进程，bind 阶段） | `applied ≥ 1`（`libjavacore` 被 patch，5 符号） |
| `hook stats` 增量 | 不应出现诊断模式的 `applied=50` |
| **`W-ext-synthpath`** | **`text/html` 且 body = `WVPAGE_OK`** |
| `W2` | 仍 `text/plain`（宿主包名问题，与本方案无关） |
| 容器主进程（未 bind） | 规则表为空 ⇒ 不翻译 ⇒ **零影响**（可用 `checks.log` 的 `path rules=0` 佐证） |
| via | 不受影响（`pkgDeny` 未配置；其规则表照旧） |

### 4.4 风险与登记

| 风险 | 说明 |
| --- | --- |
| 多实例并存时规则表互串 | **已知缺口 M4**（多实例 M1–M8 未做）。本方案在单实例下成立；做多实例时必须改为「进程级」（方案 C），或把规则表按 task 隔离 |
| `libAllow` 配错会 patch 到不该 patch 的库 | `symAllow` 限制为 5 个符号；`libFilterDefaults` 用子串精确匹配；改配置必须改 golden 向量 |
| 诊断模式与白名单同时开启 | `ns_open_diag_enabled()` 优先（全量 patch，性能灾难），文档已注明不可用于生产 |

## 五、一句话

> **单进程模型下，"专属注入"应理解为"专属翻译"**：库级 hook 对所有 guest 装（因为进程只有一份），
> 但**翻译只对当前 bind 的 guest 生效**（规则表驱动）。这样既满足"只给 via 注入系统库"的意图，
> 又不依赖 `g_spoofed_package_name` 的注入时机。
