# 计划：阶段 0（G3 匹配方向）+ T-1~T-3（测试体系）—— 含复用组件

- 目标：让 G3 白名单**真正生效**，并让"以为开了其实没开"这类问题**被 CI 抓住**。
- 范围：`core/lib_filter.{h,cpp}`、`native-hook.cpp`、`lib_filter_test.cpp` + 向量、探针 4 个文件。
- 一次容器编译（`container-build`）+ 一次探针编译（`probe-build`）；host 测试走 `module-test` 的 `cpp-core-test`（无需额外 CI）。

## 二、阶段 0：G3 匹配方向（代码）

### 2.1 关键设计：把匹配逻辑搬进**可测模块**

现在 `prop_list_matches` 若要写在 `native-hook.cpp`（JNI/Android 依赖），host 测试就测不到。所以：

```
core/hook/cpp/core/lib_filter.h    ← 新增纯函数声明
    bool list_matches(const char* csv, const char* subject);   // 不对 Android 有任何依赖
core/hook/cpp/core/lib_filter.cpp  ← 实现（std::string/strstr，无分配可接受）
```

`native-hook.cpp` 的 `ns_lib_allow_hit` 改成调 `nextvm::libfilter::list_matches(...)` ——
**复用已有的 host 测试二进制**（`lib_filter_test` + TSV 向量），不需要新 CI job。

### 2.2 逐文件改动

| 文件 | 改动 | 复用 |
| --- | --- | --- |
| `core/lib_filter.h` | +`bool list_matches(const char* csv, const char* subject);` | — |
| `core/lib_filter.cpp` | 实现：按 `,` 切分，逐项 `strstr(subject, item)`；空项跳过 | `has()`（已有 `strstr` 包装） |
| `native-hook.cpp` | `prop_contains(prop, needle)` → 删除；`ns_lib_allow_hit` 改调 `list_matches`（两处：libAllow / pkgAllow） | `ns_lib_allow_configured()` |
| `lib_filter_test.cpp` | TSV 第 4 列新增 `allow_pkg`/`allow_lib`（或新加一列 `mode=allow` + 两列），断言 `Decision` | 现有 TSV 解析器 |
| `lib_filter_vectors.tsv` | +6 条（见 §2.3） | — |

### 2.3 六条新向量（必须能证伪）

| # | subject（长路径/包名） | 列表 | 期望 | 抓什么 |
| --- | --- | --- | --- | --- |
| V1 | `/apex/com.android.art/lib64/libjavacore.so` | `libjavacore` | **match** | 本次 bug 的回归守卫 |
| V2 | `/apex/.../libjavacore.so` | `libmonochrome_64,libjavacore` | match | 多列表项 |
| V3 | `/apex/.../libjavacore.so` | `libmonochrome_64` | **no match** | 不能误命中 |
| V4 | `com.sandbox.probe` | `mark.via,com.sandbox.probe` | match | 包名层 |
| V5 | `com.sandbox.probe` | `mark.via` | **no match** | 包名层不误命中 |
| V6 | `openat`（symAllow 路径） | `open,stat` | **no match**（用 `prop_list_exact` 的精确语义） | `open` ⊄ `openat` |

### 2.4 判据

| 层 | 判据 |
| --- | --- |
| host | 6 条全过；**删掉 `list_matches` 的实现后 V1 必须变红** |
| 真机（guest 进程） | `hook stats` 的 `applied` 从 `1` → `≥2`（`libjavacore` 换来 5 个槽，实际 ≤5） |
| **功能** | `W-ext-synthpath` = `text/html` + `WVPAGE_OK` |

## 三、T-1：W 结果并入 `probe-report.json`

### 3.1 复用链

```
WebViewProbeActivity.rec(...)            ← 现有结果行（"W2 url=… -> finished {ct,body}"）
   └─ 结束时解析成 (id, contentType, body)
        └─ Report.put(WEBEXT, id, "webext", name, () -> "ct=…;body=…")   ← 复用 Report.put
             └─ ProbeRunner 组装 payload 时把 WEBEXT 合并进 entries     ← 复用 Report.flush
                  └─ check-probe-ids 与 CI 解析同一份 probe-report.json
```

### 3.2 改动

| 文件 | 改动 |
| --- | --- |
| `Report.java` | +`static final JSONArray WEBEXT`，+`static JSONArray webextEntries()`（与 `timeline()`/`providerEntries()` 同形） |
| `WebViewProbeActivity.java` | 每条 W 结果写完 `rec()` 后，再 `Report.put(Report.WEBEXT, id, "webext", name, …)`（**只加一行**，不动现有逻辑） |
| `ProbeRunner.java` | `root.put("webext", Report.webextEntries())`（与 `timeline`/`provider` 并列） |

### 3.3 判据

`probe-report.json` 出现 `"webext":[{id:"W-ext-synthpath", …}]`；`check-probe-ids` 能看到 `W-*` 项（需 `--write` 更新 golden）。

## 四、T-2：重复 id 去重

| 文件 | 改动 | 复用 |
| --- | --- | --- |
| `Report.java` | `put(...)` 内：写入前按 `id` 扫一遍目标数组，命中则 `remove(i)`（保留**最后**一次，即非早期窗口那轮） | `Report.put` 是唯一写入点 ⇒ 一处改动覆盖 `sink` 与 `provider`/`webext` |
| `ProbeSink.java` | 不改（透传 `Report.put`） | — |

**判据**：`entries` 数量 = 唯一 id 数；`N11–N16`/`H1`/`P28` 不再成对出现。

> 为什么保留"最后一条"：首轮来自 `ContentProvider.onCreate`（早期窗口，`J19/J20` 会 `NameNotFound`），
> 末轮才是稳定态。这与 `架构-就绪依赖与早期窗口.md` 的 R3 分类一致。

## 五、T-3：`H2.lib_allow_applied` 断言项

### 5.1 复用

`NativeHookBridge.hookStats()`（Kotlin，已有）返回 `"libs=415 patched=411 applied=1 slots=12 …"` →
探针 `ProbeRunner` 里解析（正则 `applied=(\d+)`）。

### 5.2 条目定义

```
H2.lib_allow_applied   group=native
  value: "libAllow=<值> applied=<n> slots=<m> verdict=<ok|MISS>"
  verdict=MISS 的条件：libAllow 非空 且 applied==0   ⇒ status=fail
```

| 情形 | 期望 status |
| --- | --- |
| `libAllow` 空（默认） | `ok`（`applied` 由 `libprobe.so` 决定，不断言） |
| `libAllow` 非空 且 `applied ≥ 1` | `ok` |
| `libAllow` 非空 且 `applied == 0` | **fail**（这就是本次 G3 的失败形态） |

### 5.3 改动

| 文件 | 改动 |
| --- | --- |
| `ProbeRunner.java` | `probeNative()` 里加 `put("H2.lib_allow_applied", "native", …)`；需要能读系统属性 → `android.os.SystemProperties` 反射 或 `Process.exec` 读 `getprop`（探针是 guest，**读 `debug.nextvm.libAllow` 需要能读**；若读不到则 `verdict=SKIP`） |
| `check-probe-ids --write` | 102 → 103 项 |
| `docs/输出/探针-检测项清单.md` | 补一行 |

> 若 guest 内读不到容器属性（命名空间/权限），退化为：把 `libAllow` 的**期望**通过探针的 `probe-early.json`/`probe-report.json` 从容器侧注入（一份小文件），逻辑相同。

## 七、风险与回退

| 风险 | 对策 |
| --- | --- |
| `list_matches` 放进 `lib_filter.cpp` 后，native 侧多一次函数调用 | 纯函数、无分配；`redirect_path` 本来就是每次 I/O 调用，量级相同 |
| `Report.put` 加去重后，早期窗口的 fail 项被末轮覆盖 | 这正是目的（R3 分类），但需在 `docs/输出/探针-检测项清单.md` 注明"同 id 保留最后一次" |
| `WEBEXT` 增大 `probe-report.json` | 只存 `ct` 与 body 前 80 字符（现在 `rec` 已截断），体积可控 |
| `H2` 在 guest 内读不到 `debug.nextvm.*` | 退化为"容器侧注入期望文件"，见 §5.3 |

---

## 八、明确不做

1. 不动 `classify_lib` 的四级判据（G3 只在其上叠一层白名单）；
2. 不动 `PathKinds`（`DATA_ROOT` 已覆盖 `/data/user/0/<guest>/`）；
3. 不引入新的 JNI 导出（T-3 复用 `nativeGetHookStats`）；
4. 不在本批碰 `stat/access/readlink` 的 patch 逻辑（它们已在 `symAllow` 里，等阶段 0 判据出来再验证）。
