## 二、阶段 0：G3 匹配方向 + **配置改由管理器下发**

### 2.1 配置通路（替代系统属性）

```
VirtualApplicationManager.bindApplication            ← 已有编排点（VAM:523 调 setupAppRedirections）
  ├─ nativeHookBridge.setupAppRedirections(...)      ← 已有（路径规则）
  └─ nativeHookBridge.setupLibAllow(pkg, libs, syms) ← 新增：库白名单
        └─ nativeSetLibAllow(pkg, libs, syms)         ← 新 JNI 导出（第 26 个）
             ├─ g_lib_allow_pkg/libs/syms = 参数
             └─ repatch_loaded_libs()                 ← 对"已加载但被判 skip"的库重评（见 2.3）
```

**为什么不读系统属性**（三个理由）：
1. 语义：guest 不该读容器配置（容器是管理者）；
2. 可靠性：`debug.nextvm.*` 会被属性 spoof hook 干扰，且长度/转义受限；
3. 可测：Kotlin 侧的默认值可单测，不必"设属性再来一遍"。

Kotlin 侧新增：
```kotlin
// core/hook/.../LibAllowDefaults.kt（新）
object LibAllowDefaults {
    val PKG_ALLOW: Set<String> = setOf("mark.via")            // 只对 via 开
    val LIB_ALLOW: List<String> = listOf("libjavacore")       // 先只这一个（谁在读已被 who= 证实）
    val SYM_ALLOW: List<String> = listOf("open","openat","stat","access","readlink")
    fun csv(s: Collection<String>) = s.joinToString(",")
}
```
> 默认值**先只在 debug 构建启用**；`pkgAllow` 为空即完全等价现状。

### 2.2 匹配逻辑搬进可测模块

```cpp
// core/lib_filter.h（新增，无 Android 依赖）
bool list_matches(const char* csv, const char* subject);   // "csv 中某项出现于 subject"
```

`native-hook.cpp` 的 `ns_lib_allow_hit` 改调它（删掉方向反了的 `prop_contains`）。
`lib_filter_test` 直接测它 —— **复用现有 host 测试二进制与 TSV 向量**，无需新 CI job。

### 2.3 时序：下发晚于库加载 ⇒ 必须重评（这次理由是对的）

guest 进程由 Zygote fork，`libjavacore.so` 在 fork 前就映射好了；
`nativeInit`（装 hook）发生在进程早期，而白名单在 **bind 时**才下发 ⇒ **下发的库早已被判过 skip**。

因此 `nativeSetLibAllow` 末尾要调 `repatch_loaded_libs()`：

```cpp
// 只重评"之前被判 skip 的库"，且必须在白名单命中的前提下
for (base, name in g_skipped_libs)
    if (ns_lib_allow_hit(name)) patch_library_got(base, name, dynamic);
```

> 注意：这就是上一轮被我回退的 `g_skipped_bases`/`repatch_skipped_libs` 的**正确形态** ——
> 触发点从"pkg 注入"换成"**白名单下发**"，理由从"pkg 未就绪"换成"**配置晚于库加载**"（后者是事实）。

## 三、T-1：W 结果并入 `probe-report.json`

```
WebViewProbeActivity.rec(...)                     ← 现有结果行
  └─ Report.put(Report.WEBEXT, id, "webext", name, () -> "ct=…;body=…")   ← 复用 Report.put
       └─ ProbeRunner: root.put("webext", Report.webextEntries())         ← 与 timeline/provider 并列
            └─ check-probe-ids 与 CI 读同一份 probe-report.json
```

改动：`Report.java` 加 `WEBEXT` 数组 + `webextEntries()`；`WebViewProbeActivity` 每条结果加一行 `Report.put`；`ProbeRunner` 加一行合并。
判据：`probe-report.json` 出现 `"webext":[{id:"W-ext-synthpath"…}]`；`check-probe-ids --write` 能看到 `W-*`。

## 四、T-2：重复 id 去重（用 `phase` 表达，不盲目"留最后"）

**问题**：同一 id 出现两次 —— 首轮来自 `ContentProvider.onCreate`（早期窗口，`J19/J20` 会 `NameNotFound`），
末轮来自后台 `ProbeRunner`（稳定态）。

**建议方案**（比"留最后"更可判读）：
- `Report.put(..., String phase)`：默认 `"runner"`；`ProbeProvider` 路径传 `"early"`；
- 去重规则：**同 id 时 `runner` 覆盖 `early`；同 phase 保留最后一条**；
- 被覆盖的 `early` 条目不丢 —— 它已在 `probe-early.json`（现有 `flushEarly`）。

判据：`entries` 数 = 唯一 id 数；`N11–N16`/`H1`/`P28` 不再成对；`probe-early.json` 仍保留早期证据。

## 五、T-3：`H2.lib_allow_applied` 断言项（期望值来自管理器，不读属性）

| 情形 | 判定 |
| --- | --- |
| 探针侧拿不到"容器下发的期望" | `status=skipped`（不误报） |
| 期望非空 且 `applied ≥ 1` | `ok` |
| 期望非空 且 `applied == 0` | **fail**（本次 G3 的失败形态） |

**期望怎么到探针**：容器在 `INSTALL` 探针时把期望写进 `probe-early.json` 同目录的一份 `lib-allow.json`
（容器侧 `CmdReceiver` 已有写文件能力），探针 `ProbeRunner` 读它。**不读 `debug.nextvm.*`**。

## 七、风险与回退

| 风险 | 对策 |
| --- | --- |
| `nativeSetLibAllow` 在 bind 时下发，而 WebView 的库在**更晚**才 dlopen | `nativePatchNewlyLoaded`（+5s/+20s）已覆盖"新加载库"；两者互补 |
| 重评 `g_skipped_libs` 的开销 | 只在"下发时刻"跑一次；`dl_iterate_phdr` 一次遍历 |
| `pkgAllow` 配错影响其他 guest | 默认空；`LibAllowDefaults.PKG_ALLOW` 只有 `mark.via` |
| T-1 增大报告体积 | `rec()` 已截断 body；`webext` 只存 `ct` + 前 80 字符 |
