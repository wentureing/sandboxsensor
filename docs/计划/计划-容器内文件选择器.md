# 计划：容器内文件选择器（File Picker）

- 日期：2026-11-25
- 状态：**仅计划，暂不实现**（用户明确）
- 触发：用户实测发现（见 §一）

---

## 一、观察记录（实测）

| 项 | 事实 |
| --- | --- |
| 场景 | 在 via 里设置「默认下载目录」→ 触发文件/目录选择 |
| 现象 | **成功拉起了真正的系统文件选择器**（`DocumentsUI`），**跑出了容器** |
| 后果 | 用户可选中**宿主真实目录**；via 拿到的是宿主路径/URI → 后续下载写入**容器之外**，沙箱隔离在这条链路上失效 |
| 归属 | 不是路径翻译的 bug（翻译只管 `File`/`open` 等 I/O），而是**跨进程 Intent + 系统 Activity**：`startActivityForResult` 的目标是系统组件，容器没有接管 |

> 这类"跳出容器"的入口不止文件选择器，还有：`ACTION_OPEN_DOCUMENT`、`ACTION_OPEN_DOCUMENT_TREE`、
> `ACTION_GET_CONTENT`、`ACTION_CREATE_DOCUMENT`。它们都由 `DocumentsUI`（系统 app）响应，
> 容器目前**完全没拦截**。

## 二、目标

在容器内自实现一个**文件/文件夹选择器**，用于：

| 用途 | 说明 |
| --- | --- |
| 设置默认下载目录 | via 的本次触发点 |
| 选择文件（导入到沙箱） | 与"导入替代代读"策略一致 |
| 选择文件夹（下载/保存目标） | 返回沙箱内目录 |
| 同级功能 | `CREATE_DOCUMENT`（另存为）、`GET_CONTENT`（取内容） |

**核心要求**：选择结果必须落在**该 guest 的沙箱**内，不暴露、不回传宿主真实路径。

## 三、生效规则（用户指定）

> **guest 位于白名单时不生效；否则生效。**

| guest | 容器 Picker | 理由（待确认细项） |
| --- | --- | --- |
| **白名单内** | ❌ 不启用（继续用系统 picker） | 白名单 guest 走路径形态欺骗，系统 picker 的交互更像真机；且其路径由规则翻译 |
| **白名单外** | ✅ 启用容器 Picker | 尤其**豁免 guest**（如 via）：它拿到的就是真沙箱路径，一旦拉起系统 picker 就会直接拿到**宿主真实目录** → 必须由容器接管 |

**待确认**："白名单"指哪一份？
- 若是 **`PathSpoofConfig` 的「欺骗名单」**（原 `PATH_FIDELITY_WHITELIST`）→ 规则如上表；
- 若是 **「豁免名单」**（via 在内）→ 语义要反过来（via 不启用）。

计划暂按"**欺骗名单 = 白名单**"设计（与 `VirtualConstants.isPathFidelityGuest` 一致），实现前需确认。

## 四、设计要点（给未来实现）

### 4.1 拦截点

| 层 | 位置 | 做法 |
| --- | --- | --- |
| **Binder 代理** | `ActivityManagerProxy.startActivity / startActivityForResult` | 检测 `Intent.action` 属于上面 4 个 → 不发给系统；改为启动容器自己的 `PickerActivity`（用 guest 的 stub 机制），并在返回时把结果写回 guest 的 `onActivityResult` |
| 备选 | `Instrumentation` / `ActivityThread.mH` | 若 AMS 侧拿不到 `requestCode`（部分 ROM 走 `ActivityResultLauncher`），需要从这一层补 |

**为什么必须在 AMS 层**：`DocumentsUI` 是另一个 app，guest 的 `startActivityForResult` 直接跨进程到系统——
容器若不改 `Intent` 的目标，任何"路径层"手段都无效。

### 4.2 返回形态

| 方案 | 优点 | 风险 |
| --- | --- | --- |
| **`file://` + 沙箱绝对路径** | 简单；guest 直接用 `File` 打开（走我们已 hook 的路径层） | 部分 app 只接受 `content://`（会 `SecurityException`） |
| `content://` + 容器自带 `FileProvider` | 兼容性好；URI 授权可控 | 需要实现 provider + `grantUriPermission`，且 provider 也要指向沙箱 |

**建议先 `file://`**（via 这类"自绘浏览器"接受），并在探针里记录"哪些 app 要求 `content://`"。

### 4.3 浏览范围与安全

- 根目录 = 该 guest 的 `<instance>/sdcard`（+ `files` 等），**不允许上跳**（复用 `HostReadPolicy` 的规范化/越界判定）；
- 是否允许"浏览宿主文件"？按"导入替代代读"：**不在 picker 内直接给宿主路径**，
  如果要支持导入，走"用户显式选择 → 容器拷贝进沙箱"的独立入口（与 `导入通道` 一致）。

### 4.4 debug 面

- 选择器启动/返回都写 `DebugTrace.event("picker", ...)`（**debug 才产出**）；
- 不新增系统权限；不联网。

## 五、不做什么

| 项 | 原因 |
| --- | --- |
| 复刻 `DocumentsUI` 的全部功能（搜索、最近、云盘） | 目标只是"结果落在沙箱"，不是替换系统 UI |
| 在路径层（`translatePath`）解决 | 跨进程 Intent 的目标是系统组件，路径翻译覆盖不到 |
| **NIO（`UnixNativeDispatcher`）补齐** | 用户 2026-11-25 决定：NIO 用得少，除**严重危害权限**外暂不实现（见 `调研-AOSP-hook契约对照.md` §五） |
