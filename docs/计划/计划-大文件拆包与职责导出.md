# 计划：大文件拆包与「每次导出两个职责」

- 日期：2026-11-25
- 状态：**未开始**。门禁见 §零：**必须等上一个 CI 全绿 + 独立分支 + 专属 CI 与专属测试，通过后才允许拆**
- 依据：`AGENTS.md` 规则 7/9/10、`docs/架构/架构-代码分割重构评估.md`、`docs/设计/设计-项目设计理念.md`
- 硬约束（用户定）：**每次拆分只导出两个职责**；大文件改为**包**；不为压缩行数而拆；
  **拆分不轻易进主分支**

---

## 零、门禁流程（git 与 CI 纪律）

> 用户原话：「不要轻易放进主分支，应当等待上一个 CI 通过，测试完好，然后专门分配 CI 和 1 个测试，
> 通过后才允许拆分。」

| 门 | 条件 | 不满足时 |
| --- | --- | --- |
| **G0 前置** | 上一个 CI（`module-test`）**绿**，且目标模块的测试全绿；工作区无未提交改动 | 只修红，不拆分 |
| **G1 分支** | 从 `baseline-v150` 切出专用分支 `split/b<N>-<target>`（如 `split/b1-nativehookbridge`） | 不得直接在 `baseline-v150` 上拆 |
| **G2 范围** | 单批 **≤ 2 个职责**、**≤ 1 个新包**；且必须伴随 **≥ 1 个新增测试**（规则 9） | 缩小批次或先补测试 |
| **G3 专属 CI** | 为这批**单独** dispatch 一次 `module-test`，`modules` 只列该模块（必要时 `test_filter` 指向新测试类）；本地先跑 `kotlin-lint --deps` + `check-imports` | 不得靠"上一次的绿"代替 |
| **G4 合入** | G3 绿 → 合回 `baseline-v150`（`--no-ff` 保留批次记录）→ **下一批重新从 G0 开始** | 不得连拆两批再验证 |

**禁止**：

- 把拆分与功能改动/修复混在同一提交或同一 CI；
- 用"整体编译过"代替"该模块单测过"；
- 连续拆分多批再一次性验证（一次只允许一批在途）。

**为什么这么严**：本仓库踩过"为压行数而拆，拆完职责仍混杂"；也踩过
"一次改动同时碰路径/hook/文档，CI 红了不知道是哪一块"。批次隔离是最便宜的纠错点。

## 三、拆分方法（每次只导出**两个**职责）> 反例（本仓库踩过）：为把 `NativeHookBridge` 压到 1000 行以下而拆，行数达标但剩余部分
> 仍是"门面 + JNI 声明 + 规则组合 + fake content"混杂 —— **动机错了**。

### 单次拆分的固定流程

| 步 | 动作 | 产出 |
| --- | --- | --- |
| 0 | **先列调用方假设**（谁在什么时机调、依赖哪些返回值/副作用） | 契约清单（写进变更文档） |
| 1 | 落盘计划 `docs/输出/变更/<date>-<任务>.md`（逐文件 diff 预览 + 风险 + 回退） | 待确认 |
| 2 | **只导出两个职责**：建子包，把其中一个职责的代码搬过去，第二个职责再搬一次；**每次搬完编译** | 新包 + 原文件变薄 |
| 3 | 规则 9：新文件必须有 `*Test.kt`（纯 JVM 可测部分）+ 镜像文档四节 | 测试 + `docs/代码镜像/...` |
| 4 | 规则 10：`check-refactor-equivalence.mjs` 对比 `_ref` 原文函数体 | 等价性结论进镜像文档「偏差登记」 |
| 5 | CI：`module-test` 对应模块（一次一个） | 绿 |

### 为什么"两个职责"（而不是"拆到 1000 行"）

- 一次搬两个是**可审阅的上限**：三处以上同时搬家，diff 里"逻辑是否被改"看不出来（规则 10 的等价检查也会因为函数边界变化而失效）；
- 每次搬完都编译 + 跑该模块单测，能把"漏 import / private 越界"限制在一轮内；
- 与 `docs/架构/架构-代码分割重构评估.md` 的结论一致：**职责集中、命名确切**即可，行数只是信号。

### 包结构约定

```
<模块>/src/main/java/com/nextvm/<模块>/
  <职责A>/        ← 新包：只回答一个问题
    <职责A>.kt    ← 门面（必要时）
    <职责A>Parts.kt
  <职责B>/
  <原文件名>.kt   ← 只保留"组合与协调"，不再承载实现
```

## 四、分批顺序（收益/风险排序）

| 批次 | 目标 | 拆出哪两个职责 | 为什么不先拆更大的 |
| --- | --- | --- | --- |
| **B1** | `NativeHookBridge.kt`（1 067） | ① 路径规则注册/匹配 ② 属性与 proc 伪造 | 与刚完成的数据表同域，`--deps` 与现有 41 条测试可作等价证据 |
| **B2** | `native-hook.cpp`（7 468） | ① 路径重定向（redirect + 各 hooked_*）② Java IO（`install_java_io_hooks` + `hooked_java_*`） | **有分节注释**，边界天然；C++ 无单测 → 先做"编译 + 真机回归"而非等价脚本 |

## 五、验收判据

| 项 | 判据 |
| --- | --- |
| 编译 | `module-test` 对应模块绿（一次 dispatch 一个） |
| 逻辑未变 | 规则 10 脚本等价，或镜像文档「偏差登记」写明语义等价理由 |
| 依赖方向 | `kotlin-lint --deps` / `check-imports` 通过；新包不反向依赖原文件 |
| 文档 | 每个新文件一份镜像文档（四节），同一提交 |
| 真实应用 | 触及路径/hook 的批次：装包后 via 主页 + 离线列表不回退 |
| 日志 | 拆分不得改变日志门禁（`DebugFlags.isDebugBuild()`）与 `is_container_diag_path()` 过滤 |

## 六、明确**不拆**的清单

| 对象 | 原因 |
| --- | --- |
| `DebugTrace` / `DebugFlags` | 日志系统稳定优先；只允许"强化"（新增事件），不允许换机制 |
| A 族 / B 族失败语义（`libcore.io.Linux` vs `UnixFileSystem.*0`） | Android 真实差异，合并会掩盖契约（已崩 3 次） |
| `hiddenPaths` 与 `pathRedirections` | 语义相反（精确 vs 前缀），合并会失去"只隐藏一条"的能力 |
| `PathKinds` 的 14 族数据行 | 数据表，拆开就失去"唯一来源"的意义 |
| **`core:framework`（`PackageNameValidator`/`NativeLibValidator`/`DexMetadataUtils` 等）** | **很少修改、已稳定**：用户 2026-11-25 明确"确定就不需要重构，只需要用测试铆钉行为" → 只做 golden 铆钉（见 `计划-黄金测试与覆盖率提升.md` T1），不安排拆包 |
| `_ref` 里的上游注释（`STEP n` / `Phase n`） | 是启动顺序的唯一说明书，搬家必须原样带走 |

## 七、风险

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 拆分引入行为变化（尤其 `VirtualApplicationManager`） | 每批只搬两个职责 + 规则 10 等价 + 真机回归 |
| 2 | 包化后可见性变化（`private` → `internal`） | `kotlin-lint --deps` 检查，结论写进镜像文档 |
| 3 | 一次搬太多导致 diff 不可审 | 硬约束：单次 ≤ 2 个职责、≤ 1 个包 |
| 4 | C++ 拆分破坏 GOT patch 的静态初始化顺序 | 只搬函数体，不动 `static` 变量与 JNI 注册表；每批后真机验证 popup/渲染正常 |
