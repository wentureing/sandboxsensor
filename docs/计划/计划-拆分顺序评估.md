# 评估：拆解顺序

- 日期：2026-11-24
- 目的：在「职责单一 + 命名确切」的前提下，决定**先拆哪个、后拆哪个**
- 前置：`AGENTS.md` 规则 7（判据）、规则 9（拆一次=补测试+补文档）

---

## 一、评估维度

| 维度 | 含义 | 权重理由 |
| --- | --- | --- |
| **风险** | 拆错会不会改变 guest 行为 | 容器当前有未解决故障（WebView MIME / Via），动核心链路会引入新变量，无法归因 |
| **收益** | 迁出多少行、降低多少认知负担 | 拆分的目标是让人看得懂，不是行数 |
| **可验证** | 能否单测 / 真机快速验证 | 不可验证的改动等于盲改 |
| **职责数** | 一个文件里有几种职责 | 规则 7 的判据 |
| **与故障相关性** | 是否牵涉正在排查的 WebView / 启动链路 | 高相关 = 暂缓 |

## 三、结论：调整顺序（与早前计划的差异）

**早前计划**：P0 = `ActivityThreadHook`（理由是"包已建好、引用点少"）。

**本次评估改为**：**P0 = VAM 的诊断/探测块（A）**。

### 为什么改

| 理由 | 说明 |
| --- | --- |
| **风险最低** | A 全是观测代码（写文件、采样、dump），拆错最多丢日志，**不会改变 guest 行为** |
| **收益最大** | 一次迁出 ~1610 行，VAM 从 3973 → **~2360**，认知负担立减 40% |
| **不碰故障面** | WebView/MIME 故障在 bind 流程里（对应 D 块），A 完全绕开 |
| **C/D 需要真机回归** | 核心链路拆完必须跑探针全量 + Via 启动，成本高；当前故障未收口，回归基线不稳定 |

### 最终顺序

| 顺 | 批次 | 内容 | 风险 | 验证要求 |
| --- | --- | --- | --- | --- |
| **1** | **A：VAM 诊断块** | `HijackDiagnostics` / `PluginProbes` / `MemoryDexDump` / `GuestStackDump` / `GuestBootWatchdog` | 极低 | 本地检查 + 分包 CI + `debug-trace.log` 仍有对应事件 |
| **2** | **B：ActivityThreadHook 低风险块** | `ActivityTokenAndTheme` / `ApkWatchdog` / `ActivityResultHandler` / `LaunchSupport` | 低 | 同上（分包 CI：`activitythread.*`） |
| **3** | **H：VirtualResourceManager** | `ResourceInjection` / `ThemeResolution` / `AssetInjection` | 低 | 分包 CI + 探针 W3 系列 |
| **4** | **E：SystemServiceProxyManager** | 按服务族拆子包 `proxy/services/` | 中 | 分包 CI（当前无单测，需先补） |
| **5** | **G：ActivityManagerProxy** | 按方法族 | 低 | 分包 CI |
| **6** | **C：ActivityThreadHook 核心** | `TransactionInterceptor` / `InstrumentationHook` | 高 | **探针全量 + Via 启动 + 交互** |
| **7** | **D：VAM 核心** | `GuestAppCreation` / `LoadedApkInjection` / `ProviderInit` / `AutofillSupport` | 高 | 同上 + WebView 专项 |
| **8** | **F：VirtualEngine** | 门面 + 3 块 | 高 | 全量回归 |
| **9** | **I：native-hook.cpp** | C++ 拆分 | 最高 | 故障收口后，全量回归 |

**关键原则**：
- **第 1–2 批（A+B，~2150 行）可以连续做**，因为风险都是"低"且互不依赖
- **第 6–8 批必须等**：要么故障解决，要么建立稳定的真机回归基线
- **第 9 批（C++）必须最后**：动地基会污染所有其它排查

## 四、每批的固定动作（规则 9）

```
1 补样例测试（能纯 JVM 测的先抽纯函数）
2 node tools/lint/kotlin-lint.mjs --deps <源> <新>
3 迁移（只移动不改逻辑）
4 node tools/lint/kotlin-lint.mjs <目录>
  node tools/lint/check-imports.mjs <模块 src>
  node tools/lint/check-hook-idempotent.mjs <目录>
5 写镜像文档（四节）
6 dispatch module-test（包粒度 test_filter）
7 真机验证（仅第 6 批之后要求）
```

## 五、为什么 E/F/G 排在后面（虽然行数大）

| 文件 | 为什么不是优先 |
| --- | --- |
| `SystemServiceProxyManager` 3273 | **职责单一**（就是装代理），只是按服务数量堆出来的长。拆它是"分类整理"而非"职责分离"，收益低于 A |
| `VirtualEngine` 2050 | 门面类，拆开会让 11 个调用点分散；且它是"读懂容器的入口"，保持完整更有价值 |
| `ActivityManagerProxy` 1295 | 单一 InvocationHandler，所有方法都在一个 `invoke` 里分派；拆它需要先重构分派结构，属"改造"不是"搬迁" |

> 这条对应规则 7：**行数只是可疑信号，不是拆分依据**。
