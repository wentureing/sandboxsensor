## 一、先承认问题：追加式修补的实际记录

本轮从"路径转换"开始，我的实际动作序列是：

| # | 动作 | 结果 |
| --- | --- | --- |
| 1 | 发现 `host_ext` 目标错 | 改成 `sdcard/Android/data/<guest>` |
| 2 | 发现 `external_data` / `obb` 目标错 | 改成 `sdcard/Android/data`、`sdcard/Android/obb` |
| 3 | 发现 `translatePath` 全局替换 bug | 改成 `substring` |
| 4 | 发现 external 三个方法没 pathFidelity 分支 | 加三个分支 + 三个 `synthetic*` |
| 5 | 发现 `getExternalMediaDirs` 没分支 | 加分支 + `syntheticMediaDir` + 4 条规则 |
| 6 | 发现 `deviceProtectedDataDir` / `credentialProtectedDataDir` 没合成 | 加两行（**CI 因此失败**） |
| 7 | 发现 `canonicalize0` 暴露沙箱且抛异常 | 改成返回规范化原始路径 |

**每一条都是"发现一个点，补一个点"。** 七次改动后：

- `synthetic*` 函数从 3 个变 7 个
- 规则从约 10 条变 20+ 条
- `VirtualContext` 的 `pathFidelity` 分支从 10 处变 13 处
- **没有一处结构性收敛**

**用户批评准确。** 而且第 6 条直接导致 CI 失败 —— 典型的"补洞补出新洞"。

## 二、问题的结构诊断

### 2.1 根因：同一份"路径知识"写在 5 个地方

| 地方 | 存什么 |
| --- | --- |
| `VirtualConstants.syntheticXxx(pkg)` | 假路径长什么样（7 个函数） |
| `VirtualContext` 的 13 处分支 | 哪个 API 用哪个 `syntheticXxx` |
| `PackageManagerProxy` L752-768 | `ApplicationInfo` 字段用哪个 `syntheticXxx` |
| `setupAppRedirections` / `setupExternalStorageRedirections` | 宿主前缀 → 沙箱目标的规则（20+ 条） |
| `native-hook.cpp` 的 `g_path_redirects` | 同一批规则的 C++ 副本 |

**加一个新的路径族，要同时改 5 处** —— 漏一处就是 bug（第 6 条就是这么漏的：
`ApplicationInfo` 那边加了，但忘了检查 SDK 可见性）。

### 2.2 现有的一致性保证只有测试

- T39（合成路径都有规则）
- T40（幂等）
- T41（一一对应）

**都是"事后检查"** —— 加新东西时不会提醒你，只有跑测试才红。

## 二·五、边界修正：不要为了合并而合并

**用户明确要求**：「不要为了合并而合并，允许使用配置表 + 各自独立的使用方式，
对于功能差异大的不要合并。」

### 我原来的方案过度了

原第三节的方案是「三处消费方全部查表」—— 这等于把**数据**和**控制流**一起合并了。
实际这三处消费方的**使用逻辑差异很大**：

| 消费方 | 除了"知道假路径是什么"，还要做什么 |
| --- | --- |
| `VirtualContext.getFilesDir()` 等 13 处 | **先 `sandboxManager.ensureDir(...)` 建沙箱目录**，再返回假路径 |
| `PackageManagerProxy` | **设置 `ApplicationInfo` 的不同字段**（`dataDir` / `sourceDir` / `nativeLibraryDir`…），还要反射设 `credentialProtectedDataDir` |
| `setupAppRedirections` | **注册规则**（`addPathRedirection`），且**时机**与上面两处不同（guest bind 时） |

**这三件事的共同点只有"假路径模板"，其余全是差异。**
把这些差异硬塞进一个表，等于把三套控制流挤成一套 —— 那不是精简，是耦合。

### 修正后的边界

| 层 | 是否合并 | 理由 |
| --- | --- | --- |
| **`synthetic*` 的假路径模板**（7 个函数） | ✅ **合并成配置表** | **纯数据**，无副作用、无控制流 |
| **沙箱相对位置**（`files` / `sdcard/Android/data/<pkg>/files` …） | ✅ **合并进同一张表** | 同上，纯数据 |
| **宿主前缀变体**（含/不含尾斜杠） | ✅ **合并进同一张表** | 同上，纯数据 |
| `VirtualContext` 的 13 处分支 | ❌ **各自保留** | 每处都有 `ensureDir` 副作用；**但可以抽一个辅助函数**减少重复，不强行查表 |
| `PackageManagerProxy` 的字段设置 | ❌ **各自保留** | 设的是不同字段，反射逻辑只属于它 |
| 三个 `setup*Redirections` 入口 | ❌ **各自保留** | 注册时机与组合方式不同 |
| `hiddenPaths` | ❌ **不合并** | 精确匹配，与规则的前缀语义相反 |
| C++ `g_path_redirects` | ❌ **不合并** | 跨语言；且它是同步副本，不是独立知识 |
| A 族 / B 族失败契约 | ❌ **不合并** | Android 本身的真实差异 |

### 一句话

> **表只承载「数据」，不承载「控制流」。**
> 假路径长什么样、沙箱落到哪、要劫持哪些宿主前缀 —— 这三样是数据，进表。
> 谁在什么时候用、要不要先建目录、设哪个字段 —— 这些是控制流，各自保留。

## 三、重构方案：一张表驱动

### 3.1 核心想法

**把"路径族"变成一个数据结构，其余全部从它派生。**

```kotlin
// core/model/.../PathFamily.kt —— 单一数据源
enum class PathFamily {
    DATA_ROOT, FILES, CACHE, CODE_CACHE, NO_BACKUP, DATABASES, APP_DIR,
    EXTERNAL_DATA_ROOT, EXTERNAL_FILES, EXTERNAL_CACHE, OBB, MEDIA,
    APK, NATIVE_LIB,
}

/**
 * 每个路径族的全部知识：
 *   synthetic  —— 假路径怎么拼（真机形态）
 *   sandbox    —— 沙箱内落到哪（相对 <sandbox> 的路径）
 *   hostForms  —— 需要劫持的宿主前缀（含/不含尾斜杠两种形式）
 */
data class PathFamilySpec(
    val family: PathFamily,
    val synthetic: (pkg: String) -> String,
    val sandbox: (instanceId: String, pkg: String) -> String,
    val hostForms: (pkg: String) -> List<String>,
)

val PATH_FAMILIES: List<PathFamilySpec> = listOf(
    PathFamilySpec(
        family = PathFamily.FILES,
        synthetic = { "/data/user/0/$it/files" },
        sandbox = { _, _ -> "files" },
        hostForms = { listOf("/data/user/0/$it/files", "/data/data/$it/files") },
    ),
    PathFamilySpec(
        family = PathFamily.EXTERNAL_FILES,
        synthetic = { "/storage/emulated/0/Android/data/$it/files" },
        sandbox = { _, pkg -> "sdcard/Android/data/$pkg/files" },
        hostForms = { pkg -> listOf(
            "/storage/emulated/0/Android/data/$pkg/",
            "/sdcard/Android/data/$pkg/",
            "/storage/emulated/0/Android/data/$pkg",
            "/sdcard/Android/data/$pkg",
        )},
    ),
    // ... 其余 12 个
)
```

### 3.2 消费方各自保留逻辑，只共享"查数据"

| 消费方 | 改法 | 保留什么 |
| --- | --- | --- |
| **`VirtualContext`** | 保留 13 处分支（各有 `ensureDir`），**但把"取假路径"改成查表**：`PathFamilies.synthetic(FILES, pkg)` | **保留 `ensureDir` 的顺序与副作用** |
| **`PackageManagerProxy`** | 保留字段赋值与反射，只把"取假路径"改成查表 | **保留反射 `credentialProtectedDataDir`** |
| **`setupAppRedirections`** | 规则仍由它自己 `addPathRedirection` 注册，只把"宿主前缀列表"改成查表 | **保留注册时机与三个入口的分工** |

**判据：只把"常量/模板/前缀列表"换成查表；凡是带副作用的语句（`ensureDir`、`mkdirs`、
反射、`addPathRedirection`）都留在原处。**

### 3.3 编译期/结构上的保证（替代事后检查）

| 现在 | 重构后 |
| --- | --- |
| T39 事后检查"合成路径都有规则" | **表里一行写全** —— 少写 `hostForms` 会被表结构强制（`PathFamilySpec` 三个字段都必填） |
| 手写 20+ 条规则，含/不含尾斜杠各写一遍 | 表里 `hostForms` 一处写清 |
| `VirtualContext` 13 处重复的"先 ensureDir 再返回合成路径" | 一个辅助函数 |
| `PackageManagerProxy` 里手写 4 个字段 | 表驱动 |

**T39/T40/T41 保留**（作为回归测试），但不再是唯一的保障。

## 四、执行顺序（**分四步，每步可独立验证**）

| 步 | 动作 | 验证 | 风险 |
| --- | --- | --- | --- |
| **S1** | 新建 `PathFamily.kt`（纯数据 + 表），**不改任何消费方** | 加一个测试：遍历表，断言每个 `synthetic` 都有对应 `hostForms` 与 `sandbox` | 无（纯新增） |
| **S2** | `setupAppRedirections` 改成从表生成规则 | **对比重构前后 `getPathRedirectSnapshot()` 的差异** —— 必须完全相同 | 中（规则变了会全面影响） |
| **S3** | `VirtualContext` 的 13 处分支：**只把取假路径换成查表**，分支与 `ensureDir` 保留 | T39-T41 全绿 + 真机验证 via 可用 | 低~中 |
| **S4** | `PackageManagerProxy`：**只把取假路径换成查表**，字段赋值与反射保留 | 同上 | 低 |

**S2 的关键验证手段**（已有工具）：`NativeHookBridge.getPathRedirectSnapshot()`
返回规则表的 Map —— **重构前后各导一次，diff 必须为空**。这是"逻辑未变"的硬证明（对应规则 10）。

## 五、不做什么

| ❌ | 原因 |
| --- | --- |
| 不动 C++ 的 `g_path_redirects` | 它与 Kotlin 通过 `nativeAddPathRedirection` 同步；S2 做完后 C++ 侧自动得到同样的规则，不需要改 C++ |
| **不把消费方的控制流合并** | 见「二·五」：`ensureDir` / 反射 / `addPathRedirection` 都留在原处 |
| **不合并 `hiddenPaths`** | 精确匹配，与规则的前缀语义相反 |
| 不合并 Kotlin/C++ 的翻译实现 | 那是更大的工程（需要 native 侧能回调 Kotlin）。先做表驱动，收益更大、风险更小 |
| 不加新功能 | 这次是纯结构重构，行为必须逐字一致 |
| 不改 A 族/B 族契约 | 已稳定，动它风险高 |
