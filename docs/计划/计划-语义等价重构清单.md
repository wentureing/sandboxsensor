# 计划：后续值得做的「语义等价重构」清单

- 日期：2026-11-24
- 由来：v141 的 Java IO hook 只对齐了**成功路径**，就把 Via 从"显示源码但能交互"
  打成"完全不能交互"。这类"替换实现与原实现语义不等价"的问题，在容器里还有多处。
- 本文只做**清单与判据**（不含代码改动），按"已经破坏 / 高概率 / 中风险 / 低风险"排序。

---

## 一、判据：什么算「语义不等价」

替换/代理实现只要违反下面任意一条，就算不等价：

| # | 维度 | 典型偏差 |
| --- | --- | --- |
| 1 | **异常类型** | 原实现抛 `ErrnoException`，替换实现抛 `FileNotFoundException`（v141 就是这个） |
| 2 | **errno / 返回值** | 原实现 `-1 + errno=ENOENT`，替换实现返回 `0` 或吞掉 |
| 3 | **"不存在" vs "被隐藏"** | 原实现区分 `ENOENT`/`EACCES`，替换实现一律返回空/失败 |
| 4 | **调用时序** | 原实现同步生效，替换实现延迟（如 v137 的 client 包装晚于 `loadUrl`） |
| 5 | **副作用范围** | 原实现只读，替换实现顺带 `mkdirs`/写文件 |
| 6 | **生命周期/所有权** | 返回对象的所有者、可关闭性、可重复调用性改变 |
| 7 | **并发/重入** | 原实现可重入，替换实现持锁或共享可变状态 |

**验证方法（每项都必须做）**：
1. 找 AOSP 原始实现，逐条对比上面 7 个维度；
2. 写一个"只走**失败路径**"的探针用例（成功路径通常没问题，v141 就是只测了成功）；
3. 在**真实应用**上回归（探针通过 ≠ 应用可用）。

## 二、P1：高概率破坏（建议尽快处理）

### 2.1 `hooked_opendir` —— 目录枚举完全不翻译

| 项 | 内容 |
| --- | --- |
| 位置 | `core/hook/src/main/cpp/native-hook.cpp`（`opendir` 的 hook） |
| 现状 | **只打日志后直通**，不做路径翻译（`open/stat/access` 都翻译，只有它不） |
| 不等价点 | 维度 2：同一个路径，`open()` 被翻译到沙箱、`opendir()` 看真实目录 —— **两套视图** |
| 破坏表现 | 应用列目录看到真实内容、读文件读到沙箱内容；"文件明明不存在却列出来了"或反之 |
| 重构要点 | 翻译 dir 路径；同时**过滤 `readdir`** 结果（沙箱里不该暴露的条目） |
| 验证 | 探针：`new File("/sdcard").listFiles()` 应看到沙箱内容；`File("/data/data/<guest>").list()` 应看不到容器目录 |

### 2.2 `hooked_readlink` / `hooked_stat` / `hooked_lstat` / `hooked_access`

| 项 | 内容 |
| --- | --- |
| 现状 | 已做路径翻译，但**未逐个核对失败语义** |
| 需要核对 | ① 失败时 errno 是否原样透传；② `readlink` 截断行为（`PATH_MAX`）；③ `lstat` 对符号链接是否真的不跟随；④ `stat` 的 `struct stat` 是否被完整填充 |
| 破坏表现 | 应用做"存在性/权限"判断时结论与真实不符（权限判断错误 → 拒绝访问或越权尝试） |
| 验证 | 探针对不存在的路径/无权限路径/符号链接各测一次，比对 `errno` |

### 2.3 `VirtualContext.getSharedPreferences` —— 位置与命名被改写

| 项 | 内容 |
| --- | --- |
| 现状 | 名字扁平化为 `nextvm_<instanceId>_<name>`，**存到容器的 `shared_prefs/`**（不在 guest 沙箱里） |
| 不等价点 | 维度 5/6：文件位置改变；`MODE_MULTI_PROCESS`、`getAll()` 的可见性、文件监听行为都可能不同 |
| 破坏表现 | ① guest 用 `File` 直接读自己的 `shared_prefs/xxx.xml` 会读不到（实际在容器目录）；② 多进程 guest 的 SharedPreferences 一致性 |
| 重构要点 | 改存到 `<instance>/shared_prefs/<name>.xml`，并用 `File` 语义暴露（配合 v148 的 Java IO 重定向即可读） |
| 验证 | 探针：`getSharedPreferences("x",0).edit().putString(...)` 后，用 `File` 检查 `<instance>/shared_prefs/x.xml` 存在且内容正确 |

### 2.4 `VirtualContext.getDir` —— pathFidelity 分支有可疑重复

| 项 | 内容 |
| --- | --- |
| 现状 | `pathFidelity` 时先 `File(appDir,"app_$name").also{mkdirs()}`，随后**又返回另一个路径** |
| 不等价点 | 维度 5：副作用发生在 A 目录，返回值指向 B 目录 → `getDir()` 返回的目录**可能不存在** |
| 破坏表现 | `getDir("x",0).listFiles()` 为空 / `FileNotFoundException` |
| 重构要点 | mkdirs 与 return 用同一个 `File`（`syntheticDataDir` 分支时对合成路径 mkdirs，或依赖 v148 的重定向） |
| 验证 | 探针：`getDir("wvdir",0).isDirectory` 必须为 true |

## 三、P2：中风险（需要逐个核对，量大）

### 3.1 `ActivityThreadHook` 的 main-looper crash guard

| 项 | 内容 |
| --- | --- |
| 现状 | 在主 looper 上包了一层 guard，捕获异常后**不重新抛出**（Via 的崩溃栈里能看到 `installMainLooperCrashGuard$lambda$5`） |
| 不等价点 | 维度 3：应用本该因未捕获异常而崩溃退出，被"吞掉"后进入**未知状态**（不崩但功能异常） |
| 破坏表现 | 表现为"卡住/白屏/点了没反应"，而不是明确的崩溃 —— 排查难度大幅上升 |
| 重构要点 | 区分"容器自身异常"（可吞 + 记 trace）与"guest 应用异常"（应照常抛出，或至少在 trace 里带完整栈） |
| 验证 | 故意让 guest 抛未捕获异常，确认 trace 有完整栈且行为符合预期 |

### 3.2 Binder 代理层（`ActivityManagerProxy` / `PackageManagerProxy` / `SystemServiceProxyManager`）

| 项 | 内容 |
| --- | --- |
| 规模 | `SystemServiceProxyManager` 3273 行 / 143 个函数；`ActivityManagerProxy` 1295 行；`PackageManagerProxy` 850 行 |
| 不等价点 | 每个代理函数都有"参数改写/返回值改写/异常透传"三类风险；已知 `IntentParcelSanitizer` 只在"可证明是 Bitmap"时才丢 key（这条做得对） |
| 破坏表现 | 系统服务调用返回"看似成功但数据不对"，应用逻辑走错分支 |
| 重构要点 | 按"调用频率 × 失败影响"排序，先做高频（`startActivity`、`getPackageInfo`、`queryIntentActivities`、`registerReceiver`）；每个函数写一张"输入/输出/异常"对照表 |
| 验证 | 每个代理函数配一条探针用例（容器内 + 真机各跑一次，比对返回值） |

### 3.3 `VirtualResourceManager`（资源与主题）

| 项 | 内容 |
| --- | --- |
| 不等价点 | 用 framework 的 LoadedApk 重建 guest 资源 → 资源 ID、配置变更、主题解析可能与真实安装不同 |
| 破坏表现 | 界面样式错乱、`Resources.NotFoundException`、夜间模式不生效 |
| 重构要点 | 先做"资源 ID 映射表"的正确性验证，再谈重构 |

## 四、P3：低风险 / 死代码（先决定去留，不必重构）

| 项 | 建议 |
| --- | --- |
| `FileAccessInterceptor`（`NativeHookBridge.kt` 尾部，~100 行） | **零调用**。v148 已有 native 实现 → 删除，避免后人误用 |
| `AntiDetectionEngine`（805 行） | 零调用。要么接线（并修 `is_path_hidden` 精确匹配、无 `readdir` 过滤两个缺陷），要么删 |
| `IdentitySpoofingEngine` | 零调用。同上 |
| `hooked_syscall` / `fork` / `mmap` / `mprotect` / `connect` / `getaddrinfo` | 只打日志。按之前决定**保留**（诊断价值），但要明确标注"无重定向语义"，避免误以为它们在改写参数 |

## 五、执行顺序建议

| 顺 | 项 | 为什么这个顺序 |
| --- | --- | --- |
| 1 | **验证 v148 的 Java IO 语义等价**（Via 可交互） | 刚做完，必须先确认这一步真的解决了问题 |
| 2 | **2.4 `getDir`**（最小、最明确） | 一行改动级别的可疑点，先清掉 |
| 3 | **2.1 `opendir`**（视图不一致） | 影响面广（所有做目录遍历的应用） |
| 4 | **2.2 stat/access/readlink 的 errno 核对** | 需要探针配合，工作量中等 |
| 5 | **2.3 `getSharedPreferences`** | 改动涉及存储位置，需要迁移逻辑 |
| 6 | **3.1 crash guard 语义** | 影响"故障可见性"，直接关系后续排查效率 |
| 7 | **3.2 Binder 代理逐个核对** | 量最大，按频率分批 |
