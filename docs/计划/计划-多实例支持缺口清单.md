# 计划：多实例支持的缺口清单（2026-11-27 实测）

- 问题：用户同时启动多个 via / 多个 probe 时，哪些地方还不完整？
- 结论先说：**当前架构支持"同一 instance 多窗口（多 task）"，但不支持"同一 guest 包两套独立数据（真多实例）"**。
- 关联：`架构-slot租约与进程术语.md`、`架构-进程名与包名身份模型.md`

---

## 一、实测事实（2026-11-27）

| 项 | 结果 | 证据 |
| --- | --- | --- |
| instance 创建 | ✅ 正常 | `files/virtual/apps/` 下有 `mark.via_1795668196660.json`（slot=0）、`com.sandbox.probe_1795668196990.json`（slot=1） |
| 同 instance 第二窗口 | ❌ **修前完全不生效** | 日志恒为 `Launched: Via via stub …P0$Standard00`；`dumpsys` 只有 1 个 task（t1739） |
| 原因 | `StubRegistry.candidatesFor` 没过滤 `inUseStubs` → planner 永远取 `Standard00` → 同组件/同 affinity → 系统折叠回同一 task | 已修（`c0394e8`）：过滤后新会话拿 `Standard01` |
| 池上限 | 每 slot 5 个 standard stub（`ProcessSlot.kt`）→ **同一 instance 最多 5 个窗口**；真满时 `No available stub`（E 级 + `checks.log`） | 常量 `STUB_ACTIVITIES_STANDARD = 5` |

## 二、真·多实例（同包两套数据）的缺口清单

> 触发场景（用户原话）：「我启动多个 via 和多个探针」。若两套数据各要一份，就撞上下表。

| # | 位置 | 现状 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| **M1** | `VirtualPackageManagerService.registerPackage` | `packages[app.packageName] = record`（`:81/:163`） | **同包第二个 instance 覆盖第一个**的注册 → 后装的生效，前一个"消失" | 键改为 `instanceId`（同时改所有按 pkg 查询的 API 的调用点） |
| **M2** | `ActivityManagerProxy.virtualApps` | `virtualApps[app.packageName] = app`（`:147`） | 同包覆盖；`findCallingGuestPkg()` 只能返回一个包 | 键改为 `instanceId` 或 `(pkg, instanceId)` |
| **M3** | 合成路径 `VirtualConstants.syntheticDataDir` | 不含 `instanceId`（已知缺陷） | 同包两实例的 `/data/user/0/<pkg>` 合成到同一路径 → 数据互串 | 合成路径带 instanceId（会改变 guest 可见路径，属行为变更） |
| **M4** | `VirtualProcessManager` | 每 instance 一个 slot ✓；但 `processSlot` 是安装时持久化的值，容器重启后内存表为空（L2） | 重启后两实例可能被分配同一 slot | 启动时按持久化值重建占用表（L2 修复） |
| **M5** | `VirtualActivityManagerService.activityStack` | 键是 `stubClassName` | 同一 slot 上多 task 共用组件名时会**覆盖记录**（L11 同源） | 键改 `(instanceId, taskId)` |
| **M6** | `LauncherScreen` | 按 instance 显示图标（同包两实例会显示两个图标） | 两个图标点开都进同一包 → 误导 | M1/M2 修好后自然正确；过渡期可在图标上标 slot |
| **M7** | `findCallingGuestPkg()` / `currentProcessGuestPackage()` | 取 `virtualApps` 第一个 | 多实例下无法判断"我是谁" | 与 M2 一起改（按当前进程名匹配） |
| **M8** | `GuestClassLoaderRegistry` / `runningApps` / GMS-FCM | 都按 `instanceId` ✓ | — | 无需改 |

## 三、建议的推进顺序（若要做真多实例）

1. **M4（L2）**：slot 分配一致性 —— 小、独立、无行为变更；
2. **M5**：activityStack 键改 `(instanceId, taskId)` —— 配合"按 task 清理"一起；
3. **M1/M2**：VPMS/代理的键改 `instanceId` —— 大改，需要全量回归（PMS/AMS/Provider 路径）；
4. **M3**：合成路径带 instanceId —— 行为变更（guest 可见路径），必须走变更流程 + 探针 W36 回归；
5. **M6/M7**：最后一层 UI/调用者识别。

**在此之前**，用户侧的"多开"只有一种可用形态：**同一 instance 多窗口**（长按 → New instance，最多 5 个窗口/slot）。
