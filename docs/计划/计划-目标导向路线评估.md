## 二、每个目标的关键障碍与**唯一可行路线**

### 2.1 via WebView（已收敛，路线明确）

**定论**（`记录-W2-text-plain机制收敛.md` + `archive/错误结论-2026-11/README.md`）：

- `file://` 沙箱路径的 MIME 由 **Chromium 的 loader 选择**决定，**不是 Java 层**：
  - 前缀在 **app dataDir 内**（`/data/user/0/com.nextvm.app/...`）→ 走 `FileURLLoaderFactory` → **内容嗅探**（只认 GIF/JPEG/PNG/序列化魔数）→ HTML 无魔数 → `text/plain`
  - 前缀在 dataDir **之外**（如 `/data/local/tmp`，W14）→ 按**扩展名** → `text/html` ✅
- 已被否证的方案：假 `dataDir`（W37：dataDir 变了、MIME 仍错）、`shouldInterceptRequest` 补 MIME（拦不到 `file://`）、包装 WebViewClient（时序晚一步，已 revert）。

**因此唯一还没被试过的解药**：**把 guest 的内容目录放到"容器 app dataDir 之外"** ——
即 `/storage/emulated/0/Android/data/com.nextvm.app/files/...`（外部存储的 app 私有目录）。
历史上"迁外部存储"这条线被记成"已推翻"，但**推翻的理由是 W19 的 `/sdcard` 写入 EPERM**（文件没创建，实验无效），
而**外部存储的 app 私有目录**（`getExternalFilesDir`）是 app 有写权限的 —— 这是一条**没被否证、可直接验证**的路。

> 判定实验（探针已有 W 系列骨架）：把同一个 `.html` 写到
> `/storage/emulated/0/Android/data/com.nextvm.app/files/wvprobe_ext.html`，`loadUrl("file://…")`，
> 读 `document.contentType`：`text/html` ⇒ **解药成立**，目标 1 的 WebView 部分就只剩"把内容目录迁到外部存储"。

#### 2.1.1 存储路径选型与权限前提（2026-11-27 核实）

**容器实际持有的存储权限**（`app/src/main/AndroidManifest.xml` + 设备 `dumpsys`/`appops`）：

| 声明 | 设备实际 | 说明 |
| --- | --- | --- |
| `MANAGE_EXTERNAL_STORAGE` | **appops `allow`** | 唯一真正生效的存储权限（"所有文件访问"） |
| `READ_EXTERNAL_STORAGE` | `granted=false`，appops `ignore` | API 33+ 被 `READ_MEDIA_*` 取代；targetSdk 35 下**声明也不授予** |
| `WRITE_EXTERNAL_STORAGE` | `granted=false`，appops `ignore` | API 29+ 已废弃；targetSdk ≥ 29 时**不授予** |
| `android:requestLegacyExternalStorage="true"` | 仅 legacy flag | 只对 targetSdk ≤ 29 生效，本项目 targetSdk 35 ⇒ **无效果** |

**对"内容放外部存储"方案的直接后果**：

| 候选路径 | 需要什么 | 结论 |
| --- | --- | --- |
| `/storage/emulated/0/Android/data/com.nextvm.app/files/…`（`getExternalFilesDir`，**私有外部**） | **零权限**（自有包，API 19 起免权限） | ✅ **首选**：不依赖 appops 状态，干净安装也不丢 |
| `/storage/emulated/0/Download/…`、`/sdcard/xxx`（**公有**） | `MANAGE_EXTERNAL_STORAGE` | 🟡 备选：当前 allow，但**干净安装会重置为 ignore**，需脚本重授；好处是路径真实存在、guest 不拼路径时不需重定向 |
| 其他 app 的 `/storage/emulated/0/Android/data/<other>/` | **不可访问**（Android 11+ 对 `/Android/data`、`/Android/obb` 的硬限制，`MANAGE_EXTERNAL_STORAGE` 也不放行） | ❌ 不可用 |

**因此 `W-ext` 判定实验要测两组，一次拿对照**：

1. `W-ext-private`：写到 `getExternalFilesDir()` → `loadUrl("file://…")` → 读 `contentType`
2. `W-ext-public`：写到 `/sdcard/Download/…`（依赖 `MANAGE_EXTERNAL_STORAGE`）→ 同测

判读：
- 两者都 `text/html` ⇒ 选**私有**（少一个 appops 依赖）；
- 只有 public 是 `text/html` ⇒ 说明 Chromium 对 `Android/data` 有特殊判断，走公有目录方案（并接受 appops 依赖）；
- 两者都 `text/plain` ⇒ 换方向（`WebViewAssetLoader` / 内置 WebView 评估），不要再在路径上试。

**注**：guest 视角的 `/storage/emulated/0/Android/data/<guest包名>/` 在真实文件系统里**不存在**（只有 `com.nextvm.app`），
所以那类路径必须靠重定向（GOT patch / C-dual）；而公有目录（`/sdcard/Download` 等）是**真实存在**的，少一层依赖。

### 2.2 MT 基础功能（先修 L3，再谈文件）

L3 是**启动期崩溃**，与路径无关；必须先做"可诊断"，再决定修法：
1. 让 `bindApplication` 失败时落 `bind FAILED <原因>` 到 breadcrumb（现在只有笼统栈）；
2. 用 `NoClassDefFoundError: l.۠᩹ܽ` 定位：是 **legacy 路径的 dex 解析/CL 组装** 缺类，还是 MT 的加固壳在 bind 期做了自校验；
3. 修好后才是 C-dual：让 `File` 系操作落真路径。

### 2.3 跨应用 A→B（最可能是"已实现但没接线/没验证"）

代码里三件套都在（VPMS 解析 / VAMS 启动 / stub 池），**缺的是端到端验证与失败路径**。
最小实验：在 via 或 probe 里 `startActivity(Intent().setClassName("com.sandbox.probe", "…ProbeActivity"))`，
看是否走到 `VAMS.startActivity` → 目标 guest 进程被拉起 → 目标 Activity `onActivityResumed`。
判据全在 breadcrumb（两个 guest 各一份）+ `[Dbg/ctx]`/`v129` 事件。

### 2.4 采样 + 深入欺骗（按需，不阻塞 1–3）

`EnvSampler` + L0–L3 分级（详见 `计划-可运行优先与C-dual.md`）。
**关键纪律**：L3 只在"某个目标 guest 的功能被检测阻断"时才开；不做"为了过检测"的军备竞赛。

## 三、重构要不要继续？—— 按"对目标有无贡献"重排

| 重构项 | 对目标贡献 | 处置 |
| --- | --- | --- |
| **N2（lib_filter）/ N2-B / N2-C（applied/slots）** | ✅ 已完成，且给了 hook 判定能力 | 保持 |
| **N1b（`proc_spoof` 拆"读+转"）** | 🟡 间接：maps 伪造要可测（目标 4 / 检测面） | **降优先级**，等目标 1/2 有结论 |
| **R1（Kotlin 启动链收尾，VAM 1633→1400）** | ❌ 纯维护性，对四个目标零直接贡献 | **暂停**（除非 MT 崩溃定位到 VAM 编排，届时只拆那一段） |
| **R2 剩余（N3 seccomp / N4 库过滤扩展）** | ❌ 对目标无直接贡献（seccomp 只作诊断） | **暂停**，需要时单独立项 |
| **R3-1（L3：MT 启动崩溃可诊断）** | ✅✅ **直接阻塞目标 2** | **立即做** |
| **R3-2（L4 provider 成功率两条路径不一致）** | 🟡 via/provider 相关，可能影响目标 1 的稳定性 | 观察，必要时提前 |
| **契约工具 / golden / 探针** | ✅✅ 所有目标的验收仪表 | **保持并扩展**（跨应用、WebView、MT 都要新探针项） |

**结论**：**重构从"主线"降为"按需"**。只保留两类：
① 目标直接阻塞的（R3-1 / 必要时 R3-2）；
② 验收必要的（探针/契约/判据）。
其余（R1、N3、N4）等目标推进中出现真实痛点再做 —— 这正是"可运行优先"的落地。

## 五、风险与舍弃

| 风险 | 对策 |
| --- | --- |
| WebView 外部存储方案也可能失败（Chromium 可能对所有 file:// 都嗅探） | **P1 是"判定实验"而不是"实现"**：先花半天验证，不成立就换方向（回到 `WebViewAssetLoader`/内置 WebView 的评估） |
| MT 的 L3 崩溃可能是加固壳自校验（不可修） | 先做"可诊断"；若确认是自校验 → 明确记为"不支持"，不硬啃 |
| 跨应用触发多实例缺口（M1–M8 暂缓） | 先用"单实例 + slot 复用"验证；多实例问题单独立项 |
| C-dual 打开后包名暴露 | 用 maps/status 伪装（不依赖路径翻译）+ 探针量化；L3 按需 |
| 重构暂停导致技术债累积 | 保留契约工具与判据；每阶段末回顾"是否有重构项该提前" |

## 六、立即可做的第一批（建议顺序）

1. **P0-②**：加 3 个探针项（`W-ext` / `X1` / `H1`）—— 它们是后面所有阶段的判据；
2. **P0-①**：`EnvSampler`（只采样，零行为变更）；
3. **P1**：`W-ext` 判定实验（半天量级，决定 WebView 方向）；
4. **P3**：R3-1（MT 崩溃可诊断）—— 与 P1 并行，互不干扰。

这样**在同一天内就能拿到两个决定性答案**：WebView 能不能靠"换存储位置"解决、MT 到底崩在哪。
