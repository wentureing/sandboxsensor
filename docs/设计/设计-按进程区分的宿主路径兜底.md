# 设计：按进程区分 + 容器目录改造，能否解决「guest 逃到宿主 external」

- 日期：2026-11-25
- 触发：用户提出「之前明确过 hook 需要过滤进程；如果区分进程，或把容器目录新增改造、
  容器不再用经典目录，自噬问题能否解决」
- **结论：能解决，而且现有代码已经具备前提（P0-3 主进程不装 hook）。**

---

## 一、先明确我上一份文档的错误

上一份说「方案 A（加规则 `.../data/com.nextvm.app/` → 沙箱）会**自噬**」——
**这个判断错了**。

错在哪：我默认"容器和 guest 共享同一个进程的规则表"，但实际**不共享**：

| 事实 | 证据 |
| --- | --- |
| 主进程**完全不装 hook**（P0-3） | `NativeHookBridge.initNativeHooks` 开头：`if (procName == hostPkg) { skip; return false }` |
| 规则表是**进程级**（per-process @Singleton） | `NativeHookBridge` 每个进程一份实例 |
| 每个 guest 在**独立进程** | `mark.via:p0`、`com.sandbox.probe:p1`（实测 `ps`） |

**所以**：
- 规则 `.../data/com.nextvm.app/ → <sandbox>` **只在 guest 进程生效**
- 容器主进程（`com.nextvm.app`）**根本看不到这条规则** → **不会自噬** ✓

---

## 二、多 guest 会不会冲突？不会

| 场景 | 结果 |
| --- | --- |
| guest A（`:p0`）注册 `.../data/com.nextvm.app/ → sandboxA` | 只在 `:p0` 进程生效 |
| guest B（`:p1`）注册 `.../data/com.nextvm.app/ → sandboxB` | 只在 `:p1` 进程生效 |
| 两者同时跑 | **进程隔离，各自生效** ✓ |

前提：**同一包名的两个实例不能同时跑在同一进程**（容器用 `:p0`/`:p1`… 分槽，已满足）。

---

## 三、还要确认一件事：guest 是否依赖「容器真实的 external」

如果 guest 进程里有代码要读**容器放在 external 的东西**，那重定向后会读不到。

**实测**：容器 external 下 `.../files/` 的 8 个目录（`filters`/`font`/`gm`/`logs`/`offline`/`proxy`/`syncing`/`tabs`）
**全部为空**（`find -type f` 无结果），且是 **11:07 才创建**（= via 启动时自己建的）。

→ **容器没有在 external 放任何东西给 guest**（容器自己的数据都在 `files/` 内部存储：
`virtual/apks`、`virtual/data`、`debug-trace.log` 等）。

**所以重定向 `.../data/com.nextvm.app/` 是安全的** ✓

---

## 四、方案设计

### 4.1 方案 A（最小改动）：加一条"宿主 external 兜底"规则

在 `NativeHookBridge.setupAppRedirections`（或新增一个 `setupHostExternalRedirect`）里加：

```
/storage/emulated/0/Android/data/<HOST_PKG>/   →  <sandbox>/host_ext/
/sdcard/Android/data/<HOST_PKG>/               →  <sandbox>/host_ext/
```

以及对应的 Java 侧（`VirtualContext.getExternalFilesDir` 对 `HOST_PKG` 也要给沙箱路径）。

**效果**：
- via 用 `getOpPackageName()` 拼出的宿主路径 → 落到 `<sandbox>/host_ext/`
- 保存 + 列表**都在沙箱** → 一致 → **能看到** ✓

**风险点**（必须验）：
1. guest 需要读**容器真实** external 时会被挡 → 实测容器 external 为空，**当前无影响**
2. `host_ext` 目录需要预建（否则又是 ensureDir 那类问题）
3. 与 `pathFidelity` 模式的交互需要单独确认

### 4.2 方案 B（更彻底）：容器"搬家"，不再使用 classic 目录

用户提的第二条思路 —— 让容器根目录不再叫 `com.nextvm.app` 的 classic 位置。

| 做法 | 说明 |
| --- | --- |
| 容器所有数据移到 `files/`（内部存储） | 已经基本如此（`files/virtual/...`） |
| **容器不再创建 `Android/data/com.nextvm.app/` 下的功能子目录** | 需要审计：目前 8 个目录是 **via 创建的**，不是容器的 ✓ |
| 容器自己的"导出"类文件（如日志/APK 导出）改用 `Download/` 或 SAF | 让用户可见 |

**收益**：`.../data/com.nextvm.app/` 变成"只被 guest 误用"的目录，可以**无条件整体重定向**，
不需要担心和容器冲突。

**成本**：需要审计容器所有写 external 的地方（`DebugFlags`/`collectProbeOutput` 等）。

### 4.3 两者关系

- **方案 A 是方案 B 的最小可行版**：不改容器目录布局，只加兜底规则。
- **方案 B 是长期正解**：容器不占用"guest 可能误以为是自己的"目录名。

**建议**：先做 A（小、可回退），验证有效后再评估 B。

## 五、还要补的两个 hook（这是用户"必要 hook 未实现"的实质）

| # | 缺什么 | 为什么必须 |
| --- | --- | --- |
| **1** | **`getOpPackageName()` 的路径语义兜底** | 它返回宿主是必要的（appops），但**用它拼路径的代码**需要额外重定向 |
| **2** | **`ContextImpl.mPackageName` 的间接使用** | `LoadedApk.mPackageName` 被故意设宿主（L1067），凡是走 `ContextImpl` 内部用 `mPackageName` 拼路径的 API 都会逃逸（`getExternalFilesDir` 的**未包装**版本、`Environment.buildExternalStorageApp*`） |

**即**：不是"漏了某个方法 hook"，而是**"宿主包名"这条信息被用在了两处语义不同的地方**：
- appops 归因（必须宿主）
- 路径构造（应该 guest）

**兜底的正确位置**：**路径层**（重定向规则 / `Environment` hook），而不是改包名返回值。

| # | 检查项 | 判据 |

| 1 | 主进程确实不装 hook | `debug-trace.log` 有 `initNativeHooks skip: container main process` |

| 5 | via 离线列表能看到条目 | 用户目视 |
| 6 | 容器主界面功能不受影响 | 导入 APK（从 `/sdcard/Download`）仍可用 |

## 七、一句话结论

> **能解决。**关键前提已经具备：**hook 是进程级过滤的，主进程根本不装**。
> 所以"把 `.../data/com.nextvm.app/` 重定向到沙箱"**不会自噬**。
>
> 我上一份文档把"自噬"当成障碍是错的 —— 那是我没考虑到 P0-3 的进程过滤。
>
> 方案 A（加兜底规则 + 预建 `host_ext`）即可解决 via 的"保存与列表不一致"；
> 方案 B（容器不再占用 classic 目录）是长期正解。
