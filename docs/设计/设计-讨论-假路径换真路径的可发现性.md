# 讨论：从假路径到真路径，via 能不能直接发现？能不能做到不被发现？

- 日期：2026-11-25
- 背景：`contentPathsUseReal = false` 之后，8 个内容目录返回**真实沙箱路径**
- 问题：via 主进程能否直接发现自己在容器里？能否做到"不直接发现"（WebView 那侧不管）？

---

## 一、结论先行

> **在当前架构下，「via 不能直接发现」与「WebView 能读到文件」是互斥的。**
>
> **原因链**：WebView 的 isolated 进程只认**真实存在**的路径 →
> 交给它的路径必须真实 → 而那个路径是 via 从 `getFilesDir()` 拿的 →
> **所以 via 拿到的必然也是真实路径** → **必然可被发现**。
>
> **唯一解**是 hook `WebView.loadUrl`（让"真路径"只在交给 WebView 的那一刻出现）。
> 那需要改 `ArtMethod` entry，代价大。
>
> **但"能被发现"和"会被判定为容器"不是一回事** —— 下面把可发现面按严重程度分级，
> 先做代价最低的几个改善。

---

## 二、via 能直接发现的地方（按严重程度分级）

### 🔴 严重：逻辑自相矛盾，任何检测逻辑都会命中

| # | 检测 | 真机 | 我们现在的状态 |
| --- | --- | --- | --- |
| **1** | **`getFilesDir().getParentFile() == getDataDir()`** | **true** | **false** ← **最致命**<br>`getFilesDir()` = `/data/user/0/com.nextvm.app/files/virtual/data/<inst>/files`<br>`getDataDir()` = `/data/user/0/mark.via` |
| **2** | **`getDataDir() + "/files" == getFilesDir()`** | **true** | **false** |
| **3** | **`getCacheDir()` 与 `getFilesDir()` 同一父目录** | **true** | **true** ✓（都没变，都是真路径） |

**为什么 #1 最致命**：这不是"路径长得奇怪"，而是**框架不变量被破坏**。
任何检查"我的目录结构是否自洽"的代码（哪怕不是专门的反双开逻辑）都会命中。

**Android 自己就有这类检查**：`ContextImpl.makeFilename(getFilesDir(), name)`、
`StorageManager.fixupAppDir`，以及各种 `ensureDirExists`。

### 🟠 中等：路径内容异常，一眼可见

| # | 检测 | 我们看到的值 |
| --- | --- | --- |
| 4 | `getFilesDir().getAbsolutePath()` | 含 `com.nextvm.app` + `virtual/data` + `mark.via_1795592068530` |
| 5 | `getExternalFilesDir(null)` | 含 `com.nextvm.app` |
| 6 | `getFilesDir()` 的**段数** | 9 段（正常是 5 段） |
| 7 | 路径里含**实例 ID**（`mark.via_<数字>`） | 正常 app 的路径不含这种后缀 |
| 8 | `StatFs(getFilesDir())` | 会成功（真路径），但挂载点是容器的 data 分区 |

### 🟡 轻微：真机上也可能出现，不足以单独定罪

| # | 检测 | 说明 |
| --- | --- | --- |
| 9 | `getOpPackageName()` = `com.nextvm.app` | 真机上"共享 uid"的应用（如 Google 系）也会返回别的包名 |
| 10 | `getPackageName()` = `mark.via` | 正确 ✓ |
| 11 | `/proc/self/cmdline` | `mark.via` ✓ |
| 12 | `/proc/self/maps` 里的 APK 路径 | 合成（`/data/app/~~VmK8x2==/`）✓ |
| 13 | `getApplicationInfo().dataDir` | 合成（`/data/user/0/mark.via`）✓ |

### ✅ 已伪装好的

| # | 项 | 状态 |
| --- | --- | --- |
| 14 | `getDataDir()` / `ApplicationInfo.dataDir` | 合成 ✓ |
| 15 | `sourceDir` / `publicSourceDir` / `nativeLibraryDir` | 合成 ✓ |
| 16 | `getPackageName()` / `getPackageCodePath()` | 正确 ✓ |

## 三、能不能做到"不直接发现"

### 3.1 为什么不可能（在当前架构下）

```
WebView isolated 进程
    ↑ 只认真实存在的路径
    │
via 从 getFilesDir() 拿路径 → 传给 WebView
    ↑
如果 getFilesDir() 返回假路径 → WebView 读不到（当前问题的来源）
如果 getFilesDir() 返回真路径 → via 自己也能看到（当前状态）
```

**没有第三个选项** —— 除非在"传给 WebView"那一刻做替换。

### 3.2 三条理论上可行的路

| 路 | 做法 | 能解决吗 | 代价 |
| --- | --- | --- | --- |
| **A. hook `WebView.loadUrl`** | 在 via 进程内把假路径换成真路径再交给 WebView | ✅ **完整解决** | 需改 `ArtMethod` entry（per-API 偏移表），与"精简"理念冲突 |
| **B. 让假路径"真的存在"** | 让 `/data/user/0/mark.via/` 真实存在（mount --bind / 符号链接） | ✅ 完整解决 | **需要 root 或挂载权限** —— 容器在非 root 环境做不到 |
| **C. 全部用真路径**（当前） | 接受暴露 | ⚠️ 牺牲伪装 | 零成本 |

**A 的替代思路（代价可能更低）**：
不 hook `loadUrl`，而是 **hook `WebView` 的构造函数**，注入一个自定义 `WebViewClient`？
—— 不行，via 自己会 `setWebViewClient`，把我们的覆盖掉。

**A 的另一个思路**：hook `Context` 的 `startActivity`？—— 与 `file://` 无关。

### 3.3 降低严重程度（代价低，收益明确）

即使做不到"完全不发现"，也可以把 🔴 严重项消掉：

#### 改善 1：让 #1/#2 成立 —— 统一 `getDataDir()` 与 `getFilesDir()` 的根

| 选项 | `getDataDir()` | `getFilesDir()` | #1 成立? | 反双开检测 |
| --- | --- | --- | --- | --- |
| **现状** | 合成 | 真 | ❌ | ✅ 通过（dataDir 是假的） |
| **改法 A** | **真**（同 `getFilesDir()` 的父） | 真 | ✅ | ❌ **挂** |
| **改法 B** | 合成 | **合成** | ✅ | ✅ | **但 WebView 又读不到** |

**结论**：**改善 1 与"WebView 能读"互斥** —— 和 3.1 是同一个矛盾。

#### 改善 2：让真路径"看起来更正常"（**这条可以立即做**）

现状：
```
/data/user/0/com.nextvm.app/files/virtual/data/mark.via_1795592068530/files
```

可以缩短/改形为：
```
/data/user/0/com.nextvm.app/files/vmd/<inst>/files        ← 少两层、去掉 "virtual data"
```

**收益**：段数从 9 → 7，"virtual" 这种明显字样消失。
**局限**：仍然含宿主包名与实例 ID，**仍然是 🟠 级**。

#### 改善 3：把实例 ID 换成不含包名的形态（**可评估**）

现状 `mark.via_1795592068530` → 改成 `i1795592068530` 或纯数字 ID。
**收益**：路径里不再重复出现 guest 包名（因为 `getPackageName()` 已经能拿到）。
**局限**：仍是实例 ID，仍是容器特征。

## 四、建议的取舍（按"投入 / 收益"）

| 优先 | 动作 | 收益 | 代价 | 建议 |
| --- | --- | --- | --- | --- |
| **P1** | **接受现状**（🔴 #1 存在） | 0 | 0 | **短期必须接受** —— 否则 WebView 读不到 |
| **P2** | **改善 2**（缩短真路径、去掉 `virtual data` 字样） | 🟠 级项减少 | 低（改 `SandboxManager` 的目录布局 + 规则） | **值得做**，但要动路径布局，影响面大，需单独计划 |
| **P3** | hook `WebView.loadUrl` | **彻底解决** | 高（`ArtMethod` 偏移表） | **内置 WebView 时一起做**（那时渲染进程是我们自己的，不需要 hook，直接给假路径即可） |
| ❌ | 让假路径真的存在（mount） | 彻底解决 | 需要 root | 本项目前提不成立 |

### 关键判断

> **P3（内置 WebView）是唯一能同时满足"WebView 能读 + via 看不出"的路。**
> 因为内置之后，渲染进程由容器自己 fork → **能装 hook** → **可以用假路径**。
>
> **所以现在的 `contentPathsUseReal = false` 是过渡态**：
> 牺牲"via 看不出"换取"WebView 能用"，
> 等内置 WebView 之后再改回 `true`。

---

## 五、一句话

> **"via 不能直接发现"与"WebView 能读到文件"在当前架构下互斥——因为 WebView 只认真实路径，
> 而那个路径必然经过 via 的手。**
>
> **现状是一个刻意的取舍**：用"via 能看到容器路径"（🔴 #1 逻辑不自洽）换"WebView 能用"。
> **彻底解决要等内置 WebView**——那时渲染进程归我们所有，才能既给假路径又让它读到文件。

## 六、附：现状下 via 最可能踩到的两个具体检测

如果 via（或它的某个第三方库）真的做反双开检测，最可能命中的是这两个：

```java
// 检测 1：父子关系不成立
File files = getFilesDir();
File data  = getDataDir();
if (!files.getParentFile().equals(data)) {
    // 真机上永远相等；我们这里不相等 -> 立刻判定为容器
}

// 检测 2：路径段数/字样
if (files.getAbsolutePath().contains("/virtual/")) {
    // "virtual" 这个词在真机上不会出现
}
```

**这两条都比"含宿主包名"更容易写、更常见** —— 因为它们不依赖任何"猜包名"的逻辑，
只是检查框架不变量。
