# 设计：项目设计理念（三条，按优先级）

- 日期：2026-11-25
- 状态：**有效，约束后续所有改动**
- 本文档是评审任何改动的第一道尺子。改动与本文件冲突时，要么改改动，要么先改本文件。

## 理念 1：在尽可能有条理、技术易实现的前提下工作

### 反面（本项目真实踩过的）

| 做法 | 后果 |
| --- | --- |
| 边想边改 | 修好 A 弄坏 B，`DiagnosticsSink` 半成品、WebView hook 先加后回退 |
| 凭记忆判定"某能力有没有覆盖" | 同一轮内三次误判（`getFileStreamPath` / `getPackageCodePath` / `dataDir` 实际都已覆盖） |
| 遇到一个崩溃修一处 | 同一个 `ErrnoException` 类名错误藏了 4 个版本（v141→v148） |
| 一个文件塞多种职责 | `VirtualApplicationManager` 4540 行、`native-hook.cpp` 6500+ 行，没人说得清它负责什么 |
| 用"能不能跑"当唯一判据 | 探针 W38 通过，Via 却完全不可交互 |

### 正面（本项目已经被证明有效的方法）

| 方法 | 具体做法 | 证据 |
| --- | --- | --- |
| **三源交叉** | AOSP 源码看行为 / 设备 dex 看谁是真 native / 日志看谁没生效 | 三次关键发现分别来自三源（见下） |
| **契约驱动** | 先列出「所有调用方对该方法的假设」，再动代码 | `IoUtils.canOpenReadOnly` 假定 `open` 非 null → 我们返回 null 就崩 |
| **分层可见** | 每层 hook 独立计数，`checks.log` 能直接读出"哪层没生效" | 多层架构下"哪层没生效"不能靠猜 |
| **最小必要** | 只在"别的层做不到"时才 hook Java 层 | 能靠 `VirtualContext` 解决的，一律不 hook |
| **先测再改** | 写测试钉住现状，让测试先红再改 | T8 在写测试时才发现 `String.replace` 全局替换的 bug |
| **改完就跑静态检查** | `kotlin-lint` 毫秒级拦括号/KDoc/跨文件 private | 已连续 3 轮靠它拦住 CI 失败 |

### 三源交叉的具体分工

| 源 | 回答什么 | 典型发现 |
| --- | --- | --- |
| AOSP 源码（`libcore_io_Linux.cpp` / `UnixFileSystem_md.c`） | **行为**：失败抛什么异常、返回什么值 | `createFileExclusively0` 非 EEXIST 要抛 `IOException` |
| 设备 dex（`dexdump`） | **谁是真 native** | `File` 的 native 在 `UnixFileSystem` 而非 `Linux`；`checkAccess`/`getLength` 已是 Java 方法 |
| 运行时日志 | **谁没生效** | `ErrnoException unavailable` → 类名写错（`libcore.io` vs `android.system`） |

**缺任何一源都会错**：
- 只看源码 → 会去 hook `getLength` 这种已经是 Java 的方法
- 只看 dex → 不知道失败该抛什么异常
- 只看日志 → 不知道该补什么

### 判据（自查三问）

1. 这个结论**有实测证据**吗（日志 / 反汇编 / 探针编号）？没有就是猜测。
2. 改动**影响几个文件**？≥3 个或 ≥50 行 → 先落盘计划再动手。
3. 有没有**先写测试**？改 hook 行为却不加测试 = 下一个版本会被别的东西改回去。

## 理念 2：充分利用上游代码

### 上游已有的，先找再改

| 需要的能力 | 上游**已有** | 我们的正确做法 |
| --- | --- | --- |
| 路径保真（假路径 + 真映射） | `pathFidelity` / `v135-pathfidelity`，含 `syntheticDataDir` / `syntheticApkPath` / `syntheticLibDir` | **直接用，只扩展白名单**（原来是 `packageName == CM_PACKAGE`，改成可编辑集合） |
| `ApplicationInfo` 的路径伪装 | `PackageManagerProxy` L752-758 已有 pathFidelity 分支 | **在分支里加两行**（`deviceProtectedDataDir` / `credentialProtectedDataDir`），**不另起一套** |
| guest 生命周期追踪 | `GuestBreadcrumb` 全链路 **199 处**埋点 | **直接用**，不要另加日志体系 |
| 诊断体系 | `Diagnostics` / `CheckResult` / `DiagnosticsRouter` / `FileSink` | **先用，验证可用性后再改**（已做过专项验证：`docs/输出/调研/调研-上游诊断体系可用性验证.md`） |
| 多槽位 / 进程隔离 | `ProcessSlot` / `VirtualContext` / `VirtualApplicationManager` | 沿用，不改架构 |
| native GOT patch | `install_plt_hooks` + `NS_HOOK_SYSTEM_LIBS` | 沿用 |

### 上游的 bug 修，上游的机制用

这两件事必须分开：

| 情形 | 处置 |
| --- | --- |
| 上游**机制**是对的，只是某个参数/目标写错 | **改参数，保留机制** —— 例：`external_data/` / `obb/` 目标写错，机制（规则映射）本身是对的 |
| 上游机制有**设计缺陷** | 记录在「偏差登记」，评估后决定是否改 —— 例：`syntheticDataDir` 不含 `instanceId`（多实例撞车） |
| 上游**代码风格**不合我们偏好 | **不改** —— 与 guest 可用性无关 |

**反例（本项目踩过）**：看到 `external_data` / `obb` 目标错，第一反应是"上游不可信，全部重写"；
实际上**规则映射这个机制是对的**，只需要改两个目标字符串。重写会把 `pathFidelity` 那套也一起丢掉。

### 判据

1. 这个能力，**上游有没有现成实现**？有 → 先读它、扩展它。
2. 我要改的，是**参数**还是**机制**？参数错 → 改参数；机制错 → 先记录再评估。
3. 我的改动**会不会让上游的其它模块失配**？例：改 `syntheticDataDir` 必须同步
   `PackageManagerProxy`（它也在设 `dataDir`）。

## 理念 3：路径欺骗 —— 看起来真实、用起来重定向、骗不过就放弃

### 三句话拆开

| # | 原则 | 含义 | 当前实现 |
| --- | --- | --- | --- |
| **3.1** | **路径看起来真实** | guest 拿到的路径与真机安装完全一致，不含宿主包名 / `virtual/data` / `instanceId` | `syntheticDataDir` = `/data/user/0/<pkg>`；`syntheticExternalDir` = `/storage/emulated/0/Android/data/<pkg>`；`syntheticApkPath` 用 `VmK8x2` token 与 `/proc/self/maps` 对齐 |
| **3.2** | **用起来重定向** | 假路径的 I/O 全部映射回沙箱，读写正常 | `setupAppRedirections` 的规则 + `hooked_ufs_*` / `Linux.*` 的路径翻译 |
| **3.3** | **骗不过就放弃** | 某个组件（如 WebView）无法被欺骗时，**放弃对它欺骗**，不为了它牺牲整体 | `Environment` / `MediaStore` / `StorageVolume` 全部**不骗**（它们本来就不含包名） |

### 3.3 是务实原则，不是妥协

"骗不过就放弃"不等于"放弃目标"，而是**分清哪些地方需要骗、哪些不需要**：

| 对象 | 需要骗吗 | 依据 |
| --- | --- | --- |
| `Context.getFilesDir()` / `getExternalFilesDir()` | **需要** | 返回值含宿主包名 + `virtual/data`，一眼看出双开 |
| `ApplicationInfo.dataDir` / `sourceDir` | **需要** | 同上 |
| `Environment.getExternalStorageDirectory()` | **不需要** | 返回 `/storage/emulated/0` —— 共享存储根，**真机就是这个值，不含包名** |
| `MediaStore.*` | **不需要** | 走 `content://` URI，**不返回绝对路径** |
| `StorageVolume.*` | **不需要** | 卷路径，不含包名 |
| `getPreloadsFileCache()` | **不需要** | `/data/preloads/...` 系统路径 |
| `getSharedPreferencesPath()` | **不需要** | 已扁平化到宿主目录（`nextvm_<instanceId>_<name>.xml`），不走这条 |
| `WebView` 的 MIME 判定 | **按结果决定** | 若 `getDataDir()` 给假路径后 MIME 恢复正常 → 骗成功；若骗不过 → 放弃对 WebView 的欺骗，保证 app 主体正常 |

**"保证 guest 被骗即可"** ：目标是**让 guest 的主体逻辑认为自己在真机上**，
不是"让每一个 Android API 都返回假路径"。

### 3.4 「只误导，不危害读写」—— 这是硬约束

欺骗的前提是**功能不能坏**。三条可检验的约束：

| # | 约束 | 执行方式 |
| --- | --- | --- |
| 1 | **每个合成路径都必须被某条规则覆盖** | `T39 每个合成路径都有对应规则` —— 穷举 14 个具体路径，断言被改写、不是 `/dev/null`、等于预期沙箱目标 |
| 2 | **合成路径翻译必须幂等** | `T40 合成路径翻译幂等` |
| 3 | **合成路径与沙箱真身一一对应** | `T41` —— 不允许两个合成路径映射到同一处（反例：`external_data/` 与 `sdcard/Android/data/<pkg>/` 曾同时被当真身） |

**第 4 条（尚待实现）**：合成路径的**父目录**必须在沙箱内真实存在，否则
`File.mkdirs()` 在假路径上的行为会依赖 hook 是否漏映射。

### 3.5 反面案例：`canonicalize0` 曾经两头都错

```
失败时：throw IOException          → 危害（StorageManager.fixupAppDir 报错）
成功时：return realpath 结果       → 暴露（那是 <sandbox>/... 沙箱路径）
```

**正确的做法**：合成路径**永远**返回「逻辑规范化后的原始路径」——
与 `realpath` 结果同形、实际不存在、不泄露沙箱、不抛异常。

**这就是 3.1 + 3.2 + 3.4 三个原则的交点**：
- 看起来真实（3.1）→ 返回的是合成路径
- 用起来重定向（3.2）→ 后续 I/O 由规则接管
- 不危害读写（3.4）→ 不抛异常

### 判据（改任何路径相关代码前的四问）

1. 这个路径**会不会被 guest 看到**？会 → 需要合成；不会 → 不合成。
2. 合成之后，**有没有对应规则**？没有 → 就是"危害读写"，必须补（T39 会红）。
3. 这个方法**失败时**该抛异常还是返回空？**返回空会不会让调用方崩**？
   （`IoUtils.canOpenReadOnly` 假定 `open` 非 null → 空值会让它 NPE）
4. 这个方法**成功时**返回的值里，**有没有宿主包名 / `virtual/data` / `instanceId`**？
   有 → 说明还在泄露。

## 三条理念的关系

```
理念 1（有条理、易实现）
   ↓ 提供方法：三源交叉、契约驱动、先测再改
理念 2（充分用上游）
   ↓ 提供基座：pathFidelity、Breadcrumb、Diagnostics、ProcessSlot
理念 3（路径欺骗）
   ↓ 在此基座上做具体的事：看起来真实 + 重定向 + 骗不过就放弃
   ↓ 硬约束：只误导、不危害读写
```

**理念 1 是方法，理念 2 是资源，理念 3 是目标。**
三者冲突时：**理念 3 的硬约束（不危害读写）优先于一切** ——
宁可不骗，也不能把 guest 弄坏。
