# 设计：重构前后行为等价性验证

- 日期：2026-11-24
- 问题：已经拆了 ~1350 行（v148–v158），只验证了「能编译 + 单测过」，
  **没有机制证明"行为没变"**。
- 目标：用测试自动证明「重构前后行为等价」，并落进 CI。

---

## 一、业界三种方案

| 方案 | 做法 | 适用 | 本项目可用性 |
| --- | --- | --- | --- |
| **Characterization / Golden Master** | 重构前把现有输出录成「批准文件」，重构后逐字对比 | 有确定输出、可批量输入 | ✅ **主方案** |
| **Differential（新旧并存）** | 旧实现与新实现同时跑同一输入，比较结果 | 重构期间临时保留旧代码 | ✅ 用于高风险块 |
| **Property-based** | 随机生成输入，验证不变量（如"永不抛"） | 有明确数学性质 | ⚠️ 辅助 |

**不采用**：纯覆盖率（覆盖率 100% 也可能行为变了）。

## 二、本项目的三层设计

### 第 1 层：纯函数 Golden（**现在就能做，价值最高**）

对**所有不依赖 Android 运行时的函数**，准备固定语料 → 录输出 → 逐字对比。

当前可覆盖的纯函数：

| 函数 | 语料 | 输出形态 |
| --- | --- | --- |
| `TransactionItemDescriber.describe(item, className)` | 各类 item 形态（正常/缺字段/类型不符/未知） | 单行文本 |
| `PathRedirectRegistry.translate(path)` | 11 条真实规则 + 边界路径 | 翻译后路径 |
| `ProcSpoofing.buildFakeProcStatus(pid, pkg)` | 常规/超长包名/极值 pid | `/proc/self/status` 文本 |
| 开关与白名单判断 | 各种包名/类名 | `true`/`false` |

### 第 2 层：Differential（高风险块专用）

拆分**核心链路**（如 `TransactionInterceptor`、`InstrumentationHook`）时：

```
src/main/.../activitythread/TransactionInterceptor.kt      ← 新（拆分后）
src/test/.../legacy/LegacyTransactionInterceptor.kt        ← 旧实现（仅测试源集，不打包）
```

测试同时调用两者，对同一批输入断言输出一致。**合并后删除 legacy 版本**。

> 好处：不用先录 golden（省一步），且旧实现就是真相来源。
> 代价：拆分期间要维护两份代码。

### 第 3 层：真机行为 Baseline（探针）

探针 W1–W40 的结果落盘为 JSON，重构前后各跑一次做 diff。

```
probe-reports/baseline/<日期>-<容器sha>.json     ← 存进仓库，作为历史基线
```

**不能全自动**（需要设备），但可以：
- 每次大重构后**手动跑一次**，把 JSON 存进仓库
- 用 `tools/compare-probe-baseline.mjs` 做结构化 diff（按探针编号逐项比）

## 三、仓库结构

```
core/<module>/
  src/
    main/java/...                      业务代码
    test/
      java/...                         单元测试
      resources/golden/                ← 新增：批准文件（进仓库、可 review）
        TransactionItemDescriber/
          approved.txt
        PathRedirectRegistry/
          approved.txt
        ProcSpoofing/
          approved.txt
tools/
  golden/
    golden.mjs                         读/比对/重录（UPDATE_GOLDEN=1）
```

**为什么 golden 文件要进仓库**：

1. **可 code review** —— 重构的 PR 里能直接看到"输出有没有变"，这比断言更直观；
2. **变更要有意识** —— 想改 golden 必须显式重录，等于"承认行为变了"；
3. 避免"测试通过但行为漂移"（断言写松了就漏）。

## 四、CI 设计

**不新增 workflow**，直接扩展现有的 `module-test.yml`：

| 步骤 | 说明 |
| --- | --- |
| `testDebugUnitTest` | 已包含 golden 测试（普通 JUnit） |
| **`UPDATE_GOLDEN` 必须为空** | CI 里**禁止**自动重录 —— 否则行为变化会被静默"批准" |
| golden 不匹配时 | 测试失败，日志打印**实际 vs 期望的 diff**（逐行） |

额外给 `module-test.yml` 加一个 `fail_on_golden_mismatch`（默认 true）—— 其实不需要，JUnit 断言失败就是失败。

**关键规则（写进 AGENTS.md）**：

> **CI 永远不设置 `UPDATE_GOLDEN`。** 重录只能在本地、且必须在 commit message 里说明"为什么行为变了"。

## 五、Golden 的实现约定

### 记录格式

```
# <case 名称>
输入描述 => 输出
```

**要求**：
- **逐字对比**（不 trim、不忽略空白）—— 空白变化也可能影响日志解析
- 每个 case 一行，便于 diff
- 顺序固定（按语料数组顺序，不排序）—— 顺序变化也算行为变化

### 重录流程

```powershell
# 本地：确认行为变化是有意的，然后重录
$env:UPDATE_GOLDEN='1'; .\gradlew :core:virtualization:testDebugUnitTest --tests "*GoldenTest"
git diff core/virtualization/src/test/resources/golden/   # 看清到底变了什么
```

### 断言失败时的输出

必须打印**具体哪一行不同**：

```
--- approved
+++ actual
- case-03: NewIntentItem intents=[a,b]
+ case-03: NewIntentItem <describe failed>
```

## 六、实施顺序

| 顺 | 内容 | 前置 | 价值 |
| --- | --- | --- | --- |
| **1** | `tools/golden/golden.mjs`（读/比对/重录工具） | — | 基础设施 |
| **2** | `TransactionItemDescriber` golden（4–6 case） | 1 | 已有 7 个单测，补 golden 后可防"断言写松" |
| **3** | `PathRedirectRegistry` golden（11 条真实规则 + 边界） | 1 | 路径翻译是最容易悄悄变的 |
| **4** | `ProcSpoofing` golden（status 文本） | 1 | 格式一改 guest 可能看得出来 |
| **5** | 探针 baseline 工具 `compare-probe-baseline.mjs` | — | 真机行为 diff |
| 6 | Differential 层 | 拆核心块时 | 高风险块专用 |

## 七、与现有测试的关系

| 现有 | 作用 | golden 补充什么 |
| --- | --- | --- |
| `TransactionItemDescriberTest`（7 例） | 钉住**特定断言**（如"含 `<describe failed>`"） | 钉住**完整输出**（连空格、字段顺序都算） |
| `PathRedirectRegistryTest`（10 例） | 钉住规则语义 | 钉住**全部规则的组合输出** |

**两者不重复**：断言测"关键性质"，golden 测"整体不变"。

## 八、限制（诚实说明）

| 限制 | 影响 |
| --- | --- |
| 只能覆盖**纯函数** | `LegacyMessageHandlers`（全反射）、`InstrumentationHook`（要真 Activity）覆盖不到 |
| golden 会**锁死实现细节** | 例如故意改日志格式也会让 golden 红 —— 这是**特性**不是 bug（改就得承认） |
| 真机层要**手动** | 无法进 CI，靠流程约束 |
| 不验证"重构前的行为是否正确" | golden 只保证"和以前一样"，不保证"以前是对的" |
