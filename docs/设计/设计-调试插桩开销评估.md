# 评估：当前调试插桩是否危害时间与执行时机（只设计，不执行）

- 日期：2026-11-24
- 触发：用户问「调试 hook 是否严重危害时间和执行（例如错过时机）」
- **结论：会。有一条插桩必须立刻改** —— `handleMessage` 每条消息同步写文件。
- 证据来源：`DebugTrace.kt` 实现（L137–155）+ `ActivityThreadHook` 插桩位置

---

## 一、现状：每条日志到底花了什么

`DebugTrace` 的落盘路径（`FileLogTree.appendRaw`）：

```kotlin
fun appendRaw(line: String) {
    synchronized(lock) {                        // ① 全局串行（跨线程互斥）
        if (file.length() > MAX_BYTES) file.writeText("")   // ② 每次一个 stat syscall
        file.appendText(line)                   // ③ 每次 open + write + close
    }
}
```

`formatLine` 里：

```kotlin
private fun processTag(): String = try {
    android.app.Application.getProcessName()    // ④ 每次调用（Binder/AMS 查询）
    ...
```

### 每次 `event()`/`detail()` 的固定成本

| # | 开销 | 量级 | 备注 |
| --- | --- | --- | --- |
| ① | 全局锁竞争 | 0–数百 µs | 主线程与 guest 线程共用同一把锁 → **串行化** |
| ② | `file.length()` = stat | ~10–50 µs | |
| ③ | `appendText` = open+write+close | **~100–800 µs**（UFS/eMMC） | **主项** |
| ④ | `Application.getProcessName()` | ~10–100 µs | 可能走 Binder |
| | **合计** | **≈ 0.15–1 ms / 条** | 设备越慢越高 |

**关键**：这是**同步**的，在**调用线程**上执行。谁调用它，谁就付这个钱。

## 二、危害矩阵：哪些插桩在关键时序窗口里

| 插桩位置 | 触发频率 | 所在线程 | 是否在时序窗口 | 风险 |
| --- | --- | --- | --- | --- |
| **`handleMessage` → `txn msg.what=N`（detail）** | **每条主线程消息** | **主线程** | ✅ **是**（mH 消息处理） | 🔴 **严重** |
| `handleExecuteTransaction` enter | 每个事务 | 主线程 | ✅ 是 | 🟡 中 |
| `handleLaunchActivityItem` enter | 每次 Activity 启动 | 主线程 | ✅ 是（STEP 0–5 之间） | 🟡 中 |
| `replaceClassLoader` enter | 每次类加载替换 | 主线程 | ✅ 是（STEP 2 内） | 🟡 中 |
| `onActivityPreCreate` | 限流（前 20 + 每 100） | 主线程 | ✅ 是 | 🟢 低 |
| `initContentProviders` enter | 每进程 1 次 | bind 线程 | ⚠️ 是 | 🟢 低 |
| `v142 registered rules` | 每次 bind | bind 线程 | ⚠️ 是 | 🟢 低 |
| `javaIo` / `guard` / `legacy` | 低频 | 各自 | 部分 | 🟢 低 |

### 🔴 最严重的：`handleMessage` 的 detail 插桩

**为什么严重**：

1. **频率**：`mH` 每条消息都会经过 `handleMessage`（包括输入事件、绘制、生命周期、广播…）
   → 高频滚动时**每秒几十上百条**
2. **在承重墙上**：`handleMessage` 是 `ActivityThread` 的消息分发点，
   它慢 → 所有 UI 线程工作都慢
3. **每秒成本估算**：100 条/秒 × 0.5 ms = **50 ms/秒**（5% CPU，且是主线程）
   → 卡顿、掉帧，**极端情况触发 ANR**
4. **`VERBOSE` 默认 true**（v148 起）→ **默认全开**，不是可选项

**"错过时机"的具体机制**：

| 场景 | 机制 |
| --- | --- |
| STEP 0–5 注入序列 | 各步之间插入日志 → 整体耗时增加，若与 system_server 的超时/竞态窗口重叠，可能改变结果 |
| `Activity` 启动竞态 | 前置有"等 engine READY 最多 10s"，日志拖慢会压缩实际可用窗口 |
| 消息顺序 | 同步 I/O 让主线程在消息之间停顿，某些依赖"连续处理"的框架（动画/输入）表现变化 |
| **双重危害** | 日志越多 → 越慢 → 越容易触发超时 → 超时又会打更多 fail 日志 → **正反馈** |

**⚠️ 还有一个隐蔽风险**：`synchronized(lock)` 是**跨线程**的。
主线程写日志时若 guest 工作线程也在写 → **主线程被阻塞等待**，
这个等待时间不受主线程控制（取决于另一个线程的 I/O 时长）。

## 三、设计方案（三个层面，按优先级）

### 方案 A：给 `DebugTrace` 加异步批量写（改基础设施，收益最大）

```
调用方 ──> 无锁内存队列（RingBuffer）
              └─> 后台单线程：每 200ms 或攒够 64 行 → 一次 open/append/close
```

| 项目 | 改动 |
| --- | --- |
| 队列 | `ArrayDeque<String>` + `synchronized`（只保护内存操作，~µs） |
| 冲刷线程 | 单线程 `HandlerThread` 或 `Executors.newSingleThreadExecutor` |
| 触发 | 定时 200ms **或** 队列达 64 行 |
| 崩溃安全 | 保留 `fail()` 同步直写（错误不能丢） |
| 退出前 | `flush()` 在 `terminateApplication` / 进程退出钩子里调用 |

**预期收益**：调用方成本从 **0.15–1 ms → 2–5 µs**（只剩入队）。

**风险**：进程被杀时最后 ≤200ms 的日志可能丢 → 用 `fail()` 同步 + 关键 `event()` 可配同步来解决。

### 方案 B：缓存 `processTag()`（一行改动，零风险）

```kotlin
@Volatile private var cachedProcessTag: String? = null
private fun processTag(): String =
    cachedProcessTag ?: run { ...计算...; cachedProcessTag = it; it }
```

**收益**：省掉每条的 `getProcessName()`（10–100 µs）。

### 方案 C：给关键路径插桩定"预算"（规范层）

| 位置 | 允许级别 | 频率上限 |
| --- | --- | --- |
| `handleMessage` | **禁止逐条**；改为"每秒最多 1 条汇总"（`txn msg count=N`） | 1/秒 |
| `handleExecuteTransaction` | `detail`，可按 what 采样（每 10 次打 1 次） | 10% |
| `handleLaunchActivityItem` | `event`（低频，可全打） | 每次 |
| `replaceClassLoader` | `event` | 每次 |
| `onActivityPreCreate` | 已限流 ✅ | 20 + 1/100 |

**最小改动**：**立刻把 `handleMessage` 那条 detail 干掉**（改成每秒汇总或降为 VERBOSE 关闭时静默）。

## 四、如果要"测量"而不是"估算"

设计一个最小测量点（不改行为）：

```kotlin
// 在 DebugTrace 内部统计自身开销（开关控制，默认关）
DebugFlags.HOOK_TIMING -> 记录每次 emit 的纳秒耗时，每 1000 次打一行汇总：
   hooktrace cost n=1000 total=412ms avg=412us max=3200us
```

**这样能回答**：在本机上，日志到底占了多少主线程时间。

## 五、结论与建议顺序

| 顺 | 动作 | 类型 | 风险 | 收益 |
| --- | --- | --- | --- | --- |
| **1** | **删/改 `handleMessage` 的逐条 detail** | 行为提交 | 极低 | **立刻消除最大风险** |
| 2 | `processTag()` 缓存 | 行为提交 | 极低 | 每条省 10–100 µs |
| **3** | `DebugTrace` 异步批量写 | 基础设施重构 | 中（需保证 fail 不丢、退出前 flush） | 调用方降 2 个数量级 |
| 4 | 插桩预算规范（写进 AGENTS.md 规则） | 规范 | 无 | 防止以后再犯 |
| 5 | `HOOK_TIMING` 自测开关 | 新增 | 无 | 用数据替代估算 |

**在真机测试之前，至少完成 1 和 2** —— 否则真机测出来的"卡顿/时机问题"可能是**我们自己插桩造成的**，
会把排查带偏（而且这正是本项目反复踩的"把插桩当成现象"的坑）。

## 六、一个更根本的判断

> **日志不该出现在"正在被观测的行为"的时序窗口内。**

本项目的 hook 全都对**时机敏感**（STEP 0–5 是竞态窗口），
而 `DebugTrace` 是**同步落盘** —— 这两件事天然冲突。

所以设计上应该：
- **关键路径只记"状态转移"**（进入/离开/结果），不记"过程中的每一步"
- **高频事件走汇总**（计数 + 秒级采样）
- **落盘永远异步**，且失败可降级为内存

这不是"少打日志"，而是"把日志从关键路径搬走"。
