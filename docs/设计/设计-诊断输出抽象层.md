# 设计：诊断输出抽象层 —— 从「记录过程」转向「验证结果 + 严重错误」

- 日期：2026-11-24
- 触发：用户要求「debug 输出改为验证和输出严重错误信息，综合运用日志系统，
  **设计抽象，不要之后换日志系统就到处修改**」
- 核心：**业务代码只依赖一个接口**；换通道 = 换实现，零业务改动

---

## 一、现状的问题（为什么必须抽象）

### 问题 1：业务代码绑死了具体实现

现在 12 个文件里有 **60+ 处** 直接调用：

```kotlin
com.nextvm.core.common.DebugTrace.event("v142", "registered rules=$rules ...")
com.nextvm.core.common.DebugTrace.detail("txn", "mH msg.what=${msg.what}")
com.nextvm.core.common.DebugTrace.fail("v142", "register failed", t)
```

**后果**：
- 换成 `EventLog` 或异步文件 → **要改 60+ 处**
- 而且每处都要决定"这条该走哪个通道"（散落各处，无法统一策略）
- 无法在测试里替换成假实现（静态对象，不可注入）

### 问题 2：输出的是"过程"而非"结论"

```
v142 registered rules=11 appDir=/... sdcard=/...
initNativeHooks installing hooks
javaIo installed=true
```

**这些全部是"我执行到这一步了"，没有一条回答"hook 到底成功了没有"**。
`installed=true` 只说明函数返回 true，不说明真挂上了（v143 假 dataDir 就是这么假成功的）。

---

## 二、设计：三层结构

```
业务代码
   │  只依赖 ↓
   ├───────────────  Diagnostics（接口，3 个方法）
                          │  实现 ↓
                    DiagnosticsRouter（按级别路由到多个通道）
                          │
      ┌───────────────────┼───────────────────┐
      ↓                   ↓                   ↓
  FileSink          EventLogSink         TraceSink
  （严重错误，         （验证结果，         （临时时序，
    同步不丢）           结构化低开销）        需主动抓）
```

### 2.1 接口（唯一的业务依赖）

```kotlin
package com.nextvm.core.common.diagnostics

/**
 * 诊断输出。业务代码只依赖这个接口，不关心落到哪里。
 * 换通道时只替换实现，业务代码零改动。
 */
interface Diagnostics {

    /** 验证结果：成功/失败都必须调用，且必须带上下文。 */
    fun check(check: CheckResult)

    /** 严重错误：必须落盘、不能丢、不能抛。 */
    fun error(tag: String, message: String, cause: Throwable? = null)

    /** 关键状态转移（低频）：只在"阶段进入/离开"时用，不用于高频路径。 */
    fun stage(tag: String, message: String)
}
```

**为什么只有 3 个方法**：

| 方法 | 用途 | 频率 | 是否保留 |
| --- | --- | --- | --- |
| `check` | **验证**（本设计的核心） | 每进程数十次 | ✅ |
| `error` | 严重错误 | 罕见 | ✅ |
| `stage` | 阶段转移 | 每进程数十次 | ✅ |
| ~~`detail`~~ | 高频过程细节 | 每秒上百 | ❌ **取消**（正是它造成主线程 I/O） |

### 2.2 验证结果的结构（`CheckResult`）

```kotlin
data class CheckResult(
    val name: String,                        // "nativeGOT" / "classLoader" / "pathRedirect"
    val ok: Boolean,
    val target: String,                      // 被验证的对象
    val expected: String,                    // 期望
    val actual: String,                      // 实际
    val context: Map<String, String> = emptyMap(),
    val reason: String? = null               // ok=false 时必填（枚举语义）
)
```

**关键约束（写进接口 KDoc + 检查脚本）**：
- `ok=true` 时也必须填 `expected` / `actual` —— 否则无法发现"挂错对象也报成功"
- `ok=false` 时 `reason` 必填
- `context` 至少要有 1 个键（如 `pkg=` / `rules=`）

### 2.3 路由器（决定去哪，业务不关心）

```kotlin
internal class DiagnosticsRouter(
    private val sinks: List<DiagnosticsSink>
) : Diagnostics {

    override fun check(check: CheckResult) {
        sinks.forEach { it.onCheck(check) }        // 所有通道都收（结构化，成本低）
    }

    override fun error(tag: String, message: String, cause: Throwable?) {
        sinks.forEach { it.onError(tag, message, cause) }   // 严重错误全通道
    }

    override fun stage(tag: String, message: String) {
        sinks.forEach { it.onStage(tag, message) }
    }
}

internal interface DiagnosticsSink {
    fun onCheck(check: CheckResult) {}
    fun onError(tag: String, message: String, cause: Throwable?) {}
    fun onStage(tag: String, message: String) {}
}
```

**换通道 = 换 `sinks` 列表**，业务代码不变。

### 2.4 三个 Sink 的职责

| Sink | 收什么 | 实现要点 | 成本 |
| --- | --- | --- | --- |
| **FileSink** | `error` 全部；`check` 汇总；`stage` | **异步批量写**（200ms/64 行），`error` 例外同步直写 | 调用方 2–5 µs |
| **EventLogSink** | `check` + `error` | `EventLog.writeEvent(1000001, ...)`，二进制结构化 | 10–30 µs |
| **TraceSink** | `stage`（可选） | `Trace.beginSection/endSection`，仅临时开启 | 1–5 µs |

**分层依据**：
- 要**长期留存 + 完整上下文** → FileSink
- 要**低开销 + 结构化可统计** → EventLogSink
- 要**看时序/耗时** → TraceSink（临时）

## 三、输出的内容怎么变（从"过程"到"结论"）

### 改造前

```kotlin
DebugTrace.event("v142", "registered rules=$rules appDir=$appDir sdcard=$sdcard")
DebugTrace.detail("txn", "mH msg.what=${msg.what}")          // 高频，删
DebugTrace.event("javaIo", "installed=$ok translate=$translate")
```

### 改造后

```kotlin
diagnostics.check(
    CheckResult(
        name = "pathRedirect",
        ok = rules > 0 && nativeRules == rules,
        target = "NativeHookBridge.g_path_redirects",
        expected = "rules=$rules native=$rules",
        actual = "rules=$rules native=$nativeRules",
        context = mapOf("appDir" to appDir, "sdcard" to sdcard, "pkg" to guestPkg),
        reason = if (nativeRules != rules) "native_not_synced" else null
    )
)

// 高频路径：不记录每条消息，只在阶段结束时给汇总
diagnostics.stage("txn", "handled ${count} messages")
```

**差别**：
| 改造前 | 改造后 |
| --- | --- |
| "我执行了这行" | **"验证通过/失败，期望 X 实际 Y"** |
| 高频逐条 | 汇总 |
| 无法统计 | `check` 可聚合成 `ok=6 fail=1` |
| 直接调静态对象 | 注入接口，测试可替换 |

## 四、为什么这个抽象能承受"换日志系统"

| 变化场景 | 需要改哪里 |
| --- | --- |
| 文件 → EventLog | 只改 `sinks` 列表 |
| 同步 → 异步 | 只改 `FileSink` 内部 |
| 加 Trace | 加一个 `TraceSink` |
| 加新通道（如 SQLite、网络上报） | 加一个 Sink |
| **测试里验证"确实调用了 check"** | 注入 `RecordingSink`，业务代码零改动 |
| 减少输出（release） | 换 `NoopDiagnostics` |

**业务代码永远只看到 `Diagnostics` 的 3 个方法。**

## 五、迁移路径（分阶段，每阶段可独立验证）

| 阶段 | 内容 | 业务改动 | 风险 |
| --- | --- | --- | --- |
| **1** | 新建 `Diagnostics` 接口 + `CheckResult` + `DiagnosticsRouter` + `FileSink`（包现有 `DebugTrace`） | 无 | 极低 |
| **2** | **删掉 `handleMessage` 的逐条 detail**（最大风险源） | 1 处 | 极低 |
| **3** | 12 个 hook 各写一个 `check`（替换现有 `event`） | 12 处 | 低 |
| **4** | 加 `EventLogSink`（与 FileSink 双写对照，同时实测"是否被吞"） | 无 | 低 |
| **5** | 按实测结果决定是否移除 FileSink 的部分职责 | 无 | 中 |
| **6** | 加 `NoopDiagnostics`（release）与 `RecordingSink`（测试） | 无 | 低 |

**阶段 1–2 应立即做**：抽象层到位 + 消除最大性能风险。
**阶段 3 是核心价值**：把"过程日志"改成"验证结论"。

## 六、与现有 `DebugTrace` 的关系

| 现状 | 迁移后 |
| --- | --- |
| `DebugTrace.event/detail/fail`（静态 object，60+ 调用点） | `Diagnostics` 接口（注入） |
| `DebugTrace.init(filesDir)` | `FileSink` 的构造参数 |
| `DebugTrace` 的 pending 缓冲 | 保留在 `FileSink` 内部（这是实现细节） |

**过渡期兼容**：阶段 1 让 `FileSink` **内部复用现有 `DebugTrace`**，
这样老的 60+ 调用点可以继续工作，逐批迁移到 `diagnostics.check(...)`。

---

## 七、需要落地的约定（供后续执行时遵守）

1. **业务代码禁止直接 import `DebugTrace` / `EventLog` / `Timber`** —— 一律通过 `Diagnostics`
   （可用 `tools/lint/check-log-abstraction.mjs` 扫描：非 `common` 模块出现 `DebugTrace.` 即报）
2. **`check` 的 4 个必填字段**：`name`/`ok`/`target`/`expected`/`actual`
3. **`ok=true` 也必须带 `expected`+`actual`**（防止假成功）
4. **高频路径禁止任何同步 I/O**（`handleMessage`、`onDraw`、Binder 返回路径）
5. **新加输出前先问**：这是"验证"还是"过程"？过程 → 删或汇总；验证 → `check`

---

## 八、结论

| 问题 | 答案 |
| --- | --- |
| 怎么避免"换日志系统到处改" | **接口化 + 注入**：业务只依赖 `Diagnostics`（3 个方法） |
| debug 输出改成什么 | **验证（`check`）+ 严重错误（`error`）+ 阶段（`stage`）**，取消高频 `detail` |
| 怎么综合运用日志系统 | `DiagnosticsRouter` 按级别路由到 FileSink / EventLogSink / TraceSink |
| 最大价值 | `check` 让"hook 是否成功"变成**结构化可断言**的事实，而不是散文日志 |
