# 设计：拆分标准流程（对标业界）

- 日期：2026-11-24
- 来源：[Feathers《Working Effectively with Legacy Code》实践化工作流](https://raw.githubusercontent.com/laurigates/claude-plugins/refs/heads/main/software-design-plugin/skills/design-legacy-seams/SKILL.md) + Fowler「两顶帽子」

---

## 一、业界标准（原文要点）

> **The sequence is non-negotiable: get it under test first, change it second.**
> Characterization tests document what the code **does** (not what it **should** do), so a
> refactor that preserves behaviour stays green and a behaviour change shows up as a
> deliberate, reviewed diff.

### 四步

| 步 | 动作 | 关键点 |
| --- | --- | --- |
| **1** | 找出**改动点**及其阻塞依赖 | 内建协作者、全局/单例、时钟、随机、I/O、网络、静态调用 |
| **2** | **找或造接缝（seam）** | Object seam（可注入协作者/可覆盖方法）/ Link seam / 预处理 seam。<br>造接缝的两个最小手法：**Extract & Override**、**Parameterize Constructor/Method** |
| **3** | 写 **characterization test** | **记录"实际"行为，不是"应该"的行为**；测试失败就改断言去匹配实际输出 |
| **4** | 现在才改，改完汇报 | 该绿的继续绿；有意改变的部分成为可 review 的 diff |

### Anti-patterns（原文）

| 错误 | 正确做法 |
| --- | --- |
| 靠"小心"手改无测试代码 | 先纳入测试 —— 小心不是安全网 |
| 写"应该"行为的测试 | 记录"实际"行为 |
| 为让一个方法可测而大改写 | 最小接缝编辑（Extract & Override / Parameterize） |
| 中途"修复"意外行为 | **标记为 finding，另开变更** |

## 二、对照我们的做法

| 业界标准 | 我们的实际 | 判定 |
| --- | --- | --- |
| **先纳入测试，再改** | v151–v155 先拆了 ~1350 行，v158 才补测试 | ❌ **顺序反了** |
| 记录"实际"行为 | golden 是我按**重构后**的实现推导的 | ❌ 只能算"当前基线" |
| 最小接缝编辑 | `translatePath` 的 `hiddenPaths` → `isHidden` 回调注入 | ✅ 正是 Parameterize |
| 意外行为标记不修 | `catch (Throwable)` 吞 OOM → 记入偏差登记，未改 | ✅ 做对了 |
| 一次大改写 | 单次迁移 492 行（CustomerProbes） | ⚠️ 偏大 |
| 行为改动与重构分开 | v151 把「拆分」和「debug 插桩」放在同一个提交 | ❌ 违反「两顶帽子」 |

**结论**：我们的**工具**（golden / 静态等价 / 三层防护）是对的，
但**顺序**和**提交粒度**有问题，靠事后补偿。

## 三、今后的标准流程（修正后）

### 每拆一个职责，按这个顺序

```
0. 选目标：一个职责（规则 7），不是"凑行数"
1. 识别依赖：这个职责现在依赖了谁的私有状态？
2. 造接缝：把依赖改成构造注入 / 回调 / 参数（最小改动，属"重构"）
      ↓ 此时先单独提交（纯重构，行为不变）
3. 写 characterization test：锁定"实际"输出（golden）
      ↓ 提交
4. 搬代码：只移动，不改逻辑
5. 证明未变：check-refactor-equivalence（规则 10）
      ↓ 提交（纯搬迁）
6. 需要可观测性？单独提交插桩（不在搬迁提交里）
```

### 「两顶帽子」纪律

| 提交类型 | 允许包含 | 禁止包含 |
| --- | --- | --- |
| **重构提交** | 移动代码、改可见性、抽接缝、改命名 | 加日志、加开关、改逻辑、修 bug |
| **行为提交** | 加插桩、改逻辑、修 bug | 搬代码 |

**为什么**：行为提交若混进重构，出问题时无法判断是"搬错了"还是"新逻辑错了"。
v151 就是混在一起，后来查 `LegacyMessageHandlers` 差异时才发现插桩是那次加的。

### 拆不动怎么办（接缝不可造）

| 情况 | 处置 |
| --- | --- |
| 依赖是 `ActivityThread` 等系统类 | 用 Robolectric（成本高）或**暂不拆**，等有真机回归基线再说 |
| 全反射 | 镜像文档写明"不可纯 JVM 测"+ 靠真机 `debug-trace` 覆盖 |
| 依赖 native | 同上 |

## 四、立即要做的

| 顺 | 动作 | 理由 |
| --- | --- | --- |
| **1** | **真机回归**（部署当前构建，跑探针 W1–W40 + Via） | 累积 ~1350 行改动**从未在设备上验证**。业界标准里"每步可验证"是前提 |
| 2 | 建立探针 baseline JSON + diff 工具 | 让「行为是否变」可结构化对比，而不是肉眼 |
| 3 | 之后按修正后的流程拆 P0（VAM 诊断块） | 诊断块依赖少，容易造接缝 |

**为什么真机回归优先**：静态等价检查只能证明"函数体没变"，证明不了
"把这些函数搬到新文件后，进程级初始化顺序、类加载、native 规则注册仍然正确"。
后者只有真机能验证。
