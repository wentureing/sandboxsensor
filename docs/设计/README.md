## 二、当前已定的设计决策（结论）

| # | 决策 | 依据 |
| --- | --- | --- |
| 1 | **主进程零 hook，guest 全 hook** | `架构/架构-主原生guest全hook.md`、`输出/变更/20261124-p0-3-main-process-no-hook-scope.md` |
| 2 | **只 patch 应用/沙箱库的 GOT/PLT，系统库默认不 patch** | `01-技术调研` §21、`架构/架构-拦截能力层次.md` |
| 3 | **不做自研 DEX 运行时** | `01-技术调研` §184（同作者项目已验证不可行） |
| 4 | **"无必要不引入 ART 方法 hook"** | `01-技术调研` §30/§3.4（稳定性 + LGPL 风险）；但 Java 层路径重定向**不需要** ART hook（见 `架构/架构-Java层路径重定向-施工方向与方案.md`） |
| 5 | **拒绝优于伪造** | `架构/架构-代理范式.md` §2.3（检测方无法区分"不存在"和"被隐藏"） |
| 6 | **导入代替代读**（用户文件） | `架构/架构-主原生guest全hook.md`（代读要 fd 跨进程，导入只需一次拷贝） |
| 7 | **路径改写（而非路径保真）** | `架构/架构-拦截能力层次.md` §3.5：路径像真机 vs 路径含容器包名，二者互斥 |

## 三、还没定的设计问题

| # | 问题 | 现状 |
| --- | --- | --- |
| 1 | **WebView 的 `file://` MIME** 怎么治 | 代读（`shouldInterceptRequest`）有效但注入时机做不到；改 dataDir 是短命补丁；见 `输出/记录/记录-W2-text-plain机制收敛.md` |
| 2 | **Java 层路径重定向**要不要做 | 方案已写清（`RegisterNatives` + `translatePath`），风险最高（覆盖 boot classpath 的 native 方法），尚未决策 |
| 3 | 路径保真（pathFidelity）是否推广到普通 guest | 目前只对定制包开；缺"Java 层重定向"时，纯 Java 应用会读不到假路径 |
| 4 | 反检测（`AntiDetectionEngine`）何时接线 | 805 行零调用；接线前要先修它的两个缺陷（`is_path_hidden` 精确匹配、无 `readdir` 过滤） |
