# 设计：启动编排的成熟测法与「标准行为」的正确来源

- 日期：2026-11-24
- 触发：用户指出 `application.Step 1–6` 与 `activity.STEP 0–5` 很重要，
  问「成熟的测试该怎么做、怎么获取标准行为的记录」
- 核心结论：**标准行为的来源是 AOSP / 原生真机，不是原项目**。
  原项目只能证明"重构没改"，不能证明"行为正确"。

---

## 一、我此前的做法为什么不够

| 做法 | 问题 |
| --- | --- |
| 用 `stage("application", "step2 createApplication done")` | 只记录"执行到这行"，**没有顺序断言**、**没有标准对照** |
| 用 `check(expected="done", actual="done")` | 这是**自证** —— 期望值是我自己写的，不是外部标准 |

**两者都无法回答**："Step 5（装 Provider）真的早于 Step 6（App.onCreate）吗？"
只能回答："这行执行了"。

## 二、成熟做法：用 Android 官方的生命周期观测点

### 2.1 关键洞察

`application.Step 1–6` 和 `activity.STEP 0–5` 本质是**生命周期编排**。
而 Android **本来就提供了官方的观测点**：

| API | 能观测什么 | 何时可用 |
| --- | --- | --- |
| **`Application.ActivityLifecycleCallbacks`** | `onActivityCreated/Started/Resumed/Paused/Stopped/Destroyed` | API 14+ |
| **`onActivityPreCreated`** / `onActivityPreStarted` / `onActivityPreResumed` | **Activity 创建前的回调**（容器插桩的正是这里） | **API 29+** |
| **`ContentProvider.onCreate`** | Provider 初始化时刻 | 全版本 |
| `Application.onCreate` | Application 初始化时刻 | 全版本 |

**这意味着**：不需要在容器代码里插 `stage`，只要**注册一个官方的 `ActivityLifecycleCallbacks`**，
就能拿到**系统给出的真实顺序**。

### 2.2 记录器设计（零侵入）

```kotlin
/**
 * 标准行为记录器：只依赖 Android 官方 API，不碰容器代码。
 * 输出：按时间顺序的生命周期事件序列。
 */
class LifecycleRecorder : Application.ActivityLifecycleCallbacks {

    private val events = mutableListOf<String>()

    // ---- API 29+ 的 pre 回调（容器插桩就在这些点之前）----
    override fun onActivityPreCreated(activity: Activity, savedInstanceState: Bundle?) {
        events += "pre_created:${activity.javaClass.simpleName}"
    }
    override fun onActivityCreated(activity: Activity, savedInstanceState: Bundle?) {
        events += "created:${activity.javaClass.simpleName}"
    }
    override fun onActivityPreStarted(activity: Activity) {
        events += "pre_started:${activity.javaClass.simpleName}"
    }
    override fun onActivityStarted(activity: Activity) {
        events += "started:${activity.javaClass.simpleName}"
    }
    override fun onActivityPreResumed(activity: Activity) {
        events += "pre_resumed:${activity.javaClass.simpleName}"
    }
    override fun onActivityResumed(activity: Activity) {
        events += "resumed:${activity.javaClass.simpleName}"
    }
    // ... paused/stopped/destroyed 同理

    fun dump(): List<String> = events.toList()
}
```

**注册方式**：在 `Application.onCreate` 之前（`attachBaseContext` 里）注册 →
**能捕获到第一个 Activity 的 `pre_created`**。

### 2.3 加上 Application / Provider 的时刻

```kotlin
// 容器不改逻辑，只在测试 APK 里注册一个"旁观者" Application 包装
events += "application_attachBaseContext"
events += "application_onCreate"
// Provider 自己记录
class ProbeProvider : ContentProvider() {
    override fun onCreate(): Boolean { record("provider_onCreate:${javaClass.simpleName}"); return true }
}
```

**输出示例（标准顺序）**：

```
application_attachBaseContext
provider_onCreate:com.example.InitProvider      <-- AOSP：Provider 早于 App.onCreate
application_onCreate                              <-- 
pre_created:MainActivity
created:MainActivity
pre_started:MainActivity
started:MainActivity
pre_resumed:MainActivity
resumed:MainActivity
```

**这就直接验证了 Step 5 早于 Step 6**（Provider 在 App.onCreate 之前）。

## 三、标准行为（golden）的正确来源：三份记录

| 来源 | 是什么 | 用途 |
| --- | --- | --- |
| **① AOSP 源码** | `ActivityThread.performLaunchActivity` / `LoadedApk.makeApplication` 的调用顺序 | **事实标准**（不需要跑，读代码即是定义） |
| **② 原生真机** | 同一个 APK **不装容器**跑，用 `LifecycleRecorder` 记录 | **运行时标准**（最权威的钱） |
| **③ 容器真机** | 同一个 APK **装容器**跑，同样记录 | 被测对象 |
| ~~④ 原项目真机~~ | 原项目跑同一 APK | **只用于"证明重构没改"**，不用于"证明正确" |

**关键区别（用户此前的表述需要修正）**：

> "golden 只能依据原项目得到" → 对**"重构等价"**成立
> 但**"行为是否正确"**的基准是 **AOSP / 原生真机**，原项目本身可能有偏差

**举例**：如果原项目把 Provider 装在 `App.onCreate` **之后**（顺序错），
那"原项目哪来当 golden"，就会把错误固化。而原生真机不会。

## 四、对比矩阵（两种问题分开答）

| 问题 | 对比对象 | 手段 |
| --- | --- | --- |
| **重构有没有改行为？** | 原项目 vs 重构版 | `check-refactor-equivalence`（已完成）+ 各自真机 checks |
| **容器行为对不对？** | **原生真机 vs 容器** | `LifecycleRecorder` 输出顺序对比 |
| **hook 有没有真挂上？** | 期望 vs 实际（`CheckResult`） | 我们的 `check` |

**我们此前的 23 条 check 只覆盖第三行**（hook 生效），
第二行（行为对不对）**完全没覆盖** —— 这才是用户点出的缺口。

## 五、两者如何结合（设计）

```
容器代码                          标准记录器（旁观）
─────────────────────────────────────────────────
STEP 0 preRegisterToken    ┐
STEP 1 swapActivityName    │
STEP 1.5 breadcrumb        │  容器编排（stage）
STEP 2 replaceClassLoader  │
STEP 2.5 bootApplication   ┘
                                   pre_created:MainActivity   ← 官方回调
                                   created:MainActivity
                                   pre_started:MainActivity
                                   ...
```

**断言规则（关键设计）**：

| # | 断言 | 意义 |
| --- | --- | --- |
| 1 | 所有容器 STEP 0–5 **必须早于** `pre_created` | 容器编排必须在 Activity 创建前完成 |
| 2 | `provider_onCreate` **必须早于** `application_onCreate` | AOSP 语义（缺陷会在这一步暴露） |
| 3 | `application_onCreate` **必须早于** `created:<第一个 Activity>` | Application 先于 Activity |
| 4 | `pre_created` / `pre_started` / `pre_resumed` 顺序固定 | 官方回调本身的顺序（健全性检查） |

**这 4 条是"结构性断言"，顺序错就是硬错**，比 23 条 `check` 更根本。

## 六、怎么在测试里跑（三种环境）

| 环境 | 可行性 | 做法 |
| --- | --- | --- |
| **纯 JVM** | ❌ | 没有 Activity 生命周期 |
| **Robolectric** | ✅ **可做** | `ActivityLifecycleMonitorRegistry.getInstance().addLifecycleCallback(...)`<br>+ `Robolectric.buildActivity(MainActivity::class.java).setup()`<br>→ **能在 CI 里断言上面 4 条规则** |
| **真机** | ✅ 最真实 | `LifecycleRecorder` 记录 → 导出对比 |

**Robolectric 这条路很重要**：它让"启动编排顺序"第一次可以进 CI。

**但有个坑**（已在 `调研-androidx-test-core风险.md` 记过）：
Robolectric 里 Activity 创建会走 Shadow，可能与容器 hook 交叉 →
**建议用"只跑 recorder，不装容器 hook"的方式**，验证的是"我们的断言规则本身"，
而不是"容器的真实行为"。真实行为仍需真机。

## 七、落地设计（分三步，都不改业务逻辑）

### 步骤 1：`LifecycleRecorder`（新增，零侵入）

- 放 `app/src/debug/` 或独立 `probe` 模块
- 在 `attachBaseContext` 注册
- 输出到 `checks.log` 的 `path=lifecycle` 段

### 步骤 2：`StartupOrderTest`（Robolectric，CI 可跑）

- 断言第五节那 4 条规则
- **不需要容器 hook**，只验证"规则可在 CI 验证"这条链路通

### 步骤 3：把容器 `stage` 与 recorder 对齐

- 容器 `stage` 记录编排
- recorder 记录官方回调
- 两者合并成一条时间线 → 断言"容器编排早于 pre_created"

## 八、回答"怎么获取标准行为的记录"

| 层次 | 方法 | 产物 |
| --- | --- | --- |
| **定义层** | 读 AOSP `ActivityThread.performLaunchActivity` / `LoadedApk.makeApplication` | 顺序定义（写进文档） |
| **运行时层** | 原生真机 + `LifecycleRecorder` | `lifecycle-golden.txt`（**这才是真 golden**） |
| **对照层** | 容器真机 + 同样的 recorder | `lifecycle-actual.txt` |
| **CI 层** | Robolectric + `ActivityLifecycleMonitorRegistry` | 4 条结构性断言的自动化 |

**关键**：`lifecycle-golden.txt` 必须来自**原生真机**（不装容器），
这样才叫"标准行为"；原项目的数据只能证明"重构等价"。
