# 概念澄清：路径形态欺骗 / 沙箱隔离 / 合成路径 三者的用途

- 日期：2026-11-25
- 目的：把这三个概念分开，避免后续讨论混用
- 关联：`docs/输出/变更/20261125-路径欺骗豁免与轻度重构.md`

---

## 一、三者各自的用途

| 概念 | 用途 | 解决什么问题 | 谁从中受益 | 代价 |
| --- | --- | --- | --- | --- |
| **① 沙箱隔离** | 把 guest 的 I/O 送到 `<containerDataDir>/.../data/<inst>/`，**不碰宿主真实目录** | 数据安全 / 多开互不污染 | 所有 guest | 需要规则表 + hook |
| **② 路径形态欺骗** | 让 guest 看到的路径**长得像真机安装**（`/data/user/0/<pkg>`），而不是容器路径 | **通过反双开检测** | 有反双开逻辑的 app | WebView isolated 读不到（见下） |
| **③ 合成路径** | **实现 ② 的技术手段**：定义"假路径长什么样"（`synthetic*` 七个函数） | — | — | 每条合成路径都要配一条规则（T39 守着） |

### 三者的真实关系

```
③ 合成路径  ──是──►  ② 路径形态欺骗 的手段
                        │
                        └─ 可能被 guest 察觉（反双开检测）

① 沙箱隔离  ──独立目标──► 不依赖 ②③，也不需要 guest 察觉
```

**关键点**：**① 和 ② 是两个独立的目标**，③ 只是实现 ② 的工具。
所以"豁免"可以**关掉 ②③、保留 ①** —— 它们在语义上不冲突。

---

## 二、为什么 ② 和 WebView 冲突（当前已知的唯一硬冲突）

| | 同进程 I/O（via 自己） | 跨进程交给 WebView（`file://`） |
| --- | --- | --- |
| **合成路径**（`/data/user/0/<pkg>/...`） | ✅ 规则能翻译 → 正常 | ❌ isolated 进程没 hook → `ERR_FILE_NOT_FOUND` |
| **真沙箱路径**（`<containerDataDir>/...`） | ✅ 正常 | ✅ isolated 能读（W35a 证明） |

**所以**：对依赖 WebView 加载本地 HTML 的 app（via 就是），**② 必须关掉**，否则主页空白。

这就是当前 `contentPathsUseReal = false` 的原因，也是"豁免机制"要解决的问题。

---

## 三、问题 1 的三条路径，各自的用途（待你选择）

豁免后有三条相关路径会同时变真，需要你确认是否三条都变：

| 路径 | 用途 | 现状 | 豁免后（若三条都变真） |
| --- | --- | --- | --- |
| **`getFilesDir()`** | 文件操作入口（`openFileOutput`、`.mht` 保存、主页 HTML 读取） | **已是真**（`contentPathsUseReal=false`） | 真（不变） |
| **`getDataDir()`** | **反双开检测最常看的入口**（多数检测写成 `getDataDir()` 或 `getApplicationInfo().dataDir`） | 假（`/data/user/0/<pkg>`） | **真** |
| **`getFilesDir().getParentFile() == getDataDir()`** | **框架不变量**（真机上永远成立） | **不成立**（🔴 最容易被检测） | **成立** ✓ |

### 三种选择的取舍

| 方案 | `getDataDir()` | 反双开检测 | 框架不变量（父子关系） | 推荐度 |
| --- | --- | --- | --- | --- |
| **A. 三条都变真** | 真 | ❌ 会挂 | ✅ **成立** | ⭐ **推荐**（豁免的本意） |
| B. 只 `getFilesDir()` 真、`getDataDir()` 假 | 假 | ✅ 通过 | ❌ **不成立**（🔴 危险） | 不推荐 |
| C. 全部假（回到 pathFidelity 原状） | 假 | ✅ 通过 | ✅ 成立 | ❌ WebView 读不到 |

**方案 A 的额外好处**：**顺手消掉了之前讨论的 🔴 #1**（父子关系不成立）——
因为三条都真实，路径结构反而**自洽**。

**方案 A 的代价**：`getDataDir()` 暴露容器路径 → 有反双开逻辑的 app 会被发现。
但**这正是"豁免"的语义** —— 用户明确要求"不执行任何路径欺骗"。

**所以推荐 A**：豁免 = 这个 guest 上**完全没有欺骗**，路径全部真实且自洽。

## 四、已确认的两项

| # | 问题 | 决定 |
| --- | --- | --- |
| 2 | 豁免后是否保留 `setupExternalStorageRedirections`（`/sdcard/` → 沙箱） | **保留** —— 那是隔离（①），不是欺骗（②） |
| 3 | 配置文件格式 | **可读性优先** —— 行式 `key=value` + 注释 + 分节，便于手改与 CmdReceiver 写入 |

### 配置文件草案（可读性优先）

```ini
# 路径欺骗配置 —— 改完需重启容器/guest 生效
# 说明见 docs/输出/变更/20261125-路径欺骗豁免与轻度重构.md

[豁免名单]
# 这些包不做任何路径形态欺骗（不用合成路径），但仍隔离到沙箱
# 每行一个包名
mark.via

[各族开关]
# 缺省 = on；off = 该族不产生合成路径（但仍保留翻译规则）
# 可选值：on / off
FILES=on
EXTERNAL_FILES=on
OBB=on
MEDIA=on
APK=on
NATIVE_LIB=on
```

**为什么行式而非 JSON**：
- 无需解析依赖（`org.json` 在容器里可用，但没必要）
- 手改友好（加注释、分节）
- `CmdReceiver` 写入简单（定位到节内增删行）
- 出问题时能直接 `cat` 看懂

## 五、已确认（2026-11-25）

**问题 1：豁免后 `getDataDir()` 是否也返回真路径？→ 已确认「是」（方案 A）**

- 三条全真，框架不变量 `getFilesDir().getParentFile() == getDataDir()` 成立，路径自洽；
- 代价是反双开检测会挂 —— 这正是"豁免"的语义；
- 代码现状：`getDataDir()` 只在 `pathFidelity || detachedAppInfoEnabled()` 时合成，
  豁免后 `pathFidelity=false`（且 `detached` 只对 `com.sandbox.probe` 生效）→ **返回真沙箱路径**。

## 六、via 的最终决定：零欺骗 + 写入必须落沙箱 + 名单可配置

> 背景：针对 via 的反复失败（主页空白、离线列表空、popup 闪退），确定这条硬约束。

| # | 约束 | 落地位置 | 自动化验证 |
| --- | --- | --- | --- |
| 1 | **via 不执行任何目录欺骗**（`getFilesDir`/`getDataDir`/`ApplicationInfo.dataDir` 全部真沙箱路径） | `path_spoof.conf` 的 `[豁免名单]` 含 `mark.via`；`VirtualConstants.isPathFidelityGuest` 命中豁免即 false | `PathWhitelistEffectTest.W1/W2/W6` |
| 2 | **写入仍必须导入沙箱** | 规则注册与豁免**正交**：`PathPolicy.isRedirectionEnabled` 恒 true，`NativeHookBridge` 注册规则时不查豁免 | `W7`（14 条规则对任何名单都注册，目标都在沙箱内）+ `PathSpoofPolicyTest.H9` |
| 3 | **名单可配置，代码不写死包** | 配置文件两份名单；`DEFAULT_EXEMPT_PKG` 只作模板种子；运行时 `setGuestExempt` / `setSpoofListed` | `H11–H13`（模板含欺骗名单、增删往返、两份名单互不影响）+ `W3–W5` |

### 三个已知的限制（诚实记录）

| # | 限制 | 影响 | 下一步 |
| --- | --- | --- | --- |
| 1 | 本条只保证**能翻译的写入**进沙箱 | guest 用 Java `File` 直接写**硬编码宿主路径**时，翻译依赖 L3/L5；而 `debug.nextvm.javaIo` **默认关**、`libjavacore` 不被 patch → 这类写入仍会落到真实宿主 | 回归判据：宿主 `.../data/com.nextvm.app/files/` 下不得出现**有内容**的新文件（空目录壳是已知现象） |
| 2 | 内容目录用真路径是**全局**开关（`contentPathsUseReal=false`），与 per-guest 豁免重叠 | 两套开关描述同一件事 | B 阶段收敛为查 `PathPolicy`（`shouldUseSyntheticContent` 已把判据隔离成一处） |
| 3 | `pathFidelity` 是构造期求值 | 改名单必须重启 guest 才生效 | 已接受（`SPOOF_EXEMPT_*` 输出"重启后生效"） |

### 为什么"零欺骗"不等于"取消容器"

```
① 沙箱隔离  ← 保留（规则仍注册，I/O 仍落 <containerData>/.../data/<inst>）
② 路径欺骗  ← 关闭（不产生 /data/user/0/<pkg> 这类假路径）
③ 合成路径  ← 关闭（② 的手段）
```

via 拿到的是**真实沙箱路径**：读写天然落沙箱（不需要翻译），WebView 的 isolated 进程也能读到；
它自己拼的宿主形态路径（如 `getOpPackageName()` 拼出的 `/storage/emulated/0/Android/data/com.nextvm.app/...`）
仍由 `hostFallbackRules` + 规则翻译兜底 —— 这是"写入仍导入沙箱"的机制来源。
