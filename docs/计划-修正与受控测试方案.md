## 一、先修正我上一轮的错误

### 1.1 我说过"renderer 按标准路径读真实磁盘" —— **这个结论没有验证**

**我当时的推理**：
```
guest 传 file:///data/user/0/mark.via/files/homepage2.html
  → renderer（isolated uid）按自己的 uid 读那个路径
    → 真实磁盘上不存在 → 失败
```

**问题**：**前提"renderer 读文件"没有验证。**

### 1.2 Chromium 的架构（需要确认的事实）

```
guest 进程（browser process）
  ├─ WebView / AwContents（Java）
  ├─ ContentBrowserClient / AwContentBrowserClient（native，在 guest 进程）
  │    └─ URLLoaderFactory
  │         └─ FileURLLoaderFactory  ← file:// 的读取很可能在这里（guest 进程）
  └─ 通过 Mojo IPC
       ↓
renderer 进程（isolated uid）
  └─ 只负责 HTML 解析 / JS 执行 / 布局渲染
     └─ 需要子资源时，通过 Mojo 请求 browser 去加载
```

**如果 `FileURLLoaderFactory` 在 guest 进程** → **`file://` 的读取用的是 guest 的权限** →
**容器 hook 会重定向它** → **读到沙箱** → **应该成功**。

**但这与"显示源码"的事实矛盾** → **所以要么前提错，要么还有别的原因。**

### 1.3 所以：**必须做受控测试**（用户的要求完全正确）

## 二、WebView 的 `file://` 与 Android 11+ 的系统限制（**已确认**）

来源：[Android 11（target SDK 30）WebView 加载内部存储 HTML 报 ENOENT](https://www.volcengine.com/article/3358238)

> **Android 11+ 上 Target SDK ≥30 时，WebView 默认禁止直接通过 `file:///data/` 前缀的路径
> 访问应用内部私有存储文件，就算文件实际存在也会抛出 ENOENT 错误。**

**解法**（原文给的两个）：
```kotlin
// 方案 1：显式开启
webView.settings.allowFileAccess = true
webView.settings.allowContentAccess = true

// 方案 2：WebViewAssetLoader（更安全，用 https://appassets.androidplatform.net/ 映射）
```

### 2.1 这对我们意味着什么

**设备上 Via 的 targetSdk = 36**（实测：`versionCode=20260823 minSdk=19 targetSdk=36 versionName=7.3.3`）

**所以**：
- **标准环境下**，Via 加载 `file:///data/user/0/mark.via/...` **也需要它自己设了 `allowFileAccess = true`**
- Via 作为浏览器**肯定设了**（否则读不了本地文件）
- **所以标准环境正常** ✓

**那容器内为什么异常？** → **需要受控测试**（见第四节）

## 三、renderer 是谁的？用户期望"WebView 看真的、Via 看假的"

### 3.1 renderer 的身份（明确的事实）

| 项 | 事实 |
| --- | --- |
| **进程名** | `com.google.android.webview:sandboxed_process0:org.chromium.content.app.SandboxedProcessService0:0` |
| **uid** | **99497 / 99498 / 99499**（isolated，**不属于 Via 也不属于容器**） |
| **由谁 fork** | `webview_zygote`（不是应用的 zygote） |
| **职责** | **HTML 解析 / JS 执行 / 布局渲染** |
| **能不能被容器 hook** | ❌ **不能**（另一个进程，容器进不去） |

**所以**：**renderer 是 WebView（Chromium）自己的沙箱进程**，**不是 Via 的**，**也不是容器的**。

### 3.2 用户期望"WebView 看真的、Via 看假的" —— 需要先确认可行性

**如果 `file://` 的读取在 guest 进程**（browser process）：
- → **WebView 读的就是 guest 的路径** → **被容器 hook 重定向到沙箱** → **看假的（沙箱）**
- → **用户的期望（WebView 看真的）无法实现**，除非**主动给 WebView 一条"旁路"**

**如果 `file://` 的读取在 renderer**：
- → renderer 用 isolated uid → 读不到沙箱 → **只能读真实路径**
- → **用户的期望（WebView 看真的）天然成立**，但**guest 的数据就暴露给 renderer 了**

**所以**：**这个设计决定必须先确认"谁在读文件"**。

### 3.3 三种可能的实现（取决于测试结果）

| 若读取在… | 方案 | 复杂度 |
| --- | --- | --- |
| **guest 进程** | ① 接受"WebView 读沙箱"（现状）<br>② 或 hook `AwSettings`/`URLLoader` 做"file:// 白名单旁路" | ① 零；② 高 |
| **renderer** | ① 接受"renderer 读真实路径"<br>② 宿主代读（`WebResourceResponse`） | ① 零；② 中 |
| **两者都有**（Chromium 有 `--single-process` 模式，但我们不能开） | 需要具体分析 | — |

**结论**：**先测试，再设计。**

## 四、受控测试方案（用户要求）

### 4.1 目标

用**最小可控的样本**回答四个问题：

| # | 问题 | 判据 |
| --- | --- | --- |
| **Q1** | WebView 的 `file://` 读取在哪个进程？ | logcat 里哪个 pid 报 ENOENT / 哪个 pid 有 `open` 日志 |
| **Q2** | 容器内 `file://` 到沙箱路径能不能成功？ | `onPageFinished` 是否触发、内容是否渲染 |
| **Q3** | `file:///android_asset/` 在容器内是否正常？ | 同上（作为对照） |
| **Q4** | 标准 Via vs 容器内 Via 的行为差异 | 同一 URL 在两边分别 loadUrl，看结果 |

### 4.2 测试载体：**探针加一个 Activity**（不依赖 Via）

```java
// probe/src/main/java/com/sandbox/probe/WebViewProbeActivity.java
public class WebViewProbeActivity extends Activity {
    private static final String TAG = "WVPROBE";

    @Override protected void onCreate(Bundle b) {
        super.onCreate(b);
        // 1) 准备三个文件
        File f1 = new File(getFilesDir(), "wvprobe_files.html");   // 私有目录
        write(f1, "<html><body><h1>FILES_DIR_OK</h1></body></html>");
        // 2) assets 里的对照组（需要 probe 自带一个 assets/wvprobe.html）

        WebView wv = new WebView(this);
        setContentView(wv);
        wv.getSettings().setJavaScriptEnabled(true);
        wv.getSettings().setAllowFileAccess(true);        // 关键：显式开启
        wv.getSettings().setAllowContentAccess(true);
        wv.setWebViewClient(new WebViewClient() {
            @Override public void onPageFinished(WebView v, String url) {
                Log.i(TAG, "onPageFinished url=" + url);
                // 用 JS 读 body 文本，判断渲染是否成功
                v.evaluateJavascript(
                    "(document.body && document.body.innerText) || 'EMPTY'",
                    value -> Log.i(TAG, "bodyText=" + value));
            }
            @Override public void onReceivedError(WebView v, WebResourceRequest r,
                                                  WebResourceError e) {
                Log.e(TAG, "onReceivedError url=" + r.getUrl()
                        + " code=" + e.getErrorCode() + " desc=" + e.getDescription());
            }
        });

        // 逐个加载，间隔 3 秒
        String[] urls = {
            "file://" + f1.getAbsolutePath(),                       // 私有目录（假路径 → 沙箱）
            "file:///android_asset/wvprobe.html",                   // assets（对照）
            "data:text/html,<h1>DATA_OK</h1>",                      // data（对照）
        };
        // ... 用 Handler 依次 loadUrl
    }
}
```

### 4.3 判据（**在容器外也跑一遍作为基准**）

| URL | 容器外预期 | 容器内预期（若一切正常） |
| --- | --- | --- |
| `file://<filesDir>/wvprobe_files.html` | `FILES_DIR_OK` | `FILES_DIR_OK`（被重定向到沙箱，读到沙箱文件） |
| `file:///android_asset/wvprobe.html` | `ASSET_OK` | `ASSET_OK`（`AssetManager` 不受限） |
| `data:` | `DATA_OK` | `DATA_OK` |

**同时抓**：
```powershell
adb logcat -d -b all > wvprobe.txt
# 找：WVPROBE 的 onPageFinished / onReceivedError
# 找：chromium / aw_browser / sandboxed_process 的错误
# 找：NextVM-Native 的 open 重定向日志（看有没有拦到 WebView 的读取）
```

**关键观察点**：
> **如果 `file://<filesDir>` 在容器内失败，而 `NextVM-Native` 的日志里没有对应的 `open` 重定向记录**
> → **说明读取不在 guest 进程**（在 renderer）→ **users 的"WebView 看真的"期望成立**
>
> **如果有重定向记录但最终失败** → **读取在 guest 进程，但某处（MIME/权限）失败**

### 4.4 这个测试为什么比"看 Via"可靠

| 项 | 用 Via | 用探针 `WebViewProbeActivity` |
| --- | --- | --- |
| 变量数 | 多（Via 自己的逻辑、设置、URL 处理） | **只有一个**（loadUrl + settings） |
| 可重复 | 差（Via 行为依赖网络/缓存） | **好**（每次一样） |
| 能看到什么 | 只能看最终界面 | **四个回调 + logcat** |
| 能否对照 | 需要另一个设备 | **同一个设备跑两遍**（容器内/外） |

## 五、guest 不该知道"沙箱"：设计与危害

### 5.1 当前路径的三种视图

| 视角 | 看到什么 | 谁在看 |
| --- | --- | --- |
| **Java 层（`VirtualContext`）** | `/data/user/0/mark.via/files/...`（**干净**） | guest 的正常代码 |
| **native 层（`/proc/self/maps`、`readlink`）** | `<dataDir>/files/virtual/data/mark.via_1795511947815/...`（**露容器包名 + 沙箱结构**） | 加固壳、native 反查 |
| **`/proc/self/fd/N` 的 readlink** | 同上（露真实路径） | `P21`/`P24` 检测项 |

### 5.2 所以"不该知道沙箱"这件事，**Java 层已经做到了**

**关键**：`VirtualContext` 已经伪造了 `getFilesDir()`/`getDataDir()` → **Java 层看到的是干净路径** ✓

**问题只在 native 层**：
- `readlink("/proc/self/fd/N")` → 返回真实沙箱路径
- `/proc/self/maps` → 露 `<dataDir>/files/virtual/**`
- `stat` 返回的 `st_dev`/`st_ino` → 能推断位置

### 5.3 设计与危害评估

| # | 方案 | 效果 | 代价 | 危害（如果做） |
| --- | --- | --- | --- | --- |
| **A. 现状** | Java 干净、native 露 | Java 层完全隐蔽 | 零 | — |
| **B. `readlink` 伪造** | 把 `/proc/self/fd/N` 的返回值改写成假路径 | native 层也隐蔽 | 中（已有 `hooked_readlink`） | **低**（只需字符串替换） |
| **C. 换沙箱根**（去掉 `com.nextvm.app`） | `/data/misc/<随机>/...` | 路径不含容器包名 | **高**（要迁移 + `/data/misc` 不可写） | ⚠️ 可能拿不到可写目录 |
| **D. `pathFidelity = true` 全面启用** | guest 真的用 `/data/user/0/<pkg>` | 最隐蔽 | **不可行**（真实目录需要真实安装） | — |

**建议**：
- **A + B**：Java 层（已做）+ `readlink` 伪造（B，中等工作量）
- **C 不可行**（`/data/misc` 应用写不了）
- **D 不可行**

### 5.4 "多大危害"—— 现在的暴露面

**如果 guest 用 native 反查**：

```
readlink("/proc/self/fd/N") → "/data/user/0/com.nextvm.app/files/virtual/data/mark.via_xxx/files/x"
```

**guest 能推断出**：
1. **容器包名** `com.nextvm.app` → **直接暴露"我在容器里"**
2. **沙箱结构** `files/virtual/data` → 暴露容器的实现
3. **实例 ID** `mark.via_1795511947815` → 暴露"多开"

**危害等级：高**（如果被检测）

**但**：
- **需要检测方主动用 `readlink` 反查自己的 fd**
- **加固壳会做**（`P21`/`P24` 就是测这个）
- **普通应用不会**

**所以**：**`readlink` 伪造（方案 B）是值得做的**，优先级中高。
