## 一、WebView 的 `file://` 关键区分（`android_asset` vs 真文件系统）

### 1.1 实测发现的线索

```
$ adb shell unzip -l /data/app/~~ZieOt3qHtO7aDBRKUjHYrg==/mark.via--Bw_Pqlf8IFOHB8PrcTMwQ==/base.apk | grep -i 'assets/.*html'
  479  assets/error.html
```

**Via 的 APK 里只有 `assets/error.html`（错误页）** —— **主页不在 assets**。

**所以"Via 主页正常"可能不是 `file://` 的成功案例**，而是：
- 主页是**网络页面**（`https://...`）
- 或**动态生成的 HTML**（`loadDataWithBaseURL`）

### 1.2 但 `assets/` 这条路径确实"正常"，原因是机制不同

| URL 形式 | 读取机制 | 受 renderer uid 限制吗 | 在容器里可用吗 |
| --- | --- | --- | --- |
| **`file:///android_asset/x.html`** | 通过 **`AssetManager`**（APK 内部的 zip 表），**不是文件系统** | ❌ **不受限** | ✅ **可用** |
| **`file:///sdcard/x.html`** | 真实文件系统 `open()` | ✅ **受限** | ❌ 读不到沙箱 |
| `https://...` | 网络 | — | ✅ 可用 |
| `loadDataWithBaseURL` | 字符串 → renderer 内存 | — | ✅ 可用 |

**关键洞察**：
> **`android_asset` 走的是 `AssetManager`（Binder 到 `Resources` / 直接读 APK 的 zip 目录），
> 不是文件系统调用，所以不受 renderer 的 isolated uid 限制。**
>
> **这就是"规范方式"：本地资源就该放在 `assets/` 里。**

### 1.3 所以"容器模仿"的含义

| 场景 | 真机做法 | 容器能否模仿 |
| --- | --- | --- |
| **应用自带的 HTML/JS/CSS** | 放 `assets/`，用 `file:///android_asset/` | ✅ **完全可用**（APK 在沙箱，`AssetManager` 照常工作） |
| **应用生成的本地页**（如缓存预览） | 写 `getCacheDir()`，用 `file://` + 绝对路径 | ⚠️ **写能成功（沙箱），但 renderer 读不到** |
| **用户提供的 HTML** | 从 `/sdcard` 读 | ❌ 需要导入 + 仍受 renderer uid 限制 |
| **网络内容** | `https://` | ✅ 可用 |

**结论**：
> **99% 的应用本地页面都在 `assets/` 里**（这是规范做法）。
> **真正需要用 `file:///sdcard/` 的场景极少**（本地 HTML 阅读器、离线文档）。
>
> **所以 WebView 的问题没有我担心的那么大** —— 只有"应用自己写文件再用 file:// 打开"这一种会失败。

### 1.4 但"应用自己写 cache 再用 file:// 打开"这类确实会失败

**典型场景**：
- 应用把 HTML 报告写到 `getCacheDir()/report.html`，然后 `loadUrl("file://" + path)`
- **写成功**（沙箱），**读失败**（renderer uid）

**这一类**才是 P1-3 要解决的。**代价 4–5 天且可能只覆盖部分**。

**用户说"稍后组织 Gaia 机制研究，暂不执行"** → **记录待办，不设计**。

## 二、不删旧 hook：改为"用途待确认"

### 2.1 我之前的建议（**撤回**）

我说"删 `syscall`/`fork`/`mmap`/`mprotect`，因为它们只打日志"。

**你的提醒是对的** —— 这和"判死代码"是同一类错误：
- **只打日志 ≠ 没有用途**：日志本身是**诊断能力**（`DIAG syscall nr=... by <caller>` 能定位是谁在调）
- **现在不用 ≠ 以后不用**：`mmap`/`mprotect` 的 hook 可能是为**未来的 maps 伪造**准备的
- **删掉就丢失了"这个函数被谁调用"的观测能力**

### 2.2 修正后的处置

| 符号 | 我之前的建议 | **修正后** |
| --- | --- | --- |
| `syscall` | 删 | **保留**，标记「**纯诊断**（`DIAG` 日志），未参与拦截」 |
| `fork` | 删 | **保留**，同上 |
| `mmap` / `mprotect` | 删 | **保留**，标记「**用途待确认**（可能与 maps 伪造有关）」 |
| `ptrace` | 待定 | **保留**，标记「**待确认**（可能是反调试伪装）」 |
| `connect` / `getaddrinfo` | 待定 | **保留**，标记「**可能用于网络重定向**」 |

**唯一真正该动的是**：**把它们的"日志级别"和"用途"在文档里写清楚**，而不是删除。

### 2.3 但"减少痕迹"的目标仍然有效 —— 换个做法

| 原方案（删） | **新方案（可配置）** |
| --- | --- |
| 删掉 hook 表项 | **加开关**：`NS_HOOK_DIAG_ONLY=0` 时，纯诊断类的 hook **不装**（但代码保留） |

**这样**：
- 默认可以关掉（减少痕迹）
- 需要诊断时打开
- **不丢能力**

**缺点**：多一个开关（但比删除安全得多）。

## 三、攻防论证：导入代替代读

### 3.1 可用的情况（✅）

| 场景 | 为什么可用 |
| --- | --- |
| **导入 APK** | 一次性、用户主动、拷进沙箱后不再需要真实路径 |
| **导入文档/图片/电子书** | 同上 |
| **导入配置文件** | 同上 |
| **guest 自己产生的文件** | 在沙箱内，不需要导入 |

### 3.2 不可用的情况（❌）

| 场景 | 为什么不可用 | 影响 |
| --- | --- | --- |
| **相机拍照** | 相机应用（或系统相机通过 Intent）写 `/sdcard/DCIM/Camera/xxx.jpg` → **真实路径** → guest 读自己的沙箱 → **看不到** | **相机功能完全不可用** |
| **文件下载到 `/sdcard/Download`** | 浏览器/下载器写真实路径 → guest 读沙箱 → 看不到 | 下载功能受限（除非下载到沙箱内） |
| **监听目录变化**（`FileObserver`） | 只能监听沙箱 → 真实路径的变化看不到 | 自动化/同步类应用不可用 |
| **大文件**（视频编辑） | 双份空间 | 存储受限 |
| **外部应用写文件给 guest** | 需要先导入 | 跨应用协作受限 |
| **`MediaStore` 查询** | 查的是系统媒体库（真实），不是沙箱 | 相册类应用看到的是"真实媒体库" → **可能与沙箱不一致** |

### 3.3 "导入范围完全由用户确定"的四个问题

#### 问题 1：**用户不知道 guest 需要什么**

- guest 需要 `/sdcard/DCIM/Camera/IMG_001.jpg` → 用户**不知道这个路径**
- **结果**：guest 报错"文件不存在"

#### 问题 2：**沙箱的 `/sdcard` 是空的 → 与真机不一致 → 可被检测**

**这是最严重的问题**：

```
真机： ls /sdcard → DCIM/ Pictures/ Download/ Music/ Movies/ ...  （几百个文件）
容器： ls /sdcard → （空，或只有导入的几个文件）
```

**guest 只要 `listFiles("/sdcard")` 就能发现异常**。

**这是 D3 层（文件系统检查）的检测面，而且导入方案无法解决** —— 因为"导入"本来就是"用户决定放什么"。

#### 问题 3：**导入的时机与 guest 的期望不匹配**

- guest 启动时扫描 `/sdcard/DCIM` → 空 → 认为"没有照片"
- 用户导入后，guest 需要**重启或刷新**才能看到

#### 问题 4：**权限模型不一致**

- 真机：guest 有 `READ_EXTERNAL_STORAGE` → 能读所有
- 容器：guest 能读沙箱，但沙箱内容由用户决定 → **两者语义不同**

### 3.4 "如果为空是什么后果"—— 逐层分析

| 层级 | 空沙箱的后果 |
| --- | --- |
| **功能性** | 相机/相册/下载/文件管理器类应用**基本不可用** |
| **检测面（D3）** | `listFiles("/sdcard")` 返回空 → **与真机明显不一致** → **强证据** |
| **检测面（D6 行为）** | 「声称有存储权限，但 `/sdcard` 空」→ **自相矛盾** |
| **崩溃风险** | 部分应用假设"至少有一个目录存在"（如 `DCIM/`）→ 可能 NPE |

### 3.5 结论：导入**不能完全替代**代读，但可以作为**默认策略**

| 策略 | 适用 | 补充措施 |
| --- | --- | --- |
| **导入（默认）** | 用户主动提供的文件 | — |
| **+ 预置"像真机"的目录骨架** | 缓解 D3 检测 | 在沙箱里预建 `DCIM/Camera/`、`Pictures/`、`Download/`、`Music/` 等空目录（**真机上这些目录通常存在**） |
| **+ 可选"共享真实 /sdcard 只读"** | 需要读真实文件的场景 | ⚠️ 需要 `MANAGE_EXTERNAL_STORAGE` → **会传导给所有 guest**（见权限传导文档） |

**关键建议**：
> **至少要在沙箱里预置 `/sdcard` 的标准目录骨架**（`DCIM`、`Pictures`、`Download`、`Music`、`Movies`、`Documents`、`Android/data/<pkg>`）。
> **这是零成本、直接减少 D3 检测面的措施。**

**Android 的 `/sdcard` 标准目录**（AOSP `Environment.java` 定义）：
```
Alarms/ Android/ DCIM/ Documents/ Download/ Movies/ Music/ Notifications/
Pictures/ Podcasts/ Recordings/ Ringtones/
```

**预置这些空目录，`listFiles` 的结果就和真机"看起来一样"**（虽然内容是空的，但"新手机"也这样）。

## 四、`:probe` 进程：放弃

用户明确"允许放弃"。理由已充分：
- guest 进程本身就是"全 hook"环境 → 测试直接跑那里
- 避免多一个进程的复杂度

**从计划里移除。**
