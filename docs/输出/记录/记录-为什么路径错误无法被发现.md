# 复盘：为什么"路径转换错了"能一直不被发现

- 日期：2026-11-25
- 触发：用户问「为什么常常不能直接知道错误在哪，连路径转换错了都不知道」
- 这是本项目**最有价值**的一次提问 —— 因为它指向的不是某个 bug，是**诊断能力的结构性缺失**

---

## 一、根本原因：在这个系统里，「错」和「空」长得一模一样

一次路径翻译错误的完整表现：

```
应用：  File.listFiles()  on  /sdcard/Android/data/<pkg>/files/offline
规则：  /sdcard/Android/data/<pkg>/  ->  <sandbox>/external_data/     ← 目标错了
syscall：opendir("<sandbox>/external_data/files/offline")
         -> 成功（目录被 mkdirs 创建过，但从来没写入）
返回：  空数组
应用渲染：空列表
```

**全程：没有异常、没有崩溃、没有 error 日志。**

而**"目录真的是空的"表现完全相同**：`opendir` 成功 → 空数组 → 空列表。

> **这就是为什么"连路径转换错了都不知道"** ——
> **错误的表现与正常空状态无法区分。**

---

## 二、三层可观测性的缺失（逐层看）

| 层 | 现在能观测到 | **盲区** |
| --- | --- | --- |
| **规则层** `translatePath` | 命中翻译时 `java_io_record(source)` | **只记源路径，不记翻译成了什么** |
| **行为层** `list0` | 失败时记录 errno | **成功但返回 0 条 —— 完全静默** |
| **语义层** 应用侧 | 无 | **应用期望 N 条，实际拿到 0 条，无人知道** |

### 2.1 规则层：只记了"我命中了一条规则"，没记"翻到哪"

```cpp
if (translated) java_io_record("list0", real.c_str(), 0, 0);
//                                     ^^^^^^^^^^^^^^ 这是翻译后的路径
```

**看起来记了翻译后路径** —— 但 `java_io_record` **只在命中翻译时触发**，
而 via 的场景是 `translated=0`（它全用沙箱路径），**所以一条都不记**。

**于是"规则到底把 A 映射成了 B"这件事，在运行时完全不可见。**

### 2.2 行为层：成功但空，不算失败

```cpp
if (d == nullptr) { ... 记录 errno ... }   // 失败有记录
...
return arr;                                 // 成功（哪怕 0 条）无任何记录
```

**这是最致命的设计** —— "返回 0 条"是**合法返回值**，代码作者不会想到要记它。

### 2.3 语义层：没有任何"预期值"

**修 bug 之前，这个项目里没有一句话说"`/sdcard/Android/data/<pkg>/` 应该映射到哪"。**

只有两处独立代码：
- `SandboxManager.getExternalAppFilesDir()` → `<appDir>/sdcard/Android/data/<pkg>/`
- `NativeHookBridge.setupAppRedirections()` → `<appDir>/external_data/`

**各自看都合理，只有并排比才发现不一致。**

---

## 三、为什么"并排比"这件事没人做

| 原因 | 具体表现 |
| --- | --- |
| **两个模块职责被分开了** | `SandboxManager`（沙箱布局）与 `NativeHookBridge`（路径规则）属于不同包，改一个不用看另一个 |
| **各自的命名都"看起来对"** | `external_data` 听起来就是"外部数据"，没人会怀疑它 |
| **上游就是这么写的** | 照抄上游 → 继承了上游的错误，且没有理由怀疑 |
| **没有测试表达这个契约** | 38 条测试是**今天才写**的，之前 0 条 |

---

## 四、今天补上的三样东西（以及它们各自防什么）

| # | 措施 | 防的是 | 状态 |
| --- | --- | --- | --- |
| 1 | **T35：写入侧 vs 读取侧一一对应** | 两侧映射不一致（本次三类错误） | ✅ |
| 2 | **`list0` 打印 `-> N entries` 与 `(EMPTY)`** | 成功但空返回的静默 | ✅ `66095ed` |
| 3 | **T30 对偶性 / T33 模糊** | 漏注册某种写法 / 未预见的输入组合 | ✅ |

**其中第 1 条是根本性的** —— 它把"预期"从**人的记忆**变成**可执行断言**：

```kotlin
// 写入侧（SandboxManager 的真实返回）  vs  读取侧（规则翻译结果）
"/storage/emulated/0/Android/data/$guest/files" to "$guestExternalData/files"
```

**任何一侧被改动，这条测试立刻红。**

---

## 五、还缺什么（诚实清单）

| # | 缺口 | 后果 |
| --- | --- | --- |
| 1 | **翻译时同时记录源和目标** | 出问题时仍要靠猜"翻到哪了" |
| 2 | **没有"运行时规则快照"**：启动时把全部规则 dump 一次 | 无法确认"规则真的注册上了" |
| 3 | **没有"空结果"的告警级别**：`(EMPTY)` 只是 LOGI | 会被淹没在日志里 |
| 4 | **应用侧的"预期"无从得知**：只能靠人工判断 | 无法自动发现"应该非空却空了" |

**第 2 条最容易补且收益最大**：启动时打印全部规则（源 → 目标），
一眼就能看出"`external_data` 这个目标是不是我想要的那个"。

---

## 六、方法论：诊断能力应该和功能一起设计

**这次的教训不是"我漏查了什么"，而是：**

> **当一个操作有多种"正常的坏结果"（空列表 / 空文件 / 默认值），
> 就必须在写实现的同时定义它的可观测点 —— 否则错误会伪装成正常。**

具体到路径翻译，有三条可执行的规则：

| 规则 | 做法 |
| --- | --- |
| **规则 1：翻译必须可回放** | 记录 `source -> target`，而不是只记 `source` |
| **规则 2：空返回必须显式** | 返回 0 条时打 WARN 并带路径，不要静默 |
| **规则 3：跨模块一致必须有测试** | 凡是"一处写入、另一处读取"的路径，都必须有对应断言 |

**这三条里，只有第 3 条今天做到了。**

---

## 七、一句话

> **"连路径转换错了都不知道"，不是因为没查，是因为这个系统的错误没有形态**
> —— 它返回一个合法的空数组，然后继续跑。
>
> **让它有形态的办法只有两个：给它一个预期（不变量测试），或者给它一个声音（EMPTY 日志）。**
> 今天两样都补了，但都是被踩到之后才补的。
