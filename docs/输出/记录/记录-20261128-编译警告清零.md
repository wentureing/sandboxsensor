## 二、成因（git 溯源）

### 2.1 `hooked_java_linux_opendir` —— **我们自己造的，且它是"Java IO hook 从未装上"的直接原因**

| 提交 | 作者/日期 | 做了什么 |
| --- | --- | --- |
| `c71d7ed` | wentureing / 2026-11-25 | `feat(hook+diag): Java 层文件操作 hook 扩到 6 个` —— 加第 6 个方法 `opendir`（函数 + `RegisterNatives` 注册项） |
| `9d33da0` | wentureing / 2026-11-25 | `fix(hook): 找到两个真实错误 —— opendir 不存在 + File 根本不走 libcore.io.Linux`。**反编译设备上的 `core-libart.jar`**，逐个比对 `Llibcore/io/Linux;` 的 **150 个方法 / 134 个 native**，发现 **没有 `opendir`**（`opendir` 只在 `sun.nio.fs.UnixNativeDispatcher` 里是 Java 方法）。⇒ 批量 `RegisterNatives` 是**全或无**，一个签名不对 ⇒ **整批失败 `code=-1`** ⇒ 「Java IO hook 从来没装上过」 |
| `9d33da0` 的处置 | 同上 | **只删了注册项，保留函数实现** ⇒ 变成死代码（本轮警告来源） |
| `9c0d3e9` | 本轮 | 删除该函数 |

**为什么删而不是重新接线**：`Linux.opendir` 在设备上不存在；而 `File.listFiles()` 走的是 `UnixFileSystem.list0`（已 hook），
`File.list()` 的底层 `opendir` 由 `libjavacore.so` 直接调 libc ⇒ 已被 native GOT hook `hooked_opendir` 覆盖。
**保留函数只会制造"看起来支持 opendir"的错觉**，所以删除是对的。

### 2.2 `probe_signal_handler` —— **上游遗留死代码**

| 提交 | 作者/日期 | 说明 |
| --- | --- | --- |
| `7cdcf01` | **Tanvir Hossain / 2026-03-07** | `Initial release: NEXTVM Android Virtual Environment Engine` —— 该函数与 `g_probe_jmp`/`g_probing` 一起引入 |
| （此后 251 个提交） | — | `git log -S 'probe_signal_handler'` 只命中引入与删除两次 ⇒ **从未被引用**；`is_address_readable` 实际用 `mincore()` 而非 SIGSEGV 探针 |

⇒ 属上游"写了没接线"的死代码，与我们的 fork 无关，本轮直接删除（连同 `g_probe_jmp`/`g_probing`）。

### 2.3 一句话对照

```
hooked_java_linux_opendir  → fork 后（c71d7ed）引入，9d33da0 证伪后残留 → 本轮删除（根因：设备上 Linux 类没有 opendir）
probe_signal_handler       → 上游（7cdcf01）引入即未用        → 本轮删除（根因：上游改用 mincore）
```
