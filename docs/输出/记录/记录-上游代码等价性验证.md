## 三、等价性验证结果（`check-refactor-equivalence.mjs`）

工具新增 `--ignore <正则>`：比较前删除匹配的整行，用于忽略新增的插桩行。

| 函数 | 结果 | 说明 |
| --- | --- | --- |
| `handleMessage` | ✅ **等价** | 忽略插桩后逐字相同 |
| `handleExecuteTransaction` | ✅ **等价** | 同上 |
| `handleLaunchActivityItem` | ✅ **等价** | 同上（**STEP 0-5 核心路径未变**） |
| `replaceClassLoader` | ✅ **等价** | 同上 |
| `hookInstrumentationIfNeeded` | ✅ **等价** | 同上 |
| `preRegisterActivityToken` | ✅ **等价** | 同上 |
| `createApplication` | ✅ **等价** | **Step 1-6 未变** |
| `setupAppRedirections` | ✅ **等价** | 规则内容未变 |
| `onActivityPreCreate` | ⚠️ 插桩残留 | 限流插桩是**多行 if 块**，`--ignore` 只删单行 → 残留 `if (...) {}`，属工具局限 |
| `bindApplication` / `initContentProviders` / `initNativeHooks` | ⚠️ 插桩残留 | 同上下（新增的 check 是多行调用） |
| `addPathRedirection` | 🔴 **结构性改造**（预期内） | 实现搬到了 `PathRedirectRegistry.add`，已在 `PathRedirectRegistry.md` 的偏差登记里写明 |

**结论**：
> **`ActivityThreadHook` 的 6 个核心函数、`createApplication`、`setupAppRedirections`
> 在忽略插桩后与上游逐字相同** —— 拆分没有改业务逻辑。
> 唯一真实的结构改动是 `addPathRedirection`（委托给独立类），属 v154 的有意重构。

**工具局限（诚实记录）**：`--ignore` 只能删单行，多行插桩块（`if` + 调用）会留下骨架，
造成误报。要彻底解决需要做 AST 级比较，超出当前投入。

## 四、关于「在上游植入测试获取 golden」

### 为什么 CI 里拿不到行为 golden

| 需要 | 上游有吗 | CI 能做吗 |
| --- | --- | --- |
| 诊断层代码（`CheckResult` / `Diagnostics` / `FileSink`） | ❌ 无（我们新增） | ✅ 可复制过去 |
| `DebugFlags` / `DebugTrace`（诊断层依赖） | ❌ 无 | ✅ 可复制 |
| **真机执行 hook** | — | ❌ **不能** |
| **`checks.log`（真实行为）** | — | ❌ **不能，只能真机** |

**所以**：
- **格式/契约** golden → 可在 CI 用上游代码生成（就是现在这 23 条模板）
- **行为** golden → **必须真机跑两次**（上游一次、重构版一次）才能对比

### 可行的两条路

| 路线 | 做法 | 成本 | 价值 |
| --- | --- | --- | --- |
| **A. 静态等价检查**（已做） | `check-refactor-equivalence` + 上游代码 | **已完成** | **直接证明"逻辑未变"**，覆盖所有分支 |
| **B. 真机 golden 对比** | 上游装一次、重构版装一次，各导出 `checks.log`，diff | 2 轮真机 | 证明"运行时行为一致"，但要 2×装机 |

**建议**：**A 已经给出足够强的证据**（8 个核心函数逐字相同）。
B 的价值主要在"插桩之后的实际路径编排"，可以等真机测试时顺带做（只需在真机上跑一次重构版，
与 CI 模板对比，而不是再装一次上游）。
