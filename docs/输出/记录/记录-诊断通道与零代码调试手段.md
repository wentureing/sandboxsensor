## 一、项目已有的插桩能力（代码为准，无需新增）

| 通道 / API | 落盘位置 | 何时可用 | 适合写什么 | 谁在消费 |
| --- | --- | --- | --- | --- |
| `DebugFlags.init(context)` | 触发两件事 | `VirtualEngine.initialize → nativeHookBridge.initNativeHooks`（`:368` → `NativeHookBridge.kt:208`） | 主进程也会执行（P0-3 只是"不装 hook"，init 在早退之前） | — |
| `DebugTrace`（Timber 文件 Tree） | `files/debug-trace.log`（`DiagFiles.DEBUG_TRACE`） | 同上，**debug 包**才 plant | 自由文本事件；`Timber.*` 自动进这里 | 人读（`run-as cat`） |
| `DiagOutput` | 由 `DebugFlags.init` 绑定 `filesDir`（`DebugFlags.kt:92`） | 主进程同左 | 具名通道追加/覆盖（`DiagFiles` 规范名） | 各诊断生产者 |
| `DiagnosticsHolder`（`CheckResult` / `error` / `stage`） | `files/checks.log`（主进程 `VirtualEngine.kt:307` 已 install `FileSink`） | 主进程 | **低频阶段转移**（`S tag msg`）与错误（`E tag msg`，同步直写不丢） | 自检 / 探针 / 人读 |
| `GuestBreadcrumb` | `<sandbox>/files/breadcrumb-<pid>.log` | **guest 进程**（`attachFile` 之后） | guest 生命周期顺序（启动链契约 C1–C12） | `BreadcrumbGoldenContractTest` |
| `DiagFiles` + `diag_channels.tsv` | 命名唯一规范 | 新增通道必须改 TSV → `gen-diag-channels.mjs` → `check-diag-channels.mjs` | 新增文件名会用 C++ `is_container_diag_path` 的配额判断 | C++ / 生成物 `.inc` |
| 探针 APK（`com.sandbox.probe`） | 报告 JSON / D 系列 | 独立 APK，guest 进程 | 观测面一致性（J/W/N/P） | `collect-probe.ps1` |
| `CmdReceiver` 命令 | `logcat -s CmdReceiver` + 文件 | 主进程 | INSTALL/LAUNCH/STOP/LIST/SELF_CHECK/COLLECT_OUT… | 设备脚本 |

**关键事实**：`DebugTrace` 是"全局 Timber tree"，所以**任何 `Timber.tag(...).i(...)` 在 init 之后都会落 `debug-trace.log`** ——
不需要每个类都改成 `DebugTrace.event`。这也是为什么"只打 Timber"在 debug 包里并非只到 logcat。

## 二、本轮新代码最终用到的通道（Step 0a/0b/1）

| 事件 | 通道 | 位置 |
| --- | --- | --- |
| slot 探测失败 | `DiagnosticsHolder.error("slot", …)` → `checks.log` 的 `E slot …`；`DebugTrace.fail` → `debug-trace.log` | `VirtualEngine.slotStatus()` |
| stub 归还（L1） | `DiagnosticsHolder.stage("slot", …)` → `checks.log` 的 `S slot released stubs slot=N killed=k/total`；`DebugTrace.event("l1", …)`；`Timber.i` | `VirtualEngine.stopApp()` |
| slot 快照 | **不落盘**（只进 UI 的 `ProcessSlotsScreen`） | `engine.slotStatus()` |

**为什么没有新增日志文件（如 `slots-<pid>.log`）**：
新增通道要改 `diag_channels.tsv`、重跑 `gen-diag-channels.mjs`（生成物进 C++ 的 `.inc`）、再过 `check-diag-channels.mjs`。
本轮只是"观测 + 归还"，用现有两条 shared 通道（`checks.log` / `debug-trace.log`）已足够；
**引入新通道的收益（可读性）小于触碰 C++ 契约（配额/差异区）的风险**。若 Step 3 之后确需独立时间线，再按规范加。

**为什么不用 `GuestBreadcrumb`**：它绑的是**当前进程**的 filesDir（guest 侧沙箱），主进程写会把 slot 事件混进 guest 生命周期 golden 序列，
破坏 C1–C12 的"逐行相等"契约。

**为什么不用 `checks.log` 的 `check()`**：`check()` 是结构化验证结果（`hookcheck ok=N fail=N` 由探针解析），
slot 事件属"阶段转移"，用 `stage()` 语义更准确、也不会污染探针的前缀解析。

## 三、「零代码改动」的调试手段（本轮 U1–U5 直接用）

### 3.1 系统通道（无需改任何代码）

| 想回答 | 命令 | 读什么 |
| --- | --- | --- |
| **是否复用了原进程** | `adb shell ps -A -o PID,ELAPSED,NAME \| findstr "nextvm.app:"` | 点前后 pid **是否相同**、ELAPSED 是否连续增长 |
| **是否新建了 Task** | `adb shell dumpsys activity activities \| findstr /i "nextvm stub taskAffinity"` | `taskId=` 是否变化、`taskAffinity=com.nextvm.vt.p1.s00` 是否仍是同一个 |
| 当前前台 Activity | `adb shell dumpsys activity activities \| findstr /i "mResumedActivity"` | 是哪个 stub 组件 |
| 进程 importance / 是否 cached | `adb shell dumpsys activity processes \| findstr /i "nextvm"` | `cached` / `foreground` |
| 最近任务列表 | `adb shell dumpsys activity recents \| findstr /i "nextvm"` | 有几个容器 task（每次点击多一个 = R2 未修） |
| 时间线（进程创建 / Activity / task） | `adb shell perfetto -o /data/misc/perfetto-traces/slot.pftrace -t 10s -a am -a wm` | Perfetto UI 里看 process start 与 activity launch |

### 3.2 项目文件通道（判定只读文件，符合 AGENTS 约定）

```powershell
# 主进程：slot 事件（Step 1 的归还有没有发生 / 杀了几个）
adb shell run-as com.nextvm.app cat files/checks.log | Select-String "slot"
adb shell run-as com.nextvm.app cat files/debug-trace.log | Select-String "released stubs|slotStatus failed"

# guest 侧：是否发生了新的 bind（复用时不出现新的 bind start）
adb shell run-as com.nextvm.app ls files/virtual/data
# 再 cat <instance>/files/breadcrumb-<pid>.log
```

### 3.3 既有脚本 / 探针（无需新代码）

| 工具 | 用途 |
| --- | --- |
| `tools/device/clean-install-and-test.ps1 -Apk dist\c.apk` | 一键冒烟（SELF_CHECK + 探针 + via 三连判定） |
| `tools/device/capture-breadcrumb-golden.ps1` | STOP + LAUNCH 采 golden（本任务的"单次会话"基线） |
| `tools/device/collect-probe.ps1` | 拉探针报告 |
| 探针 APK（J/W 系列） | guest 视角一致性 |

## 四、成熟项目 / 工具推荐（按"是否要改代码"排序）

| 方案 | 是否改项目 | 适合本任务什么 | 取舍 |
| --- | --- | --- | --- |
| **dumpsys（AOSP 自带）** | ❌ 不改 | ✅ task / 进程 / Activity 栈的**权威事实**，正好对应 U1/U5 | 输出格式随版本变，命令要按 ROM 调 |
| **ps / procps** | ❌ 不改 | ✅ 进程 pid 与存活时间（复用判定） | 需要 `adb`，只看得到进程不看 task |
| **Perfetto / atrace** | ❌ 不改 | ✅ 时间线（进程创建、activity launch、wm） | 要抓 trace 文件 + Perfetto UI 看；部分 ROM 限制 atrace |
| **项目内 `checks.log` / `debug-trace.log`** | ❌ 不改 | ✅ 我们自己的 slot 事件与失败 | 只有我们写的事件，不含系统视角 |
| **Android Studio Layout Inspector / Compose Preview** | ❌ 不改 | UI 结构与状态（ProcessSlotsScreen 是否按 state 渲染） | 不回答进程/task 问题 |
| **LeakCanary** | ⚠️ 加 `debugImplementation` | Activity/进程泄漏（会话复用做错会漏 Activity） | 引入依赖 → 改 gradle、影响 CI 缓存与包体；本轮不引入 |
| **UIAutomator / androidx.test** | ⚠️ 加依赖 + 测试 APK | 把 U1–U5 自动化 | 成本高；本轮用"脚本 + dumpsys 判据"更便宜 |
| **Robolectric** | ❌ 已有 | 纯 JVM 单测（`SlotReconciler` 已在用普通 JUnit） | 不需要；`ActivityManager` 行为测不了 |

**结论**：本任务不需要引入任何第三方调试库。**dumpsys + ps + 项目文件通道**已经能给出 U1–U5 的全部判据；
Perfetto 作为"时间线复核"备用。

## 五、本轮验收命令（可直接粘）

```powershell
# 0) 基线：进程与任务
adb shell ps -A -o PID,ELAPSED,NAME | findstr "nextvm.app:"
adb shell dumpsys activity activities | findstr /i "nextvm taskAffinity"

# 1) U1：点 guest → Home → 再点同一 guest，重复上面两条
#    判据：pid 不变、taskId 不变、ELAPSED 持续增长；breadcrumb 无新的 bind start

# 2) U2：连做 6 次
adb shell run-as com.nextvm.app cat files/checks.log | Select-String "slot"
#    判据：不出现 No available stub；Step 1 之后每次 STOP 出现一条 "released stubs slot=N"

# 3) U3：kill guest 进程后回设置页刷新
adb shell kill <pid>     # 或从 ps 取
#    判据：设置页 usedSlots 减 1；checks.log 有 STALE 回收记录（Step 3 之后）

# 4) U4/U5：设置页显示 "n / 10 in use"；列表 pid 与 ps 一致
```
