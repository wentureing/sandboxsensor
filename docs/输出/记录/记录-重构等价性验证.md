# 记录：用 _ref 原始代码验证重构等价性

- 日期：2026-11-24
- 触发：用户指出「当前 golden 来源是重构后的实现，需要依据 `_ref` 原始代码验证」

---

## 一、问题（我之前的做法错在哪）

`approved.txt` 是我**读重构后的实现推导**出来的。这只能证明"实现与推导一致"，
如果抽取时逻辑被改动，golden 会跟着一起错，测试照样通过。

**golden ≠ 重构等价性**：

| 目标 | 正确手段 |
| --- | --- |
| 锁定**当前**行为、防未来回归 | golden（已做） |
| 证明**这次重构**没改逻辑 | 必须对照 `_ref` 里的原始代码 |

## 二、做法：静态等价性检查

新增 `tools/lint/check-refactor-equivalence.mjs`：

1. 用 `git show <commit>:<path>` 把**重构前**的文件导出到临时文件
2. 从新旧两份源码里各截出目标函数体（按花括号配对）
3. **归一化**：去注释、去字符串内容、空白归一
4. 逐字对比；不等价则打印第一处差异（带上下文）

> 沙箱限制：脚本内不能 `spawn git`（EPERM），所以导出交给 shell，脚本只读文件。

## 三、验证结果（2026-11-24）

### ✅ `describeTransactionItem` → `describe`

```
等价 ✓  归一化后逐字相同，743 字符
旧：63346e6:.../engine/ActivityThreadHook.kt:describeTransactionItem
新：.../engine/activitythread/TransactionDiagnostics.kt:describe
```

**结论**：v151 抽取是纯搬迁，逻辑零改动。这也反过来支持了 golden 的可信度
（golden 虽然按新实现推导，但新实现 == 旧实现，所以等价关系成立）。

### ✅ `buildFakeProcStatus` → `buildFakeProcStatus`

```
等价 ✓  70 字符逐字相同
旧：7cc0848^:.../hook/NativeHookBridge.kt
新：.../hook/ProcSpoofing.kt
```

**结论**：v154 搬迁零改动。

### ⚠️ `translatePath` → `translate`（结构性改造，语义等价）

```
第 6 字符处不同:
  - 旧: if (hiddenPaths.contains(originalPath)) { return "/dev/null" } var bestMatch = ...
  + 新: if (isHidden(originalPath)) return "/dev/null" var bestMatch = ...
```

**差异性质**：把"直接读 `NativeHookBridge.hiddenPaths` 字段"改成"通过回调 `isHidden` 注入"。

**语义等价的证明**：`NativeHookBridge` 里的绑定是

```kotlin
private val pathRedirects = PathRedirectRegistry(
    isHidden = { hiddenPaths.contains(it) },   // ← 与原实现完全相同的判定
    ...
)
```

**结论**：这是**有意的解耦**（让规则表不依赖 NativeHookBridge 的私有状态），
不是逻辑改变。属"必要的结构性偏差"，已记入 `PathRedirectRegistry.md`。

## 四、这个工具的定位

**它是重构的验收标准，不是可选的检查**：

| 场景 | 要求 |
| --- | --- |
| 纯搬迁（移动代码） | 必须报「等价 ✓」 |
| 结构性改造（解耦/注入） | 允许不等价，但**必须在镜像文档「偏差登记」里解释语义为何等价** |
| 逻辑应当改变 | 必须走变更计划（`docs/输出/变更/`），不能藏在重构里 |

## 五、用法

```powershell
# 1) 导出重构前的文件（commit 用容器仓库的，不是主仓库的）
git -C _ref/ShitJumpingVM show <commit>:<path> | Set-Content tools/tmp/old.kt -Encoding UTF8

# 2) 对比
node tools/lint/check-refactor-equivalence.mjs `
  --old-file tools/tmp/old.kt --old-fn <旧函数名> `
  --new-file <当前文件> --new-fn <新函数名>
```

## 六、局限

| 限制 | 说明 |
| --- | --- |
| 只对比**函数体** | 签名变化（参数增减、可见性）不报；需人工确认调用点 |
| 归一化会**忽略字符串内容** | 若日志文案改变，这里看不出来（golden 能看出来） |
| 表达式函数体（`fun x() = ...`）不支持 | 会返回"未找到函数"，需人工处理 |
| 不支持跨函数搬移 | 一个职责被拆到多个函数时，要逐段对比 |

**与 golden 互补**：静态检查覆盖所有分支（但不能证明运行时行为），
golden 覆盖真实输出（但只覆盖语料）。两者一起用。

## 八、补充验证（v158d）

### ✅ handleLegacyLaunchActivity / handleCreateService / handleReceiver

`
不等价 ✗  （三处相同性质的差异）
  - 旧: ... Timber.tag(TAG).d("...") } catch (e: Exception) { Timber.tag(TAG).e(e,"...") ...
  + 新: ... DebugTrace.event("legacy","...") Timber.tag(TAG_LEGACY).d("...") } catch ...
`

**差异性质（逐项确认）**：

| 差异 | 是否改变业务逻辑 |
| --- | --- |
| 新增 `DebugTrace.event("legacy", ...)` | ❌ 不改 —— 只在 `DebugFlags` 开启时写调试日志 |
| `Timber.tag(TAG)` → `Timber.tag(TAG_LEGACY)` | ❌ 不改 —— 只是日志 tag 改名，便于按模块过滤 |
| 其余（反射字段读写、classloader 替换、条件判断） | **逐字相同** |

**结论**：属于 v151 拆分时**主动加入的可观测性插桩**（当次提交说明里写了"含 debug 插桩"），
业务逻辑未变。已作为「必要偏差」记入 `LegacyMessageHandlers.md`。

### ⚪ classifyLooperThrowable（无法做函数级对比）

这个函数是 v150 从 `MainLooperGuard.install` 的 `catch` 块里**新抽出来的纯函数**，
旧代码里不存在同名函数，因此静态等价检查无法对比。

**替代保障**：`MainLooperGuardTest` 的 7 个用例钉住了分类规则
（普通异常 NONE / GMS 两类 / Toast UID mismatch / 深层 cause 链），
等价性由测试保证而非静态 diff。
