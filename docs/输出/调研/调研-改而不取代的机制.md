# 调研：有没有"改而不取代"的机制用于目录替换

- 日期：2026-11-25
- 触发：用户提问 —— 调查与 `RegisterNatives` 功能相似、但能**直接修改原有行为**（目录替换）而不是**取代**的机制
- 目的：找出一条"只翻译路径、其余全交给原实现"的路，彻底摆脱"手工仿真 AOSP 行为"的负担

---

## 一、先验证最直接的想法：能不能 `dlsym` 拿原 JNI 实现

**想法**：JNI 函数导出的符号名是 `Java_<类>_<方法>`，若 `libjavacore.so` 导出了它们，
就能 `dlsym` 拿到原实现，然后"翻译路径 → 调原实现 → 原样返回"，**零仿真**。

**实测（`tools/analyze/check-jni-exports.py`，解析设备 ELF 的 `.dynsym`）**：

```
文件: dist/native/libjavacore.so  (296496 bytes, ELF64)
  .dynsym: 232 个符号

=== 目标符号是否导出 ===
  [NOT FOUND] Java_java_io_UnixFileSystem_list0
  [NOT FOUND] Java_java_io_UnixFileSystem_createDirectory0
  [NOT FOUND] Java_java_io_UnixFileSystem_createFileExclusively0
  [NOT FOUND] Java_java_io_UnixFileSystem_getBooleanAttributes0
  [NOT FOUND] Java_java_io_UnixFileSystem_getLastModifiedTime0
  [NOT FOUND] Java_libcore_io_Linux_open / access / mkdir / stat / fstat

=== 所有 Java_* 符号 ===
  共 0 个
```

**结论**：**Android 把 JNI 实现全部隐藏了**（编译时 `-fvisibility=hidden` 或 `--version-script` 只导出 android_* 等公开符号）。

→ **`dlsym` 这条路走不通**，`RegisterNatives` 替换后拿不到原实现。

## 二、所以有哪些"改而不取代"的可行机制

### 方案 A：动态代理 `libcore.io.Os`（**可行，覆盖 `Os.*`**）

**可行性依据**（设备 dex 实测）：

```
Llibcore/io/Os;       flags = PUBLIC INTERFACE ABSTRACT     ← 公开接口，可 Proxy
Llibcore/io/Libcore;  flags = PUBLIC FINAL                  ← 字段 os 可反射替换
```

**做法**：

```java
Os original = Libcore.os;                     // 反射拿原值
Os proxy = (Os) Proxy.newProxyInstance(
    Os.class.getClassLoader(),
    new Class[]{ Os.class },
    (p, method, args) -> {
        // 只对"路径型 String 参数"做翻译，其余原样
        Object[] newArgs = translatePathArgs(method, args);
        return method.invoke(original, newArgs);   // ← 转交给原实现
    });
Libcore.os = proxy;                           // 反射替换静态字段
```

**优点**：
- **零仿真**（异常/返回值/EINTR 全由原实现决定）
- **版本适配免费**（方法名不变即可）
- **可精确回退**（把 `os` 换回原值）

**局限（关键）**：
> **覆盖不到 `File.*`** —— `File` 走 `UnixFileSystem.*0`，**不经过 `Libcore.os`**。

而实测 app 的 `File` 调用量是 `Os` 的 **100–400 倍**（1380–2060 vs 5–13）。
**所以这个方案收益有限**，但**对 `Os.*` 那一小部分是真优雅**。

### 方案 B：替换 `File.fs`（**最理想，但需要字节码生成**）

**想法**：`File` 的所有操作都委托给静态字段 `fs`（类型 `FileSystem`）。
把 `fs` 换成一个"只翻路径、其余委托"的子类实例 → **`File.*` 全部零仿真**。

**可行性依据**（设备 dex）：

```
Ljava/io/File;         有字段 fs : Ljava/io/FileSystem;
Ljava/io/FileSystem;   flags = ABSTRACT（**没有 PUBLIC**）   ← 包私有，普通反射继承不了
Ljava/io/UnixFileSystem;  包私有
```

**难点**：`FileSystem` 是**包私有 abstract class**，应用层的 `class MyFS extends FileSystem` 编译不过。

**但有三条绕过路径**：

| 路径 | 做法 | 风险 |
| --- | --- | --- |
| B1 | **字节码生成**：在容器里用 `DexClassLoader` + 动态生成 dex，声明 `package java.io; class MyFS extends FileSystem`（同包 → 可见） | 中（要生成 dex，容器有这能力但要写） |
| B2 | **`Unsafe.defineAnonymousClass`** 或 `MethodHandle.defineClass` 定义同包类 | 高（hidden API，Android 版本相关） |
| B3 | **`Proxy` 不可用**（`FileSystem` 是 class 不是 interface） | — |

**B1 是唯一现实路径**：容器已经有"生成/加载 dex"的能力（它就是个虚拟容器），
生成一个 `java.io.MyFileSystem extends FileSystem` 的类，把 `File.fs` 换过去。

**收益**：**`File.*` 全部零仿真** —— 这是当前 99% 调用量的那一层。

**代价**：要写 dex 生成 + `File.fs` 字段替换（`final static` 需绕过）。

### 方案 C：改 ART 的 `ArtMethod.entry_point_`（**Xposed 方式，通用但复杂**）

**做法**：找到目标 `ArtMethod` 结构，保存 `entry_point_`（原实现地址），替换成我们的入口；
我们的入口里翻译路径后**跳到原 entry**。

**优点**：**对所有 Java 方法通用**（不只 native），且**能拿到原实现**（保存的指针）。

**缺点**：
- `ArtMethod` 布局**随 Android 版本变**（需要维护偏移表）
- 需要 `mprotect` 改内存权限
- 属于"非常规手段"，与项目的"可维护"目标冲突

### 方案 D：VFS 层路径映射（**Android 10+ 已不可行**）

老 Android 用 `sdcardfs`/`ESDFS` 可以在内核层做路径映射，容器只需挂载。
但 **Android 10+ 改用 FUSE**（`/mnt/user/0/emulated`），**应用侧无法挂载**。
→ **这条路已关闭**。

## 三、四个方案对比

| 方案 | 覆盖范围 | 仿真负担 | 复杂度 | 建议 |
| --- | --- | --- | --- | --- |
| **A 动态代理 `Libcore.os`** | `Os.*`（app 调用量的 1%） | **零** | 低 | ✅ **值得做** |
| **B1 生成同包 `FileSystem` 子类 + 换 `File.fs`** | **`File.*`（99%）** | **零** | 中高 | ⭐ **最有价值，建议立项** |
| C 改 `ArtMethod.entry_point_` | 所有 Java 方法 | 零 | 高 | ❌ 与可维护目标冲突 |
| D VFS 挂载 | — | — | — | ❌ Android 10+ 不可行 |
| （现状）`RegisterNatives` 替换 | `File.*` + `Os.*` | **高**（手工复刻行为） | 低 | ⚠️ 被迫 |

## 四、对"目录替换而不是取代"的直接回答

**当前实现的本质确实是"取代"**（`RegisterNatives` 换掉原方法，原实现不可达）。
**要做到"只替换目录、其余原样"**，只有 **方案 B1** 真正覆盖 `File.*`：

```
理想形态（方案 B1 实现后）：

  File.listFiles()
    → FileSystem.list()          [原实现，未动]
      → MyFileSystem.list()      [我们的子类]
           translatePath(f.getPath())        ← 唯一的介入点
           → super.list(new File(sandboxPath))   ← 交给原实现
             → UnixFileSystem.list0()             [原实现，未动]
               → libc opendir()                    [原系统调用]
```

**这样：**
- 只要"翻译路径"这一件事是对的
- **异常类型、返回值、边界、EINTR 全部由 AOSP 原实现负责**
- 版本升级时，只要 `FileSystem` 的抽象还在，**自动适配**

**这就是用户想要的"改而不取代"。**

## 五、建议的推进顺序（**均未执行**）

| 优先 | 动作 | 说明 |
| --- | --- | --- |
| **P0** | **先补齐当前的最小可运行集合** | `Linux.fstat` / `stat` / `lstat` —— 这是"能不能跑"的前提，不能等重构 |
| P1 | 立项 **方案 B1**（生成同包 `FileSystem` 子类 + 换 `File.fs`） | 验证点：生成的类能加载、`File.fs` 能被替换、`File.listFiles` 走我们的子类 |
| P2 | 方案 A（动态代理 `Libcore.os`） | 收益小但成本低，可与 B1 并行 |
| ❌ | 方案 C / D | 不作为候选 |

### B1 的三个技术验证点（立项后先做）

| # | 验证 | 方法 |
| --- | --- | --- |
| 1 | 能否在**运行时生成**一个 `package java.io; class X extends FileSystem` 的类并加载 | 用容器的 dex 生成能力，`DexClassLoader` 加载后 `Class.forName` 检查 |
| 2 | `File.fs`（`private static final`）能否被反射改 | `Field.setAccessible(true)` + 去 final（`Field.modifiers` 或 `Unsafe`）；Android hidden API 可能拦 |
| 3 | 换掉 `fs` 之后，`File.listFiles` 是否真的走我们的子类 | 在子类方法里打一条 `checks.log`，看调用是否到达 |

**这三个验证都不大，但决定 B1 是否可行 —— 建议先做验证再做设计。**

---

## 六、一句话

> **JNI 层没有"改而不取代"的机制**（`Java_*` 全部未导出，`dlsym` 拿不到原实现）。
> **Java 层有**：`File.fs` 这个委托点是最理想的介入位置，但 `FileSystem` 是包私有，
> 必须**在容器里动态生成一个同包子类**才能实现 —— 这就是方案 B1，也是唯一能让 `File.*` 零仿真的路。
>
> **但当前优先级仍是"先补齐最小可运行集合"**，B1 是重构，不能替代"能不能跑"。
