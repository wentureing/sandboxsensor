# 调研：诊断体系能否统一拆出？该不该换成熟框架？

- 日期：2026-11-25
- **核实基准**：容器 `baseline-v150 @ 56f?`（实为 `2d3e?`）——以当前工作区 `core/` 与 `app/` 实测
- 结论先给：
  1. **可以全面拆出，但动作是"收编到已有的 `core:common/diagnostics`"，不是新建一套**；
  2. **不建议换成熟框架**（Sentry/Crashlytics/Firebase/Logback 全都与"仅 debug、离线、可被 R8 删除"冲突）；
  3. 真正该做的是**收敛通道 + 统一命名/格式 + 分类**，分三步走。

---

## 一、事实盘点

### 1.1 调用分布（DebugTrace 只有 36 处 —— 比想象中少）

| 模块 | `DebugTrace.event/detail/fail` 调用 |
| --- | --- |
| `core:hook` | 13 |
| `core:sandbox` | 12 |
| `core:virtualization` | 10 |
| `core:common` | 1（自身） |

### 1.2 但**输出文件已经碎片化成 15+ 种**

```
debug-trace.log              ← 统一通道（Timber 文件 Tree）
checks.log                   ← DiagnosticsSink / FileSink
breadcrumb-<pid>.log         ← 生命周期有序记录
stackdump-<pid>.log          ← 栈转储
startactivity-trace-<pid>.log
hijacktrace-<pid>.log
shortcut-probe-<pid>.log
webviewwarm-<pid>.log / webviewwatch-<pid>.log
v139-probe.log / v144-intent-probe.log / v145-intent-probe.log / v148-connect-probe.log
v154/v155/v156 → *-filtered.log / v155-init-filtered.log
seccomp-diag.log
dexmem-<pid>.log / memdex-<pid>-<n>.dex
path_spoof.conf（配置，非诊断）
```

### 1.3 统一层**已经存在**（`core:common/diagnostics`，5 个类 / 247 行）

| 类 | 作用 |
| --- | --- |
| `Diagnostics` | 对外入口（stage/event/result） |
| `DiagnosticsHolder` | 全局安装点 |
| `DiagnosticsRouter` | 多 sink 路由 |
| `FileSink` | 落文件 |
| `CheckResult` | 结构化结果（探针用） |

**问题不是"没有统一层"，而是 15+ 种文件里有大半是 `File(...).appendText(...)` 直接写的**，
绕过了 Router/FileSink —— 于是限流、轮转、命名、门禁各写各的。

## 二、能不能"全面拆出"？——能，但要分两类

| 类别 | 例子 | 处置 |
| --- | --- | --- |
| **通用能力**（与业务无关） | 文件 sink / 限流（`pathLogCount`）/ 环形缓冲（`fs_record`）/ 转储格式化（栈、maps、dex）/ 命名与轮转 | ✅ **收编到 `core:common/diagnostics`**（已有底座，加 1~2 个类即可） |
| **业务探针**（依赖具体 guest 对象） | plugin probe（355 行）、login probe、autofill probe、auth intent probe、hijack trace | ❌ **留在各模块的 `diag` 包**，只允许通过 `Diagnostics` 出口写文件 |

判据：**"换个 guest 还能用" 的是通用能力；"只对某类 app 有意义" 的是业务探针。**

## 三、该不该换成熟框架？——**不该**，逐条给理由

| 候选 | 为什么不适用 |
| --- | --- |
| **Sentry / Crashlytics / Firebase** | 假设"release 也上报 + 能联网 + 后台收集"。本项目要求**仅 debug 进产物、离线可分析、R8 能删除**；引入还会带网络权限与隐私面 |
| **Logback / kotlin-logging** | 解决的是"日志门面与格式化"，而我们真正的痛点是**多通道落文件 + 限流 + guest 日志被吞**，这些它不解决，还多一份依赖 |
| **Perfetto / AndroidX Trace** | 只解决性能追踪，且是**系统级工具**（不需要打进 APK）。可以**选配**用于启动耗时，但不承担诊断日志 |
| **Timber（已在用）** | 恰好合适：轻量、可 plant 多个 Tree、未 plant 时 no-op → 现有 `FileLogTree` 就是对的用法 |

**唯一值得补的外部能力**是"崩溃栈收集"（`Thread.setDefaultUncaughtExceptionHandler` 已有 `MainLooperGuard`/`ProcessKillGuard`）——
但也不需要框架：现有 guards 已覆盖主线程 uncaught 与 `System.exit`。

## 四、建议路线（三步，都不破坏 debug 面）

| 步 | 动作 | 判据 |
| --- | --- | --- |
| **D1 通道收编** | 给 `FileSink` 加"具名通道"（`DiagChannel(name, maxBytes, append/rotate)`），把 15 种文件**逐个**改走它；**文件名与格式一字不改** | 拆分前后同一场景的 `checks.log`/`stackdump` **逐字 diff 为空** |
| **D2 转储工具集中** | 栈 / maps / dex 转储抽到 `core:common/diagnostics/dump/`（与 B4-1 合并做） | 转储文件内容逐字一致 |
| **D3 结构化** | 散落的 `appendText` 改为 `Diagnostics.stage/event` + `CheckResult` | 每条诊断能 grep 到统一前缀（`S ` / `E ` 等） |

D1 的价值：现在"为什么某条诊断没出现"要猜是哪个文件、哪个门禁；
收编后**一个地方决定"写哪、限流、轮转、release 是否产出"**。

## 五、风险（与"不得破坏 debug"直接相关）

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 改文件路径/文件名 → 现有排查脚本与 `collect-probe.ps1` 失效 | D1 明确"**只改写入方式，不改名字**"；一次只改 1~2 个通道 |
| 2 | 限流语义变化 → 关键日志被吞 | 限流仍留在调用方（如 `pathLogCount` 在 `NativeHookBridge`），通道只负责落盘 |
| 3 | release 里意外产出 | 通道构造前必须过 `DebugFlags.isDebugBuild()`；`DebugFlags` 默认 false |
| 4 | 与 B4 拆分冲突（同一个文件两边改） | 先 B4-1（转储工具搬家，D2 的一部分），再 D1；一次一批 |

## 六、结论

> **诊断可以全面拆出，但"拆出"= 把 15+ 种散写收编到已有的 `core:common/diagnostics`，
> 而不是引入新框架。** 框架选型上维持 Timber + 自建 FileSink；
> 唯一可选的外部增强是 Perfetto（系统工具，不进包）用于启动耗时。
