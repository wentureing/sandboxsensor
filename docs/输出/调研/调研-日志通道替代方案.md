# 调研 + 设计：用更成熟的通道替换同步文件 I/O

- 日期：2026-11-24
- 触发：用户要求「寻找更成熟的 debug 输出工具，看能不能绕过当前同步文件 I/O 和干扰」
- 结论：**有两条更好的通道**（`android.util.EventLog` / `android.os.Trace`），
  但**都不解决"要长期留存完整上下文"的需求**，所以最终方案是**混合**。
- 前提：`EventLog` 是否被 vivo 的日志策略过滤 **必须实测**（本项目已知 `Log.i` 会被吞）。

---

## 一、五种输出通道对比

| # | 通道 | 写入路径 | 单条开销 | 抓取方式 | 容量 | uid 过滤风险 |
| --- | --- | --- | --- | --- | --- | --- |
| **0** | **当前：同步 `file.appendText`** | 文件 I/O（open+write+close） | **150–1000 µs** | 直接读 app 目录文件 | 磁盘（1.5MB 截断） | ❌ 不受影响 |
| **1** | `android.util.Log` | socket → logd → **main buffer** | 10–50 µs | `adb logcat` | 环形（默认 256KB） | ⚠️ **本项目实测被吞**（vivo 按 uid 过滤） |
| **2** | **`android.util.EventLog`** | socket → logd → **events buffer**（**二进制结构化**） | **~10–30 µs** | `adb logcat -b events` | 环形（默认 256KB） | ❓ **待实测**（events 是独立 buffer） |
| **3** | **`android.os.Trace`** | **ftrace ring buffer**（内核 per-CPU） | **~1–5 µs** | `atrace` / perfetto | 环形（KB 级，秒级覆盖） | ✅ 内核层，不受 uid 策略影响 |
| **4** | 异步文件（内存队列 + 后台线程） | 文件 I/O，但**不在调用线程** | 入队 2–5 µs | 直接读文件 | 磁盘 | ✅ 不受影响 |

### 关键事实

**`EventLog`**（[参考](https://juejin.cn/post/7661505897454387235)）：
- 写入 **events 缓冲区**，与 `main`/`system` **并列但独立**
- 二进制记录：数字 ID + 类型化字段，体积小
- **tag 编号 `1000000–2000000` 预留给厂商自定义**（不与平台冲突）
- API：`EventLog.writeEvent(tag, Object... values)`
- **单条有长度上限**（payload 数 KB），长上下文要截断

**`android.os.Trace`**：
- 写内核 ftrace marker，**per-CPU 无锁**，开销最低
- 但**只适合短时间窗口**（buffer 秒级覆盖），且需要 `atrace -t N` 主动抓
- **不适合**"长期开着当日志"

**⚠️ 开销不要盲信厂商说法**：
[Gracker 的 atrace 笔记](https://github.com/Gracker/android-internals-wiki/blob/master/src/part5-app/ch26-observability/14-ebpf-atrace-online-tracing.md)
明确指出："生产开销低于 1% 这类说法缺上游基准，**必须按目标设备、事件密度实测**"。

## 二、为什么单一通道都不够

| 需求 | 文件（0） | Log(1) | EventLog(2) | Trace(3) | 异步文件(4) |
| --- | --- | --- | --- | --- | --- |
| **低开销**（高频路径可用） | ❌ | ✅ | ✅ | ✅✅ | ✅ |
| **长期留存**（几分钟~几小时） | ✅ | ⚠️ 环形覆盖 | ⚠️ 环形覆盖 | ❌ 秒级 | ✅ |
| **完整上下文**（长文本/栈） | ✅ | ✅ | ❌ 长度上限 | ❌ | ✅ |
| **本设备可读**（uid 过滤） | ✅ | ❌ | ❓ | ✅ | ✅ |
| **崩溃后仍可读** | ✅ | ✅ | ✅ | ⚠️ | ⚠️ 最多丢 200ms |

**结论**：**没有单一通道能同时满足"低开销 + 长期留存 + 本设备可靠"**。
必须分层：**高频走低开销通道，关键走可留存通道**。

## 三、设计方案：三通道分层

```
DebugTrace
├── event(tag, msg)   ── 关键事件 ──> ① EventLog（结构化，立即）+ ② 异步文件（完整上下文）
├── detail(tag, msg)  ── 高频细节 ──> ① EventLog（采样后）
└── fail(tag, msg, t) ── 失败 ─────> ① EventLog + ② 任意同步文件（不能丢）
```

### 3.1 通道分配

| 级别 | 主通道 | 备份 | 理由 |
| --- | --- | --- | --- |
| `fail` | **同步文件**（现状） | EventLog | 错误不能丢，宁可慢 |
| `event` | **EventLog**（10–30µs） | 异步文件 | 关键但频率低，两条都写得起 |
| `detail` | **EventLog**（采样） | 无 | 高频，只留结构化计数 |

### 3.2 EventLog 的编码方式（不需要改 .logtags）

使用厂商保留号段，一个通用 tag + 结构化字段：

```kotlin
// 自定义 tag：1000001 = NEXT_VM_TRACE
EventLog.writeEvent(1000001, tag, level, message)
```

读法：
```powershell
adb logcat -b events -d | Select-String "1000001"
# 或解析成可读格式
adb logcat -b events -v threadtime -d
```

**优点**：
- 不需要在系统里注册 `.logtags`（厂商号段允许自定义）
- 二进制、体积小、logd 层就带时间戳和 pid/uid
- **独立 buffer**，可能绕过 main buffer 的 uid 过滤 ← **待实测**

### 3.3 异步落盘（替代方案 0）

```
调用方 -> 无锁环形队列（ArrayDeque，只保护内存操作）
       -> 单线程每 200ms 或攒 64 行 -> 一次 open+append+close
       -> fail() 例外：同步直写
       -> 进程退出/terminateApplication 时 flush()
```

**收益**：调用方 150–1000µs → **2–5µs**。

### 3.4 是否需要 Trace？

| 场景 | 用不用 |
| --- | --- |
| 观察"某段代码耗时"（如 STEP 0→5 总耗时） | ✅ 用 `Trace.beginSection/endSection`，但需 atrace 主动抓 |
| 长期诊断日志 | ❌ 不用（buffer 秒级覆盖） |

**建议**：只在"排查时机问题"时临时开，不做常驻。

## 四、必须先实测的 3 件事（否则方案站不住）

| # | 问题 | 怎么测 | 判据 |
| --- | --- | --- | --- |
| **1** | **`EventLog` 是否被 vivo 的 uid 策略过滤？** | 在 guest 进程写一条 EventLog，`adb logcat -b events -d` 看能否取到 | 能→方案成立；不能→退回"异步文件为主" |
| **2** | **`EventLog` 实际开销** | 循环写 10000 条，测耗时 | < 50µs/条可接受 |
| **3** | **`events` 缓冲区容量与覆盖速度** | 灌满后看保留时长 | 至少覆盖一次完整启动（~10s） |

**为什么第 1 项最关键**：本项目已知 `Log.i` 被吞（非默认 uid），
如果 `EventLog` 同样被吞，那它只是"更快的 `Log`"，解决不了"本设备可读"的问题。

## 五、迁移方案（对调用方零改动）

`DebugTrace` 的对外 API（`event` / `detail` / `fail`）**保持不变**，只改内部路由：

| 阶段 | 改动 | 风险 |
| --- | --- | --- |
| 1 | 加 `EventLog` 输出（与文件并存，双写对照） | 极低（只加不改） |
| 2 | 实测三项（第四节） | — |
| 3 | 按实测结果决定：`detail` 是否只走 EventLog | 中 |
| 4 | 文件落盘改异步（`fail` 保持同步） | 中（需 flush 保证） |
| 5 | 删掉 `handleMessage` 的逐条 detail（改为每秒汇总计数） | 极低 |

**关键**：前 3 阶段都不动现有行为，可以安全地边测边改。

## 六、结论

| 问题 | 答案 |
| --- | --- |
| 有更成熟的通道吗？ | **有**：`EventLog`（结构化、独立 buffer、10–30µs）、`Trace`（内核 ring buffer、1–5µs） |
| 能绕过同步文件 I/O 吗？ | **能**，但不能完全替代 —— 长期留存 + 完整上下文仍需要文件 |
| 推荐方案 | **三通道分层**：`detail`→EventLog（采样）、`event`→EventLog+异步文件、`fail`→同步文件 |
| 最大不确定性 | `EventLog` 是否被 vivo uid 策略过滤 → **必须先实测** |
| 立即能做的低风险项 | ① 缓存 `processTag()`；② 删 `handleMessage` 逐条 detail；③ EventLog 双写对照 |

**一句判断**：不是找"更好的工具"，而是**按"留存时长 × 频率"给每条日志选通道** ——
高频的用内存/内核通道，要留的走异步文件。
