# 调研：启动链这类模块适合怎么自动化测试

- 日期：2026-11-26
- 触发：B4-4 系列（启动链拆分）落地后，需要回答"这类模块用什么方式测才划算"
- 基准：容器 `baseline-v150`；现状 `core:virtualization` 103 条单测 / 探针 98 项 / 自检 8 项 / 8 份 golden
- 关联：`docs/现状/现状-启动链测试覆盖与可测试性.md`、`docs/设计/设计-hook自动化测试与上下文.md`（L1–L4 分层）

---

## 一、先界定"这类模块"的特征（测试方式由特征决定）

| 特征 | 启动链的具体表现 | 对测试的含义 |
| --- | --- | --- |
| 大量 **framework 内部反射** | `Class.forName("android.app.ActivityThread")`、`LoadedApk.makeApplication`、`ContextImpl.createAppContext` | android.jar 是 `Stub!` 桩 → 纯 JVM 一调就抛；必须"给个真 Android"或"完全不碰执行" |
| **顺序即语义** | provider 必须早于 `Application.onCreate`；`patchFrameworkDataDir` 必须早于 `WebViewWarmup` | 单元断言抓不到顺序 → 需要"序列级"证据（golden / 契约） |
| **全局可变状态** | `ActivityThread.mInitialApplication`、`sInitialApplication`、mPackages | 断言要能看"改完之后世界什么样"，不是只看返回值 |
| **时序敏感** | 早期窗口（PM 表未就绪）、watchdog（+0.3…+20s）、探针 ~2s | 早查必空 → 测试要带 `ageMs`/三态，不能固定 sleep |
| **真机独占** | native GOT patch、direct svc、seccomp | 任何 JVM 方案都覆盖不到，只能真机 |

**结论**：不存在"一种方式全盖"，必须按层组合。这与 `设计-hook自动化测试与上下文.md` 的 L1–L4 分层一致。

## 二、候选方式与适配度矩阵

| 方式 | 能覆盖的层 | 对本模块适配度 | 成本 | 能抓住的缺陷 | 抓不到 |
| --- | --- | --- | --- | --- | --- |
| **A. 纯 JVM 单测**（判据/纯函数） | L1 决策、L2 状态 | ✅ 高 | 极低（毫秒） | 判据写错、回退分支 | 任何执行、顺序 |
| **B. golden 序列比对**（本项目已用） | 顺序/计数 | ✅ **高（最匹配）** | 中（一次采集 + 归一化） | 顺序被改、阶段重复/缺失、失败降级被改成中止 | 时序耗时、执行细节 |
| **C. 契约测试（不变量）** | 顺序/分支 | ✅ 高 | 低（golden 之上） | 语义反演（"provider 失败即中止"这类） | 同上 |
| **D. Robolectric** | L3 的 Java 部分 | ⚠️ 有限（需 Shadow） | 中 | `ActivityThread` 字段改写、Context 行为 | 真 native、真实 CL 解析、真实 Binder |
| **E. 设备内 `androidTest`**（Instrumentation） | L3 真执行 | ✅ 高（但重） | 高（需设备 + CI 支持） | `apply()` 真跑、反射字段真存在、真实 LoadedApk | native、跨进程时序 |
| **F. Espresso/UIAutomator（容器自身 UI）** | UI | ❌ 低 | 高 | 容器 UI 崩 | guest 内部（guest 在容器里，测试 runner 进不去） |
| **G. 探针 APK（guest 黑盒，本项目已用）** | guest 视角 | ✅ 高 | 中（已有 98 项） | guest 看到的路径/权限/服务与真实不一致 | 容器内部实现细节 |
| **H. 自检（容器主进程，本项目已用）** | 容器动作可行性 | ✅ 高 | 低（8 项） | 规则/诊断/写入不可用 | guest 视角、顺序 |
| **I. 静态等价检查**（`check-refactor-equivalence`） | 重构证据 | ✅ 高 | 极低 | 重构时偷改逻辑 | 行为等价性（只能证"函数体没变"） |
| **J. 变异测试**（pitest 等） | 测试有效性 | ⚠️ 局部 | 中 | "测试没在固定行为" | 顺序类（变异点不在判据里） |
| **K. Record & replay** | — | ❌ 不适用 | — | — | Android 对象不可序列化，回放无意义 |
| **L. 覆盖率门槛（JaCoCo）** | — | ⚠️ 误导 | 低 | 无（只证明"跑过"） | 见 §五 |

## 三、逐方式评估（针对本模块）

### A 纯 JVM 单测 —— 只能测"判据"，但**判据要主动抽出来**

现状：27 条（`classNameOf`、`isShizukuProvider`、`isShizukuSecurityException`、`isPathFidelityGuest` 等）。
价值来自"把内联判断抽成纯函数"：`isEnabled()`、`isShizukuProvider()` 都是这样来的。

**判据**：一个函数能否纯 JVM 测，取决于它有没有 `import android.*` 的**执行**。
`object` 里有 `Application` 类型参数不影响测其它纯函数（JVM 懒解析）。

### B + C golden / 契约 —— **这类模块的主力**

为什么最匹配：启动链的"正确"就是**顺序 + 计数 + 分支**，而这正好是序列文本能表达的。
本项目 8 份样本（2 guest × 2 次 × 2 条路径）+ C1–C12，已经抓住过：路径分支（C12）、
provider 失败降级（C5）、豁免分支（C9）。归一化把 `r8-map-id`/行号抹掉后，重构不会误红。

成本主要在**采集**：需要真机、需要控制现场（STOP + LAUNCH）、受 L1（stub 5 次上限）限制。

### D Robolectric —— 值得做一次**探路试验**，但别当主力

- 能用：`ShadowActivityThread` 存在，可以拿到 `currentActivityThread()`；`ShadowLooper` 能控主线程。
- 不能信：真实 `LoadedApk`/`ContextImpl`/DexPathList 都是 shadow 版，**CL 解析、资源、native 全假** →
  用它验证"provider 能不能加载 emoji2"这类问题是**假绿**（这正是 L4 未定论的问题）。
- 建议：只用来覆盖 `ActivityThreadApplicationPatch.apply` 的"字段存在/不存在"两条分支（成本 ~半天），
  **不要**用它替代 golden 或设备内测试。

### E 设备内 `androidTest` —— 唯一能真执行 L3 的方式

- 形式：容器仓库加 `androidTest`（debug），用 `AndroidJUnitRunner` 在设备上跑，直接 `Class.forName("android.app.ActivityThread")`。
- 能拿到：真实 `ActivityThread` 实例、真实 `LoadedApk`、真实 CL → 覆盖 `apply()`、`buildApplicationInfo()` 的真实效果。
- 代价：CI 需要 `connectedAndroidTest`（设备/模拟器），本项目目前只有真机脚本（`auto-test.ps1`），没有 CI 设备。
- 结论：**不建议现在上**，但它是 L4/L5/L6 修复期的正确工具（那些缺陷的判据需要"真实对象图"）。

### F Espresso/UIAutomator —— 对 guest 无效

容器把 guest 跑在自己的进程里，测试 runner 只能驱动容器 UI；guest 的界面是容器 `stub` 里的 Activity。
所以 UI 自动化只能测"容器 UI"，测不到"guest 内部"——那是探针的活。

### G 探针 APK —— guest 视角的唯一手段（已用）

98 项（J/F/D + P/N 窗口项）。本轮实测证明它**对两条 bind 路径的判定完全一致**（53/2/43），
说明它测的是"guest 看到的世界"，不随容器内部路径变化 —— 这是它的价值（也是它的盲区：看不到容器内部）。

### H 自检 —— 容器动作可行性（已用）

8 项（S1–S8）。局限已记录：S1–S6 用自造 `/tmp` 式规则，抓不到"真实规则没注册"→ 才有 S7。

### I 静态等价检查 —— 重构期必备（已用）

本轮的用法值得固定下来：`--ignore` 精确列出"已登记的结构性改造"，剩下的逐字比对。
每次拆分都在用（B4-4a: 703/1245 字符；B4-4b: 1296/785；B4-4c: 882）。

### J 变异测试 —— 用它的**思路**，不必上工具

规则 18.1 的自检（"删掉分支测试应变红"）就是手工变异。Kotlin 变异测试生态弱（pitest 主要 JVM+JUnit4，
对 Android 模块配置成本高）。建议：**对新增的纯判据函数，手工做一次"改坏 → 确认红"**，写进镜像文档。

## 四、推荐组合（按"未来要改什么"映射）

| 未来要改的点 | 首选方式 | 兜底 |
| --- | --- | --- |
| 判据/开关（`isEnabled`、`isShizukuProvider`、`classNameOf`） | **A 纯 JVM** | — |
| 启动顺序、阶段计数、路径分支（L4/L5/L6 修复时） | **B+C golden/契约**（8 份样本已就绪） | 真机 breadcrumb |
| 反射改写的**真实效果**（`apply()`、`buildApplicationInfo`） | **E 设备内 androidTest**（修复期再上） | Robolectric 探路（仅判"字段在不在"） |
| guest 视角是否一致（路径/权限/服务） | **G 探针 98 项** | — |
| 容器动作是否可用（规则/诊断/写入） | **H 自检 8 项** | — |
| 重构"逻辑未变" | **I 静态等价** | 镜像文档偏差登记 |
| 端到端可用性（Via 能否启动/主页） | 真机脚本 + 截图 | 人工 |

## 五、明确**不建议**的方式

| 方式 | 为什么不适合 |
| --- | --- |
| **覆盖率门槛（JaCoCo + 百分比 gate）** | 启动链里大量代码是"一行调一个 framework API"，覆盖率上去了也不代表行为对；本项目历史上"探针绿 ≠ 应用可用"（v141 把 Via 打成不可交互而探针全绿） |
| **Record & replay** | Android 对象（LoadedApk/ContextImpl/ClassLoader）不可序列化，录下来的只有"调用了什么"，没法回放 |
| **Espresso 驱动 guest** | runner 进不到 guest 进程 |
| **mock 掉 ActivityThread 测顺序** | 顺序是**真实框架**决定的；mock 之后测的是"我写的顺序"，不是 AOSP 的顺序 → 假绿 |

## 六、落地建议

**现在就能做（半天）**

1. 给纯判据函数补"手工变异自检"记录：改坏判据 → 确认测试红（写进镜像文档「约束与坑」）。
2. Robolectric 探路：只测 `ActivityThreadApplicationPatch.apply` 在 `ShadowActivityThread` 下的两条分支（成功 / `currentActivityThread()` 为 null）。
3. golden 的采集成本再降：本轮的 `-LegacyBind` 已做到"一条命令切路径"，可以再抽一个 `capture-all-golden.ps1`（8 份一次跑完，自动重启容器绕开 L1 上限）。

**修复期（L3–L6）再做**

4. 容器仓库引入 `androidTest`，把 `apply()` / `buildApplicationInfo()` 的真实效果纳入设备内断言。
5. L4（provider 的 CL 差异）定论必须用"设备内 + 一条 CL 身份观测"，**不能用 Robolectric**（它的 CL 是假的）。

**长期不做**

6. 覆盖率 gate、Record&replay、espresso 驱动 guest。
