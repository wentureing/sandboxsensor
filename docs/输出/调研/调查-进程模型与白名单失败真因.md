# 调查：进程模型与白名单失败的真正原因（2026-11-28，不编码）

## 一、进程模型：**多进程**（我上一轮结论错误，用户设计正确）

### 1.1 我之前错在哪

用 `ps -A | grep nextvm` 找进程 —— 但 **guest 进程的 argv0 被改写成 guest 包名**（`架构-进程名与包名身份模型.md` 的三层身份），
它**不含 "nextvm"**，所以被 grep 漏掉了，于是我错误地得出"单进程"结论。

### 1.2 全量测量（实测）

```
ps -A -o PID,PPID,USER,NAME
  600  1583  u0_a389  com.nextvm.app                 ← 主进程（容器自身）
  839  1583  u0_a389  com.sandbox.probe              ← ★ guest 进程（argv0 = guest 包名）
 4409  4308  u0_i9731  com.google.android.webview:sandboxed_process0:…
```

```
dumpsys activity activities
  packageName=com.nextvm.app  processName=com.nextvm.app:p1    ← 该 Activity（stub）的系统面进程名
```

⇒ **同一进程的三个名字**：系统面 `com.nextvm.app:p1`（slot）／guest 可见面 `com.sandbox.probe`（argv0）／PPID 都是 Zygote(1583)。

### 1.3 与设计文档一致

| 设计 | 实测 | 结论 |
| --- | --- | --- |
| 主进程属于容器，**不装 hook** | `[Dbg/initNativeHooks] skip: container main process (proc=com.nextvm.app)` | ✅ 一致 |
| 拦截/翻译**只对 guest 进程生效** | `hook stats` 的日志 tag 是 `[com.sandbox.probe]`（guest 进程）；主进程只有 `skip` | ✅ 一致 |
| 一 guest 一进程（slot 0–9） | guest 进程 839 独立；`processName=…:p1` | ✅ 一致 |

**因此"专属系统库注入"在进程层面是成立的** —— guest 进程本来就只服务一个 guest。
我之前说的"单进程 ⇒ 无法专属"是**基于错误进程模型**的推论，作废。

## 二、那白名单为什么还是 `applied=1`？—— **`prop_contains` 的参数方向写反了**

### 2.1 代码

```cpp
static bool prop_contains(const char* prop, const char* needle) {
    char v[PROP_VALUE_MAX] = {0};
    __system_property_get(prop, v);
    return strstr(v, needle) != nullptr;   // v = 属性值（"libjavacore"），needle = 传入
}
// 调用处：
return prop_contains("debug.nextvm.libAllow", lib_name);
//                                     ↑ lib_name = "/apex/com.android.art/lib64/libjavacore.so"
```

**实际执行的是 `strstr("libjavacore", "/apex/com.android.art/lib64/libjavacore.so")` → NULL**：
- 属性值是**列表**（`libjavacore`），传入的是**长路径**；
- 方向应当反过来：**遍历列表项，看每一项是否出现在 `lib_name` 里**。

所以 `ns_lib_allow_hit()` 对任何系统库都返回 false ⇒ 白名单从未命中 ⇒ `applied` 停在 1（只有 `libprobe.so`）。
`pkgAllow` 的调用**恰好方向对**（`g_spoofed_package_name` 是包名字符串，属性值是包名列表），所以只有 lib 那一层失效。

### 2.2 排除的其他假说

| 假说 | 证伪 |
| --- | --- |
| "包名注入晚于装 hook" | 日志：`[p1] /proc/self spoofed: pid=26021, pkg=com.sandbox.probe`（:5730）**早于** `hook stats`（:5787）57 ms |
| "`libjavacore` 没有 `open` 的 PLT 槽，patch 不上" | **我的假阴性**：toybox 的 `readelf` **不支持 `-r`**（输出 1 行空）。证据反转：诊断模式 `applied=50 slots=55` 证明 50 个系统库（含 ART 库）**确实能被打上** |
| "`libjavacore` 受 RELRO 保护" | 它有 `BIND_NOW + GNU_RELRO`，但 `patch_got_entry` 会 `mprotect`；诊断模式的 `slots=55` 已证明可写 |
| "读取在 WebView 独立进程" | guest 进程 839 的 maps 有 `libjavacore`、`libwebviewchromium_loader/plat_support`、`libwebviewchromium64.relro`（**无 monochrome**）；`webview-read.log` 的 pid 是 guest 进程 |

### 2.3 顺带修正一条旧记录

`who=libmonochrome_64.so`（2 条）是 **`dladdr` 对 `libwebviewchromium64.relro` 段的误判**（该 relro 段属于 monochrome，但库本体在
`com.google.android.webview:sandboxed_process0` 里，不在我们的 guest 进程）。主读取者仍是 `libjavacore.so`（22/24）。

## 三、修复计划（下次编码时执行）

### 3.1 修 `prop_contains` 的方向（核心）

```cpp
// 语义改为"属性列表里是否有某一项出现在 subject 中"
static bool prop_list_matches(const char* prop, const char* subject) {
    char v[PROP_VALUE_MAX] = {0};
    __system_property_get(prop, v);
    if (v[0] == '\0' || subject == nullptr) return false;
    const char* p = v;
    while (*p != '\0') {
        const char* comma = strchr(p, ',');
        const size_t len = comma ? static_cast<size_t>(comma - p) : strlen(p);
        if (len > 0) {
            std::string item(p, len);
            if (strstr(subject, item.c_str()) != nullptr) return true;  // 库路径包含库名
        }
        if (comma == nullptr) break;
        p = comma + 1;
    }
    return false;
}
```
调用点改：`ns_lib_allow_hit(lib)` 用 `prop_list_matches("debug.nextvm.libAllow", lib)`；
`ns_lib_allow_hit` 的 pkg 部分用 `prop_list_matches("debug.nextvm.pkgAllow", g_spoofed_package_name.c_str())`。

### 3.2 进程模型确认后的设计简化（重要）

既然 **guest 进程天然专属**，`pkgAllow` 其实**不必参与放行决策**：
- 进程只有这一个 guest ⇒ `libAllow` 命中即 patch，语义已经专属；
- `pkgAllow` 可保留为**保险丝**（只允许列出的 guest 使用白名单，防止误配影响其他 guest）。

### 3.3 判据

| 项 | 期望 |
| --- | --- |
| `hook stats`（guest 进程，bind 阶段） | `applied ≥ 1`（`libjavacore` 被打上） |
| `hook stats` 与诊断模式对比 | 远小于 `applied=50`（只白名单库） |
| **`W-ext-synthpath`** | **`text/html` + body `WVPAGE_OK`** |
| 主进程 | 仍 `skip: container main process`（不变） |
| 其他 guest | 未配置 ⇒ 不受影响 |

### 3.4 工具侧教训

- **toybox `readelf` 不支持 `-r`** ⇒ 静态查重定位表要用本地 python 解析（`adb exec-out cat` 拉 so）；
- **`ps | grep <容器名>` 不可靠**：guest 进程 argv0 是 guest 包名 ⇒ 必须用 `ps -A -o PID,NAME` 全量 + `dumpsys activity` 的 `processName` 交叉确认。
