# 验证：上游诊断体系（`virtualization/diag/Diagnostics`）是否真实可用

- 日期：2026-11-25
- 触发：用户指出"需要验证上游诊断体系是否真实可用，不要轻易并入，不要轻易删除上游代码"
- 结论先行：
  - **静态可用 ✅** —— 接口与实现完整、逻辑正确、release 零开销
  - **运行时不可用 ❌** —— 缺三处接线，`sink` 永远是 `NoOp`
  - **因此不该删除，也不该并入** —— 它是**另一层**（桥接既有埋点），与 `diagnostics/` 用途不同

---

## 一、它是什么（完整代码，78 行）

`com.nextvm.core.virtualization.diag`：

```kotlin
interface DiagnosticsSink {
    fun onEvent(phase: String, detail: String)     // 过程事件
    fun onSnapshot(name: String, value: String)    // 可断言的快照
}

object Diagnostics {
    @Volatile var sink: DiagnosticsSink = NoOp
        private set

    fun install(s: DiagnosticsSink) { sink = s }   // 注入
    fun reset() { sink = NoOp }                    // 还原
    val isInstalled: Boolean get() = sink !== NoOp // 自检

    inline fun event(phase: String, detail: () -> String) {
        val s = sink
        if (s !== NoOp) s.onEvent(phase, detail())
    }
    inline fun snapshot(name: String, value: () -> String) { ... }

    private object NoOp : DiagnosticsSink { ... }
}
```

**设计质量评价（逐项）**：

| 关注点 | 实现 | 评价 |
| --- | --- | --- |
| 热路径开销 | `@Volatile` 读 + `!== NoOp` 早退 | ✅ release 里等价于一次 volatile 读 |
| lambda 开销 | `inline` + 早退在 lambda 求值**之前** | ✅ release 里 lambda 根本不会执行 |
| 线程安全 | `@Volatile`，只在启动时写一次 | ✅ 读路径无锁 |
| 生命周期 | `install` / `reset` / `isInstalled` 齐全 | ✅ 完整 |
| 默认行为 | `NoOp` | ✅ 不装零成本 |

**这不是半成品，是一个"设计完成、接线未做"的注入点。**

## 二、"可用性"分两层判定

### 2.1 静态可用 ✅

| 检查 | 结果 |
| --- | --- |
| 编译 | ✅ CI 通过（`baseline-v150` 多次构建成功） |
| 逻辑正确性 | ✅ 无并发/空指针问题（`sink` 非空、`inline` 早退） |
| 可被外部实现 | ✅ `DiagnosticsSink` 是 `public` 接口，任何模块可 `install` |

### 2.2 运行时可用 ❌（**当前完全没作用**）

**实测：三处接线全部缺失**

| 接线点 | KDoc 说的 | 实际 |
| --- | --- | --- |
| 独立模块 `:core:diagnostics` | "提供真实实现，通过 `debugImplementation` 引入" | **模块不存在**（`settings.gradle.kts` 无此 include） |
| `app/src/debug/.../DebugInit.kt` | "在 `Application.onCreate` 里调用 `Diagnostics.install(...)`" | **`app/src` 只有 `main`，没有 `debug` 源集** |
| 桥接器 | "在 debug 下把 Breadcrumb 的输出镜像到 sink" | **不存在** |

**外部引用数 = 0**（全仓库搜 `DiagnosticsSink`，命中的 9 处全在这两个簇内：）
- `virtualization/diag/DiagnosticsSink.kt` 自身（4 处）
- `common/diagnostics/*` 的同名接口与实现（5 处，**不同包、不同接口**）

**因此**：既然没有任何地方 `install`，`sink` 恒为 `NoOp`，`event()`/`snapshot()` 恒为无操作。

## 三、与 `common/diagnostics/` 是**两层，不是重复**

这是本次验证**最重要的更正**。我上一份调研说它们"重复"，判断不准。

| 维度 | `virtualization/diag/Diagnostics`（上游） | `common/diagnostics/Diagnostics`（重构期新增） |
| --- | --- | --- |
| 接口方法 | `onEvent(phase, detail)` / `onSnapshot(name, value)` | `onCheck(result, seq)` / `onError(...)` / `onStage(...)` |
| 数据形态 | **无结构的文本流**（phase + detail） | **结构化**（`CheckResult` 带 `CheckState{OK,FAIL,SKIP}` + 期望/实际/reason） |
| 设计目的 | **桥接既有埋点** —— 把 `GuestBreadcrumb` 的 199 处输出、`StateProbe` 的快照，镜像成程序可读的流 | **新增验证点** —— 让"检查有没有通过"有统一记录，产出可 diff 的 `checks.log` |
| 谁在用 | 0 处 | 6 处（23 个验证点 + 已注入 6 处） |
| 是否可 diff | ❌ 文本流无法稳定比对 | ✅ 固定格式，golden 可锁定 |

**结论**：
- 上游那层解决"**把已有埋点导出来**" —— 现在**没有任何机制能做这件事**（199 处 breadcrumb 只能 cat 文件）
- 重构那层解决"**新增可断言的验证点**"
- **两者互补，不该互相替代**

## 四、接线方案（**仅设计，不执行**）

若要真正启用上游那层，需要三步，**每步都可独立回退**：

| 步 | 动作 | 风险 | 判据 |
| --- | --- | --- | --- |
| **A** | 给 `core:virtualization` 加测试配置 + 上面那两个测试 | 极低 | 测试绿 → 证明静态可用是真的 |
| **B** | 新建 `:core:diagnostics` 模块，实现 `DiagnosticsSink`（写 `diagnostics.log` 或复用 `FileSink` 语义） | 低（新增模块） | 用 `debugImplementation` 引入；release 不含 |
| **C** | 桥接器：`GuestBreadcrumb.log()` 尾部加一行 `Diagnostics.event("crumb") { ... }` | **中**（改 199 处调用的公共入口，不是 199 处） | breadcrumb 仍写文件；额外多一份程序流 |

**关键**：C 步只需改 `GuestBreadcrumb.log()` **一个函数**，不是 199 个调用点 —— 因为所有埋点都走那一个入口。

**先做 A**：成本最低，且能回答"它到底可不可用"这个用户最关心的问题。

## 六、一句话结论

> 上游 `virtualization/diag/Diagnostics` **实现完整、设计良好、静态可用**，
> 但**三处接线全缺**，运行时恒为 `NoOp`。
>
> 它与 `common/diagnostics/` **不是重复而是互补**：一个负责"把 199 处既有埋点导出成程序流"，
> 一个负责"新增可断言的验证点"。
>
> **不删除、不并入**；建议先加两个测试证明它真的可用（A 步），再评估接线。
