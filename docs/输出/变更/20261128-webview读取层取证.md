# 变更：WebView 读取层取证（B 方案，2026-11-28）

## 目标

一句话：**查明 `file://` 的内容读取到底发生在"容器进程的 libc"还是"别的层"**，
为"guest 用假路径 / WebView 看真路径"是否可行提供直接证据。

## 背景（为什么需要）

- 静态取证已排除"Chromium 主库在容器进程"（容器 maps 只有 `libwebviewchromium_loader.so` + `libwebviewchromium_plat_support.so`；
  WebView 主库 `lib/armeabi-v7a/libmonochrome_64.so` 是 ELF32，跑在 `com.google.android.webview:webview_service` 等进程）。
- A 方案（只读现有日志）已做，但**证据不足**：
  - W 系列期间 `debug-trace.log` 新增 437 行，其中**没有**任何 `open`/`read` 记录（只有路径规则注册）；
  - 沙箱文件权限 `-rw------- u0_a389`、`vsandbox` 文件 `-rw-rw---- u0_a0:media_rw` ⇒ 反证"WebView 独立进程不可能读到"，
    但**不能区分**"容器进程 Java 层代读"与"容器进程 libc 读"。
- 因此按用户指示"证据不足就补上 B"。

## 风险

| 风险 | 评估 |
| --- | --- |
| 热路径开销 | 只做两次 `strstr`（路径含 `wvprobe`/`vsandbox` 才写文件）⇒ 常规 I/O 无文件写，strstr 开销 < 100ns，符合规则 21 红线 1 |
| 递归 | 日志写入用 `syscall(SYS_openat/SYS_write/SYS_close)`，**不经 hook** |
| 日志膨胀 | 只在探针实验期间产生；`wvprobe` 文件数量有限（~10 个/次） |
| 长期留存 | 属**临时取证**，取证完成后必须删除（登记在计划里） |

## 验证方法

1. `container-build` 绿；
2. 装机 → 重启容器（等 10s）→ 起 `WebViewProbeActivity`；
3. 读 `run-as com.nextvm.app cat files/webview-read.log`：
   - **有** `wvprobe.html` 的 `open` 记录，且 `who=libopenjdk.so`/`libjavacore.so` ⇒ **读取在容器进程 Java 层**；
   - **有** 记录且 `who=` 其他 app 库 ⇒ 容器进程内某个 native 读者；
   - **没有** 记录但 `wvprobe-result.txt` 有内容 ⇒ 读取**不在容器进程的 libc**（要另找层，最可能是 WebView 通过其他机制拿到内容）。

## 判据（决定后续方向）

| 结果 | 含义 | 下一步 |
| --- | --- | --- |
| 有记录 + `libopenjdk` | Java 层代读 | MIME 判定在 Java/WebView 交界 ⇒ 找判定点（可能可改 `getFilesDir` 解决） |
| 有记录 + 其他 | native 读者（如 plat_support） | 可对该库做 GOT 白名单 |
| 无记录 | 不在容器进程 | 回到"路径必须真实可读"（W-ext 结论），或查 WebView 的 IPC 机制 |
