## 二、为什么这次 golden 会变（重要）

入库 golden 停在上一次采集（容器仓库 `0b2f451` "guest 启动链 breadcrumb golden + 11 条契约"）。
之后 `880ade3`（B4-4a）把 provider 初始化从 `VirtualApplicationManager.initContentProviders`
搬成 `lifecycle/startup/ContentProviderInitializer.install`。

由于 via 的 `androidx.startup.InitializationProvider` 会抛 `ClassNotFoundException`，
这条被吞异常的**栈里多了一帧**：

```
 # 旧（入库 0b2f451）
   at ...lifecycle.VirtualApplicationManager.initContentProviders(VirtualApplicationManager.kt:<LINE>)
 # 新（当前实现）
   at ...lifecycle.startup.ContentProviderInitializer.install(ContentProviderInitializer.kt:<LINE>)
   at ...lifecycle.VirtualApplicationManager.initContentProviders(VirtualApplicationManager.kt:<LINE>)
```

归一化规则只抹掉行号（`.kt:<LINE>`），**不抹栈帧的类名/方法名**，所以 `gen --check` 报不一致。
这是「重构挪代码就会变」的那一类，不是 guest 行为变化：

| 判据 | 结果 |
| --- | --- |
| 启动链事件 **顺序** | 8 份样本全部未变 |
| 启动链事件 **计数** | 全部未变（`bind start`/`bind complete`/`provider ok`/`v118-provider-fields` 等） |
| `provider FAILED (bind continues)` 降级 | 仍在，异常类型与消息未变 |
| 差异所在 | 只有 `provider FAILED` 之后那条**栈的帧序列**（85 → 86 行） |
| 受影响样本 | 仅 `via-1`/`via-2`（framework）；`probe-*`、`via-legacy-*`、`probe-legacy-*` **逐字未变** |

## 五、探针侧现场（换包后的实测）

| 项 | 值 |
| --- | --- |
| guest 实例 | `com.sandbox.probe_1795747008694`（UNINSTALL 旧实例后 INSTALL；旧 `…_1795746372452` 已删） |
| 沙箱内 APK | `files/virtual/apks/com.sandbox.probe_1795747008694.apk` = **568893 B**（新探针入沙箱成功） |
| `suite=round` | `entries=106`（`ok=57 skipped=47 fail=2`），fail = `P25,P26` |
| `suite=all` | `entries=106`（`ok=93 fail=13`），fail = `P25,P26` + N 系列首轮 11 项 |
| **`N16.libc_maps`** | 第 1 轮 `lines=3252 pkg_hit=18 nextvm_hit=0`；第 2 轮 `lines=3244 pkg_hit=0` |
| `N10.maps_scan` 对照 | `lines=3252 base_apk=14 pkg_hit=18 probe_lib=4` |

**两条判读（都不是容器回归）**：

1. `P25/P26 fail` = `WindowManager$BadTokenException: token null is not valid`，
   同轮 `P27` 显示 `decor=DecorView token=false attached=false` —— **取样时机**问题
   （`UiProbe.run` 在 `ProbeActivity.onCreate` 里跑，decorView 还没 attach），
   与 `STATUS.md` §2 #9 已登记的结论一致。
2. `entries=106` 里有 **7 个 id 出现两次**（`N11..N16`、`P28.sdcard_write`）：同一 guest 进程里
   `ContentProvider.onCreate` 与 `Activity.onCreate` 各跑了一轮；**首轮**处于早期窗口，
   N 系列读到的是未就绪状态（`N13 errno=2` 等），**次轮**全部 ok。
   唯一 id 数 = **99**（静态项集合 golden 为 100，差 1 项待查，见 §七）。

> `N16` 的结论：经 libc `open/read` 读 `/proc/self/maps` 时 `pkg_hit=18`，与 `N10`（`fopen` 路径）**一致**
> → native 侧 `/proc` spoof 的 `PLT` 路径确实被计数，`STATUS.md` §2 #10「待验证」**可结案**。
> `spoof/maps_lines` 仍为 0（`[Dbg/native]`），与基线文档 §四的解释一致（本轮仍没有"经 libc 读 maps 的 native 读者"，
> 探针自身的 N16 走的是它自己的 `libprobe.so`，不经过容器 PLT）。
