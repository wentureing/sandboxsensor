## 一、目标

1. **`DiagChannel` 由「超限清空」改为「环形保留尾部」**——崩溃前现场不再被一次性抹掉；
2. **新增唯一落盘出口 `DiagOutput`**——业务代码只给「通道名 + 内容」，不碰 `File` / 锁 / 上限；
3. 消除已发现的**重复实现**：`FileSink` 自己那份「超限清空」、`DebugTrace` 自己那份 `MAX_BYTES`；
4. 补测试：**显式写满**，验证环形保留的可见效果。

不在本批（留 L1-c）：17 处 `File(...).appendText(...)` 的逐个迁移（除 `GuestBreadcrumb` 与 `v148` 两处示范）。

### 4.2 `DiagOutput`（新增，唯一出口）

```kotlin
object DiagOutput {
    @Volatile private var dir: File? = null
    private val channels = ConcurrentHashMap<String, DiagChannel>()

    /** guest 侧在 attachFile 时绑定；切换目录会清空通道缓存。 */
    fun setDir(d: File?) {
        if (dir == d) return
        dir = d
        channels.clear()
    }

    fun append(name: String, text: String, maxBytes: Long = DiagChannel.DEFAULT_MAX_BYTES): Boolean {
        val d = dir ?: return false
        val ch = channels.getOrPut(d.path + "/" + name) { DiagChannel(File(d, name), maxBytes) }
        return ch.append(text)
    }

    fun line(name: String, text: String, maxBytes: Long = DiagChannel.DEFAULT_MAX_BYTES): Boolean =
        append(name, text + "\n", maxBytes)
}
```

## 九、审计：自噬 / 定向 / 被记录（2026-11-26 静态检查）

> 问题：日志写入会不会①触发日志风暴 ②被路径系统异常定向 ③被日志记录。全部按代码路径核对。

### 9.1 会不会触发日志风暴 —— **不成立，但有 4 倍落盘放大**

guest 进程的写入链路（`debug.nextvm.javaIo=1` 时）：

```
DiagOutput.line → DiagChannel.append → File.appendText
  → FileOutputStream → libcore.io.Linux.open
  → hooked_java_linux_open (native-hook.cpp:6869)
  → java_io_resolve (:6840) → redirect_path（纯 C++ 读 g_path_redirects，:99）
  → ::open
```

| 检查点 | 结论 | 证据 |
| --- | --- | --- |
| 是否回调 Java/触发 `translatePath` | **否** | `redirect_path` 只读 native 规则表，与 Kotlin `NativeHookBridge.translatePath` 无关 → **不触发** `logPathTranslation`(:781) → **无递归** |
| GOT 层 `hooked_open` 会不会打日志 | 只在不翻译时静默 | `:669` `if (!redirected.empty()) LOGD(...)`；诊断路径不命中规则 → 不打 |
| 单条日志落盘次数 | **最多 4 次** | logcat(`Timber.i`) + `breadcrumb-<pid>.log` + `debug-trace.log`（FileLogTree 也收 Timber）+ 前 200 条镜像 `checks.log` |
| 量级 | 每进程 ~500 条 × 4 ≈ 2000 次 `open` | breadcrumb 5s 定时器 120 次 + 每次 resume；不构成风暴，但是 IO 噪声 |

→ 结论：**无递归、无 logcat 洪水**；但"一条 breadcrumb 三四个文件"的放大应登记（未来可让 breadcrumb 不再进 `debug-trace.log`）。

### 9.2 会不会被路径系统异常定向 —— **当前不会命中**

`setupAppRedirections`（`NativeHookBridge.kt:405-459`）注册的前缀只有：

```
/data/data/<guest>/          /data/user/0/<guest>/
/storage/emulated/0/Android/data|obb|media/<guest>/   (+ /sdcard 变体、无尾斜杠变体)
/storage/emulated/0/Android/data/com.nextvm.app/...   ← 宿主包名 external 兜底
```

诊断文件在 `/data/user/0/com.nextvm.app/files/...`（主进程）或 `.../files/virtual/data/<inst>/files/...`（guest），
**不落在任何前缀下** → `PathRuleStore.translate()` 未命中、原样返回（`:102-135`）。

两个要记住的边界：

1. **early 阶段**：`DiagOutput.setDir` 之前 `append` 返回 `false`，事件只进内存 buffer（`MAX_BUFFER_LINES=4000`），**超出即静默丢失**。建议后续补一行 `dropped=N` 到 attach 后的文件里。
2. **宿主 external 兜底规则会命中探针的外置副本**：`/storage/emulated/0/Android/data/com.nextvm.app/files/probe-report.json` 命中 `:424/428` → 翻译到 guest 的 `sdcard/Android/data/<guest>/files/`。21:45 实测：沙箱侧有该文件、宿主侧**也有** —— 宿主那份来自 early 阶段（规则未生效），与 `记录-实机测试-47c4763.md` §3 的结论一致，**不是规则缺失**。

### 9.3 会不会"日志写入被日志记录" —— **是，两处，要修**

| # | 问题 | 位置 | 影响 |
| --- | --- | --- | --- |
| 1 | **统计污染**：诊断文件写入也计入 Java IO open 总数 | `native-hook.cpp:6887` `g_java_io_open_total.fetch_add(1)` 在过滤**之前** | `JavaIoHooks.stats()` 的 `open` 数含日志自身写入，指标失真 |
