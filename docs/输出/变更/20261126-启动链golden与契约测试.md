## 四、契约清单（10 条，待确认）

对 4 份 golden **全部**跑（参数化），每条都对应 `docs/架构/架构-启动链契约.md` 的一节。

| # | 契约 | 固定的行为 | 为什么这条重要 |
| --- | --- | --- | --- |
| C1 | 首行是本进程的 `breadcrumb begin pkg=<guest> pid=<n> wall=<t>`，且全段只出现一次 | 新进程一定开新会话 | 复用进程时只会出现 `(already active, kept)` → 采到假样本（本轮踩过） |
| C2 | `replaceClassLoader done` 早于 `bind start` | CL 换装先于 bind | R2 初始化窗口：换晚了 bind 就按旧 CL 走 |
| C3 | `v118-provider-fields` 条数 = `bind start … providers=N` 的 N，且都早于 `bind start` | provider 元数据先读后 attach | provider 列表读错 → attach 到错误 authority |
| C4 | `framework makeApplication enter` → `instr newApplication <App>` → `framework makeApplication exit app=<App>` 严格相邻顺序 | 只构造一次 Application，且出口带同一类名 | 重复 makeApplication = guest 状态被清 |
| C5 | 所有 `provider attachInfo enter` / `provider ok|FAILED` 都早于 `Application.onCreate enter`，且 `provider FAILED` 之后仍有 `Application.onCreate` | provider 失败不中止 bind | 这是"失败降级"的既有契约（via 的 emoji2 就是这条） |
| C6 | `Application.onCreate exit` → `v142-redirect registered rules=N`（N>0） → `guest diagnostics installed` → `v130-watchdog started` | 规则与诊断都在 onCreate 之后、watchdog 之前 | `DiagnosticsHolder.install` 晚于规则注册会静默丢事件（R1） |
| C7 | `engine breadcrumb callbacks registered` → `bind complete (framework path)` → `instr newActivity` 严格顺序，且 `bind complete` 只出现一次 | bind 段的终结点唯一 | 重复 `bind complete` = bind 被跑了两遍 |
| C8 | Activity 段顺序：`instr newActivity` → `instr callActivityOnCreate enter` → `preCreate enter` → `cb onActivityCreated` → `instr callActivityOnCreate exit ok` → `cb onActivityStarted` → `cb onActivityResumed` | 首 Activity 生命周期顺序 | B4-4 拆的就是这段，拆错先红 |
| C9 | **豁免分支**：`mark.via` 出现 `v143-datadir skip (whitelist)`；`com.sandbox.probe` 出现 `v143-datadir pkg=… -> /data/user/0/com.sandbox.probe` | 路径欺骗豁免 = via 零欺骗 | 直接对应「设计理念第三条」；改坏了 no-one-notices |
| C10 | 每份 golden 的 `bind start` / `makeApplication enter` / `bind complete` / `instr newActivity` 各恰好 1 次 | 启动链不重复执行 | 防"复扫/重入"类回归 |

**额外一条（不占契约编号）**：同 guest 两次采集归一化后**逐行相等** —— 这条铆住"启动链可重复"，
不需要手写期望值，且本轮已实测成立（via ×2、probe ×2）。

## 五、golden 归一化规则（写进 `架构-启动链契约.md`）

设备采集的原文含必然漂移的字面量，入库前统一归一化（生成脚本负责）：

| 模式 | 替换为 | 理由 |
| --- | --- | --- |
| `[+123ms] [main] ` 前缀 | 解析成 `(ms, thread, text)` 三元组 | 时间戳是每轮必然不同的量，但**顺序**要保留 |
| `pid=\d+` / `wall=\d+` | `pid=<PID>` / `wall=<WALL>` | 每次启动都变 |
| `#\d+`（identity hash） | `#<ID>` | 每次启动都变 |
| `_1795659911286`（instance 时间戳） | `_<TS>` | 重装后变 |
| `entries=\d+` / `len=\d+` | `entries=<N>` / `len=<N>` | 随 APK 版本变 |
| `rules=22` | `rules=<N>`（契约里断言 `N>0`） | 规则条数会随功能增长，不是启动链行为 |

**不归一化**（否则契约失效）：包名、类名、`pkg=`、`appClass=`、authority、路径族名、事件名。

## 九、本轮新发现（与 golden 无直接关系，但影响可重复性）

### N1 `StubRegistry` stub 泄漏：每 slot 启动 5 次后再也起不来（**建议优先修**）

- **现象**：第 6 次 `LAUNCH_ACTIVITY` 报 `No available stub for process slot 1`（`VirtualEngine.kt:634`）。
- **证据（本轮实测）**：11:04–11:21 期间 `mark.via` 在 slot 1 上启动 5 次（含 2 次 golden 采集），
  随后 `LAUNCH_ACTIVITY com.sandbox.probe`（同为 slot 1）直接报错；`LIST` 显示 `mark.via` 与
  `com.sandbox.probe` **都是 `slot=1`**；重启容器（内存态重建）后立即恢复。
- **根因**：`StubRegistry.resolveStub()` 把 stub 放进 `inUseStubs`（`StubRegistry.kt:56-59`），
  但**生产代码里没有任何地方调用 `releaseStub` / `releaseAllStubsForSlot`**（只有定义与测试调用）。
  `stopApp()` 释放了 `processSlot`（`VirtualEngine.kt:731`），却没释放 stub。
- **性质**：AOSP 无对应机制（stub 池是容器自造）→ 属**有害偏差**（Accidental），不是必要偏差。
- **与既有测试的关系**：`StubRegistryTest` G 系列测了"release 之后能再取"，但生产从不 release →
  **测试绿、行为错**，这正是 `现状-容器自测覆盖矩阵.md` 缺口 #1「自检用自造规则，抓不到真实路径」的同类问题。
- **处置建议**：`stopApp()` 里 `stubRegistry.releaseAllStubsForSlot(slot)`（一处）+ 单测 S5「stop 后再 launch
  同 slot 仍可解析」；需走变更流程 + CI + 装机验证。**本轮不夹带在 golden 提交里。**

### N2 两个实例被分到同一 slot

- `LIST` 显示 `mark.via` 与 `com.sandbox.probe` 都是 `slot=1`（进程复用、stub 池共用），
  而 `allocateSlot` 逻辑本身不会重复分配 → 说明 `processSlot` 是**安装时持久化的值**，
  容器重启后内存 `slots` 表全空、与持久化值不一致。
- 与 N1 叠加后表现为"N 次启动后彻底起不来"。修 N1 前，采集/回归脚本必须容忍"启动失败需重启容器"。
