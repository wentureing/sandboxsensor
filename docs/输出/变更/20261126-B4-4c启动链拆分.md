## 二、必要性（三条，都有代码/commit 证据）

### 必要性 1：它是 **L5 的唯一落点**，而 L5 是"两条路径行为不一致"里最难查的一条

- 职责 ① 就是 `v138-appctx` 那条日志的生产者：`mInitialApplication <before> -> <after>`。
- 现状实测（8 份 golden）：framework 下 `-> com.nextvm.app`（不改），legacy 下 `-> mark.via`（改成 guest）。
  这不是日志差异，是 **`ActivityThread.mInitialApplication` 这个全局 Context 的真实身份差异**。
- L5 修复（`计划-启动链已知缺陷（重构后修复）.md`）必须动这段代码；它现在埋在 2 249 行的
  `VirtualApplicationManager` 中部（`:870`），改之前得先读懂上下 200 行的启动链上下文。
- **搬到独立文件后**：修 L5 只需打开一个 51 行的文件，配合 golden C6（`v142` 前后顺序）与探针 J 系列即可闭环。

### 必要性 2：4 个后台任务在两条路径**各写一遍**，且本项目已经因为"只加一处"翻过车

```
framework  :252-255   DexMemDump / StateProbe / WebViewWatch / WebViewWarmup
legacy     :345-348   DexMemDump / StateProbe / WebViewWatch / WebViewWarmup   ← 逐字相同
```

历史事故（同类）：`00673c9`「v139-fix 把 dataDir patch **挂到 framework bind 路径上**」→ 当天 `612cef5` revert，
原因正是"只加在一条路径上，注入点还得再评估"。两份实现的存在本身就是持续风险（规则 18.2 要求收敛）。

### 必要性 3：为 B4-4d（搬两条路径本身）**降低 diff 面积**

B4-4d 要搬 `bindApplication`（编排，212 行）与 `bindViaFrameworkLoadedApk`（169 行）。
如果先不动这两块，B4-4d 的 diff 里会混着"收尾序列的 11 行 ×2"与"51 行 patch"，
一旦等价检查报不等价，**分不清是搬运带来的还是本来就有**。先把这两块清出去，B4-4d 只搬"装配 + 编排"。
