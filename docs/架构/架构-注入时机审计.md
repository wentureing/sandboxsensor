# 审计：哪些注入应该发生在 guest 启动时

- 日期：2026-11-24
- 起因：v141 的 Java 层重定向装成功了（`installed=true`）却无效，诊断出
  **guest 进程 `rules=0`** —— 规则只在主进程注册。这暴露出一类系统性问题：
  **注入点与生效进程不一致**。
- 本文只做调查（不含代码改动），给出判据与全量清单。

---

## 一、判据：什么必须"在该进程注入"

容器的注入目标分两类，**只有第二类受进程边界影响**：

| 类别 | 例子 | 是否进程级 | 结论 |
| --- | --- | --- | --- |
| **主进程持有的元数据** | 已安装 guest 列表、APK 解析、UI 状态 | ❌ 全局 | 放主进程即可 |
| **进程级运行时状态** | native 表（`g_path_redirects` / `g_hidden_paths` / property spoof）、`ServiceManager` 缓存里的 Binder 代理、ART 方法/native entry、静态字段、`/proc/self` spoof、seccomp 过滤器 | ✅ **每进程独立** | **必须在目标进程内注入** |

**一句话判据**：
> 注入的是「主进程的管理数据」→ 放 `launch()`；
> 注入的是「本进程的运行环境」→ 必须在 `VirtualEngine.initialize()`（每进程）或
> `bindApplication`（guest 启动）里做。

`NativeHookBridge` 是 `@Singleton`，但它每进程一份 —— **Kotlin 侧的镜像表也是进程级的**，
这一点和 native 表一样，容易误以为"主进程注册了就等于全局生效"。

## 二、全量清单（按当前注入位置）

### 2.1 ✅ 已经在正确位置（每进程 / guest 内）

| 注入项 | 位置 | 证据 |
| --- | --- | --- |
| `installAllProxies()`（Binder 代理：AM/PM/系统服务） | `VirtualEngine.initialize()` | ServiceManager 缓存是进程级 → 必须每进程装，位置正确 |
| `contentResolverProxy.install()` | 同上 | 同上 |
| `nativeHookBridge.initNativeHooks()` | `VirtualEngine.initialize()` + `getOrCreateClassLoader()` | 内部有 P0-3 判断：主进程直接 return，guest 继续 |
| `nativeSetHostDataPrefix` / `nativeSetVirtualDataRoot` | `initNativeHooks()` 内 | 进程级 native 状态，位置正确 |
| `/proc/self` spoof / `setProcessName` / seccomp | `ensureGuestApplicationBooted()`（guest） | guest 启动流程内 |
| `WebViewWarmup.schedule()` | bind complete（guest，异步） | 已在 guest 且早于首次 WebView |
| v138 `patchActivityThreadApplication` | `bindApplication`（guest） | — |
| v141 Java I/O hook（`libcore.io.Linux`） | `initNativeHooks()`（guest） | — |
| **v142 路径规则（`setupExternalStorageRedirections` + `setupAppRedirections`）** | `bindApplication`（guest，**本次新增**） | 修 `rules=0` |

### 2.2 ❌ 确认有问题的（只在主进程注册，但目标是进程级状态）

| 注入项 | 位置 | 问题 | 影响 |
| --- | --- | --- | --- |
| **路径重定向规则** | `VirtualEngine.launch()` L604 | **已由 v142 修复** | guest `rules=0`，Java/native 翻译全部失效 |
| **`setupPathFidelityRedirections`** | `launch()` L895 | **同一个坑**：只在主进程注册合成路径规则 | pathFidelity 的 guest 若走 Java 层，合成路径读不到（native so 也不会有规则） |
| **`registerVirtualSdcard`** | `launch()` L496 | 注册到 `systemServiceProxyManager`，若该表是进程级则 guest 缺失 | guest 内的 `file://` 探查/文档提供者可能拿不到虚拟 sdcard 映射 |
| **`installDeferredProxies`** | `launch()` L607 | 延迟代理（如 NotificationManager）安装在主进程 | guest 进程可能缺少这些代理 |

> ⚠️ 后三项需要实测确认（本次未做）：判断依据是"`SystemServiceProxyManager` 的代理表
> 是否每进程独立"。`installAllProxies` 放在 `initialize`（每进程）说明设计者知道它是
> 进程级的 —— 那么 `installDeferredProxies` 放 `launch` 就很可能是漏项。

### 2.3 ⚠️ 代码存在但**零调用**（能力闲置）

| 能力 | 规模 | 状态 |
| --- | --- | --- |
| `AntiDetectionEngine` | 805 行 / 8 项能力 / 12 个公共方法 | **零调用**（README 明示）。内含 40+ 处 `hidePath` / `spoofSystemProperty` / `setFakeFileContent`，全部未生效 |
| `IdentitySpoofingEngine` | 用 `HookEngine.hookStaticField` 改 `Build.SERIAL` 等 | **未应用**（README 明示："no profile is applied in the current boot path"） |
| `FileAccessInterceptor` | `interceptFile/FileInputStream/FileOutputStream/Exists/ListFiles` | **零调用**（v141 另写了 native 实现，这个仍是死代码） |

这三项如果将来接线，**全部必须在 guest 进程内执行**（它们改的都是进程级状态）。

## 三、规律与建议

### 3.1 规律

> **凡是 `launch()` 里做的"环境类"注入，都要怀疑一遍。**
> `launch()` 是**主进程的管理动作**（改数据库、启动 stub、分配 slot），
> 但很多人把"设置环境"也顺手写进去了 —— 而环境是进程级的。

已经踩到的第一个坑（`rules=0`）就属于这一类，而且它**同时废掉了 native 层和 Java 层**两条重定向路径。

### 3.2 建议的检查办法（每次新增注入时问三句）

1. 这个状态是**主进程的元数据**，还是**本进程的运行环境**？
2. 如果是运行环境：目标进程是主进程还是 guest？注入代码在哪个进程执行？
3. 有没有"主进程注册、guest 使用"的跨进程假设？（目前没有任何跨进程同步机制 ——
   `NativeHookBridge` 的 `pathRedirections` 是 Kotlin 表，各进程一份，**不会同步**）

### 3.3 待办（按风险排序，均未编码）

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | 确认 `SystemServiceProxyManager` 的代理表是否进程级 | 决定 `registerVirtualSdcard` / `installDeferredProxies` 是否也要搬到 guest |
| 2 | `setupPathFidelityRedirections` 搬到 guest | 与 v142 同一处修法 |
| 3 | `AntiDetectionEngine` 接线（并放到 guest） | 但按 README，它还有 2 个缺陷需先修（`is_path_hidden` 精确匹配、无 `readdir` 过滤） |
| 4 | `FileAccessInterceptor` 去留 | v141 已用 native 实现覆盖，建议删除或明确标注"仅参考" |
| 5 | 建立"注入位置"检查表并写进 `AGENTS.md` | 避免再犯 |
