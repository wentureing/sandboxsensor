# 架构：就绪依赖与早期窗口（容器为什么到处"必须早于"）

- 日期：2026-11-26
- 触发：探针 `J19/J20` 在容器刚启动时稳定 `NameNotFoundException`，重启 + 等 10s 后自愈
- 一句话：**容器的每个能力都是"在 AOSP 生命周期的某个特定时刻插进去的"**，所以存在
  「准备阶段 → 生效点」的时间线；在生效点之前使用该能力，看到的必然是"未就绪"。

---

## 一、三类根因（代码里所有"就绪/时机/必须早于"都能归到这三类）

### R1 注册顺序型：谁先注册、谁先查

| 场景 | 代码/文档 | 现象 |
| --- | --- | --- |
| 虚拟 PM 包列表未就绪 | `VirtualPackageManagerService` 实例注册 vs guest 首次 `getPackageManager()` | `J19/J20` `NameNotFoundException`（重启+10s 自愈） |
| 规则注册点 ≠ 生效进程 | `VirtualApplicationManager.registerGuestRedirections`（v142） | 主进程自检 S7 空表；guest 侧 `rules=22` |
| 诊断出口未装 | `DiagnosticsHolder.install`（78ms）晚于规则注册（71ms） | 早期 `stage()` 被 NoOp 静默丢弃 |
| 诊断目录未绑定 | `DiagOutput.setDir` / `DiagOutput.isReady()` | 早期事件只进内存 buffer（4000 行上限） |
| native 侧表未同步 | `PathRedirectRegistry` / `ProcSpoofing`「native 未就绪时空操作」 | 规则先留 Kotlin 侧，`initNativeHooks` 补推 |

### R2 初始化窗口型：某组件初始化后不可逆

| 场景 | 代码/文档 | 为什么不可逆 |
| --- | --- | --- |
| `replaceClassLoader done` → `bind start` | `ActivityThreadHook` / breadcrumb 序列 | LoadedApk/CL 一旦换好，bind 就按它走 |
| 假 dataDir 必须早于 WebView 预热 | `patchFrameworkDataDir`（v143）注释 | `WebViewFactory` 初始化后 context 固化 |
| `patchActivityThreadApplication` 必须早于 `registerBreadcrumbCallbacks` | VAM（v138-appctx） | 回调注册时 `WebViewWarmup` 会预热 provider |
| Instrumentation 换装窗口 | `swapInStockInstrumentation` | 只覆盖 `attachBaseContext` → `onCreate` |
| 等 engine 初始化 | `ActivityThreadHook:511`「Engine not ready — waiting (max 10s)」 | 拦截器需要引擎先可用 |
| native hook 安装时机 | `initNativeHooks`（进程刚起、libcore 已就绪后） | GOT patch 后不能重复装 |

### R3 异步产出型：后台定时/延迟生成，早查必空

| 场景 | 产出时机 | 早查的结果 |
| --- | --- | --- |
| watchdog 线程栈 | bind 后 `+0.3s…+20s` 分批 | `D03 exists=false`（已改三态 `not-yet`） |
| 方法 trace 过滤 | 停止后后台过滤 | trace 文件暂时只有原始大文件 |
| 探针报告 | `LAUNCH` 后 **~2s** | 报告不存在/是上一轮内容 |
| `checks.log` 首行 | 规则注册后（70ms 级） | `D02 exists=false`（首轮） |

---

## 二、判读规则（本项目统一口径）

1. **窗口内的"空/失败"不等于"能力缺失"**：先判 `not-yet` 还是 `missing`。
   已实现：`D03` 三态（`exists` / `not-yet` / `missing` + `ageMs`）。
   应类推：`D02/D05`（`checks.log` 不存在时也给 `ageMs`）、探针整体报告的"轮次标记"。
2. **不要用固定 sleep 掩盖**：优先"就绪探测"（轮询到条件成立），sleep 只作兜底上限。
   已有：`ActivityThreadHook` 10s 等待、`auto-test.ps1` 已改为 1s 粒轮询。
3. **归因顺序固定**：① 先问"有没有就绪依赖"（本文三类）→ ② 再按 18.4 做回退验证判是否真回归。
4. **脚本层前置**：采集/回归脚本在 `LAUNCH` 前等容器就绪（`MainActivity` 起来后 ≥10s，
   或轮询 `LIST` 到目标实例出现）。

## 三、待修的根因（不是所有窗口都只能"等"）

| # | 问题 | 能否根治 | 处置 |
| --- | --- | --- | --- |
| 1 | `J19/J20` 早期 `NameNotFound` | ✅ 能：`INSTALL` 完成后立即把实例写入虚拟 PM 表，不等首次查询 | 独立批次（不在 STOP 改动内） |
| 2 | `SandboxManager` 首次 `mkdirs` 失败被"永久记忆" | ✅ 能：失败不缓存"已确保" | 见 `记录-上游基线修复清单.md` |
| 3 | `checks.log` 首轮不存在 | ⚠️ 部分：容器可在 bind 最早处建空文件 | 低优先 |
| 4 | watchdog stackdump | ❌ 不能（设计就是延迟转储） | 保留 `not-yet` 三态 |

## 四、结论

- 容器里"时机"问题的本质是**插入点由 AOSP 生命周期决定**，不是实现随意拖沓；
- 因此**判读早期窗口必须带时间信息**（`ageMs`），否则会把"还没到"当成"坏了"；
- 能根治的只有 R1 里的"注册滞后"（如 PM 实例表），R2/R3 只能靠**就绪探测 + 三态判读**。
