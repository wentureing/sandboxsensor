# /sdcard 的沙箱模仿：能否做到"guest 能读能写且看起来像真机"

- 日期：2026-11-24
- 起因：用户指出 —— **因为 `/sdcard` 重要性，沙箱应该内置 `/sdcard` 的模仿，guest 大多数情况能读能写，能否做到**
- 结论先给：**"能读能写"已经做到了**（在它自己的沙箱里）；**缺的是"看起来像真机"**，
  分四层，L1 目录骨架能解决 80%，L2 示例文件是双刃剑

---

## 一、先分清两个不同的问题

| 问题 | 现状 |
| --- | --- |
| **guest 能否读/写 `/sdcard`？** | ✅ **能** —— 重定向到 `<沙箱>/sdcard`，读写都正常 |
| **guest 看到的 `/sdcard` 像不像真机？** | ❌ **不像** —— 沙箱是空的 |

**这两个问题经常被混为一谈。** 前者早就解决了（`addPathRedirection("/sdcard", virtualSdcardDir)`）。

---

## 二、四层"模仿"，可行性逐层分析

### L1：目录骨架（✅ **完全可行，零风险，建议立刻做**）

**做法**：在 `<沙箱>/sdcard/` 下预建 AOSP `Environment.java` 定义的 12 个标准目录：

```
Alarms/        Android/     DCIM/         Documents/
Download/      Movies/      Music/        Notifications/
Pictures/      Podcasts/    Recordings/   Ringtones/
```

再加上应用私有目录：
```
Android/data/<guest-pkg>/
Android/obb/<guest-pkg>/
```

**为什么这能解决问题**：
- **真机刚开机时这些目录也是空的** —— 所以"空目录"本身不是异常
- `listFiles("/sdcard")` 返回 12 个目录 → **与真机一致**
- 应用假设 `DCIM/` 存在 → **不会 NPE**

**成本**：~20 行（`SandboxManager` 创建实例时预建）

**风险**：**零**（只是 mkdir）

**收益**：**直接消除 D3 检测面里"`/sdcard` 空"这一条**

### L2：示例文件（⚠️ 可行但**双刃剑**）

**做法**：预置几张示例图片/音频/文档。

**收益**：
- `DCIM/Camera/` 里有照片 → 相册类应用能显示内容

**风险**（**这是关键**）：
| 风险 | 说明 |
| --- | --- |
| **假文件被检测** | 放一个不是有效 JPEG 的 `IMG_001.jpg` → 应用解码失败 → **比"没有文件"更可疑** |
| **时间戳异常** | 所有文件同一时间创建 → 真机不会这样 |
| **EXIF 缺失** | 真机照片有 EXIF（GPS、设备型号）→ 假文件没有 → **可检测** |
| **数量规律** | 真机可能有几十张照片，假文件只有 3 张 → 反常 |

**判断**：
> **L2 要么做得非常真（生成带 EXIF 的图片、随机时间戳），要么不做。**
> **半吊子的示例文件比空目录更糟。**

**成本**：做得真需要 ~200 行 + 资源文件（每张图 ~100KB）

**建议**：**暂不做**，等 L1 落地看实测效果。

### L3：共享真实 `/sdcard`（❌ **不可行，与权限目标冲突**）

**做法**：不重定向 `/sdcard`，让 guest 直接访问真实路径。

**问题**：
- **需要 `MANAGE_EXTERNAL_STORAGE`** → **传导给所有 guest**（见 `记录-三方对比-P28...`）
- guest 能读写用户的真实文件 → **安全风险**
- 多个 guest 之间**互相可见** → 违背容器愿景

**结论**：**不采用**。

### L4：按需导入（✅ 已讨论，作为补充）

**做法**：用户手动把文件导入沙箱。

**问题**（见 `调研/调查-导入代替代读的攻防.md`）：
- 用户不知道 guest 需要什么
- 时机不匹配
- **不能解决"沙箱空"的问题**（因为本来就是用户决定放什么）

**定位**：**L1 的补充，不是替代**。

## 三、"guest 大多数情况能读能写"的准确回答

### 3.1 已经能做的（不需要任何改动）

| 操作 | 结果 |
| --- | --- |
| guest 写 `/sdcard/Download/x.jpg` | ✅ 写到沙箱，成功 |
| guest 读自己写的 `/sdcard/Download/x.jpg` | ✅ 成功 |
| guest 读 `/sdcard/DCIM/`（自己创建的） | ✅ 成功 |
| guest 用 `MediaStore` 插入图片 | ⚠️ 走系统 MediaProvider → **写真实媒体库**（不是沙箱） |
| guest 用 `Environment.getExternalStorageDirectory()` | ✅ 返回 `/storage/emulated/0` → 被重定向到沙箱 |

**所以"能读能写"完全成立。**

### 3.2 做不到的

| 操作 | 为什么 |
| --- | --- |
| 读用户的真实照片 | 沙箱里没有（除非导入） |
| 用系统相机拍照后读 | 相机写真实 `/sdcard/DCIM`，guest 读沙箱 → 看不到 |
| `MediaStore` 查询用户的媒体 | 查的是系统数据库（真实），不是沙箱 → **数据不一致** |
| 其他应用写的文件 | 真实路径，沙箱看不到 |

### 3.3 `MediaStore` 是最大的裂缝

**为什么**：
- `MediaStore` 的数据在 `system_server` 的 `MediaProvider` 里
- **它索引的是真实 `/sdcard`**
- guest 通过 `ContentResolver.query(MediaStore.Images...)` → **查到的是真实照片列表**
- 但 guest 用 `File` 打开那个路径 → **沙箱里没有** → **打不开**

**这就是典型的"假代理不一致"（D6）**：
```
query(MediaStore) 返回 100 张照片
  但 open("/sdcard/DCIM/Camera/IMG_001.jpg") → ENOENT
    → 自相矛盾 → 可被检测
```

**解法**（三选一）：
| 方案 | 做法 | 成本 |
|---|---|---|
| **A. 让 `MediaStore` 也返回沙箱内容** | hook `ContentResolver.query` 过滤/伪造 | 高（要造假的 Cursor） |
| **B. 让沙箱内容进入 `MediaStore`** | 导入时调 `MediaScanner` 扫描沙箱 | 中（但会污染系统媒体库） |
| **C. 让 `MediaStore` 返回空** | 对 guest 隐藏所有媒体 | 低，但**功能缺失**（相册类应用不可用） |

**建议**：**A 是唯一正确的方向**，但成本高。**暂记为待办。**

## 四、建议的实施顺序

| 顺序 | 项 | 成本 | 收益 | 风险 |
|---|---|---|---|---|
| **1** | **L1 目录骨架** | ~20 行 | 消除"`/sdcard` 空"这个 D3 检测面 | **零** |
| 2 | 观察 L1 后的实测效果（探针 `P16`/`P30`） | — | 决定是否要做 L2 | — |
| 3 | `MediaStore` 一致性（A 方案） | 高（2–3 天） | 消除 D6 检测面 | 中 |
| 4 | L2 示例文件（只在 3 之后考虑） | 中 | 相册类应用可用 | 中 |

## 五、一句话

> **"guest 能读能写 `/sdcard`" 早就实现了 —— 在它自己的沙箱里。**
> **缺的是"看起来像真机"：先补 12 个标准目录（零成本），
> 再考虑 `MediaStore` 一致性（这是最大的裂缝），
> 示例文件要么做得非常真，要么不做。**
