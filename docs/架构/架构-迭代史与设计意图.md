## 一、为什么需要这份文档

本仓库反复出现同一类浪费：**做过的又被重做，或两个实现并存互相冲突**。已发生的例子：

| 现象 | 后果 |
| --- | --- |
| 同一份路径知识写在 4 处（`synthetic*` / `VirtualContext` / `PackageManagerProxy` / `setupAppRedirections`） | 改一处漏三处；`guestExternalData`/`guestExternalDir` 曾重复定义（已消除，`04f3c5c`） |
| 架构文档落后代码（"mkdir 无 hook"、"hook 表 21 个"、"L4 是空壳"） | 差点基于错误前提去改代码 |
| WebView 方向连试 3 个补丁（v137/v139/v140） | 全部 revert，浪费数轮 |
| 同一路径族的根形态缺口（`/data/user/0/<pkg>`）与守它的测试同时诞生却没人跑 | T39/T41 红了两轮 CI |

**解法**：迭代史（本文）+ 代码为准文档（`架构-hook实现现状-代码为准.md`）+ 每篇文档标注核实基准（见 `README.md` 的时效规则）。

## 二、时间线（按 commit，均可 `git show` 复核）

### 2.1 上游基线（`63346e6`，fork 点）

上游已具备：`VirtualContext` 路径改写、Binder 代理、native GOT patch（22 条符号）、
五处"同一知识多份"的结构（见 `架构-路径转换分层现状与重复设计.md` §9.0）。

**上游没有**：系统库过滤宏（全 patch，含图形栈）、写操作 hook（`mkdir`/`unlink`/`rename`）、
路径族数据表、豁免机制。

### 2.2 pathFidelity 的扩张（`3f9f079` → `54f3649` → `2fcfbc7`）

| commit | 动作 | 动机 | 留下的问题 |
| --- | --- | --- | --- |
| `3f9f079` | 补 `syntheticExternalDir` / `ExternalCache` / `ObbDir` | 只合成 data 目录时，external/obb 仍暴露沙箱 | 每条新合成路径都要配规则（T39 事后才发现漏） |
| `16b4f58` / `2fcfbc7` | 修 external/obb 规则的**无尾斜杠变体** | `getObbDir()` 返回无斜杠，`startsWith` 不成立 | 只解决子项；**族根仍然无规则** |
| `54f3649` | 补 `syntheticMediaDir` + 新增 T39/T40/T41 | 用测试守"每个合成路径都有规则" | 测试首次运行就红（缺口与测试同一天诞生） |

> **意图**：路径欺骗必须"只误导、不危害读写"；每加一个合成形态，都要能翻译。
> **困难**：这个契约靠**事后测试**守，而不是结构保证（2026-11-25 才由 `PathKinds` 部分补上）。

### 2.3 WebView 的三次失败与真路径的胜利（`73b7f5b` … `c3c918a`）

| commit | 动作 | 结果 |
| --- | --- | --- |
| `73b7f5b` | 把进程 `Application` 指向 guest | 部分有效（修 context 根因） |
| `ad90b05` | **revert** v137（包装 `WebViewClient` 补 MIME） | 时序做不到：`loadUrl` 早于视图树扫描（`installed=0(+132ms)`） |
| `1480713` / `612cef5` | **revert** v139（假 dataDir 注入 framework bind 路径） | 注入点无效，`VirtualContext.super` 拿的是容器自己的 `LoadedApk` |
| `b979b87` | `getApplicationInfo` 返回副本 | 防止原地改共享对象（必须保留） |
| `c3c918a` | **内容目录改真实沙箱路径**（`contentPathsUseReal=false`） | ✅ 有效：WebView 的 isolated 进程只认真实存在的路径 |

> **意图**：WebView 渲染在 `sandboxed_process0`（独立 uid、无 hook），假路径它读不到。
> **结论**：凡是"路径字符串交给别的进程解析"的场景，**只能给真路径**。
> **不要再做**：给 WebView 补 MIME/delegate、给 `ApplicationInfo.dataDir` 注入假路径。

### 2.4 Java 层 hook：能装、但会弄坏应用（`c717f82` → `19904f5`）

| commit | 动作 | 结果 |
| --- | --- | --- |
| `c717f82` | v141 默认开启 Java IO 翻译 | 崩：`ErrnoException` 在 `android.system` 而非 `libcore.io` |
| `19904f5` | v147 默认**关闭**（`debug.nextvm.javaIo=0`） | Via 从"完全不可交互"恢复 |

> **意图**：让 `File`/`FileInputStream` 也走路径翻译。
> **现状**：16 个方法已实现但默认不装（见 `架构-hook实现现状-代码为准.md` §三）。
> **不要再做**：无前提地打开 `javaIo=1`；要开必须先过 A 族/B 族失败语义（已崩 3 次）。

### 2.5 豁免机制 → 数据表 → 族根语义（`6b5cfbe` → `f983716` → `11f23d5`）

| commit | 动作 | 动机 |
| --- | --- | --- |
| `6b5cfbe` | **A 阶段**：`PathKind` / `PathPolicy` / `PathSpoofConfig` + CmdReceiver 三命令 | via 不能欺骗（WebView），但必须保留隔离 → "豁免" = 关②③留① |
| `f983716` | 两份名单**配置化**（豁免 / 欺骗）+ `PathWhitelistEffectTest` | via 不能写死在代码里；"白名单是否生效"必须可自动化验证 |
| `b561921` | **`PathKinds` 数据表**（14 族 × 三种形态 + 规则生成） | 消除"同一知识 4 处"；让 T39 从"事后检查"变"结构推导" |
| `11f23d5` | **ROOT_FORM 匹配语义**（Java + C++ 同改） | 族根 `/data/user/0/<pkg>` 无规则覆盖（T39/T41 红的真因） |
| `031eba8` | T41 的 APK 目标改用沙箱内路径 | 测试口径与真实形态不一致（`<virtualRoot>/apks/<instance>.apk`） |

> **意图链**：`③ 合成路径` 是 `② 路径形态欺骗` 的手段，`① 沙箱隔离` 是独立目标。
> 豁免 = 关 ②③、留 ①。数据表只放"三种形态长什么样"，控制流留在消费方。
> **详见** `docs/设计/设计-澄清-欺骗与隔离与合成路径.md`、`docs/设计/设计-项目设计理念.md`。

## 三、**已做过，不要再做**（最重要的一节）
