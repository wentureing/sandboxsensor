# 架构：当前开发中的困难与摩擦（2026-11-25）

- 日期：2026-11-25
- **核实基准**：容器 `baseline-v150 @ 031eba8`
- 用途：把"反复卡住的地方"写下来，避免每轮重新发现；每条都给出可操作的下一步。

---

## 一、困难清单

### D1 「实现了」≠「生效」——三层开关

| 症状 | 查了半天代码，行为没变；或"探针过了但应用坏了" |
| --- | --- |
| 根因 | `NS_HOOK_SYSTEM_LIBS`（编译期，默认 0）、`debug.nextvm.javaIo`（默认 0）、`debug.nextvm.javaIoTranslate`（默认 1） |
| 现状缓解 | `架构-hook实现现状-代码为准.md` §二/§三 列出"实现 vs 生效" |
| 仍缺 | **没有一处统一的"当前生效面"打印**。建议：guest 启动时把三个开关 + 规则数 + 库过滤结果打一行 `DebugTrace.event` |

### D2 层间不一致：Java 落宿主、native 落沙箱

| 症状 | 宿主出现空目录壳、文件却在沙箱；或"写进去了但读不到" |
| --- | --- |
| 根因 | `libjavacore.so` 是系统库（不 patch）+ `javaIo=0`（Java 层不装） → Java I/O 不翻译；而 app 自带 `.so` 的 libc 调用被 patch → 翻译 |
| 现状缓解 | 内容目录改真路径（`c3c918a`）后，"自己拿到的路径"不需要翻译 |
| 仍缺 | guest **自己拼的宿主路径**（`getOpPackageName()` 拼出的 `/storage/.../com.nextvm.app/...`）仍依赖翻译；`hooked_open` 没有 `ENOENT` 兜底 |

### D3 文档落后代码（最贵的摩擦）

| 症状 | 按文档改代码，改错方向 |
| --- | --- |
| 实例 | "`mkdir` 无 hook"（其实已 hook）、"hook 表 21 个"（其实 27）、"L4 是空壳"（其实 16 个方法）、"media 未加分支"（已加） |
| 现状缓解 | `架构-hook实现现状-代码为准.md` + `docs/archive/错误结论-2026-11/` 登记 |
| 仍缺 | 没有强制"文档写核实基准"的机制 → 已在 `docs/架构/README.md` 加时效规则与状态总表 |

### D4 本地无法验证，每次修复 = 一次 CI

| 症状 | 一个"测试口径"小错（如 T41 的 `/apk/x.apk`）就要花一整轮 CI |
| --- | --- |
| 根因 | 本机 SDK 只有 `android-34/36`，缺 `android-35`；SDK 目录在工作区外（沙箱不可写）；受限 shell 不能下载 |
| 现状 | 只能靠 `kotlin-lint` / `check-imports`（毫秒级）+ `module-test`（~35s + 排队） |
| 建议 | 需要时由用户在标准模式安装 `platforms;android-35`，或在 CI 里加一个"fast lane"只跑受影响模块的测试 |

### D5 C++ 与真机行为没有自动化

| 症状 | `redirect_path` 改完只能靠真机；Robolectric 被 `@Ignore`（100 MB jar 下载不稳） |
| --- | --- |
| 影响 | ROOT_FORM 这种"Java + C++ 双改"的改动，只能保证 Java 侧有单测 |
| 现状缓解 | Java/C++ 语义写在同一份变更文档 + 两边注释互相指向；真机回归看 `Dbg/path` 与 `open: A -> B` |
| 建议 | 给 `redirect_path` 抽一个可在 host 编译的纯函数单元（不含 JNI），用 C++ 侧最小编译测试跑同一组向量 |

### D6 契约靠"事后测试"，而不是结构保证

| 症状 | 加了合成路径却忘加规则 → 直到 T39 才红（而且没人跑） |
| --- | --- |
| 现状缓解 | `PathKinds.rulesFor` 由数据表推导；`PathKindsTest.K6` 断言"每族都有 hostForms 或 coveredBy" |
| 仍缺 | 消费方**尚未接线**（仍手写注册）→ 结构与测试还没有真正合一 |

### D7 via 连败 5 轮的教训

| 错误路径 | 正确做法 |
| --- | --- |
| 从 UI 症状（主页空白、列表空、popup 闪退）直接猜模块 | 先确认**谁在解析这个路径**（主进程 / guest / isolated 进程），再决定能不能被骗 |
| 在 Java 层找 MIME 原因 | 实测它不参与（`AndroidProtocolHandler.open()` 返回 null） |
| 加补丁链（v137→v139→v140） | 每个补丁都要能被一句话否证；否证不了就不算定位 |

### D8 「两套真相」重叠

`contentPathsUseReal`（全局硬编码 false）与 `PathPolicy`（per-guest 可配置）描述同一件事。
判据已收敛到 `shouldUseSyntheticContent` 一处，但**语义仍有两套**；B 阶段应收敛为只查策略。

### D9 多实例被冻结（但缺陷还在）

合成路径不含 `instanceId`，同包两份 → 规则 key 冲突 → 数据互串。
**开发暂停**，但任何"按 pkg 生成规则"的新代码都必须假设"只有一个实例"，
否则会在恢复多实例时被迫返工。

### D10 日志系统既是命脉也是易碎品

- 设备（vivo）会吞非默认 uid 的 `Log.i` → 只能靠 `debug-trace.log`；
- 因此**日志不能被 hook 影响**：`is_container_diag_path()` 排除自身诊断文件（`438eab2`），
  容器自身库永不 patch；
- 约束：日志只在 debug 产物里（`DebugFlags.isDebugBuild()` 首行 return），
  新增日志必须保持该门禁，且不得让日志写入经过被 hook 的层。

### D11 诊断能力碎片化

`nativeGetFsStats()` 只覆盖 `open/stat/mkdir/opendir/unlink/rename` 六个操作；
`javaIo` 有 `total/fail/translated` 但没有按族的分布。
排障时经常"知道没生效，但不知道哪一层/哪一族"。

### D12 CI 纪律带来的成本

`module-test` 一次只能一个模块组合、`cancel-in-progress` 会取消同分支的前一个 run，
所以**每次验证都要精算**：一次 dispatch 要把该修的、该测的都带上。
反作用：容易出现"修一个错、再暴露下一个"的串行往返（T39→T41 就是）。

## 二、摩擦最小化：动代码前的三查

| 改什么 | 先查 | 再查 |
| --- | --- | --- |
| hook（符号/过滤） | `架构-hook实现现状-代码为准.md`（27 条符号 + 三开关 + 四级过滤） | 三个开关在目标环境是否为"开" |
| 路径族（合成/规则） | `PathKinds`（14 族三形态）+ `PathKindSpec` | `PathPolicy` 与 `path_spoof.conf` 两份名单 |
| "看到什么路径" | `VirtualContext.shouldUseSyntheticContent`（唯一判据） | `contentPathsUseReal` 是否把它压成真路径 |
| 加日志 | `DebugFlags.isDebugBuild()` 门禁 | 日志路径是否会被自己的规则翻译 |

## 三、一句话

> **本项目的真正成本不在写代码，而在「分辨哪份信息是真的」** ——
> 代码、文档、既有结论三者经常不一致。所以本轮之后的顺序固定为：
> **读代码 → 写核实基准 → 再动代码**。
