## 一、10 个层次（从最容易到最不可能）

| # | 层 | 手段 | 覆盖什么 | 状态 | 难度 |
| --- | --- | --- | --- | --- | --- |
| **L1** | **容器自己的 Java API** | `VirtualContext` / `SandboxManager` | 容器自己构造的任何对象 | ✅ **已做到** | 容易 |
| **L2** | **Binder 代理** | `IActivityManager` / `IPackageManager` / `IContentResolver` | guest 调系统服务 | ✅ **已做到**（`ActivityManagerProxy` 1295 行、`PackageManagerProxy` 850 行、`ContentResolverProxy` 651 行） | 容易 |
| **L3** | **组件生命周期** | `ActivityThreadHook`（2133 行） | Activity/Service/Application 的创建与启动 | ✅ **已做到** | 中 |
| **L4** | **Java 层文件 API** | `RegisterNatives` 替换 `libcore.io.Linux.*`（8 个）+ `java.io.UnixFileSystem.*0`（8 个） | guest 的 Java 代码读写文件 | ⚠️ **已实现 16 个方法，但默认关闭**（`debug.nextvm.javaIo=0`） | 中 |
| **L5** | **native GOT（启动时已加载的库）** | `patch_library_got` + `dl_iterate_phdr` | 容器初始化时已在内存里的库 | ✅ **已做到** | 中 |
| **L6** | **native GOT（运行期新加载的库）** | `hooked_dlopen` → `patch_newly_loaded_libraries` | `System.loadLibrary` 加载的库 | ❌ **链断了**（调用方是 `libnativeloader.so`，没被 patch） | **难** |
| **L7** | **直接系统调用** | `hooked_syscall` **只打日志、原样透传** | `syscall(SYS_openat, ...)` | ❌ **未拦截** | 难 |
| **L8** | **isolated 进程**（WebView renderer） | 无手段 | `sandboxed_process0` | ❌ **不可能** | **不可能** |
| **L9** | **继承来的 fd** | 无手段 | guest 从容器继承的 `ParcelFileDescriptor` | ❌ **不可能** | **不可能** |
| **L10** | **DAC / SELinux**（同 uid） | 无手段 | 内核层 | ❌ **不可能** | **不可能** |

## 二、逐层说明

### L4：Java 层文件 API —— 唯一"还没做但能做"的空洞

**现状**：

```kotlin
private fun hookFileClass(): Boolean {
    / We can't directly hook File constructors in pure Java...
    Timber.tag(TAG).d("File class hook points prepared")   / ← 只打日志
    return true
}
```

**为什么它重要**：
- guest 的**纯 Java 文件访问**（`new File(path).exists()`、`FileInputStream`）现在**完全不受容器影响**
- 只有 `native` 层被 GOT patch 的库才受影响
- 但很多应用（尤其国内 App）**大量用 Java IO**

**能做吗**：能，但要选对切入点：

| 切入点 | 可行性 | 说明 |
| --- | --- | --- |
| hook `java.io.File` 的构造/方法 | ❌ 难 | framework 类，方法内联，无法替换 |
| hook `java.io.FileInputStream` 的 `open` | ❌ 难 | 同上 |
| **hook `libcore.io.Linux` / `Os`**（Java 层的 syscall 封装） | ⚠️ 中 | 这些是 `libcore` 的类，**不是 boot classpath 的一部分？** 需要验证 |
| **hook `BlockGuard` / `StrictMode`** | ⚠️ 中 | 只能观测不能改 |
| **改 `System.getProperty("java.io.tmpdir")` 之类** | ✅ 容易 | 治标 |

**结论**：**L4 实际可做的很有限**，因为 `java.io` 是 framework 类。这一层的"代理"只能靠 **L2（ContentResolver）** 覆盖走 `ContentResolver` 的那部分。

### L6：运行期加载的库 —— 唯一"应该做且做得到"的

**现状**：`hooked_dlopen` 存在，但 `System.loadLibrary` 的调用方是 `libnativeloader.so`（系统库，未被 patch）→ `patch_newly_loaded_libraries()` 不执行。

**P28 实测证据**：
- `libprobe.so`（`System.loadLibrary("probe")` 加载）的 `fopen` **没被 hook**
- 结果：`/sdcard/Download/probe-wtest.txt` **被真实改写**

**能做吗**：能（方向 A），只需把 `libnativeloader` 加入 patch 列表。

### L7：`hooked_syscall` —— **只打日志，不拦截**（2026-11-23 核实）

```cpp
/ native-hook.cpp:1301
static long hooked_syscall(long number, ...) {
    bool interesting = number == 48 || number == 56 || ...;   / 12 个 number 只是日志白名单
    if (interesting && logged_int < 40) {
        LOGI("DIAG syscall nr=%ld a1=%ld ...");               / ← 只打日志
    }
    if (real_syscall) return real_syscall(number, a1, a2, a3, a4, a5, a6);  / ← 原样透传
}
```

**不修参数、不重定向、不伪造。** 应用用 `syscall(SYS_openat, ...)` 可以完整绕过所有 GOT hook。

**但"要不要单独拦"是另一回事**：
- `syscall` 直接调用是**少见写法**（正常代码用 libc）
- 用它的人（加固壳/反调试）读的是**同一批文件**（`/proc/self/maps`、`/proc/self/cmdline`、dataDir）
- **只要在"数据源"层面伪造好，libc 和 syscall 看到的一致**
- 单独给 syscall 做路径重定向性价比极低（要覆盖 12+ 个 number，容易漏）

**前提**：伪造必须发生在**被读的内容**上（如 `open("/proc/self/maps")` 返回伪造 fd），
而不是**读的路径**上。现有 `make_proc_spoof_fd` 就是这思路 —— 但**探针的 `libprobe.so` 没被 patch（L6）**，
所以探针自己读不到伪造内容。

**所以 L6 是 syscall 问题的前置。**

### L8/L9/L10：三层硬边界

| 边界 | 为什么不可能 |
| --- | --- |
| **L8 isolated 进程** | `webview_zygote` fork 的进程，容器完全无法介入（`docs/records/记录-WebView问题全链路.md`） |
| **L9 继承的 fd** | fd 在打开那一刻就绑定了 inode，后续任何 hook 都改不了它指向哪 |
| **L10 DAC/SELinux** | 同 uid，内核无法区分容器与 guest |

## 三、代理方式的适用范围（能不能扩大）

### 3.1 代理的本质

> **把"guest 做不到的事"转交给"宿主能做到"，通过 fd / stream / Binder 传递。**

### 3.2 已经用代理的地方

| 场景 | 代理什么 | 通道 |
| --- | --- | --- |
| **包管理** | `PackageInfo` / `ApplicationInfo` | Binder（`PackageManagerProxy`） |
| **组件启动** | Activity/Service 的启动参数 | Binder（`ActivityManagerProxy`） |
| **ContentResolver** | `content:/` URI 的查询/打开 | Binder（`ContentResolverProxy`） |
| **导入通道** | 容器读 APK 后装进沙箱 | 容器自己的 `File`（主进程不装 hook） |

### 3.3 可以扩大的地方

| 场景 | 代理方式 | 可行性 | 价值 |
| --- | --- | --- | --- |
| **WebView 的 `file:/`** | 宿主代读 + `WebResourceResponse` | ⚠️ 需要找到注入点（`setWebViewClient` 是 framework 方法） | **高**（P1-3） |
| **`MediaPlayer` / `ExoPlayer` 的本地文件** | 宿主代读 + `setDataSource(fd)` | ✅ 可行（fd 跨进程） | 中 |
| **`BitmapFactory.decodeFile`** | 宿主代读 + `decodeFileDescriptor` | ✅ 可行 | 中 |
| **native 库读不到的路径** | 宿主代读到沙箱，**让 guest 的路径就是真实的** | ✅ 可行（这是"路径保真"路线） | **高** |
| **`file:/` Intent（`ACTION_VIEW`）** | 宿主代读 + `FileProvider` | ✅ 可行 | 中 |
| **`/sdcard` 的整个访问** | 宿主代读 + fd | ⚠️ 受 L9（继承 fd）影响，只能代理"新打开"的 | 中 |

### 3.4 代理**不能**解决的

| 场景 | 为什么 |
| --- | --- |
| **isolated 进程（WebView renderer）** | 宿主无法介入另一个应用的进程 |
| **native 直接 syscall** | 不经过任何可代理的接口 |
| **fd 已继承** | 打开时机早于任何注入 |

### 3.5 一个关键的思路转变：**"路径保真"比"路径代理"更彻底**

**现在的问题**：guest 看到的 `/sdcard` 是**虚拟的**（重定向到沙箱），所以：
- 应用用真实路径找不到文件 → 走代理补救
- 代理要覆盖每一个入口（`open`/`fopen`/`stat`/...）→ **永远有漏**

**另一条路（Gaia 的思路）**：
- 让 guest 的 `dataDir` / `externalDir` **就是真实路径**（`gaia/data/user/0/<pkg>`）
- 应用自己访问时**不需要任何翻译**
- 容器只在**必要处**（如 maps 伪造、包名伪装）介入

**代价**：真实路径里含容器包名（`/data/user/0/com.app.hider.../gaia/...`）→ **暴露容器**

**权衡**：
| 路线 | 优点 | 缺点 |
| --- | --- | --- |
| **路径改写（我们）** | 路径看起来像真机 | 每个 IO 入口都要 hook，**永远有漏**（P28 就是漏） |
| **路径保真（Gaia）** | 不需要覆盖所有 IO 入口 | 路径含容器包名 → 可被检测 |

## 四、"容器主动针对某些 guest 不使用权限"

### 4.1 用户的问题

> 容器能不能"主动"让某个 guest **没有**某权限？

### 4.2 分三层回答

| 层 | 能不能挡 | 手段 | 有效性 |
| --- | --- | --- | --- |
| **应用自查权限**（`checkSelfPermission` / `ContextCompat.checkSelfPermission`） | ✅ **能** | `PackageManagerProxy` 对指定 guest 返回 `PERMISSION_DENIED` | **高**（大部分应用会先自查） |
| **走系统 API**（`ContentResolver` / `MediaStore`） | ✅ **能** | `ContentResolverProxy` 抛 `SecurityException` | **高** |
| **直接 `open()` / `fopen()`** | ❌ **不能** | 同 uid，DAC 放行 | **零** |

### 4.3 所以"按 guest 关闭权限"的实际效果

```
一个"守规矩"的应用：
  checkSelfPermission(DENIED) → 不尝试访问 → ✅ 成功挡住

一个"不守规矩"的应用（或 native 直接 open）：
  直接 open("/sdcard/xxx") → 内核按 uid 放行 → ❌ 挡不住
```

**实测佐证（P28）**：
- 我们的容器有 `MANAGE_EXTERNAL_STORAGE`
- 探针**没有先自查权限**，直接 `fopen` → **写成功**
- 如果探针先 `checkSelfPermission(MANAGE_EXTERNAL_STORAGE)`，容器可以返回 DENIED → 探针可能就不会尝试

### 4.4 推荐做法：**"权限声明与实际授予分离"**

```kotlin
/ guest 请求的权限 → 容器决定"宣称授予"还是"实际授予"

data class GuestPermissionPolicy(
    val guestPackage: String,
    val declared: Set<String>,          / guest 在 manifest 里声明的
    val virtualGranted: Set<String>,    / 容器"宣称"授予的（应用自查会看到这个）
    val realGranted: Set<String>,       / 容器实际有、且真的会传导的
)
```

**关键**：**`virtualGranted` 可以比 `realGranted` 小** —— 也就是说：
- **容器对应用说"你没有存储权限"**（`checkSelfPermission` → DENIED）
- **但容器自己有** → 应用如果硬来（直接 open）仍能成功

**这不是真正的防护**，但能：
1. 让守规矩的应用行为正常（不会崩）
2. 减少无意的越权访问

### 4.5 真正有效的只有一条

> **容器自己不申请该权限。**（`docs/设计-权限传导与hook规划.md` §3.1）

**理由**：同 uid → DAC 层放行 → Java 层代理挡不住 native。

## 五、总结表：能力 / 状态 / 下一步

| 能力 | 状态 | 下一步 |
| --- | --- | --- |
| 容器自己的 Java API 虚拟化 | ✅ 已做到 | — |
| Binder 代理（AMS/PMS/ContentResolver） | ✅ 已做到 | 补 `READ_MEDIA_*` 相关 |
| 组件生命周期接管 | ✅ 已做到 | — |
| **Java 层文件 API hook** | ⚠️ 空壳 | **可做但有限**（framework 类难 hook） |
| native GOT（已加载库） | ✅ 已做到 | — |
| **native GOT（运行期加载）** | ❌ 链断 | **方向 A：patch `libnativeloader`** |
| 直接 syscall | ❌ **只打日志** | **不单独做**（见 L7 说明：伪造数据源即可，修 L6 是前置） |
| **WebView 的 file:/** | ❌ 不可能 | **只能靠宿主代读（P1-3）** |
| **isolated 进程** | ❌ 不可能 | 接受边界 |
| **继承的 fd** | ❌ 不可能 | 接受边界 |
| **DAC / 同 uid** | ❌ 不可能 | **容器不申请敏感权限** |
| **按 guest 关闭权限** | ⚠️ 只能挡"守规矩"的应用 | 配合 `virtualGranted < realGranted` |

## 六、一句话

> **能拦的：guest 主动发起、经过可 hook 接口的调用（L1–L6）。L7（syscall）目前只打日志。**
> **拦不住的：isolated 进程（L8）、已继承的 fd（L9）、同 uid 的 DAC（L10）。**
> **代理唯一能突破的是 L8**（把数据递进 isolated 进程），但需要找到注入点。
> **"按 guest 关闭权限"只能骗过守规矩的应用，真正的防护是容器自己不申请。**
