# 架构：进程名与包名的身份模型（2026-11-27）

- 回答：**guest 的"进程名/包名"在每一层分别是什么、谁在生产、谁在读、哪一层不能改。**
- 设计意图（用户 2026-11-27 明确）：**guest 进程名就是 guest 包名**（`mark.via`），其它 guest 同理。
- 关联：`架构-启动链契约.md`、`架构-两条bind路径的由来.md`、变更文档 `20261127-process-slots-会话复用与UI解绑.md`

---

## 一、三层身份（不要在错误的层上改名字）

| 层 | 包名 | 进程名 | 谁看得到 | 依据 |
| --- | --- | --- | --- | --- |
| **① 系统面**（AMS / PMS / AppOps） | **`com.nextvm.app`（宿主）** | `com.nextvm.app:pN`（manifest `android:process`） | 系统、其它 app、`dumpsys` | `app/src/main/AndroidManifest.xml`（stub 组件 `android:process=":pN"`）；`bindViaFrameworkLoadedApk` 把框架 LoadedApk 的 `mPackageName` patch 成宿主（避免 AppOps `checkPackage` SecurityException） |
| **② guest 面**（guest 代码 / Java API / `/proc`） | **guest 包名**（`mark.via`） | **guest 包名**（主进程），子进程 `pkg:suffix` | guest 自己、SDK、检测面 | 见 §二 各通道 |
| **③ 容器内部**（引擎/租约/进程表） | — | **不用进程名做主键** | 容器 | `slot`（`:pN` 的 N）+ `instanceId`；`SlotReconciler`/`SlotLeaseRegistry`/`VirtualProcessManager` 全部按这两个键 |

**硬约束**：
1. 系统面身份**必须**保持宿主（否则系统调用被拒）。→ 不要"顺手把 LoadedApk.mPackageName 也改成 guest 包名"。
2. guest 面进程名**必须**是 guest 包名（用户设计意图）。
3. 容器内部**不得**依赖进程名 —— 改名是单向、不可逆的（`setArgV0`/prctl 之后再也读不到 `:pN`）。

## 二、每条"名字通道"的现状（代码为准）

| 通道 | 生产点 | 值 | 一致性 |
| --- | --- | --- | --- |
| `Application.getProcessName()`（guest） | `VirtualEngine.rewriteBoundProcessName()` 改写 `ActivityThread.mBoundApplication.processName`（约 `:1900-1912`，bind 时调用 `:2084-2090`） | guest 包名 | ✅ |
| `/proc/self/cmdline`（`ps`、`Runtime.exec("ps")`、`/proc/<pid>/cmdline`） | `Process.setArgV0(packageName)`（约 `:2069-2072`） | guest 包名 | ✅ |
| 内核 comm（`/proc/<pid>/stat`、`status Name`、task 视图、其它进程视角） | `NativeHookBridge.setProcessName()` → native `prctl`（`NativeHookBridge.kt:671-683`） | guest 包名 | ✅ |
| `ApplicationInfo.processName`（guest 视角 PM） | `ApplicationInfoFactory:23`（`processName = packageName`）；`VirtualPackageManagerService:462`（`processName = app.packageName`） | guest 包名 | ✅ |
| `ActivityManager.getRunningAppProcesses()`（**guest 调用**，真实 AMS 经 proxy） | `ActivityManagerProxy.handleGetRunningAppProcesses`：透传前把**本进程条目**的 `processName`/`pkgList` 改写（`:1065-1085`，2026-11-27 新增） | 本进程 = guest 包名；其它条目 = 系统记录（宿主/stub） | ✅（本轮修复） |
| guest 代码判断"我是不是主进程" | `ActivityManagerProxy.currentProcessGuestPackage()`：`Application.getProcessName()` 与 `virtualApps` 前缀匹配（`:629-638`） | 依赖上表第 1 行 | ✅ |
| 容器 `getCallingSlot()`（binder 调用者 slot 推导） | `VirtualCallerResolver.cacheProcessSlotFromCurrentName()`（约 `:56-83`），在改名**之前**调用（`VirtualEngine:2057`） | 缓存 `:pN` 的 N | ✅（顺序敏感） |
| `VirtualActivityManagerService` 的虚拟进程记录（**容器管理面**） | `startProcess`：`processName = "$packageName:p$processSlot"`（`:134`） | `mark.via:p0` | ✅ **允许**（用户 2026-11-27 拍板：容器管理面可用"包名+编号"；只要不泄漏到 guest 可见 API） |
| 容器侧"这个 guest 进程还活着吗" | `GuestProcessStopper.findPids(pkg)` 按 `/proc/<pid>/cmdline` 匹配 guest 包名 | guest 包名 | ✅（正因改名才成立） |
| 容器侧 slot 观测 | `SlotStatusProbe` 用 `ActivityManager.getRunningAppProcesses()` 的 **AMS 记录名** `com.nextvm.app:pN` 解析 slot（`SlotReconciler.parseSlotFromProcessName`） | 宿主 + `:pN` | ✅（AMS 记录不随改名变化） |

## 三、2026-11-27 的改动（对齐设计意图）

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| `getRunningAppProcesses` 本进程条目改写 | `ActivityManagerProxy.kt:1065-1085` | `processName = guestPkg`、`pkgList = [guestPkg]`；保留 `ProcTrace` 日志（改写前后可见） |
| 探测侧不动 | `SlotStatusProbe` / `SlotReconciler` | 改用 AMS 记录名解析 slot，**不受** guest 改名影响（否则永远判不到进程） |
| 进程名 = 包名的前提 | `VirtualEngine` 的 `setArgV0` / `setProcessName` / `rewriteBoundProcessName` | 三者必须都在 bind 成功路径上执行；任一失败只打 W，不阻断 bind |

## 四、已知不一致 / 缺口（诚实清单）

| # | 项 | 现状 | 影响 | 建议 |
| --- | --- | --- | --- | --- |
| **1** | ~~VAMS `record.processName` 不一致~~ | 已按 2026-11-27 结论**归为容器管理面允许项**（`mark.via:p0` 保留） | 仅当它泄漏到 guest 可见 API 才有问题 | 保持现状；新增 guest 可见进程列表时必须显式改写（见 §二 `getRunningAppProcesses` 行） |
| **2** | `VirtualMultiProcessManager.isMainProcess` | `processName == packageName`（`:769`） | 若调用方传 `:p0` 会误判主进程 | 多进程能力当前暂停；恢复时统一"传 guest 包名" |
| **3** | `findCallingGuestPkg()` | 取 `virtualApps` 第一个（`:1292-1295`） | 同包多实例无法区分 | 多实例暂停；恢复时改为按调用者 slot/instanceId |
| **4** | `getRunningAppProcesses` 只改"本进程条目" | 其它条目保持系统记录 | 符合"只看到自己"的隔离；但若 guest 依赖"同实例子进程"信息会缺 | 多进程恢复时再补 |
| **5** | 进程名改写的**顺序契约** | `cacheProcessSlotFromCurrentName()` 必须早于 `setArgV0` | 顺序颠倒 → binder 调用者 slot 推导失效（PM 隔离破） | 已写进本文件 §二；改 `ensureGuestApplicationBooted` 顺序时必查 |

## 五、改代码时的判据（四问）

1. 这个 API 是 **系统面**还是 **guest 面**？系统面 → 保持宿主/stub；guest 面 → guest 包名。
2. 这个值会不会被容器自己当**主键**？会 → 换成 `slot`/`instanceId`。
3. 改名（`setArgV0`/prctl）之后还能读到旧名吗？不能 → 任何"从进程名反推 slot"的代码必须在改名**前**执行或走缓存。
4. 有没有日志能证明改对了？→ `ProcTrace`（getRunningAppProcesses 改写）、`AppBindData.processName rewritten`（mBoundApplication）、`Process renamed to guest`（prctl）。
