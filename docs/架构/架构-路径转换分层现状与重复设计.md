# 架构现状：路径转换的分层设计与疑似重复/复杂处

- 日期：2026-11-25
- 目的：把「路径转换」这条链上**每一层在做什么**列清楚，并列出**疑似重复 / 过度复杂**的设计
- 说明：本文只描述**现状**与**问题**，不含改动方案（方案见文末「建议」）

---

## 一、六层结构总览

```
┌─ L0  guest 应用代码
│      new File(context.getFilesDir(), "x.json")
│      new FileInputStream("/storage/emulated/0/Android/data/<pkg>/files/a.mht")
│
├─ L1  VirtualContext（Java · override android.content.Context）
│      core/sandbox/.../VirtualContext.kt
│      getFilesDir / getCacheDir / getExternalFilesDir / getObbDir / getDataDir / ...
│      返回「合成路径」或「沙箱路径」（由 pathFidelity 分支决定）
│
├─ L2  PackageManagerProxy（Java · Binder 代理）
│      core/binder/.../PackageManagerProxy.kt
│      设置 ApplicationInfo.dataDir / sourceDir / publicSourceDir /
│           nativeLibraryDir / deviceProtectedDataDir / credentialProtectedDataDir
│      同样受 pathFidelity 控制
│
├─ L3  Java native hook（RegisterNatives 替换）
│      core/hook/cpp/native-hook.cpp（install_java_io_hooks）
│      libcore.io.Linux.*        open / access / mkdir / unlink / rename
│      java.io.UnixFileSystem.*0 list0 / createDirectory0 / createFileExclusively0 /
│                                getBooleanAttributes0 / getLastModifiedTime0 /
│                                setLastModifiedTime0 / setReadOnly0 / canonicalize0
│      这些方法内部调 translatePath（Kotlin）→ 再调 libc
│
├─ L4  translatePath + 规则表（Kotlin · 纯逻辑）
│      core/hook/.../NativeHookBridge.kt
│      pathRedirections: ConcurrentHashMap<String, String>   （最长前缀胜）
│      hiddenPaths: Set<String>                              （精确匹配 → /dev/null）
│      三个注册入口：
│        setupAppRedirections            data / external / obb / media / 宿主兜底
│        setupExternalStorageRedirections 通用 /sdcard/ /storage/emulated/0/ ...
│        setupPathFidelityRedirections  上面两个 + apk + lib
│      通过 nativeAddPathRedirection 同步给 native 层
│
├─ L5  native GOT patch（C++ · libc）
│      native-hook.cpp 的 install_plt_hooks
│      open / openat / access / stat / lstat / readlink / fopen /
│      mkdir / unlink / rename / opendir
│      内部调 redirect_path（C++）→ 再调 real_*
│
└─ L6  内核
```

---

## 二、每层的职责边界

| 层 | 负责 | **不负责** |
| --- | --- | --- |
| **L1 VirtualContext** | 决定「应用看到什么路径」—— 合成路径 or 沙箱路径 | 不做 I/O 翻译（那是 L3/L5） |
| **L2 PackageManagerProxy** | 决定 `ApplicationInfo` 里的路径字段 | 不碰 Context 的目录方法 |
| **L3 Java native hook** | 在 Java 层 I/O 入口翻译路径 + 复刻 AOSP 的异常/返回值契约 | 不碰应用拼路径（那是 L4 的规则） |
| **L4 translatePath** | 规则匹配与翻译（纯字符串） | 不做 I/O |
| **L5 native GOT patch** | 应用自带 .so 直接调 libc 时翻译 | 覆盖不到 libcore（系统库不 patch） |
| **L6 内核** | — | — |

**关键分工**：**L1/L2 决定"看到什么"，L3/L4/L5 决定"用起来去哪"。**
两者必须一致 —— 否则就是「写到一个地方、从另一个地方读」。

## 三、疑似重复的设计（5 处）

### 重复 1：**两套规则表 + 两套翻译实现**

| | Kotlin（L4） | C++（L5） |
| --- | --- | --- |
| 存储 | `pathRedirections: ConcurrentHashMap<String, String>` | `g_path_redirects`（vector of pair） |
| 匹配 | `originalPath.startsWith(from)` + 最长前缀 | `path_str.compare(0, len, from) == 0` + 最长前缀 |
| 替换 | `bestRedirect + originalPath.substring(bestMatch.length)` | `best_to + path_str.substr(best_from.length())` |
| 隐藏 | `hiddenPaths`（精确匹配 → `/dev/null`） | **没有对应机制** |
| 同步 | `nativeAddPathRedirection(from, to)` | 由 Kotlin 调用写入 |

**重复成本**：
1. **两份实现要各自修 bug** —— 实际情况是：**Kotlin 曾经有 `String.replace` 全局替换的 bug，
   而 C++ 一直是对的**（用 `substr`）。**同一份逻辑，一个对一个错，说明双份实现必然脱节。**
2. **语义不一致**：C++ 多了 `/data/user/0/` → `/data/data/` 的兜底重试，Kotlin 没有
3. `hiddenPaths`（`/dev/null`）只在 Kotlin 侧生效，native 侧完全不知道

### 重复 2：**`pathFidelity` 与 `HOST_EXTERNAL_FALLBACK` 两套 external 兜底**

| 机制 | 触发条件 | 源前缀 | 目标 |
| --- | --- | --- | --- |
| `pathFidelity.syntheticExternalDir` | 白名单内的 guest | `/storage/emulated/0/Android/data/<guestPkg>/` | `<sandbox>/sdcard/Android/data/<guestPkg>/` |
| `HOST_EXTERNAL_FALLBACK.HOST_EXT_PREFIX_A` | 所有 guest | `/storage/emulated/0/Android/data/**com.nextvm.app**/` | **同一个目标** |

**为什么会有两套**：前者是「guest 用自己的包名」，后者是「guest 用 `getOpPackageName()`（宿主包名）拼路径」。
目标相同、来源不同，**但两者写在同一张表里，靠"最长前缀"与"目标恰好相同"来避免冲突**。

**风险**：目标相同的巧合是**手工维护**的 —— 谁改了其中一个，两者就会分叉。

### 重复 3：**三个注册入口写同一张表**

```kotlin
setupAppRedirections(...)                  // data / external / obb / media / 宿主兜底
setupExternalStorageRedirections(...)      // 通用 /sdcard/ /storage/emulated/0/ /mnt/sdcard/ ...
setupPathFidelityRedirections(...)         // = setupAppRedirections + apk + lib
```

**复杂度**：`setupPathFidelityRedirections` **内部调用** `setupAppRedirections`，
所以调 `setupPathFidelityRedirections` 就等于把所有 app 规则也注册了一遍。
**调用顺序不同会导致"最长前缀"结果不同**（虽然理论上最长前缀与顺序无关，
但**目标冲突**时后注册的会覆盖 —— `ConcurrentHashMap.put`）。

### 重复 4：**路径合成逻辑分散在 L1/L2 两处**

| 路径族 | L1 `VirtualContext` | L2 `PackageManagerProxy` |
| --- | --- | --- |
| `dataDir` | `getDataDir()` override | `dataDir` 字段 |
| `files` | `getFilesDir()` override | — |
| `sourceDir` | — | `sourceDir` / `publicSourceDir` |
| `nativeLibraryDir` | — | `nativeLibraryDir` |
| `external files` | `getExternalFilesDir()` override | — |
| `obb` | `getObbDir()` override | — |
| `media` | `getExternalMediaDirs()` override | — |

**问题**：同一个概念（如"这个 guest 的 data 目录"）在**两个类里各自算一遍合成路径**，
共享的只有 `VirtualConstants.synthetic*` 这一层常量。
**没有一致性的结构性保证** —— 只能靠"两边都记得改"。

### 重复 5：**两套失败语义（A 族 / B 族）**

| 族 | 方法 | 失败时 |
| --- | --- | --- |
| **A 族** | `libcore.io.Linux.*` | **抛 `ErrnoException`**；空参抛 NPE |
| **B 族** | `java.io.UnixFileSystem.*0` | **返回 `null` / `false` / `0`**，不抛异常（`canonicalize0` 例外，抛 `IOException`） |

**这不是设计重复，是 Android 本身的两族契约**（真实存在，不是我们造成的）。
**但它造成的复杂度很高**：混用一次就崩，而本项目为此崩过至少 3 次：

| 版本 | 症状 | 混用方向 |
| --- | --- | --- |
| v147 | Via 工具栏点不动 | 把 B 族写法（返回 false）用在 A 族 `access` 上 |
| v147 | `FATAL: isSocket$() on null` | A 族 `open` 返回 null 而不抛 |
| 本轮 | `StorageManager: Failed to get canonical path` | B 族 `canonicalize0` 该"成功"时抛了异常 |

**缓解**：`docs/设计/设计-hook行为契约表与完整清单.md` 里有两族对照表。

## 四、疑似过度复杂的设计（3 处）

### 复杂 1：**`pathFidelity` 的分支散落在 13+ 个方法里**

`VirtualContext` 有 **13 处** `if (pathFidelity)` 分支（getFilesDir / getCacheDir /
getCodeCacheDir / getDatabasePath / getDir / getNoBackupFilesDir / getDataDir /
getExternalFilesDir / getExternalCacheDir / getObbDir / getExternalMediaDirs / ...）。

**每处都是"先调 sandboxManager 确保目录存在，再返回合成路径"的重复模式**：

```kotlin
override fun getExternalCacheDir(): File {
    val sandboxDir = sandboxManager.getExternalAppCacheDir(instanceId, guestPackageName)  // 确保存在
    return if (pathFidelity) File(VirtualConstants.syntheticExternalCacheDir(guestPackageName)) else sandboxDir
}
```

**可以抽象成一个辅助函数**（`ensureThenMaybeSynthetic(sandbox: () -> File, synth: () -> File)`），
但当前是 13 份手工重复。

### 复杂 2：**`synthetic*` 6 个函数 + 每个都要配规则 → 靠测试兜底**

```
syntheticDataDir         -> /data/user/0/<pkg>
syntheticApkPath         -> /data/app/~~VmK8x2==/<pkg>-VmK8x2==/base.apk
syntheticLibDir          -> /data/app/~~VmK8x2==/.../lib/arm64
syntheticExternalDir     -> /storage/emulated/0/Android/data/<pkg>
syntheticExternalCacheDir-> /storage/emulated/0/Android/data/<pkg>/cache
syntheticObbDir          -> /storage/emulated/0/Android/obb/<pkg>
syntheticMediaDir        -> /storage/emulated/0/Android/media/<pkg>
```

**每个都要在 `setupAppRedirections` / `setupPathFidelityRedirections` 里配对应规则，
且有/无尾斜杠两种变体**（因为 `getObbDir()` 返回无尾斜杠、`getExternalFilesDir()` 返回带子路径）。

**当前唯一的一致性保证是测试 T39**（穷举合成路径断言都有规则），
**没有编译期/结构性的保证** —— 加一个新 `synthetic*` 而不加规则，测试才会红。

### 复杂 3：**`hiddenPaths` 与 `pathRedirections` 语义不一致**

| | 匹配方式 | 结果 |
| --- | --- | --- |
| `hiddenPaths` | **精确相等** | `/dev/null` |
| `pathRedirections` | **前缀匹配** | 翻译 |

所以 `hidePath("/system/bin/su")` 只隐藏**这一个路径**，`/system/bin/sudo` 不受影响（T20 钉住了这个行为）。
而 `addPathRedirection("/system/", ...)` 会影响整个子树。

**两个机制对"前缀"的态度相反**，且 `hiddenPaths` 在 native 侧没有对应物 —— 容易误以为"hide 了就是整棵树都 hide"。

## 七、两个交叉点的查证结果

### 7.1 规则表是否始终同步：**是**

`NativeHookBridge.kt` 里所有对 `pathRedirections` 的写操作都伴随 native 调用：

| 行 | 操作 | 是否同步 |
| --- | --- | --- |
| L377 | `addPathRedirection` 内调 `nativeAddPathRedirection(from, to)` | ✅ |
| L386-388 | `removePathRedirection` 内调 `nativeRemovePathRedirection(from)` | ✅ |
| L295-296 | `pathRedirections.forEach { nativeAddPathRedirection(...) }` | ✅（批量重放，用于重启后恢复） |
| L395-399 | `clearPathRedirections()` 内调 `nativeClearPathRedirections()` | ✅（native 侧 L2410 有实现，`g_path_redirects.clear()`） |

**结论：增/删/清空三条路径都同步。** 这一项原判为「缺口」，是**误判** —— 我只看了
`pathRedirections.clear()` 这一行，没往下看三行的 `nativeClearPathRedirections()`。

> 这是本轮**第三次**「只看了半截就下结论」。前两次是 `getFileStreamPath`（实际自动跟随）
> 和 `dataDir`（实际 `PackageManagerProxy` 已合成）。
> **教训：判断"某能力有没有"，必须读完整个函数，不能只看第一行。**

### 7.2 `/data/user/0/` → `/data/data/` 兜底：**当前不体现差异，但机制上不对称**

C++ 的 `redirect_path` 有一段 Kotlin 侧没有的兜底：

```cpp
// Special case: /data/user/0/ is the same as /data/data/
if (path_str.compare(0, 13, "/data/user/0/") == 0) {
    std::string alt_path = "/data/data/" + path_str.substr(13);
    return redirect_path(alt_path.c_str());   // 重试匹配
}
```

查证：Kotlin 的 `setupAppRedirections` **同时注册了**两条规则（L412-417）：

```kotlin
addPathRedirection("/data/data/$guestPackageName/", ...)
addPathRedirection("/data/user/0/$guestPackageName/", ...)
```

**所以当前行为一致**。但机制上不对称：**如果将来只注册其中一条**，
C++ 还能靠兜底重试命中，Kotlin 会漏 —— 这类不对称正是"两份实现"的典型代价。

### 冲突 1：同一目标值被定义两次 —— **已消除**

**来源**：本轮两次独立修补撞在一起。

```kotlin
// c0996e9 引入（宿主包名兜底段）
val guestExternalDir = "$sandboxDataDir/sdcard/Android/data/$guestPackageName/"

// 16b4f58 引入（App-specific external storage 段）
val guestExternalData = "$sandboxDataDir/sdcard/Android/data/$guestPackageName/"
```

**两个变量、相同值、同在 `setupAppRedirections` 内、相隔 49 行。**

**危害**：改一处不改另一处 → 宿主包名路径与 guest 自身包名路径指向不同沙箱目录 →
就是"写到一个地方、从另一个地方读"。

**已修复**：删除 `guestExternalDir` 定义，4 处引用统一为 `guestExternalData`。

---

### 冲突 2：APK/LIB 的规则不在 `setupAppRedirections` 里 —— **暂不修复**

| 路径族 | 合成路径定义在哪 | 规则在哪 |
| --- | --- | --- |
| data / external / obb / media | `VirtualConstants.synthetic*` | **`setupAppRedirections`** |
| **APK** | `syntheticApkPath` | **`setupPathFidelityRedirections`（单独两行）** |
| **LIB** | `syntheticLibDir` | **`setupPathFidelityRedirections`（单独两行）** |

**来源**：上游 `63346e6` 就是这样分的 —— `setupPathFidelityRedirections` 的类型是
`setupAppRedirections(...)` + APK + lib，所以 APK/lib 天然落在后者的补充里。

**危害（合并时）**：如果表驱动只遍历 `setupAppRedirections` 现有的 18 条，会**漏掉 APK 和 LIB**。
T39 会红，但那是事后。

**处理要求**：表里必须有 `APK` / `LIB` 两个 `PathFamily`，且它们归属
`setupPathFidelityRedirections` 而非 `setupAppRedirections`。

### 冲突 3：合成路径形态与规则前缀形态耦合 —— **暂不修复**

| 路径族 | A 合成路径 | D 规则前缀 | 是否天然匹配 |
| --- | --- | --- | --- |
| EXTERNAL_FILES | `/storage/emulated/0/Android/data/<pkg>/files` | 带尾斜杠 `/.../data/<pkg>/` | ✅ 前缀匹配 |
| **OBB** | `/storage/emulated/0/Android/obb/<pkg>`（**无尾斜杠**） | 原只有带尾斜杠版本 | ❌ **不匹配** → `2fcfbc7` 补了无尾斜杠变体 |
| EXTERNAL_CACHE | `/storage/emulated/0/Android/data/<pkg>/cache` | 带斜杠前缀 | ✅ |
| APK | `/data/app/~~<token>==/<pkg>-<token>==/base.apk` | 完整路径（精确） | ✅ |

**来源**：`getObbDir()` 返回**无尾斜杠**，而规则的 `from` 写的是**带尾斜杠** →
`startsWith` 不成立 → 原样返回 → 与沙箱分叉。`2fcfbc7` 为此补了 4 条无尾斜杠变体。

**危害（合并时）**：表里**每个路径族必须存"两种宿主形态"**（含/不含尾斜杠），
否则重演。而且不能靠人工判断"这个族需要哪种形态" —— 应该统一都写两种。

---

### 冲突 4：`hiddenPaths` 与 `pathRedirections` 语义相反 —— **暂不修复**

| 机制 | 匹配方式 | 结果 | native 侧有吗 |
| --- | --- | --- | --- |
| `hiddenPaths` | **精确相等** | `/dev/null` | **没有** |
| `pathRedirections` | **前缀匹配** | 翻译 | 有（`g_path_redirects`） |

**来源**：两个机制在不同时期为不同目的加上，从未统一。

**危害（合并时）**：如果把两者并成一张表，**native 侧无法表达"精确匹配"** ——
`g_path_redirects` 只有前缀语义。所以 `hiddenPaths` **不能**并入同一张表，
要么保持独立，要么给 native 侧新增一个精确匹配集合。
