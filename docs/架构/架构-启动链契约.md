## 一、golden 是什么、不是什么

| 是 | 不是 |
| --- | --- |
| **某容器版本 + 某 guest 版本**下，一次真实冷启动的事件序列 | 覆盖率数字 |
| 契约断言的输入（顺序 / 计数 / 分支存在性） | 对当前输出的逐字快照（归一化后才入库） |
| "重构前后行为未变"的证据 | "能力是否可用"的判据（那是 SELF_CHECK + 探针的活） |

**采集边界**：从本进程的 `breadcrumb begin pkg=<guest> pid=<n>` 到首个 `cb onActivityResumed`（含）。
不截到文件尾 —— v124/v131 每 5s 的周期性打点不属于启动链。

## 三、归一化规则（为什么 golden 不逐字来自设备）

设备原文里每轮必变的量必须先抹掉，否则"两次启动一致"永远不成立：

| 抹掉 | 换成 | 原因 |
| --- | --- | --- |
| `[+123ms] [main] ` | 剥离（顺序由行序表达） | 时间戳每轮不同 |
| `#12345678` | `#<ID>` | identity hash |
| `_1795659911286` | `_<TS>` | instance 时间戳（重装即变） |
| `pid=` / `wall=` | `<PID>` / `<WALL>` | 每轮不同 |
| `entries=` / `len=` | `<N>` | 随 APK 版本变 |
| `rules=` | `<N>` | 规则条数随功能增长，不是启动链行为（`rules>=1` 由生成脚本守卫） |
| `clId=` | `<CLID>` | ClassLoader identity hash |
| `r8-map-id-<hash>` / `.kt:1234` / `.java:1234` | `<MAPID>` / `<LINE>` | **容器重编译或重构挪代码就会变** |

**不归一化**（否则契约失效）：包名、类名、authority、路径族名（`appDir` / `sdcard`）、事件名。

## 四、契约清单（11 条）

测试对 **4 份样本全部**跑；每条失败信息都带样本 tag。

| # | 断言 | 固定的行为 | 失效通常意味着 |
| --- | --- | --- | --- |
| **C1** | 首行是 `breadcrumb begin pkg=<guest> pid=<PID> wall=<WALL>`，且本进程 begin 只 1 次 | 新进程开新会话 | 样本被复用进程污染（采到假 golden） |
| **C2** | `replaceClassLoader done` 早于 `bind start` | CL 换装先于 bind（R2 不可逆窗口） | 换晚了 bind 会按旧 CL 走 |
| **C3** | `v118-provider-fields` 条数 = `bind start … providers=N`，且全部早于 bind | provider 元数据先读后 attach | provider 列表读错 → attach 到错误 authority |
| **C4** | `makeApplication enter` → `instr newApplication <App>` → `makeApplication exit app=<App>` | Application 只构造一次、出口类名一致 | 重复 makeApplication = guest 状态被清 |
| **C5** | 全部 `provider attachInfo enter/ok/FAILED` 早于 `Application.onCreate enter`；`provider FAILED` 必须带 `(bind continues)` | **provider 失败降级**（via 的 emoji2 就是这条） | 失败被当成致命 → bind 中断 |
| **C6** | `Application.onCreate exit` → `v142-redirect registered rules=` → `guest diagnostics installed` → `v130-watchdog started` | 规则与诊断都在 onCreate 之后、watchdog 之前 | 诊断出口装晚了会静默丢事件（R1） |
| **C7** | `engine breadcrumb callbacks registered` → `bind complete (framework path)` → `instr newActivity`，且 `bind complete` 只 1 次 | bind 段终结点唯一 | 重复 `bind complete` = bind 跑了两遍 |
| **C8** | `instr newActivity` → `callActivityOnCreate enter` → `preCreate enter` → `cb onActivityCreated` → `callActivityOnCreate exit ok` → `cb onActivityStarted` → `cb onActivityResumed` | 首 Activity 生命周期顺序 | B4-4 拆的就是这段，拆错先红 |
| **C9** | `mark.via` → `v143-datadir skip (whitelist)` 且不出现 patch；`com.sandbox.probe` → 必须 patch 到 `/data/user/0/com.sandbox.probe` | **路径欺骗豁免 = via 零欺骗**（`设计-项目设计理念.md` 第三条） | 豁免名单失效或误跳 |
| **C10** | `bind start` / `makeApplication enter` / `makeApplication exit` / `bind complete` / `instr newActivity` / `Application.onCreate enter` 各恰好 1 次 | 启动链只执行一次 | 复扫 / 重入类回归 |
| **C11** | 同一 guest 的两次启动归一化后**逐行相等** | 启动链可重复 | 样本不稳定（早期窗口 / 复用），golden 无效 |

## 五、测试红了怎么判（规则 18.4 的具体化）

**顺序固定，不要跳**：

1. **先看是不是 golden 过时**：容器/guest 版本变了吗？
   - 变了 → 按 §二重采 + `gen` 重新生成，并在 `docs/输出/变更/` 写明"为什么这次行为变化是预期的"。
2. **没变 → 是行为偏移**：
   - 回退被测改动，测试变绿 → 语义确实变了 → **回退代码**（不许改 golden 放过）；
   - 回退仍红 → 构造问题（golden 采错 / 断言写错）→ 修构造，不改语义。
3. **禁止**：把 golden 直接替换成新采样、放宽断言为 `contains`、`@Ignore`、删用例。

## 六、已知边界（会影响重复采集，不是契约缺陷）

| # | 边界 | 后果 | 临时处置 |
| --- | --- | --- | --- |
| 1 | **`StubRegistry` stub 泄漏**：`inUseStubs` 取出后生产代码从不归还（`releaseStub` / `releaseAllStubsForSlot` 无调用点） | 每个 slot 的 5 个 standard stub 用完后，`LAUNCH_ACTIVITY` 报 `No available stub for process slot N`（`VirtualEngine.kt:634`） | 重启容器（内存态重建）后重采；根治见变更文档 §九 N1 |
| 2 | 两个实例可能共用同一 slot（`processSlot` 是安装时的持久化值，容器重启后内存表为空） | 与 #1 叠加时更早触发失败 | 同上 |
| 3 | 容器刚启动 10s 内虚拟 PM 包列表未就绪 | `J19/J20` `NameNotFound`（不影响 breadcrumb） | 见 `架构-就绪依赖与早期窗口.md` |

## 七、覆盖面与不覆盖

| 覆盖 | 不覆盖 |
| --- | --- |
| 启动链**顺序**、**计数**、**失败降级**、**豁免分支** | 时序（每阶段耗时）—— 前缀已剥离 |
| 2 个 guest（豁免 / 非豁免各一） | 壳 guest（AW / SecNeo）、多实例、WebView 首帧 |
| 真实设备真实 APK | 单测环境下的伪造序列（不替代真机） |
