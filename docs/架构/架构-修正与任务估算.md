## 一、syscall：**我们没拦，只打了日志**

这是本轮最重要的修正。我此前在 `架构-拦截能力层次.md` 把 L7 写成"⚠️ 部分"，**过度乐观**。

### 1.1 代码事实

```cpp
/ native-hook.cpp:1301
static long hooked_syscall(long number, ...) {
    ...
    / aarch64 numbers of interest: faccessat=48, openat=56, close=57,
    / getdents64=61, read=63, pread64=67, readlinkat=78,
    / newfstatat=79, ptrace=117, kill=129, tgkill=131, clone=220
    bool interesting = number == 48 || number == 56 || ...;

    if (interesting && logged_int < 40) {
        LOGI("DIAG syscall nr=%ld a1=%ld a2=%ld a3=%ld by %s", ...);   / ← 只是打日志
    }

    if (real_syscall) return real_syscall(number, a1, a2, a3, a4, a5, a6);  / ← 原样透传
    errno = ENOSYS;
    return -1;
}
```

**结论**：
- **`hooked_syscall` 不修改参数、不重定向、不伪造**，**只统计/打日志**
- 那 12 个 syscall number（48/56/57/61/63/67/78/79/117/129/131/220）**只是日志白名单**

### 1.2 这意味着什么

```
应用调用 syscall(SYS_openat, AT_FDCWD, "/sdcard/Download/x", O_RDONLY, 0)
  → GOT 里有 syscall → 进 hooked_syscall
    → 打一条 DIAG 日志
      → real_syscall(...) 原样执行
        → 内核按 uid 判断 → 真实文件系统 → 成功
```

**完全没有路径重定向。**

### 1.3 但"要不要拦"要看它会不会被用来检测

**分两种用途**：

| 用途 | 例子 | 发现可能性 | 该不该拦 |
| --- | --- | --- | --- |
| **检测环境** | `syscall(openat, "/proc/self/maps")` 读 maps 找容器痕迹 | ★★（少，多数应用用 libc） | **该拦**（但和 maps 伪造是同一件事） |
| **检测环境** | `syscall(newfstatat, "/data/data/<容器>")` 看宿主目录 | ★★ | **该拦**（和 `P16` 同一件事） |
| **越权读写** | `syscall(openat, "/sdcard/xxx", O_WRONLY)` 直接写 | ★（更少） | 不是"检测"，是"越权" |
| **绕过 hook 自保** | 加固壳用 syscall 读自己的 dex | ★★ | 拦不住也不用拦 |

**关键判断**：
> **`syscall` 直接调用本身就是"少见的写法"**（正常代码用 libc）。
> **只有两种应用会用：加固壳、反调试库。**
> 而它们用 syscall 读的东西，**和 libc 读的是同一批文件**（`/proc/self/maps`、`/proc/self/cmdline`）。

**所以**：
> **不需要单独为 syscall 做一套路径重定向。**
> **只要把"读到的东西"伪造好（maps、cmdline、dataDir），libc 和 syscall 看到的是同一份内容。**

**但前提是**：伪造必须在**数据源**层面做（如 `open("/proc/self/maps")` 返回伪造的 fd），而不是在 `open` 的路径上做。

**这就是为什么 `N10 maps` 是"难但必要"** —— 它是**唯一的数据源级伪造**。

### 1.4 修正后的说法

| 层 | 之前的说法 | **修正后** |
| --- | --- | --- |
| **L7 syscall** | "⚠️ 部分（有覆盖）" | **❌ 只打日志，未拦截** |

### 3.1 任务 A：`P13` 宿主包不可见（半天）

| 项 | 内容 |

### 3.4 任务 D：maps 伪造（2–3 天，最难）

| 项 | 内容 |
| --- | --- |
| **目标** | `/proc/self/maps` 里不出现容器路径/库名（现在 `pkg_hit=8`，Gaia 是 `0`） |
| **手段** | ①`hooked_open("/proc/self/maps")` 返回一个 **memfd**，内容是把真实 maps 过滤后的副本（**现有代码已有 `/proc/self` spoof 框架**：`make_proc_spoof_fd`）②`read`/`pread`/`syscall(read)` 都要覆盖 |
| **难点** | ①maps 是**动态变化**的（mmap 新增区域），伪造要实时②`syscall` 直接读 maps 会绕过 → 需要同时处理 syscall③memfd 的 `/proc/self/fd/N` readlink 会露（指向 `/memfd:xxx`） |
| **风险** | **高**（maps 被大量库读取，伪造错误会导致崩溃） |
| **参考** | Gaia 做到了 `hostHits=0` → 可逆向它的实现 |

## 四、为什么 syscall "不用拦"（回答用户第 3 点）

**不是我之前说的"已拦"，而是"不需要单独拦"**，理由是：

1. **syscall 直接调用是少见写法**（正常应用用 libc）
2. **用它的人（加固壳/反调试）读的是同一批文件**（`/proc/self/maps`、`/proc/self/cmdline`、`dataDir`）
3. **所以只要在"数据源"层面伪造好**（maps 内容、cmdline 内容），libc 和 syscall 看到的一致
4. **单独给 syscall 做路径重定向的性价比极低**（要覆盖 12+ 个 number，且容易漏）

**但有一个前提**：**伪造必须发生在"被读的内容"上，而不是"读的路径"上。**

- 现在的 `/proc/self` spoof（`make_proc_spoof_fd`）**已经是这个思路**（返回伪造内容的 fd）
- **只是 `libprobe.so` 没被 patch（L6）→ 探针自己读不到伪造内容**

**所以**：**L6 是 syscall 问题的前置**。修好 L6，libc 和 syscall 两条路都会经过 spoof 的 `open`。
