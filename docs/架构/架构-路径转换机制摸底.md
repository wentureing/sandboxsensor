# 摸底：容器内的路径转换机制

- 日期：2026-11-24
- 目的：把「guest 看到的路径」与「真实文件位置」之间的转换机制一次讲清，
  避免再基于错误假设做设计（WebView 的 dataDir 实验就差点踩这个坑）
- 方法：读代码取证（`NativeHookBridge.kt` / `native-hook.cpp` / `VirtualContext.kt` / `VirtualEngine.kt`）
  + 探针实测交叉验证

---

## 一、结论先给：**三层，各管一段，互不覆盖**

| 层 | 手段 | 覆盖什么 | **不覆盖什么** |
| --- | --- | --- | --- |
| **L-Java**：`VirtualContext` | **路径改写**（不转换，直接返回另一个路径） | `getFilesDir()` / `getCacheDir()` / `getDataDir()` / `getExternalFilesDir()` … 共 26 个 override | **任何不是通过 Context 拿路径的代码**（`new File("/sdcard/x")`、`System.getenv`、hardcode） |
| **L-native**：GOT/PLT patch | 把 so 的**导入符号**换成 `hooked_*`，函数入口做**前缀字符串替换** | 被 patch 的 so 里所有 `open/openat/fopen/stat/access/readlink/opendir` 调用 | **系统库**（`NS_HOOK_SYSTEM_LIBS=0`）、**libc 自身**、**Java 层 I/O** |
| **L-syscall** | `hooked_syscall` | ❌ **只打日志，不改参数、不重定向** | 直接 `svc` 的代码完全绕过 |

**最关键的一条**：**Java 层的文件 I/O 没有任何重定向**。
证据（`NativeHookBridge.kt:710-724`）：

```kotlin
private fun hookFileClass(): Boolean {
    // We can't directly hook File constructors in pure Java,
    // but we can intercept the resolution at higher levels.
    // For Phase 1, the VirtualContext and ContentResolverProxy
    // handle most Java-level file access.
    Timber.tag(TAG).d("File class hook points prepared")
    return true          // ← 什么都没装
}
```

架构文档也写明：`installJavaIoHooks()` 是**空的**，真正起作用的是 native GOT patch。

## 二、规则清单（谁注册、什么时候、什么前缀）

### 2.1 规则表本体

`native-hook.cpp:228` `redirect_path()`：

- **最长前缀匹配**（不是精确匹配，也不是按目录边界）
- 命中 → 返回 `目标前缀 + 原路径剩余部分`
- 额外一条特殊规则：`/data/user/0/xxx` **自动再按 `/data/data/xxx` 匹配一次**（两条路径视为等价）

### 2.2 注册点（全仓只有 3 处）

| 注册函数 | 注册的前缀 → 目标 | **调用者 / 时机** |
| --- | --- | --- |
| `setupExternalStorageRedirections` | `/sdcard/`、`/storage/emulated/0/`、`/mnt/sdcard/`、`/storage/self/primary/`（含无尾斜杠的两个根）→ `<instance>/sdcard/` | **`VirtualEngine.launch()`（每个 guest 启动时）** ✔ 所有 guest 都有 |
| `setupAppRedirections` | `/data/data/<guest>/`、`/data/user/0/<guest>/` → 沙箱；`/storage/emulated/0/Android/data/<guest>/`、`/sdcard/Android/data/<guest>/` → 沙箱/external_data；obb 同理 | **只有 `setupPathFidelityRedirections` 调用它**，而后者只用于 **pathFidelity 的定制包**（`VirtualConstants.CM_PACKAGE`）→ **普通 guest 没有这条规则** |
| `setupPathFidelityRedirections` | 上面那批 + 合成 APK 路径、合成 lib 目录 → 沙箱 | 同上（CM 包专用） |

**→ 现状：探针 / Via 这类普通 guest，`/data/user/0/<guest>/` 这条规则根本不存在。**

### 2.3 另外两条「拒绝」型机制

| 机制 | 实现 | 语义 |
| --- | --- | --- |
| `hidePath()` | `is_path_hidden()` 用 `unordered_set` **精确匹配**（`native-hook.cpp:243`） | 只隐藏**那一个精确字符串**；`/data/user/0/com.nextvm.app` 被隐藏，但 `/data/user/0/com.nextvm.app/files` **不隐藏** |
| 导入豁免 | 对 `/sdcard/Download/`、`/data/local/tmp/` 前缀**放行（不重定向）** | 让 `INSTALL` 与 guest 能读到真实文件 |

## 三、被 hook 的符号（22 个）与生效范围

```
open open64   openat openat64   access   stat lstat   readlink
fopen fopen64   __system_property_get
dlopen   android_dlopen_ext   dl_iterate_phdr
ptrace   syscall   fork   opendir   mmap   mprotect   connect   getaddrinfo
```

**真正做路径转换的**：`open/open64`、`openat/openat64`、`fopen/fopen64`、`access`、`stat`、`lstat`、`readlink`（`opendir` 只打日志后直通，**不重定向**）。

**生效范围（过滤链，`native-hook.cpp:1660-1695`）**：

| 类别 | 判定 | 是否 patch |
| --- | --- | --- |
| 容器自身库 | 路径含 `com.nextvm.app` / `libnextvm` | ❌ |
| 图形栈 | `libGLES`/`libEGL`/`libvulkan`/`libllvm-glnext`… | ❌ |
| **应用/沙箱库** | 路径含 `/data/app/`、`/data/user/`、`/virtual/` | ✅ |
| 其余系统库 | 其它 | ❌（`NS_HOOK_SYSTEM_LIBS=0`） |

**由此推出的重要事实**：`libwebviewchromium.so` 位于 `/product/app/WebViewGoogle64/lib/arm64/`
→ 属于「其余系统库」→ **不 patch** → 它的 `open()` 直通真实文件系统。

## 四、覆盖矩阵（用实测校准过）

| guest 的写法 | 谁处理 | 结果 | 实测佐证 |
| --- | --- | --- | --- |
| `context.getFilesDir()` | VirtualContext（L-Java） | 直接返回**真实沙箱路径** ✓ | 探针 W2 的 URL 就是真实路径 |
| `new File("/sdcard/x").write()`（Java） | **没人处理** | 直通真实 `/sdcard` → **EPERM** | **W19：`open failed: EPERM`** ✔ 完全吻合 |
| so 里 `open("/sdcard/x")` | L-native（规则命中） | 映射到 `<instance>/sdcard/x` ✓ | 架构文档记载 |
| so 里 `open("/data/user/0/<guest>/x")` | L-native（**无规则**） | 直通 → 真实路径不存在 → 失败 | 规则只在 pathFidelity 注册 |
| **WebView 读 `file://` 沙箱路径** | `libwebviewchromium`（**不 patch**） | 直通真实路径 → **能读到** | W2 内容读到了（显示源码） |
| 直接 `syscall(SYS_openat, …)` | L-syscall（只打日志） | 完全绕过转换 | 代码注释明示 |

## 五、对 WebView 问题的直接含义

1. **URL 必须是真实路径**（Via 用 `getFilesDir()` → 真实沙箱路径 ✓）。
   把 URL 改成 guest 官方路径会让 WebView 读不到文件（它不在 patch 范围，且普通 guest 没有 `/data/user/0/<guest>/` 规则）。

2. **假 `dataDir` 目前没有 native 兜底**：如果按 v139 的思路把 `ApplicationInfo.dataDir`
   改成 `/data/user/0/<guest>`，而**没有**注册 `setupAppRedirections`，那么任何按 dataDir
   拼路径的**native** 读取也会失败（不只是 Java 层）。

3. **v140 修的是另一个坑**：`VirtualContext.getApplicationInfo()` 原来用
   `super.getApplicationInfo().apply { dataDir = ... }` **原地修改共享的
   `LoadedApk.mApplicationInfo`**，任何一次调用都会把 bind 时注入的值覆盖回去。
   已改为返回副本（应用侧看到 guest 视角，framework 侧保留注入值）。

4. **若要让假 dataDir 真正可用**，必须同时：
   - 对目标 guest 调 `setupAppRedirections(...)`（补上 `/data/user/0/<guest>/` → 沙箱）
   - 并接受「Java 层仍无重定向」这个硬限制（framework 内部 Java 读假路径会失败）

## 六、待办（按优先级）

| # | 项 | 说明 |
| --- | --- | --- |
| 1 | 给普通 guest 注册 `setupAppRedirections` | 目前只 pathFidelity 有；这是"假 dataDir 能用"的前提 |
| 2 | `opendir` 没有重定向 | 只打日志；目录枚举如果遇到假路径会列不到（`readdir` 过滤也未实现） |
| 3 | `hidePath` 是精确匹配 | 与 `架构` 文档里「按目录隐藏」的预期不符，隐藏面比想象小 |
| 4 | Java 层 I/O 无重定向 | 架构级限制；如需支持"假 dataDir"必须补 Java hook（成本高，且项目目前没有该能力） |
