# 代理范式：什么能代、什么能假、IPC 怎么代、文件代理的边界

- 日期：2026-11-23
- 起因：用户提出 —— 什么情况容器代理访问可以实现？能不能虚假代理返回预设值？
  怎么代理进程间通信？能不能在通信层面伪装结果？文件代理能拦下什么？
- 结论先给：**按"返回值类型"分三类，策略完全不同**

---

## 零、一句话框架

> **查询类调用（返回元数据）→ 直接造假值，最简单也最安全。**
> **数据类调用（返回字节流）→ 必须造一个真实可读的对象（memfd/pipe/fd）。**
> **探测类调用（问"存不存在"）→ 返回 `ENOENT`，比造假内容更彻底。**

**这三类的难度和风险递增，但第二类往往可以用第一类替代** —— 详见 §2.3。

---

## 一、代理能实现的四个前提条件

代理 = **宿主代做，把结果递给 guest**。要成立需要四个条件：

| # | 条件 | 满足不了的后果 | 例子 |
| --- | --- | --- | --- |
| **1** | **调用点在可控层**（L1–L6） | 拦不到 → 代理无从谈起 | isolated 进程（L8）、直接 syscall（L7） |
| **2** | **能构造合法返回对象** | 造不出 → 只能抛异常 | `WebResourceResponse` 的 header 必须像真的 |
| **3** | **不需要真实副作用**，或副作用可伪造 | 需要真做 → 就不能"假" | `open(O_WRONLY)` 必须有真实 fd |
| **4** | **guest 不会交叉验证** | 会验证 → 假值被戳穿 | 同时查 `stat` 和 `readdir` |

**第 4 条最关键也最常被忽略**：

```
我们伪造 stat("/data/data/com.nextvm.app") → ENOENT        ✅ 单独看没问题
但如果 guest 再 opendir("/data/data") → 列表里有 com.nextvm.app   ❌ 矛盾了
```

**所以假代理必须"成组一致"**：`stat` / `opendir` / `readdir` / `access` / `getxattr` 要同一个口径。

## 二、虚假代理（返回预设值）：能用到什么程度

### 2.1 查询类：**几乎无敌**

| 检测点 | 假值 | 现状 |
| --- | --- | --- |
| `getDataDir()` / `getFilesDir()` | 沙箱路径 | ✅ 已做 |
| `getPackageName()` | guest 包名 | ✅ 已做 |
| `getPackageInfo(容器)` | 抛 `NameNotFoundException` | ❌ 待做（`P13`） |
| `getInstalledPackages()` 列表 | 过滤掉容器 | ❌ 待做 |
| `Application.getProcessName()` | guest 包名 | ✅ 已做 |
| `getprop` 容器相关 | 真机值 | ❓ 待验（`P17`） |
| `Build.*` | 真机值 | ✅ 天然一致 |
| `stat(容器 dataDir)` | `ENOENT` | ❌ 待做（`P16`） |

**为什么几乎无敌**：
- 返回值是**结构化的元数据**（String / Parcelable / struct stat）
- 造一个合法值**只需要知道字段含义**
- **不需要任何真实资源**

### 2.2 数据类：**必须造真实对象**

| 检测点 | 能不能假 | 怎么做 |
| --- | --- | --- |
| `/proc/self/maps` | ⚠️ **能，但要造 fd** | `open()` 返回 memfd，内容是过滤后的 maps |
| `/proc/self/cmdline` | ⚠️ 能 | 同上（现有 `make_proc_spoof_fd`） |
| `/proc/self/status` | ⚠️ 能 | 同上 |
| **任意 `/sdcard/xxx` 文件内容** | ❌ **不能假** | 必须有真实 inode（宿主代读 → 给 fd） |
| `read(fd)` 的字节 | ❌ 不能改 | 除非 fd 本身就是伪造的 |

**关键区别**：
> **文件"存在性/元数据"可以假；文件"内容"必须有真实载体。**

因为 `read()` 拿的是内核返回的字节，**除非 fd 指向的是我们的 memfd，否则改不了**。

### 2.3 一个重要的替代策略：**用"拒绝"代替"伪造"**

| 想达到的效果 | 伪造内容（难） | **假装不存在（易）** |
| --- | --- | --- |
| guest 不该看到容器痕迹 | 过滤 maps 里的每一行（难，动态变化） | **`open("/proc/self/maps")` 里删掉容器行** 或 **让容器库不 mmap 到 guest 空间**（更根本） |
| guest 不该读到某个文件 | 造一个"看起来一样但内容不同"的文件 | **`open()` 返回 `ENOENT`** |

**为什么"拒绝"更好**：
- **检测方无法区分"不存在"和"被隐藏"**（这是最重要的性质）
- 假内容可能**自相矛盾**（比如 maps 的行数与 `smaps` 不一致）
- 拒绝只需要一个返回值，**不需要维护一份假的真实**

**这条原则的推论**：
> **凡是"guest 不该看到的东西"，优先让它"不存在"，而不是"存在但内容不同"。**

## 三、进程间通信（IPC）的代理

### 3.1 Android 的 IPC 有哪几种

| 类型 | 占比 | 能否代理 |
| --- | --- | --- |
| **Binder**（系统服务、应用间） | ~95% | ✅ **能（Java 层）** |
| **LocalSocket / Unix Socket** | 少 | ⚠️ 部分（`hooked_connect` 有，但只打日志） |
| **管道 / 共享内存** | 少 | ❌ 难 |
| **Intent / Bundle**（同一进程内） | — | ✅ 能（直通） |

### 3.2 Binder 代理的两个层次

```
guest 进程
  ├─ Java 层：ServiceManager.getService("package")
  │    ↓  ← 【层 A】可以在这里替换成自己的 proxy
  │  IBinder.transact(code, data, reply, flags)
  │    ↓  ← 【层 B】也可以逐次改 data/reply
  └─ native：ioctl(/dev/binder, BINDER_WRITE_READ)
       ↓  ← 【层 C】几乎不可能（Binder 协议 + 驱动）
      binder 驱动
```

| 层 | 做什么 | 现状 | 难度 |
| --- | --- | --- | --- |
| **A. 替换 IBinder** | `ServiceManager.sCache` 里塞自己的 proxy | ✅ **已做**（`SystemServiceProxyManager.kt` 3273 行 + 各 `*Proxy.kt` 共 ~7000 行） | 中 |
| **B. 拦截 transact** | 每次调用前改 `Parcel` | ✅ 已做（proxy 内部就是干这个） | 中 |
| **C. hook `ioctl`** | 直接改 Binder 驱动的数据 | ❌ 未做，也**不建议做** | **极高** |

### 3.3 能不能"在通信层面伪装结果"

**能，而且这已经是我们的主要手段** —— 但有两个硬限制：

#### 限制 1：只有走 Java `IBinder` 的调用能拦

```java
// 能拦（走 ServiceManager 拿到的 proxy）
IPackageManager pm = IPackageManager.Stub.asInterface(
    ServiceManager.getService("package"));
pm.getPackageInfo("com.nextvm.app", 0);      // ✅ 我们的 proxy 会返回 NNFE

// 拦不到（native 直接调 Binder）
// native 里：open("/dev/binder") → ioctl(BINDER_WRITE_READ)
// 完全绕过 Java 层
```

**但实践上**：**绝大多数应用（包括加固壳）都是用 Java 的 `PackageManager`**，
直接 native 调 Binder 的极少（需要自己拼 Parcel）。

#### 限制 2：返回值的类型必须"能造"

| 返回值 | 能造吗 | 说明 |
| --- | --- | --- |
| `PackageInfo` / `ApplicationInfo` | ✅ | 普通 Parcelable |
| `List<PackageInfo>` | ✅ | 过滤列表 |
| `Bundle` | ✅ | 任意字段 |
| **`ParcelFileDescriptor`** | ⚠️ **只能给真的 fd** | 这是"数据类"，造不了假的 |
| **`IBinder`**（返回另一个 binder） | ⚠️ 能，但要接着代理那个对象 | 链式代理，容易漏 |

**关键**：**`ParcelFileDescriptor` 是分界线** ——
一旦返回值是 fd，就必须有一个**真实可读的文件/管道/memfd**。

这正好对应 §2 的分类：
- **元数据（Parcelable）→ 假**
- **字节流（fd）→ 必须真**

### 3.4 一个具体的例子：`ContentResolver.openInputStream(uri)`

```
query(uri)                    → 返回 Cursor（元数据）→ ✅ 可以假造游标
openFileDescriptor(uri, "r")  → 返回 PFD（数据）      → ⚠️ 必须给真 fd
```

**所以**：
- `query` 可以完全造假（返回一个假的 Cursor，列名/行数随便编）
- `openFileDescriptor` **必须由宿主真的打开文件**（这是"宿主代读"的本质）

**这也解释了为什么 P1-3（WebView 宿主代读）难做**：
`WebResourceResponse` 需要 `InputStream` → 宿主必须真的读文件 → **不能假**。

## 四、文件代理访问能拦下什么

### 4.1 四种手段，能力递增

| # | 手段 | 能拦下什么 | 拦不下什么 | 我们的状态 |
| --- | --- | --- | --- | --- |
| **1** | **路径重定向**（改 `open` 的参数） | guest 打开的**路径**被改到沙箱 | 改不了**内容**；改不了**已继承的 fd** | ✅ 已做（L5），L6 待修 |
| **2** | **拒绝访问**（返回 `ENOENT`/`EACCES`） | 指定路径**假装不存在** | 只能用于"不该存在"的东西 | ✅ 框架有（`nativeHidePath`） |
| **3** | **内容伪造**（返回 memfd） | `/proc/self/*` 这类**可完整生成**的内容 | 任意真实文件的内容（量太大/动态） | ⚠️ 有 `make_proc_spoof_fd`，但 L6 让探针读不到 |
| **4** | **完全代读**（宿主读 → 给 fd） | guest 没权限/路径不对的文件 | 已继承的 fd（L9） | ⚠️ 只在 `ContentResolver` 做了 |

### 4.2 逐层能拦下的具体清单

#### 手段 1：路径重定向

| 路径 | 重定向到 | 效果 |
| --- | --- | --- |
| `/data/data/<guest>` | `<沙箱>/data/<instance>` | guest 看到自己的"私有目录" |
| `/sdcard` | `<沙箱>/sdcard` | guest 看到自己的"外部存储" |
| `/data/user/0/<guest>` | 同上 | 覆盖另一种前缀写法 |

**拦不下**：
- `/proc/self/maps` 里已经 `mmap` 的库路径（那不是 `open` 出来的）
- 任何**已经打开的 fd**

#### 手段 2：拒绝访问

| 目标 | 手段 | 效果 |
| --- | --- | --- |
| `/data/user/0/com.nextvm.app`（容器自身） | `nativeHidePath` | `stat` → `ENOENT` |
| `/data/data/com.nextvm.app` | 同上 | 同上 |
| `/sdcard/Android/data/com.nextvm.app` | 同上 | 同上 |

**注意**：**必须"成组一致"** —— `stat` / `access` / `opendir`（`readdir` 里要过滤掉）都要改，
否则 guest 用 `opendir("/data/data")` 遍历就能发现 `com.nextvm.app` 这个目录。

#### 手段 3：内容伪造

| 文件 | 怎么伪造 | 可行性 |
| --- | --- | --- |
| `/proc/self/maps` | 读真实 → 过滤掉容器行 → 写进 memfd → 返回那个 fd | ⚠️ 需覆盖 `read`/`pread`/`mmap` |
| `/proc/self/cmdline` | 直接生成 guest 包名 | ✅ 容易 |
| `/proc/self/status` | 替换 `Name:`、`TracerPid:` 等字段 | ✅ 中等 |
| `/proc/self/mountinfo` | 过滤掉容器挂载点 | ⚠️ 中等 |

**难点**：
1. **memfd 的 readlink 会露**（`/proc/self/fd/N` → `/memfd:xxx`）
2. **`mmap` 会绕过 `read`** —— maps 常被 `mmap` 读，那就要 hook `mmap` 并伪造整个内存页
3. **动态变化** —— maps 随 `mmap`/`munmap` 变，伪造的副本会过期

#### 手段 4：完全代读

| 场景 | 现状 | 限制 |
| --- | --- | --- |
| `ContentResolver.openInputStream(uri)` | ✅ 已做 | 只覆盖走 ContentResolver 的 |
| **直接 `FileInputStream("/sdcard/x")`** | ❌ | 需要 guest 有权限或路径对 |
| **WebView 的 `file://`** | ❌ | renderer 在 isolated 进程（L8） |

### 4.3 一个关键的边界：**fd 一旦交出去就管不到了**

```c
int fd = open("/sdcard/secret.txt", O_RDONLY);
// 从这里开始，无论 hook 什么，这个 fd 都指向那个 inode
read(fd, buf, n);   // ← 读的是真实内容，改不了
```

**推论**：
> **所有"必须真给 fd"的场景，伪造的机会窗口只在 `open` 那一刻** ——
> 要么改路径（重定向），要么拒绝（ENOENT），要么给一个自己造的 fd（memfd）。

**而"给一个自己造的 fd"只适用于内容完全由我们生成的场景**（`/proc/self/*`）。

## 五、综合：按场景选策略

| 场景 | 首选策略 | 理由 |
| --- | --- | --- |
| guest 查自己的路径/包名 | **假代理** | 元数据，随便造 |
| guest 查容器是否存在 | **假代理（ENOENT）** | 无法被区分 |
| guest 读自己的文件 | **路径重定向** | 内容必须真实 |
| guest 读 `/proc/self/*` | **内容伪造（memfd）** | 内容可完整生成 |
| guest 读它没权限的文件（导入通道） | **完全代读** | 宿主有权限 |
| guest 读 WebView 的 `file://` | **只能代读，且需找注入点** | L8 无法 hook |
| guest 用 `syscall` 读 `/proc/*` | **依赖 open 层的伪造** | 无需单独拦 syscall |

## 六、回到用户的四个问题

### Q1：什么情况容器代理访问可以实现？

**四个条件同时满足**：
1. 调用点在 L1–L6（Java 层或已 patch 的 GOT）
2. 返回值能构造（Parcelable ✅ / fd ⚠️）
3. 不需要真实副作用（查询类 ✅ / 写入类 ❌）
4. guest 不会交叉验证（或我们能成组一致地造假）

### Q2：能不能虚假代理，返回预设值？

**能，而且这是最有效的手段**：
- **查询类（元数据）：几乎无敌**，`getDataDir`/`getPackageInfo`/`stat` 全部可以假
- **数据类（字节流）**：**只能用"拒绝"或"造 mpfd"**，不能凭空编造内容
- **关键原则**：**"假装不存在"优于"编造假内容"** —— 前者无法被区分，后者可能自相矛盾

### Q3：怎么代理进程间通信？

**在 Java `IBinder` 层做**（已经做了 7000+ 行）：
- 替换 `ServiceManager.sCache` 里的 proxy
- 在 proxy 的 `transact` 里改 `Parcel`
- **`ParcelFileDescriptor` 是分界线**：元数据可假、fd 必须真

### Q4：能不能在通信层面伪装结果？

**能，但只覆盖走 Java Binder 的调用**：
- ✅ `PackageManager` / `ActivityManager` / `ContentResolver` 全部可假
- ❌ native 直接 `ioctl(/dev/binder)` 拦不到（但极少有人这么写）
- ❌ `ParcelFileDescriptor` 返回真 fd 之后，内容改不了

### Q5：文件代理访问能够拦下什么？

**逐层**：

| 层 | 能拦 | 不能拦 |
| --- | --- | --- |
| **改路径** | guest 打开时（`open` 参数） | 已继承的 fd、maps 里的 mmap 区域 |
| **拒绝** | 让指定路径"不存在" | 只能用于"不该存在"的 |
| **造内容** | `/proc/self/*` 这类可生成的 | 任意真实文件（量太大） |
| **代读** | guest 没权限但宿主有的 | isolated 进程（L8）、已继承 fd（L9） |

## 六点五、核对结果：现状比预想的更糟（2026-11-23 查代码）

写本文时假设 `nativeHidePath` 至少能隐藏"某个目录及其子路径"，查代码后发现不是。

### 事实 1：`is_path_hidden` 是**精确匹配**，不是前缀匹配

`cpp
// native-hook.cpp:243
static bool is_path_hidden(const char* path) {
    if (path == nullptr || g_hidden_paths.empty()) return false;
    return g_hidden_paths.count(std::string(path)) > 0;   // ← std::unordered_set 精确查找
}
`

**后果**：`nativeHidePath("/data/user/0/com.nextvm.app")` **只隐藏这一个精确字符串**：

| guest 访问 | 结果 |
| --- | --- |
| `stat("/data/user/0/com.nextvm.app")` | ✅ 被隐藏 |
| `stat("/data/user/0/com.nextvm.app/files/virtual")` | ❌ **不隐藏** |
| `stat("/data/data/com.nextvm.app")` | ❌ **不隐藏**（这是另一个字符串） |
| `stat("/data/data/com.nextvm.app/files")` | ❌ 不隐藏 |

**所以要用的话必须把每个具体路径都加进去**，或者改成前缀匹配。

### 事实 2：`readdir` 完全不处理

`hooked_opendir`（L1355）只对 `/proc` 开头的路径打日志，**不修改返回结果**。

**后果**：

`
guest: opendir("/data/data")
  → readdir() 逐个返回
    → "com.nextvm.app"   ← ❌ 容器目录赫然在列
`

**所以"stat 返回 ENOENT 但 
eaddir 能看到"是自相矛盾的** —— 一查就露。

### 事实 3：`/proc/self` spoof 存在，但有暂停开关

`cpp
// L167
static std::atomic<bool> g_proc_spoof_suspended{false};
// L161: "v57: while true, /proc/self spoofing is suspended and hooked readers..."
`

**说明**：这个机制存在，但**历史上曾经因为与某个加固壳冲突而被整体暂停过**（v57）。
所以"有 spoof"不等于"spoof 一直有效"。

### 修正后的任务估算

| 任务 | 原估 | **修正** | 原因 |
| --- | --- | --- | --- |
| **P16 宿主 dataDir 不可 stat** | 0.5 天 | **1 天** | 要①改前缀匹配 ②补 `readdir` 过滤 ③覆盖 `/data/data` 和 `/data/user/0` 两种前缀 |
| 其中**仅 readdir 过滤** | — | 0.5 天 | 要在 `hooked_opendir` 里包装 `DIR*`，`readdir` 时跳过隐藏项（需要自己维护一个 fd→过滤器 的映射） |

### 一个更根本的替代方案

与其"逐个隐藏路径"，不如**让容器数据根本不出现在 guest 能看到的目录里** —— 但这需要换位置，代价大。

**次优方案**：**前缀匹配 + readdir 过滤**，这是 1 天的活。

## 七、可立即落地的三条

| # | 策略 | 收益 | 成本 |
| --- | --- | --- | --- |
| **1** | **`P13`/`P16`：容器自己"不存在"**（假代理 + ENOENT，且成组一致：`stat`/`access`/`opendir` 同步） | **消灭 OWASP 点名的 package structure 检测面** | 1 天 |
| **2** | **把 `nativeHidePath` 的"成组一致性"补全**（`readdir` 过滤） | 防止 guest 用目录遍历发现容器 | 0.5 天 |
| **3** | **`/proc/self/*` 的 memfd 伪造补 `mmap` 覆盖** | `maps` 类检测（★ 高价值） | 2–3 天 |

**第 1 条和第 2 条必须一起做** —— 只做 `stat` 不做 `readdir`，等于把矛盾暴露给 guest。
