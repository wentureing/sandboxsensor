# 调试-输出缺口（哪里需要补日志）

> 起因：本轮多次"信息输出不到位"导致误判。这份文档列出**具体要补的调试输出**，按收益排序。
> 原则：**日志要能回答"这一层到底生效没有"**，而不是只打"我进来了"。

---

## 一、当前日志的三个问题

| 问题 | 后果 | 例子 |
| --- | --- | --- |
| **只打"进入"不打"决策"** | 知道走了这条路，不知道走了哪个分支 | `initNativeHooks` 只打 "Initializing..."，不打"当前进程名/是否跳过" |
| **失败只打消息不打上下文** | 排查要重新构造现场 | `installApp` 只返回 `Error("APK file not found: ...")`，没打 `exists/canRead/length` |

### 关于 `LOGD`：**保留，不改**

**用户明确**：`LOGD` 在 release 不存在是**预期行为**（避免影响 release 效率），**不改成 `LOGI`**。

**实地核对**（2026-11-23）：

| 项 | 实际 |
| --- | --- |
| CI 构建变体 | **`:app:assembleDebug`**（`container-build.yml:17/127`） |
| 设备上的包 | `pkgFlags=[ DEBUGGABLE HAS_CODE ... ]` → **debug 包** |
| `run-as` | 可用 |
| 结论 | **`LOGD` 在当前构建里一直可见**，排查不受影响 |

**约定**：**排查固定使用 debug 包**（CI 产出的就是 debug）。将来若引入 release 分发包，
排查时**必须先换回 debug 包**，不要期望 release 里有 `LOGD`。

---

## 二、必须补的输出（按收益排序）

### P0-1：`installApp` 的源 APK 可读性诊断

**现状**：`Error(message=Failed to parse APK: APK file not found: /sdcard/Download/x.apk, exception=null)`

**问题**：看不出是"不存在""权限拒""SELinux 拒"还是"被重定向"。

**要补**（`VirtualEngine.installApp` 入口）：

```kotlin
Timber.tag("VmInst").i(
    "install src=%s exists=%s isFile=%s canRead=%s len=%d redirect=%s",
    apkPath, f.exists(), f.isFile, f.canRead(), f.length(),
    NativeHookBridge.describeRedirect(apkPath)   // 见 P0-3
)
```

**判据**：一次日志就能区分 4 种失败原因，不用再猜。

### ~~P0-2：exempt 日志改用 LOGI~~ → **不做**（保留 `LOGD`）

**结论**：`LOGD` 保留，排查用 debug 包即可（见上节）。**不要为了排查把日志提级**。

~~原建议（已作废）~~：

```cpp
// 原来的建议，不采用
LOGI("open: import exempt (read): %s", path);
```

**保留现状即可**：

```cpp
static void log_exempt_once(const char* path) {
    static std::unordered_map<std::string, int64_t> last;
    int64_t now = std::chrono::duration_cast<std::chrono::seconds>(
        std::chrono::steady_clock::now().time_since_epoch()).count();
    auto it = last.find(path);
    if (it != last.end() && now - it->second < 1) return;
    last[path] = now;
    LOGI("open: import exempt (read): %s", path);
}
```

### P0-3：能"解释一条路径会被怎么处理"

**现状**：没有这样一个 API，排查时只能靠猜。

**要补**（`NativeHookBridge` 新增）：

```kotlin
/**
 * 解释一条路径在当前进程里会怎么被处理。
 * 返回: "hidden" / "exempt" / "redirect:/a -> /b" / "passthrough"
 */
external fun nativeDescribePath(path: String): String
```

native 侧对应实现，复用 `is_path_hidden` / `is_import_read_exempt` / `redirect_path` 的判断。

**价值**：`COLLECT_OUT`/`SELFCHECK` 可以直接输出"这条路径为什么读不到"。

### P0-4：`initNativeHooks` 打"当前进程 + 是否跳过"

**现状**：只打 `"Initializing native hook bridge..."`，看不出在主进程还是 guest。

**要补**：

```kotlin
val procName = android.app.Application.getProcessName()
Timber.tag(TAG).i(
    "initNativeHooks proc=%s pkg=%s isContainerMain=%s nativeAvailable=%s",
    procName, context?.packageName, procName == context?.packageName, nativeHooksAvailable
)
```

**价值**：一眼看出"主进程到底装没装 hook"，避免陷阱 3。

### P1-1：`redirect_path` 的打点要能聚合

**现状**：`LOGD("open: %s -> %s")` 每条都打，release 看不到，debug 又太多。

**要补**：改成**按前缀聚合**的统计，`COLLECT_OUT` 时输出：

```
REDIRECT /sdcard/ -> <沙箱>/sdcard/     hits=1234
REDIRECT /data/user/0/<guest>/ -> ...   hits=56
```

**价值**：知道"哪些重定向真的被触发"，而不是靠猜。

### P1-2：`CmdReceiver` 每个命令打"进程 + 线程"

**现状**：`Log.i(TAG, "INSTALL $path -> $r")`，不知道在哪个进程。

**要补**：`proc=${Application.getProcessName()} tid=${Thread.currentThread().id}`。

**价值**：本轮就误判过"CmdReceiver 在哪个进程"。

### P1-3：探针输出落点的双通道确认

**现状**：`FILE` / `FILE_EXT` 只打路径，看不出"adb 能不能取到"。

**要补**：探针额外打印一个 `CAN_ADB_READ=<bool>`（通过 `File.canRead()` + 路径是否在公共目录判断）。

## 三、补这些输出的成本与收益

| 项 | 改动量 | 收益 |
| --- | --- | --- |
| P0-1 `installApp` 诊断 | ~10 行 | **直接消灭本轮最大的误判源** |
| ~~P0-2 exempt 日志升级~~ | 0（不做） | 排查用 debug 包即可 |
| P0-3 `describePath` API | ~40 行（Kotlin + native） | 排查从"猜"变"查" |
| P0-4 进程名日志 | ~3 行 | 消灭陷阱 3 |
| P1-1 重定向聚合 | ~30 行 | 知道哪些规则真的在用 |
| P1-2 命令进程名 | ~2 行 | — |
| P1-3 探针可读性 | ~5 行 | — |
| **合计** | **~90 行** | 本轮 7 个坑里能直接防住 **3 个** |

## 四、和现有诊断设施的关系

| 现有 | 覆盖 | 缺口 |
| --- | --- | --- |
| `GuestBreadcrumb`（199 处） | guest 生命周期 | **不管路径决策** |
| `StateProbe` | AMS/Disposable 内部状态 | 同上 |
| `WebViewWatch` / `WebViewWarmup` | WebView 初始化 | 看不到 hook 范围 |
| **（缺）** | — | **路径决策、hook 生效范围、进程归属** |

**结论**：现有设施都在"生命周期"和"WebView"两个主题上，
**"文件路径到底怎么被处理"这一层是空白的** —— 而这正是本轮踩坑最多的地方。

---

## 五、落地顺序

```
1. P0-1 + P0-4（10+3 行，收益最大，风险最低）
2. P0-2 + P0-3（exempt 日志 + describePath）
3. P1-1（重定向聚合，等 SelfCheckRunner 一起做）
```

**全部是"只读诊断"，不改任何行为**，可以随任意一次构建带出去。
