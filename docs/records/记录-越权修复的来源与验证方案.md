## 二、缺陷是否真的存在：先做理论分析，再实测

### 2.1 代码层面：`fopen("r+")` 确实会被放行

```cpp
// p28 的写法
if (mode != nullptr && mode[0] == 'r' && is_import_read_exempt(path)) {
    return real_fopen(path, mode);
}
```

`"r+"` 的 `mode[0]` 是 `'r'` → **条件成立 → 放行**。这一步是确定的。

### 2.2 但"放行"≠"能写"：还要看写操作走哪条路

`fopen` 只返回 `FILE*`。真正的写发生在 `fwrite` → `write()` **系统调用**。

**关键**：`write` **没有被 hook**（hook 列表里只有 `open`/`openat`/`access`/`stat`/`lstat`/`fopen`/`readlink`/`__system_property_get`/`connect`/`dlopen`）。

所以写操作：
- **不受路径重定向影响**
- **受 DAC + SELinux + FUSE(appops) 影响**

### 2.3 三种可能的结果（**只能实测区分**）

| 场景 | 前提 | 结果 |
| --- | --- | --- |
| **A. 缺陷成立** | guest 进程有 `MANAGE_EXTERNAL_STORAGE`（继承容器） | `fopen("r+")` 拿到可写句柄 → `fwrite` 成功 → **真实 `/sdcard/Download/` 被改** |
| **B. 缺陷不成立（FUSE 拦截）** | FUSE 对 guest uid 的写判定更严 | `fwrite` 返回错误 → 写不进去 |
| **C. 缺陷不成立（重定向生效）** | `fopen` 的豁免没命中（路径不匹配） | 实际写到沙箱 → 真实文件未变 |

**注意场景 C**：如果 guest 的 `/sdcard/Download/xxx` 在被 `fopen` 之前**已经被别的 hook 改写过**，那 `is_import_read_exempt` 拿到的可能已经是沙箱路径 → 不匹配前缀 → 不加豁免。

**所以：理论分析不足以下结论，必须实测。**

## 三、验证方案（用户要求的"先验证再修"）

### 3.1 探针新增 `P28`：写越权探测

**为什么用探针而不是单元测试**：`fopen`/`fwrite` 是 native 行为，Robolectric 的 JVM 环境测不到；
只有**在 guest 进程里真实调用**才有意义。

**P28 的设计**：

```
前置（用 adb 准备，不经过容器）：
  adb shell "echo ORIGINAL > /sdcard/Download/probe-wtest.txt"
  adb shell "chmod 644 /sdcard/Download/probe-wtest.txt"

探针在 guest 进程内执行：
  1. fopen("/sdcard/Download/probe-wtest.txt", "r")   → 应成功（读）
  2. fopen("/sdcard/Download/probe-wtest.txt", "r+")  → 关键：是否成功
  3. 若 2 成功：fwrite("HACKED", 6) + fclose
  4. 记录结果到 probe-report.json（P28 项）

外部判据（adb 读，不经过容器）：
  adb shell "cat /sdcard/Download/probe-wtest.txt"
  内容 == "ORIGINAL"  → 写被拦（缺陷不成立 / 修复生效）
  内容 == "HACKED"    → **真实文件被改（缺陷成立）**
```

**这是唯一能区分三种场景的方法** —— 因为判据在**容器外部**读取真实文件。

### 3.2 三版对比

| 版本 | 容器内容 | 预期 |
| --- | --- | --- |
| **p26**（`74595e5`） | 无 `fopen` 豁免 | `fopen("r+")` 被重定向到沙箱 → 真实文件不变 |
| **p28**（`5611659` / 容器 `ec12b31`） | 有 `fopen` 豁免，`mode[0]=='r'` | **若缺陷成立：真实文件被改** |
| **p29**（`431cb0d` / 容器 `1e03781`） | 有豁免 + `strchr(mode,'+')==nullptr` | `"r+"` 不放行 → 真实文件不变（但与 p28 的"拦"机制不同） |

**注意**：p26 与 p29 的"拦"机制不同（前者是重定向到沙箱，后者是显式拒绝），
所以**不能只看"文件没变"，还要看探针记录的 `fopen` 返回值**。

### 3.3 WebView 是否受影响

| WebView 的行为 | 用的 mode | 修复后 |
| --- | --- | --- |
| 读 HTML/CSS/JS | `"r"` / `"rb"` | ✅ 不受影响（没有 `+`） |
| 读本地图片 | `"rb"` | ✅ 不受影响 |
| 写缓存（如果有） | `"w"` / `"w+b"` | ⚠️ 本来就不在豁免范围（`mode[0] != 'r'`）→ 仍被重定向到沙箱 |

**结论**：修复**不影响 WebView 读取**（它的读操作都是纯 `"r"`/`"rb"`）。

**但要用探针验证**：`P28` 之外，再确认 `P09`（`findLibrary`）与 Via 主页行为无回归。

## 四、我承认的顺序错误

**用户要求"验证缺陷存在才能执行修复"，而我是先修（p29）后想验证。**

正确的顺序应该是：

```
1. 写 P28 探针项
2. 装 p28 容器 → 跑 P28 → 看真实文件是否被改
   ├─ 被改 → 缺陷成立 → 值得修
   └─ 没被改 → 缺陷不成立 → p29 的修复是"防御性收紧"，不是"修 bug"（结论要改写）
3. 装 p29 容器 → 跑 P28 → 确认行为变化
4. 同时跑 WebView 相关项，确认无回归
```

**p29 已提交（`1e03781`）**。补验证后的两种处置：

| 验证结果 | 处置 |
| --- | --- |
| 缺陷成立 | 保留 p29，把结论写成"修复了我们自己 p28 引入的问题" |
| 缺陷不成立 | **也保留 p29**（判断更严格没有坏处），但**把结论改写**成"防御性收紧，非缺陷修复"，避免误导后来者 |

## 六、给后来者的两条规则

1. **"越权/缺陷"必须先能复现再修**：写一个能在**容器外部读到判据**的测试，
   否则无法区分"真被绕过"和"只是拿到了句柄但写不进去"。
2. **我们自己的补丁也要按上游标准对待**：`is_import_read_exempt` 是我们加的，
   它的每个分支都要有对应的测试，不能因为它"是我们写的"就默认安全。
