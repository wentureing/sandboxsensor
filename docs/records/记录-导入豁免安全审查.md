# 记录-导入豁免的安全审查

- 日期：2026-11-23
- 起因：补齐 `access`/`stat`/`lstat`/`fopen` 的导入豁免后，审查"是否危害了本不该豁免的场景"
- 结论：**发现并修复 2 个真实漏洞**，另有 1 个设计取舍需要明确记录

---

## 一、审查对象

p18 起，`is_import_read_exempt(path)` 对三个前缀放行：

```
/sdcard/Download/
/storage/emulated/0/Download/
/data/local/tmp/
```

p28 之前只有 `hooked_open` / `hooked_openat` 用了它。
p28 补到 6 个函数：`open` / `openat` / **`access`** / **`stat`** / **`lstat`** / **`fopen`**。

---

## 二、发现的 2 个漏洞（已修）

### 漏洞 1（严重）：`fopen` 放行了可写模式

**原代码**：

```cpp
if (mode != nullptr && mode[0] == 'r' && is_import_read_exempt(path)) {
    return real_fopen(path, mode);
}
```

**问题**：`"r+"` 也以 `'r'` 开头 → **被放行 → guest 能以读写方式打开**
`/sdcard/Download/` 和 `/data/local/tmp/` 下的文件 → **直接写穿导入通道**。

`"rb+"`、`"r+b"` 同理。

**修复**：

```cpp
if (is_import_read_exempt(path) && mode != nullptr &&
    mode[0] == 'r' && strchr(mode, '+') == nullptr) {
    return real_fopen(path, mode);
}
```

`strchr(mode, '+') == nullptr` 才能真正保证不可写。

### 漏洞 2（中）：`access` 放行了写权限探测

**原代码**：

```cpp
if (is_import_read_exempt(path)) {
    return real_access(path, mode);
}
```

**问题**：`access(path, W_OK)` 会被放行 → guest 可以**探测**目标文件是否可写。

虽然 `access` 只检查不写入，但它是"写通道探测"，属于信息泄漏。

**修复**：

```cpp
/ W_OK=2；F_OK=0、R_OK=4 都满足 (mode & W_OK) == 0
if (is_import_read_exempt(path) && (mode & W_OK) == 0) {
    return real_access(path, mode);
}
```

`X_OK`（执行位）也被一并排除，因为导入的是 APK 不需要执行权限探测。

## 三、需要明确记录的设计取舍（未改，但要知道）

### 取舍 1：豁免是「进程级」的，不区分调用方

`is_import_read_exempt` 只看路径，**不看是谁在调用**。所以：

| 调用方 | 是否豁免 |
| --- | --- |
| 容器自己（`CmdReceiver.INSTALL`） | ✅ 需要 |
| **guest 进程（任意应用）** | ✅ **也被豁免** |

**含义**：guest 可以主动 `open`/`stat` `/sdcard/Download/` 和 `/data/local/tmp/` 下的文件，
不只是"走 INSTALL 通道时才能读"。

**这是 p18 的原设计**（当时判断：公共目录不算新增泄漏）。但需要明确：

| 路径 | 真机上 guest 能否读 | 豁免后 | 是否新增泄漏 |
| --- | --- | --- | --- |
| `/sdcard/Download/` | ✅ 能（有存储权限即可） | ✅ 能 | **否** |
| `/data/local/tmp/` | ❌ **不能**（`drwxrwx--x shell shell`，other 无 `r`） | ✅ 能 | **是（轻微）** |

**关于 `/data/local/tmp` 的具体风险**：

- 真机权限：`other` 只有 `x`（能 enter，不能列目录）
- 豁免后：guest 能 `open`/`stat` **已知路径**
- 实际影响：guest 能读到我们 push 进去的测试文件（`probe-v17.apk`、`yespdf.apk` 之类）
- **不严重**（都是我们自己的测试产物），但**不是零**

### 取舍 2：`stat`/`lstat` 豁免会泄漏元数据

guest 可以 `stat("/sdcard/Download/某个文件名")` 来**判断文件是否存在、大小、时间**。

- 对 `/sdcard/Download/`：真机同样能（有存储权限）→ **不新增**
- 对 `/data/local/tmp/`：真机不能 → **新增**（但只对已知文件名有效，不能枚举目录）

### 取舍 3：`data/local/tmp` 是 INSTALL 的兜底路径

实测（p26 容器）：

```
INSTALL /sdcard/Download/probe-v17.apk  -> Error(APK file not found)   ← p28 已修
INSTALL /data/local/tmp/probe-v17.apk    -> Success
```

p28 补齐 `access` 后 `/sdcard/Download` 应该能用；**等 p28 验证通过，可以考虑移除 `/data/local/tmp`**
（收紧到只留公共下载目录）。

## 四、没有危害的场景（逐个确认）

| 场景 | 是否受影响 | 原因 |
| --- | --- | --- |
| 容器自己的沙箱读写 | ❌ 不受影响 | 沙箱路径不匹配三个前缀，照常 `redirect_path` |
| guest 的私有目录 | ❌ 不受影响 | 同上 |
| `/system`、`/vendor`、`/apex` | ❌ 不受影响 | 不匹配前缀，照常重定向/拒绝 |
| 其他应用的目录 | ❌ 不受影响 | 同上 |
| **写公共目录**（`open` 带 `O_WRONLY`） | ✅ 仍被拒 | `open` 的豁免限定 `O_RDONLY` |
| **写公共目录**（`fopen("r+")`） | ✅ **修复后**被拒 | 见漏洞 1 |
| **探测写权限**（`access(W_OK)`） | ✅ **修复后**被拒 | 见漏洞 2 |
| `truncate` / `unlink` / `rename` / `mkdir` | ✅ 没有 hook 也没有豁免 | 照常走原逻辑 |

---

## 五、修复后的豁免矩阵

| 函数 | 放行条件 | 备注 |
| --- | --- | --- |
| `open` | `O_ACCMODE == O_RDONLY` 且路径匹配 | p18 |
| `openat` | 同上 + `path[0]=='/'` | p18 |
| `access` | 路径匹配 且 `(mode & W_OK) == 0` | **p28 修** |
| `stat` | 路径匹配 | p28（只读元数据） |
| `lstat` | 路径匹配 | p28 |
| `fopen` | 路径匹配 且 `mode[0]=='r'` 且不含 `'+'` | **p28 修** |

**共同前提**：`path[0] == '/'`（绝对路径），且路径以 `/` 结尾的前缀匹配（`strncmp` 带长度，天然防前缀攻击）。

---

## 六、教训

1. **`fopen` 的 `'r'` 前缀不等于只读** —— `r+` / `rb+` 都是可写。凡是"按首字符判断只读"的地方都要检查 `'+'`。
2. **`access` 有 `W_OK`** —— 只读豁免必须排除写权限探测。
3. **"只读豁免"的范围要按函数语义逐个确认**：`open` 有 flags、`fopen` 有 mode、`access` 有 mode，三个语义都不一样，不能简单复制条件。
4. **进程级豁免 = guest 也能用** —— 这是设计取舍，不是 bug，但要写清楚哪些路径因此变成"guest 可读"。
