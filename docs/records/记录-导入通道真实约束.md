> ## ⚠️ 重大更正（2026-11-23 22:30 实测推翻前文）
>
> **前文的核心结论是错的。** `/sdcard/Download` **完全可以**作为导入通道，
> 前提是 `MANAGE_EXTERNAL_STORAGE` 被授予 `allow`。
>
> ### 决定性实测
>
> | 状态 | 命令 | 结果 |
> | --- | --- | --- |
> | `MANAGE_EXTERNAL_STORAGE = default`（未授权） | `INSTALL /sdcard/Download/test-probe.apk` | ❌ `APK file not found` |
> | **`MANAGE_EXTERNAL_STORAGE = allow`**（用户手动授予） | 同上，**p26 容器，不含 p28 的 access 豁免** | ✅ **`Success(...versionName=1.7...)`** |
>
> ### 我错在哪
>
> | 当时的判断 | 实际 |
> | --- | --- |
> | "`/sdcard/Download` 下文件属主 `u0_a0 media_rw`、权限 660 → DAC 层就拒" | **只在不授权时成立**；`allow` 后 FUSE 层改变权限判定，`open()` 能过 |
> | "`MANAGE_EXTERNAL_STORAGE` 通过 MediaProvider 生效，不绕过直接 `open()` 的 DAC 检查" | **错**。它改变的是 FUSE 的访问判定，直接 `open()` 同样受益 |
> | "`run-as com.nextvm.app cat /sdcard/Download/x` 报 Permission denied → 容器进程也读不到" | **`run-as` 是误导性测试**：它跑在 `runas_app` SELinux 域，与应用的 `untrusted_app` 域权限不同 |
>
> ### 教训（最重要的一条）
>
> > **验证"应用进程能不能读某个路径"，必须用应用进程自己测
> > （发起一次真实调用并看结果），不能用 `run-as`、也不能只从 `ls -l` 推断。**
> >
> > `run-as` 的 SELinux 域是 `runas_app`，`ls -l` 只能看到 DAC；
> > 而真实访问还经过 SELinux + FUSE(appops)，这三层只有**真实调用**能一起验证。
>
> ### 修正后的结论
>
> | 通道 | 是否可用 | 条件 |
> | --- | --- | --- |
> | **`/sdcard/Download/`** | ✅ **可用** | `MANAGE_EXTERNAL_STORAGE = allow`（用户手动授权，或容器引导授权） |
> | `/data/local/tmp/` | ✅ 可用 | 无需额外授权（644） |
>
> **p18 的豁免仍然有价值**：它让 **guest 进程**（路径被重定向）也能走这条通道；
> 但**容器主进程**靠 `MANAGE_EXTERNAL_STORAGE` 就能直接读，不依赖豁免。
>
> **p28/p29 的 `access`/`stat`/`lstat`/`fopen` 豁免补全仍然正确**（主进程走 `access()` 时确实需要），
> 只是**不是**"唯一让 `/sdcard/Download` 可行"的原因 —— 权限才是。

## 一、决定性实测

| 检查 | 结果 | 含义 |
| --- | --- | --- |
| `run-as com.nextvm.app cat /sdcard/Download/probe-v17.apk` | **Permission denied** | **容器 uid 在 DAC 层就读不到** |
| `run-as com.nextvm.app cat /data/local/tmp/probe-v17.apk` | **成功**（能读出 `PK...` ZIP 头） | 644 权限，任何应用可读 |
| `appops get com.nextvm.app MANAGE_EXTERNAL_STORAGE` | **`default`**（未授权） | 容器没有"所有文件访问权" |
| `ls -l /sdcard/Download/probe-v17.apk`（adb shell） | 一度显示 `-rw-rw---- u0_a0 media_rw`，后来 `No such file` | adb push 的文件属主是 `u0_a0`，不是应用 |

**关键**：`/sdcard/Download/` 下的文件属主是 **`u0_a0 media_rw`，权限 `660`** ——
容器（`u0_a318`）**既不是 owner 也不是 group**，所以：

```
p18 的豁免只作用于「路径重定向」这一层
但 /sdcard/Download 在「DAC 权限」这一层就已经被拒
→ 豁免根本走不到
```

**所以 p18 的 `/sdcard/Download` 豁免是无效的**（对 adb push 的文件而言）。

## 二、当前策略到底是什么（逐层拆解）

### 2.1 两层 hook

`NativeHookBridge.initNativeHooks()` 有两相：

```kotlin
// Phase 1: Java-level IO hooks
val javaHooksInstalled = installJavaIoHooks()
// Phase 2: native PLT hooks (GOT patching)
nativeHooksAvailable = tryLoadNativeLibrary()
```

**实测 Phase 1 是空的**：`hookFileClass()` 和 `hookRuntimeExec()` 只打日志返回 true，**没有真正 hook `java.io.File`**。

→ **所以真正生效的只有 Phase 2（native GOT patch）。**

### 2.2 native GOT patch 的作用范围（`is_self` 过滤）

```cpp
// 1) 容器自身：永不 patch
if (strstr(lib_name, "com.nextvm.app") || strstr(lib_name, "libnextvm")) return;
// 2) 图形栈：永不 patch
// 3) 应用/沙箱库：patch
// 4) 其余系统库：NS_HOOK_SYSTEM_LIBS=0 → 不 patch
```

**关键推论**：容器自己的 `open` 走 `libc.so`（第 4 类，**不 patch**）→ **容器自己的文件访问不被重定向**。

**但**：`initNativeHooks` 在 `VirtualEngine.initialize()`（`L280`）里调用，**容器主进程也会执行**。

**所以**：
- 容器主进程里，`libc.open` **不被 patch** → 走真实路径
- **`/sdcard/Download` 失败的原因是 DAC，不是重定向**
- **`/data/local/tmp` 能读，也不需要豁免**（在 `run-as` 子进程里验证过，那里同样没有 hook）

### 2.3 那 p18 的豁免到底对谁有用

| 路径 | 容器主进程（无 hook 影响） | guest 进程（有 hook） | 豁免是否有意义 |
| --- | --- | --- | --- |
| `/data/local/tmp` | 直接能读（644） | **会被重定向** → 需要豁免 | **有意义** |
| `/sdcard/Download` | **DAC 拒绝**（660，非本人） | 同样 DAC 拒绝 | **无意义** |

**结论**：

1. **`/sdcard/Download` 豁免 → 应删除**（无效 + 扩大 guest 可见面）
2. **`/data/local/tmp` 豁免 → 保留**（guest 进程确实需要），但要记录"真机上 other 无 r，豁免后 guest 可读"
3. **`CmdReceiver` 的导入通道应该只用 `/data/local/tmp`**

## 三、关于「分割进程，彻底不豁免容器本身」

### 3.1 可行，而且已经部分成立

**实测证据**：`run-as com.nextvm.app cat ...` 是**独立进程**（不装 hook）→ 读到 `/data/local/tmp` 成功。
说明**不装 hook 的容器进程本来就没有重定向问题**。

### 3.2 为什么"主进程不装 hook"能成立

| 进程 | 需要 hook 吗 | 理由 |
| --- | --- | --- |
| **容器主进程** `com.nextvm.app` | **不需要** | 它只做管理（安装/启动/UI），文件访问都是自己的真实路径 |
| **guest 进程** `com.nextvm.app:p0`（改名为 guest 包名） | **需要** | 要重定向 guest 的路径、隐藏宿主痕迹 |

**判断方法**：`Application.getProcessName()`
- 等于 `context.packageName` → 容器主进程
- 以 `packageName + ":"` 开头 → guest 进程

`ActivityManagerProxy.kt:629-635` 已经在用这个判断：

```kotlin
val processName = android.app.Application.getProcessName()
processName == packageName || processName.startsWith("$packageName:")
```

### 3.3 改造方案

```kotlin
// NativeHookBridge.initNativeHooks 开头
fun initNativeHooks(context: Context? = null): Boolean {
    if (initialized) return true

    // 容器主进程不装 hook：它不需要重定向，装了反而要处处豁免。
    val procName = android.app.Application.getProcessName()
    val pkg = (context ?: appContext)?.packageName
    if (pkg != null && procName == pkg) {
        Timber.tag(TAG).i("initNativeHooks skipped: container main process ($procName)")
        initialized = true   // 标记已处理，避免重复尝试
        return false
    }
    ...
}
```

**收益**：
- 容器主进程的 `CmdReceiver` 能直接读真实路径（`/data/local/tmp`、`/sdcard/...` 只要 DAC 允许）
- **`is_import_read_exempt` 可以整个删掉**（guest 进程不需要读 `/data/local/tmp` —— 它是容器在装包，不是 guest）

**等等**——这里有个前提要确认：**`installApp` 是在哪个进程跑的？**

`CmdReceiver` 在**主进程** → `engine.installApp()` 也在主进程 → **主进程不装 hook 后，`installApp` 完全不需要豁免** ✓

**这正是用户说的"豁免和 CmdReceiver 在一起"**：不是"给路径开豁免"，而是**让装包这条路径跑在没有重定向的进程里**。

## 四、计划

### 阶段 1（先验证，不改）：确认主进程不装 hook 的影响

**目标**：确认 `installApp` / `CmdReceiver` 只在主进程跑，且主进程不装 hook 不会破坏别的功能。

需要确认的点：

| # | 要确认 | 方法 |
| --- | --- | --- |
| 1 | `CmdReceiver` 是否只在主进程（manifest 无 `android:process`） | ✅ 已确认：`<receiver android:name=".CmdReceiver" android:exported="true" />`，无 process → 主进程 |
| 2 | 主进程是否还需要 hook 做别的事（如 `AntiDetectionEngine.hidePath`） | 查 `hidePath` / `addPathRedirection` 的调用方是否跨进程 |
| 3 | guest 进程启动时 `initNativeHooks` 是否会被调用 | 查 `getOrCreateClassLoader`（`L880`）在哪个进程跑 |

### 阶段 2：主进程跳过 hook

```
NativeHookBridge.initNativeHooks 加进程判断 → 主进程直接 return
```

### 阶段 3：清理豁免

- 删除 `is_import_read_exempt` 及其 6 处调用
- 若仍有 guest 需要读 `/data/local/tmp` 的场景，再单独评估

### 阶段 4：导入通道固定为 `/data/local/tmp`

```bash
adb push x.apk /data/local/tmp/
adb shell am broadcast ... INSTALL --es path /data/local/tmp/x.apk
```

**`/sdcard/Download` 不再作为导入通道**（DAC 660 + MANAGE_EXTERNAL_STORAGE 未授权）。

### 5.4 教训条目（写进 `docs/调试指南.md`）

> **"豁免"和"进程边界"是两回事。**
> 路径豁免只作用于 `redirect_path` 这一层；**DAC 权限、SELinux、挂载命名空间都在它之前生效**。
> 遇到"读不到文件"时，先按这个顺序排查：
> ```
> 1. 文件是否存在（ls）
> 2. DAC 权限（ls -l：owner/group/other 与调用方 uid 对比）
> 3. MANAGE_EXTERNAL_STORAGE 是否 allow（appops get）
> 4. SELinux（ls -Z + avc denied）
> 5. 才是路径重定向（容器 hook）
> ```
> 本次就是第 2 层被拒，而前几轮一直在第 5 层找原因。

## 六、一句话总结

> **p18 的 `/sdcard/Download` 豁免从根上无效**（DAC 660 先拒），
> **`/data/local/tmp` 是唯一可靠通道**（644），
> **正确做法不是"给更多路径开豁免"，而是"让装包路径跑在不装 hook 的容器主进程里"** ——
> 这正是用户提的「豁免和 CmdReceiver 在一起 + 分割进程」。
