> **容器让 WebView 的 JNI 层拿到"不一致的 Context/AssetManager 视图"**：

> 两者对同一个路径的解析结果不同。

**但这只是一个描述，还不是机制。** 需要 W14 来分层。

## 三、Via 主页加载流程（已反编译确认，`docs/records/记录-反编译Via主页加载全流程.md`）

```
① 生成 homepage2.html + homepage.css → getFilesDir()
     homepage2.html 里硬编码 <img src="file:///android_asset/logo.svg">
② loadUrl("file://" + getFilesDir() + "/homepage2.html")
③ shouldInterceptRequest（Via 自己的实现，方法 d9.q$c.shouldInterceptRequest）：
     url 以 "homepage.css" 结尾 → 自己读文件 + 手动给 text/css（方法 d9.q.E）
     其余一律返回 null → 交给 WebView
④ WebView 加载 homepage2.html（file://）→ 容器内 MIME 判成 text/plain → 显示源码 ❌
⑤ logo.svg（file:///android_asset/）→ 容器内 AndroidProtocolHandler 打不开 ❌
```

**关键证据**（DEX method 级反编译）：
```
d9.q$c.shouldInterceptRequest: Uri.toString / "homepage.css" / String.endsWith / d9.q.r3
d9.q.E (=r3):                  "text/css" / Context.getFilesDir / FileInputStream /
                               WebResourceResponse.<init> / HashMap(Cache-Control, CORS, Content-Type)
e9.u.onWriteFinished:          "<img class=\"smaller\" src=\"file:///android_asset/logo.svg\" />"
```

**Via 不用 `loadDataWithBaseURL`**（DEX 里 0 命中）→ 所以它和探针 W2 完全同构。

### P1：方案 A 落盘计划（等 W14 结果再决定要不要做）

**方案 A（W11 已验证有效）**：容器 hook `WebViewClient.shouldInterceptRequest`

```java
WebResourceResponse viaResp = userClient.shouldInterceptRequest(v, req);
if (viaResp != null) return viaResp;          // 尊重应用的 client（Via 处理 homepage.css）
if ("file".equals(u.getScheme())) {           // 应用返回 null 的才接管
    // file:///android_asset/xxx → getAssets().open()
    // file://<真实路径> → 读文件
    // 按扩展名给 MIME（MimeTypeMap 可用，W9 证明）
    return new WebResourceResponse(mime, "utf-8", stream);
}
return null;
```

**与 Via 零冲突**（Via 只拦 `homepage.css`，其他返回 null）。

**性能**（`docs/records/记录-反编译Via主页加载全流程.md` 第五节）：
- `open()` hook：单次 50–200 ns，但进程生命周期几万次 → 累计几毫秒
- `shouldInterceptRequest`：单次 ~100 μs，只在 WebView 加载时几十~几百次 → **Via 主页约 0.2 ms**
- **补 MIME 总开销比 `open()` 重定向更小**（频次低 2–3 个数量级），且天然可短路

### 5.1 签名：已彻底解决

**关键设计**（学自 `C:\Users\86177\Desktop\阅读器开发`）：
- 凭据三级来源：CI 环境变量 > `local.properties` > 无
- `File(ksStore).exists()` 显式校验
- **缺 Secret 时报 `::error::` 拒绝构建**（不再静默漂移）
- 构建后用 `apksigner` 对比 APK 证书与 keystore 指纹，不一致就失败

### 5.2 token：多 PAT 按用途分行

`token.txt` 两行：
- **第 1 行 default** —— 常规 API（列 runs / 查 release / dispatch / 删 cache）
- **第 2 行 content** —— 内容读取（`--logs` 下日志、`--asset` 下 APK）

**覆盖**：`GH_TOKEN_N=<N>`（1-based）、`GH_TOKEN_PURPOSE=default|content`

**踩过的坑**：原来用 `readFileSync(...).trim()`，`.trim()` 不去中间换行 →
加了第二行后 `Authorization: Bearer <t1>\n<t2>` → 认证必然失败。

### 5.3 代理：**12450**（不是 7897）

```
7897  -> 3/3 ECONNRESET "Client network socket disconnected before secure TLS connection"
12450 -> 3/3 HTTP 200，约 1.5s
```

`gh-api.mjs`、`gh-clean-release.mjs`、`fetch-aosp.mjs` 都已用 12450。

### 5.4 CI 触发规则（重要，我理解错过一次）

> **探针与容器必须分开触发，各自一次。**
> **一次只 dispatch 一个 workflow，且只调一次。**

| 场景 | 做法 |
| --- | --- |
| 改探针（`probe/**`） | push 主仓库 → `build-probe` 自动触发一次 |
| 改容器源码（`wentureing/ShitJumpingVM`） | 主仓库感知不到 → **手动 dispatch 一次** `container-build.yml` |
| 改文档/工具 | 两个都不跑（`paths` 过滤） |

**排查"CI 看起来像故障"**：先看 `event` 字段（`push` vs `workflow_dispatch`）。
同一 `head_sha` 出现多个 run → 先怀疑重复触发。
