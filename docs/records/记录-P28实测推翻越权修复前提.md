# 结论：P28 实测推翻了"越权修复"的前提

- 日期：2026-11-23 23:00
- 起因：用户要求"用单元测试验证缺陷存在再修"、"检查是权限障碍还是上游缺陷"
- **结果：缺陷确实存在，但机制和我们以为的完全不同；p28/p29 的改动对此毫无影响**

---

## 一、实测数据（p26 容器 + 探针 v1.8）

```
准备（adb 直接写，不经容器）：
  /sdcard/Download/probe-wtest.txt  = "ORIGINAL\n"  (9 字节, 660 u0_a0 media_rw)

探针 P28（guest 进程内，native 层）：
  fopen_r=ok  fopen_rplus=ok  fwrite=6  size=9

外部判据（adb 读真实文件）：
  内容 = "HACKEDAL"     ← ORIGINAL 前 6 字节被覆盖成 HACKED
```

**真实文件被改了 → 越权确实存在。**

---

## 二、但机制不是"豁免放行"

| 证据 | 说明 |
| --- | --- |
| **`import exempt` 日志 0 次** | `hooked_fopen` 里的豁免分支**从未执行** |
| **沙箱里没有 `probe-wtest.txt`** | 说明**没有重定向**过去 |
| **`/sdcard` 重定向规则确实存在** | logcat 有 `Path redirect added: /sdcard -> <沙箱>/sdcard` |
| **容器是 p26（`74595e5`）** | p26 **不含 p28 的 `fopen` 豁免**，却也照样能写 |

**结论：`hooked_fopen` 根本没被调用。** 既然没被调用，p28 加的豁免、p29 加的 `strchr(mode,'+')`，**都不会被执行**。

---

## 三、真正的原因：`libprobe.so` 的 GOT 没被 patch

### 3.1 判据

| 探针项 | 路径 | 结果 | 能说明什么 |
| --- | --- | --- | --- |
| `N03.open_literal` | `/data/data/com.sandbox.probe/files/...` | ❌ `errno=2` | 无法区分（真实路径和沙箱路径都不存在） |
| `N06.fopen_write` | 同上 | ❌ `errno=2` | 同上 |
| **`P28.sdcard_write`** | **`/sdcard/Download/probe-wtest.txt`** | **✅ 成功写** | **能区分**：真实文件存在、沙箱里没有 → 成功 = **没走 hook** |

**只有 P28 是可靠判据**，因为它的目标在真实路径存在、在沙箱路径不存在。

### 3.2 为什么 GOT 没被 patch

```
System.loadLibrary("probe")
  → Java 层 Runtime.loadLibrary0
    → native dlopen（调用方是 libnativehelper.so，系统库）
      → hooked_dlopen 不会被调用（因为 libnativehelper 没被 patch）
        → patch_newly_loaded_libraries() 不执行
          → libprobe.so 的 GOT 保持原样
```

**关键设计缺陷（上游）**：
- `nativeInit()` 只 patch **当时已加载**的库
- 之后新加载的库依赖 `hooked_dlopen` 触发 `patch_newly_loaded_libraries()`
- **但 `System.loadLibrary` 的 `dlopen` 调用方是系统库**（`libnativehelper.so`）→ 那个库没被 patch → **hook 链断了**

### 3.3 这条结论能解释之前的观察

| 之前的观察 | 现在能解释 |
| --- | --- |
| `N10 maps pkg_hit=13`（能看到宿主痕迹） | **因为探针的 native 层没被 hook，直接读真实 `/proc/self/maps`** |
| `N03`/`N06`/`N13` 全部 `errno=2` | 同上（`/data/data/com.sandbox.probe` 在这台设备上真实不存在） |
| 探针的 Java 层项（`J01` 等）却准确反映容器路径 | **Java 层走的是 `VirtualContext`/`PackageManagerProxy` 的 Java hook，与 native hook 无关** |

**所以探针看到的"N 系列全失败"不是"容器隔离好"，而是"探针自己的 native 调用没被容器接管"。**

## 四、对三个问题的直接回答

### Q1：是权限配置障碍，还是上游开发者留下的缺陷？

**都不是。**

- 不是权限（`MANAGE_EXTERNAL_STORAGE=allow` 已验证）
- 不是上游的"越权豁免缺陷"（上游根本没有 `is_import_read_exempt`）
- **是上游 native hook 的覆盖机制局限**：`System.loadLibrary` 加载的库拿不到 GOT patch

### Q2：修复后是否危害 WebView 等需求？

**谈不上危害 —— p28/p29 的改动从未生效。**

- 它们改的是 `hooked_fopen` 的函数体
- 而 `hooked_fopen` 在探针这类"运行期 `System.loadLibrary` 加载的库"里**不会被调用**
- 对**已被 patch 的库**（`nativeInit` 时已加载的应用库、guest 主 APK 的 lib）仍然生效

### Q3：缺陷是否确实存在？

**存在，但位置不同**：

| 我以为的缺陷 | 真实情况 |
| --- | --- |
| p28 的 `fopen("r+")` 被豁免放行 → 能写真实文件 | **豁免分支从未执行** |
| p29 修复了它 | **修复的分支同样不会执行** |
| — | **真实问题**：guest 通过 `System.loadLibrary` 加载的 native 库**完全不受容器路径重定向约束** → 能直接读写真实 `/sdcard` |

## 五、p28/p29 的处置

| 改动 | 建议 |
| --- | --- |
| p28 的 `access`/`stat`/`lstat`/`fopen` 豁免 | **保留**（对已 patch 的库仍生效，且判断本身没写错） |
| p29 的 `strchr(mode,'+')` / `(mode & W_OK)==0` | **保留**（同上，是更严格的判断） |
| **但结论要改写**：不再声称"修了越权" | 改为"防御性收紧；**不解决** native 库未 patch 导致的真实越权" |

---

## 六、真正要修的是什么（新问题，需要单独评估）

**问题**：运行期 `System.loadLibrary` 加载的应用库拿不到 GOT patch。

**可选方向**：

| 方向 | 说明 | 风险 |
| --- | --- | --- |
| A. patch `libnativehelper.so` 的 `dlopen` GOT | 让 `System.loadLibrary` 的调用也走 `hooked_dlopen` | 中（系统库，需验证不破坏 ART） |
| B. 在 `nativeInit` 之后主动扫描并 patch 新库 | 定时/事件驱动扫描 `/proc/self/maps` | 中（时序难保证） |
| C. 接受限制 | 只对容器自己的核心库做隔离，第三方 native 库不保证 | 低（但要写进已知边界） |

**这需要单独做一次调查**，不在本次范围内。

---

## 七、教训（三条）

1. **"改了一个分支"≠"这个分支会被执行"** —— 必须先证明目标函数真的被调用（本次靠 `import exempt` 日志 0 次发现）。
2. **判据要选"真实路径存在、沙箱路径不存在"的样本** —— `N03`/`N06` 两条都失败无法区分原因，只有 `P28` 的 `/sdcard/Download/` 能区分。
3. **探针的 native 项失败 ≠ 容器隔离好** —— 这次恰恰相反：N 系列全失败，而真实越权存在。
